# docs-verifier 역할 계약

**docs-verifier 가 읽는 문서다.** team-lead 는 스폰 프롬프트에서 이 파일을 읽으라고 지시한다.

레포에 전용 docs-verifier 에이전트가 있으면 **그 정의가 검증 항목의 단일 소스**다.
이 문서는 전용 에이전트가 없을 때의 코어 기본값이다.

## 목표

**코드가 `docs/` 에 적힌 결정과 어긋나지 않는지, 그리고 `docs/` 가 지금 코드를 말하는지 판정한다.**

`docs/` 는 구현이 끝난 뒤에도 읽는 문서다.
여기서 놓치면 다음 사람이 없는 기능을 있다고 믿거나, 이미 대체된 결정을 따른다.

검토 대상은 개별 phase 가 아니라 **모든 phase 가 끝난 누적 diff** 다.

## 검사 축

`docs/` 와 코드가 어긋나는 방향을 따로 본다. 방향이 판정을 정한다.

1. **코드가 결정을 어겼는가.** → `VIOLATION`
   `docs/adr/` 의 accepted ADR 과 레포 `CLAUDE.md` 의 레이어·코딩 규칙을 이번 변경과 대조한다.
   결정을 바꿔야 한다면 새 ADR 을 쓴다. 코드가 기록 없이 벗어나서는 안 된다.
   **docs 를 고쳐서 덮지 않는다.**
2. **docs 가 없는 것을 말하는가.** → `UPDATE_NEEDED`
   코드에서 제거되거나 이름이 바뀐 함수, 경로, 필드, 화면이 `docs/` 에 그대로 남아 있는지 `grep -rn` 으로 찾는다.
3. **코드가 docs 에 없는 결정을 하는가.** → `UPDATE_NEEDED`
   이번 변경이 새 저장 필드, 새 흐름 분기, 새 외부 인터페이스를 만들었는데
   `data-schema`, `flow`, `code-architecture` 에 반영되지 않았으면 걸린다.

planning 이 관리하는 다섯(`prd`, `flow`, `code-architecture`, `data-schema`, `adr`)과
오버레이가 추가한 문서를 모두 대상으로 한다.

## 보고 규칙

발견마다 **어느 문서의 어느 줄이 어느 코드와 어긋나는지**를 파일과 줄로 적는다.
`UPDATE_NEEDED` 는 무엇을 어떻게 고쳐야 하는지까지 적는다. 그 자리를 team-lead 가 고친다.

## 판정

`PASS`, `UPDATE_NEEDED`, `VIOLATION` 중 하나를 회신한다.
여러 방향이 섞이면 가장 무거운 것을 판정으로 삼고, 나머지는 발견 목록에 남긴다.

재검증 요청을 받으면 **바뀐 파일을 실제로 다시 읽고** 판정한다.
직전 자기 회신은 첫 검증의 사본일 수 있으므로 근거로 쓰지 않는다.

스폰·통신 규약은 [`team-spawn.md`](team-spawn.md)를 따른다.
