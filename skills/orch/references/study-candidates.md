# 공부 후보 모으기와 글로 잇기

일하다 판단을 정한 일반 기술 개념을 그때마다 후보로 쌓아 두고, 사용자가 공부할 후보를 고르면 글 쓰기로 잇는 절차다.
설명이 대화에만 남으면 압축될 때 사라지고, 적는 기준이 없으면 아무 주제나 쌓여 고를 때 다시 가려내야 한다.
글을 쓰는 스킬과 글이 놓일 저장소는 사용자마다 달라 오버레이가 정한다. 이 문서는 어느 저장소에서나 같은 자리와 형식, 기준만 소유한다.

## 후보 파일

후보 하나가 `<orch 루트>/study/<slug>.md` 파일 하나다. 폴더 경로는 `orch paths study` 로 받는다.
파일은 `---` 사이의 머리와 그 뒤의 본문으로 나뉜다. 머리는 명령이 고치고, 본문은 근거, 메모, 글 초안 경로를 자유롭게 쌓는 자리라 에이전트가 직접 고친다.

```markdown
---
주제: 여러 서버에서 한 번만 실행하기
질문: ShedLock 같은 분산 잠금과 선점 테이블은 각각 무엇을 막는가
생긴 곳: 예약 알림이 서버마다 한 번씩 나간 문제
참고: ShedLock README
상태: 후보
적은 날: 2026-11-02
---

## 메모

- 잠금은 같은 시각의 중복 실행을 막고, 선점 테이블은 이미 처리한 대상을 다시 처리하지 않게 막는다
```

| 칸 | 담는 것 |
| --- | --- |
| 주제 | 일반 기술 개념의 이름 |
| 질문 | 그 개념으로 정한 판단이나 사용자가 물은 것을 일반 질문으로 바꾼 것 |
| 생긴 곳 | 어떤 일을 하다 나왔는지 한 줄. 내부 맥락은 뺀다 |
| 참고 | 근거로 댈 공식 문서나 널리 알려진 글의 이름 |
| 상태 | `후보`, `리뷰함: <이유>`, `뺌: <이유>`, `글 씀: <글 경로>` 가운데 하나 |
| 적은 날 | 후보로 적은 날(`YYYY-MM-DD`). `list --today` 와 `--date` 가 이 칸으로 그날 후보를 찾는다 |

**회사 이름, 서비스 이름, 내부 식별자, 대상자 정보는 적지 않는다.** 머리와 본문 모두 공개 글의 재료가 되므로, 적는 자리에서 일반 개념과 질문으로 바꾼다.

slug 는 영문 소문자, 숫자, 하이픈으로 주제를 짧게 줄인 이름이다(`run-once-cluster`). 적는 에이전트가 짓는다.
한글 파일 이름은 길고, macOS 의 파일 이름 정규화 차이로 같은 이름 비교가 어긋날 수 있어 쓰지 않는다.
slug 가 같거나 주제가 같으면(빈칸, 대소문자, 한글 정규화 차이는 무시) 같은 후보다. 뺀 후보도 같은 후보로 본다.

머리는 명령으로 고친다. 칸 이름이나 상태 낱말이 틀리면 명령과 doctor 가 그 후보를 세지 못하기 때문이다. 명령의 옵션과 출력은 `--help` 가 소유한다.

```bash
orch study list --open
```

## 모으기

**사용자 질문이나 결정에서 일반 기술 개념이 판단을 바꿨으면, 아래 네 기준을 모두 채울 때만 그 자리에서 `후보` 로 적는다.** 사용자가 개념의 뜻을 물은 경우도 여기 든다.
「X 를 써야 하나」, 「왜 이렇게 됐나」 처럼 뜻을 묻는 꼴이 아니어도, 답하거나 정하는 데 그 개념의 트레이드오프가 쓰였으면 대상이다.
사용자에게 적을지 묻지 않는다. 무엇을 공부할지는 사용자가 쌓인 후보에서 고른다.
대화가 압축되면 그날 판단을 정한 개념을 다시 찾을 수 없어, 나올 때 적어 두는 것이다.

### 후보가 되는 기준

트리거를 넓힌 만큼 아무 주제나 올리지 않는다. 엔지니어링으로 공부할 가치가 있는 개념만 남기려고 아래 넷을 모두 채워야 적는다.

1. **저장소 밖에서도 통한다:** 이 저장소, 이 회사, 이 도구 설정을 몰라도 뜻이 통하는 일반 기술 개념이다
2. **트레이드오프가 선택을 정했다:** 이번 판단에서 선택지 사이의 선택을 정한 개념이다. 단순 사실 조회, 도구 사용법, 오타나 설정 실수, 내부 절차는 아니다
3. **더 깊이 볼 자료가 있다:** 공식 문서나 널리 알려진 글로 더 공부할 거리가 있다
4. **한두 문장으로 끝나지 않는다:** 정의 한두 문장으로 설명이 끝나는 용어가 아니다

적을 때는 `--memo` 에 네 기준을 어떻게 채웠는지 한 줄로 남긴다. 사용자가 고를 때 그 줄을 본다.

| 적는다 | 채운 기준 |
| --- | --- |
| 배치 프레임워크를 들일지, 분산 잠금과 유일 키로 중복 실행을 막을지 | 일반 개념이고, 재시작, 중복 실행, 운영 비용의 트레이드오프가 선택을 정했다 |
| 근거 없는 평가 기대값이 프롬프트 개선 방향을 끌고 가는 문제 | 평가 설계의 일반 문제이고, 무엇을 기준값으로 둘지가 개선 방향을 바꿨다 |
| 낙관적 잠금과 비관적 잠금 가운데 무엇으로 동시 수정을 막을지 | 충돌 빈도와 재시도 비용의 트레이드오프가 선택을 정했고, DB 문서로 더 볼 거리가 있다 |

| 적지 않는다 | 빠진 기준 |
| --- | --- |
| 이 저장소의 설정 파일이 어디 있는지, 내부 배포 절차가 어떤 순서인지 | 저장소 고유 사실과 내부 절차라 1 을 채우지 못한다 |
| `git rebase --onto` 의 인자 순서 | 도구 사용법이라 2 를 채우지 못한다 |
| 환경 변수 이름을 잘못 써서 생긴 실패 | 설정 실수라 2 를 채우지 못한다 |
| 「TTL」 의 뜻만 물었고 판단은 그대로였다 | 한두 문장 정의로 끝나고 선택을 정하지 않아 2 와 4 를 채우지 못한다 |

### 적는 명령

```bash
orch study add --slug "$SLUG" --topic "$TOPIC" --question "$QUESTION" --origin "$ORIGIN" --ref "$REF" --memo "$MEMO"
```

`$TOPIC`, `$QUESTION`, `$ORIGIN`, `$REF` 는 위 표의 네 칸이다. `$MEMO` 는 본문이 되고, 네 기준의 근거 한 줄을 담는다.
같은 후보가 이미 있으면 명령이 만들지 않고 종료 코드 1 로 끝나며 그 파일을 알린다. 새 질문에서 얻은 근거가 있으면 그 파일의 본문에 더한다.
같은 후보가 `뺌` 이면 사용자가 이미 뺀 개념이라 다시 적지 않는다.

### worker 가 적을 때

worker 도 같은 기준과 명령으로 적는다. 공통 지시서 틀의 「공부 후보 보고」 절이 이것을 시킨다.
워크트리에서 불러도 후보는 주 checkout 의 `study/` 에 쌓인다. 여러 worker 가 같은 개념을 적어도 같은 후보 판정으로 하나만 남고, 코디네이터의 `list --open` 에 함께 나온다.
작업 하나에 0건이 기본이다. `worker_done` 의 「공부 후보 N건」 은 0 이어도 정상이다.

## 알리기

**`orch-doctor` 가 `STUDY-OPEN <개수> <폴더>` 를 내면 「고를 공부 후보 <개수>개가 <폴더> 에 있다」 를 한 줄로 알린다.** 스킬을 열 때마다 doctor 가 상태가 `후보` 나 `리뷰함` 인 파일을 센다.
고르라고 재촉하지 않고, 후보를 남길지 뺄지 묻지 않는다. 후보는 계속 쌓고, 무엇을 공부할지는 사용자가 정할 때 정한다.
사용자가 어떤 후보를 빼라고 말했을 때만 `뺌` 으로 바꾼다. 뺀 개념은 같은 후보 판정에 걸려 다시 적히지 않는다.

```bash
orch study list --open
orch study set --slug "$SLUG" --status 뺌 --note "$REASON"
```

`$SLUG` 는 `list` 가 낸 첫 칸, `$REASON` 은 사용자가 뺀 이유다. 아래 「고르면 글로 잇기」 표에 없는 전이는 명령이 거부한다.

## 고르면 글로 잇기

사용자가 공부할 후보를 고르면 그 후보마다 아래 차례로 잇는다.

1. 글이 놓일 저장소에 같은 주제의 글이 있는지 본다. 있으면 그 글 경로를 알리고, 새로 쓸지 그 글을 고칠지 사용자에게 묻는다.
2. 상태를 `리뷰함` 으로 바꾼다. 메모는 「사용자가 고름」 이다. 글을 쓰다 세션이 끊겨도 고른 후보가 무엇인지 남는다.
3. 오버레이의 「공부 후보」 칸이 정한 글 쓰기 스킬로 넘긴다. 후보 파일 경로와 본문의 근거를 함께 넘긴다. 오버레이에 글 쓰기 스킬이 없으면 어느 스킬로 어디에 쓸지 사용자에게 묻고, 그 답을 오버레이에 적는다.
4. 글을 실제로 쓰면 상태를 `글 씀: <글 경로>` 로 바꾼다.

```bash
orch study set --slug "$SLUG" --status 리뷰함 --note "사용자가 고름"
orch study set --slug "$SLUG" --status "글 씀" --note "$POST"
```

`$POST` 는 쓴 글의 경로다. 글의 범위와 공개 판단은 글 쓰기 스킬이 소유하고, 글 초안 경로는 후보 본문에 적어 둔다.

| 바꿀 상태 | 조건 |
| --- | --- |
| `후보` → `리뷰함` | 사용자가 그 후보를 공부하겠다고 골랐다 |
| `리뷰함` → `글 씀` | 글을 실제로 썼다 |
| `후보` → `뺌`, `리뷰함` → `뺌` | 사용자가 빼라고 말했다 |

`리뷰함` 도 열린 후보로 센다. 고른 뒤 글을 쓰지 않으면 같은 개념을 다음에 또 묻게 된다.

## 옛 표 파일 옮기기

orch 5.16.0 전에는 `study/candidates.md` 한 파일의 표 한 줄이 후보 하나였다. 이 파일이 남아 있으면 doctor 와 명령이 stderr 로 알린다. 그 안의 후보는 세지 않는다.
줄마다 slug 를 지어 한 번 옮긴다. 번호는 표의 위에서부터 1 이다.

```bash
orch study migrate --slug 1=minio-object-key-length --slug 2=... --slug 8=expand-contract
```

slug 가 빠진 줄이 있으면 `NEED-SLUG <번호> <주제>` 를 내고 아무 파일도 만들지 않는다. 그 목록을 보고 slug 를 채워 다시 부른다.
상태는 그대로, 적은 날은 옛 파일의 수정 날짜로 옮기고 옛 파일은 휴지통(`~/.Trash/orch-study-<날짜>/`)으로 옮긴다.
표 앞의 규칙 글은 옮기지 않는다. 그 저장소만의 규칙이었으면 오버레이의 「공부 후보」 칸에 옮겨 적는다.
