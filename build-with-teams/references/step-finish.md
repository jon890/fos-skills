# 마감

**team-lead 가 읽는 문서다.** 두 검토가 `PASS` 를 낸 뒤에 읽는다.

## 목표

**구현한 것을 PR 하나로 올리고, 다음 사람이 이어받을 것을 남긴다.**

## 기준 브랜치 확인

통합 검증 전에 원격 기준 브랜치를 fetch 해 plan 브랜치가 뒤처졌는지 본다. phase 와 두 검토를 도는 동안 기준 브랜치에 커밋이 들어올 수 있다.
`$BASE_BRANCH` 는 사전 검사가 낸 `branch.base` 다.

```bash
# cwd: plan 작업 공간(worktree) root
git fetch origin "$BASE_BRANCH"
git rev-list --count "HEAD..origin/$BASE_BRANCH"
```

0 이면 통합 검증으로 간다. 1 이상이면 갱신한다.

| plan 브랜치 | 갱신 |
| --- | --- |
| 아직 push 하지 않았다 | `git rebase "origin/$BASE_BRANCH"` |
| 이미 push 했다 | `git merge "origin/$BASE_BRANCH"` |

- 충돌은 풀고 갱신을 끝낸다. 통합 검증은 갱신한 뒤의 상태에서 돌린다.
- 변경 이력 파일처럼 양쪽 항목을 모두 남기면 되는 충돌은 team-lead 가 푼다.
- 이번 plan 이 바꾼 파일에서 같은 줄을 양쪽이 다르게 고쳤으면 내용 판단이 필요하다. 사용자에게 올린다.

실측: 2026-10-01, 모든 phase 와 두 검토를 마친 뒤 기준 브랜치에 커밋 셋이 들어와 있었다. push 전이라 rebase 했고 CHANGELOG 충돌을 풀고 통합 검증을 다시 돌렸다.

## 통합 검증

레포 설정에서 찾은 통합 검증 명령을 실행한다. phase 마다 통과했어도 누적 후에 깨질 수 있다.
모노레포에서 변경이 두 하위 프로젝트에 걸치면 각 하위 프로젝트 오버레이의 검증 명령을 모두 실행한다.

실패하면 책임이 어디에 있는지 먼저 판정한다.

| 실패한 위치 | 판정 근거 | 대응 |
| --- | --- | --- |
| plan 범위 내 | 이번 plan 이 바꾼 파일이다 | executor 재스폰. 사용자 결정이 필요 없다 |
| plan 범위 밖 | 기준 브랜치와의 3-dot diff에 실패한 파일의 변경이 없다 | 아래 선택지를 사용자에게 제시한다 |

- 이 PR 에 fix 를 함께 담는다.
- 별도 hotfix PR 을 만든 뒤 rebase 한다.
- 그대로 PR 하고 설명에 의존 관계를 밝힌다.

무엇을 골랐는지 PR 설명에 남긴다.

## 원격 검증 목록

push, 배포, 원격 호스트 접속이 있어야 끝나는 검증을 모은다. 계획서를 지우기 전에 읽는다.

- plan 디렉터리의 `remote-verification.md` 표
- 4단계에서 phase 「검증」 절에서 뺀 명령
- executor 가 회신의 「미검증」 에 적은 원격 명령

모은 것을 PR 본문의 확인 목록으로 옮긴다. 이 스킬 안에서는 돌리지 않는다.
PR 을 올린 뒤 사람이 선행 조건(push, 머지, 배포)이 채워진 시점에 돌린다.
**실패하면 새 수정 작업으로 받는다.** 이미 커밋한 phase 를 다시 열지 않는다.
목록이 비었으면 이 절을 건너뛴다.

## 커밋 검토와 계획서 삭제

커밋이 phase 하나씩으로 나뉘어 있고, 다른 plan 의 변경이 섞이지 않았는지 확인한다.

**통합 검증이 통과하면 구현한 plan 디렉터리를 지우는 커밋을 PR 브랜치에 더한다.**
현재 사실은 `docs/` 와 코드가 소유한다. 계획서는 구현 뒤 곧 낡아서,
남겨 두면 에이전트나 사람이 다시 읽고 이미 바뀐 설계를 근거로 쓴다.
지난 계획은 git 이력에서 찾는다.

`$TASKS_DIR` 은 레포 설정의 tasks 경로이고, `$PLAN` 은 사전 검사가 낸 task 디렉터리 이름이다.

```bash
# cwd: plan 작업 공간(worktree) root
git rm -r --quiet "${TASKS_DIR:-tasks}/$PLAN"
git commit -m "chore: 구현을 마친 $PLAN 계획서를 지운다"
```

- 커밋 메시지 형식은 레포 설정의 커밋 컨벤션을 따른다.
- 지우기 전에 phase 가 인용한 근거 문서가 `docs/` 에 있는지 본다.
  계획서에만 있는 결정이 남았으면 docs-verifier 의 `UPDATE_NEEDED` 처럼 `docs/` 로 옮긴 뒤 지운다.
- phase 커밋과 분리한 커밋 하나로 둔다. 리뷰어가 구현 diff 와 삭제를 따로 본다.
- 지운 계획서는 `plan_precheck.py` 가 git 이력과 그 브랜치로 머지된 PR 에서 찾아 재실행을 막는다.
  squash 머지 뒤 브랜치를 지우면 git 이력에 남지 않아 PR 을 함께 본다. `index.json` 을 `completed` 로 바꾸지 않는다.

레포 설정이 계획서를 남기라고 정했으면 지우지 않고, `index.json` 의 `status` 를 `completed` 로 바꿔 같은 자리에 커밋한다.

## PR

다른 plan 의 변경이 diff 에 섞였으면 브랜치 범위를 정리한 뒤 `create-pr` 스킬을 호출한다.
제목과 본문 형식은 그 스킬이 소유한다. 다음 값을 넘긴다.

| 값 | 내용 |
| --- | --- |
| base와 head | base는 사전 검사에서 정한 기준 브랜치, head는 plan 브랜치 |
| 오픈 PR | 없으면 생성, 있으면 해당 PR을 갱신 |
| 커밋 맥락 | 기획 커밋과 phase별 커밋의 대응 |
| 검증과 발견 | 통합 검증 결과, 미검증 범위, 반영하지 않은 리뷰 발견과 범위 밖 후속 |
| 원격 검증 | 「원격 검증 목록」 에서 모은 항목. 선행 조건, 실행 위치, 명령, 기대값을 체크박스 목록으로 |
| 의존 관계 | 의존 PR이 있으면 그 링크와 필요한 적용 순서 |

## 팀 종료와 작업 공간 정리

1. 남아 있는 팀원 전부를 종료하고 확인한다.
   대상은 `executor-p{N}`, `critic`, `code-reviewer`, `docs-verifier` 다.
   종료 수단은 [`team-spawn.md`](team-spawn.md)의 하네스별 대응표를 따른다.
2. **PR 생성과 원격 push 가 끝난 뒤에** 작업 공간을 정리한다.
   미커밋 변경과 로컬에만 있는 commit 이 없는지 먼저 확인한다. 정리 방법은 오버레이를 따른다.

## 보고 형식

```text
PR #<번호> 생성 완료: 리뷰 반영은 /review-fix <번호>

특이사항:
- pre-existing: <executor 들이 보고한 것을 모은다> | 없음
- 신규 deprecation: <같음> | 없음
- 미검증: <같음> | 없음
- 범위 외 발견: <같음> | 없음

code-reviewer 발견 중 고치지 않은 것:
- <파일:줄> <의도된 설계 | 범위 밖 후속> <그렇게 판단한 이유>
- 없음

이번 세션 누적 노하우:
- <반복 함정 문서에 올린 것과 그 경로> | 신규 노하우 없음
```

**첫 줄은 PR 번호와 리뷰 반영 명령이다.** 후속이 필요한 특이사항은 이슈 등록을 제안한다.

## 재사용 패턴 승격

발견한 사건 중 아래를 모두 만족하는 것만 저장소의 반복 함정 문서로 승격한다.

- 다른 plan 이나 코드에서도 다시 일어날 수 있다.
- 원인과 회피 방법이 특정 사건을 떠나 일반화된다.
- `grep`, lint, test, build 처럼 구체적인 검출 방법이 있다.

1회성 오타, 특정 plan 의 상황 설명, 단순 실행 통계는 PR 본문과 결과 보고에만 남긴다.

누적 위치는 오버레이가 지정한다. 지정이 없으면 아래 기본값을 쓴다.

| 종류 | 누적 위치 |
| --- | --- |
| 구현과 검토의 반복 함정 | 오버레이가 지정한 경로, 없으면 `docs/pitfalls/` |
| 프로세스 결함 | 이 스킬의 `SKILL.md` |
| 도메인 결정 | 레포 ADR |
| 코딩 규칙 | 그 저장소의 하네스 지침 파일 |

반복 함정 문서는 패턴 하나당 파일 하나로 둔다. 같은 패턴이면 기존 파일을 갱신한다.

**패턴에 계획서 번호를 적지 않는다.** 계획서는 구현 PR 에서 지우므로,
번호로 적은 사고 사례는 그때 읽을 수 없는 참조가 된다.
사례가 필요하면 무엇이 어떻게 잘못됐는지를 그 자리에 쓴다. 출처가 필요하면 ADR 번호나 PR 번호를 적는다.

**폐기를 판정하는 시간 축에 계획서 번호를 쓰지 않는다.**
`계획서 몇 개 안에 재발이 없었나` 는 계획서가 사라지면 셀 수 없고,
계획서 생성 속도가 시기마다 달라 같은 개수가 같은 기간을 뜻하지도 않는다.
마지막으로 재발한 날짜를 적고 기간으로 판정한다. 기간의 값은 그 저장소가 정한다.

**날짜를 나중에 일괄로 채웠으면 추정값임을 그 자리에 밝힌다.**
파일의 마지막 커밋 날짜로 채우면 그 커밋이 재발이 아니라 오탈자 수정이나 링크 정리일 수 있다.
그러면 재발 시점이 아닌데 최근으로 잡혀 그 패턴이 실제보다 오래 남는다.
조기 폐기보다 안전한 방향이라 값은 그대로 두되,
다음 사람이 그것을 정확한 재발 기록으로 읽지 않게 한다.
