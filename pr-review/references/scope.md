# 리뷰인가 후속 업무인가

찾은 것을 전부 리뷰에 담으면 안 된다.
작성자가 이 PR 에서 고칠 수 없는 것을 요구하게 되고, 리뷰가 길어져 정작 중요한 지적이 묻힌다.

## 가르는 질문 하나

**이 PR 이 만든 문제인가?**

| 답 | 어디로 |
| --- | --- |
| 이 PR 이 만들었다 | 리뷰 |
| 원래 있었는데 이 PR 이 건드린 파일에 있다 | 리뷰. 다만 이 PR 소관이 아님을 밝힌다 |
| 원래 있었고 이 PR 과 무관하다 | 후속 업무 |
| 여러 컴포넌트에 같은 모양으로 퍼져 있다 | 후속 업무 |

## 원래 있던 문제를 다루는 법

Anthropic 의 관리형 Code Review 는 이것을 `Pre-existing` 이라는 별도 등급으로 남긴다.
우리는 등급으로 만들지 않고 **행선지 판정**으로 쓴다.

리뷰에 언급해야 할 때는 소관을 분명히 한다.

```
참고로 드라이브 쪽에도 쓰이지 않는 같은 빈이 있습니다.
저장소 공통이라 그쪽은 저희 후속으로 정리하겠습니다.
```

이렇게 쓰면 작성자는 자기가 고칠 것과 아닌 것을 바로 가른다.

## 후속 업무로 보낼 때

`dooray-task` 스킬이나 이슈 트래커 절차를 따른다. 그 스킬이 양식을 소유한다.

업무 본문에 담을 것은 리뷰와 다르다.

| | 리뷰 | 후속 업무 |
| --- | --- | --- |
| 읽는 사람 | PR 작성자 | 우리 팀 |
| 분량 | 한 논점 | 배경과 결정할 것까지 |
| 코드 인용 | 지적한 줄 | AS-IS 와 TO-BE |
| 측정값 | 한두 줄 | 표로 |

**측정값을 반드시 옮긴다.** 나중에 그 업무를 볼 때 왜 시작했는지가 측정값에 남는다.
측정 방법도 한 줄 적는다. 다시 재야 할 때 같은 방법을 쓸 수 있다.

## 사용자에게 확인할 것

행선지가 애매하면 묻는다. 판단이 갈리는 지점은 대개 둘이다.

- 작성자가 이 PR 에서 고칠 수 있는 범위인가
- 지금 고치지 않으면 배포에 걸리는가

두 번째가 참이면 범위를 넘더라도 리뷰로 낸다. 배포 순서에 걸리는 스키마 변경 같은 것이 그렇다.

## 리뷰에 담지 않는 것

- CI 나 포매터가 이미 잡는 것
- 생성 코드, lock 파일, vendor 디렉터리
- 이 PR 이 건드리지 않은 파일
- 사람 이름과 사내 식별자 (공개 저장소에 등록하는 경우)
