# 업무 알림함

확인: 2026-11-02

## 목표

업무 도구에서 내가 태그된 업무와 댓글, 메신저 멘션을 `/board` 창에서 바로 보고, 맥락을 읽은 답변 초안을 내가 확인한 뒤 등록한다.
도구에 묶이지 않도록 보드와 답변 흐름은 공통 항목 모델을 쓰고, 도구마다 adapter 가 받기, 맥락 읽기, 사람 이름 풀기, 답변 등록을 맡는다. 첫 adapter 는 두레이다.
프로젝트마다 오케스트레이터와 보드를 두므로, 저장소마다 그 프로젝트의 알림만 보인다.

계기는 2026-11-02 의 두 사건이다.

- 어드민개발 81 업무 댓글에서 사용자가 태그됐는데, 사용자가 전해 주기 전까지 코디네이터가 몰랐다.
- 답변 초안이 댓글 작성자의 `organizationMemberId` 를 이름으로 풀지 않아 받는 사람을 틀리게 적었다.

## 범위

이번 기능에 드는 것:

- 공통 항목 모델과 adapter 계약, 사람 단위 설정과 상태, 저장소별 필터
- 두레이 adapter: 업무 댓글 멘션, 담당·참조로 온 새 업무, 메신저 멘션을 받고 업무 댓글이나 대화방 메시지로 답한다
- 새 스킬 `inbox`: `inbox.ts` 명령과 답변 절차
- `/board` 창의 알림 상자, 상태 줄의 새 알림 수, 답변 요청문을 채우는 단축키

범위 밖:

- 사용자 확인 없이 답변을 등록하는 동작
- Slack adapter 구현. 계약과 더할 때 바뀌는 곳만 문서로 남긴다
- 두레이 프로젝트 Hook, 비공식 WebSocket, 외부 수신 서버
- `dooray stream list` 명령 구현. `jon890/dooray-cli` 에서 별도 PR 로 한다(D3)

## 설계

### 공통 항목 모델 (R2)

```ts
type InboxItem = {
  id: string              // '<adapter>:<출처>:<원본 id>'. 같은 알림은 같은 id 다
  adapter: string         // 'dooray'
  source: string          // adapter 안의 출처. 두레이는 'task', 'messenger'
  kind: 'mention' | 'assigned' | 'cc'
  title: string           // 업무 제목이나 대화방 이름
  url: string             // 사람이 여는 주소. 모르면 ''
  scope: string[]         // 저장소 필터와 맞출 값. 두레이 업무는 프로젝트 id 와 코드, 메신저는 대화방 id 와 이름
  from: { id: string; name: string }
  at: string              // ISO 8601
  excerpt: string         // 본문 앞부분 한 줄
  target: Record<string, string>   // 답변을 등록할 곳. adapter 만 읽는다
  state: 'new' | 'answered' | 'dismissed'
}
```

### adapter 계약 (R2, R3, R5)

| 동작 | 하는 일 | 두레이 |
| --- | --- | --- |
| `fetch(since)` | `since` 뒤의 항목과 출처별 오류를 낸다 | 업무: `dooray --json stream list --since`. 메신저: `messenger channels --since` 로 바뀐 방만 고르고 방마다 `messenger logs` |
| `context(item)` | 본문, 앞 대화, 참여자 | 업무 본문과 댓글 목록, 대화방의 앞 메시지 |
| `resolvePeople(ids)` | 사람 id 를 이름으로 | `dooray --json member get`, 사람 단위 캐시 |
| `answered(item)` | 알림 뒤에 내 답이 있는지 | 업무 댓글 목록이나 대화방 메시지에서 알림 시각 뒤의 내 글 |
| `reply(item, body)` | 확인받은 본문을 등록 | `dooray post comment add --id` 나 `dooray messenger channel-send --channel` |

메신저 호출 수는 두 가지로 줄인다. 지난 받기 뒤에 바뀐 대화방만 읽고(`--since`), 봇 방과 나와의 대화는 건너뛴다.
한 번에 읽는 방은 바뀐 방의 오래된 순으로 20개까지다. 남은 방은 마지막으로 읽은 방의 시각을 커서로 남겨 다음 받기가 잇는다. 읽지 못한 방은 따로 적어 다음 받기에 다시 읽는다.
업무 피드도 지난 받기 뒤만 읽는다. 커서는 출처마다 따로 두어, 한 출처의 실패가 다른 출처의 받기를 멈추지 않는다.
Slack adapter 를 더하면 adapter 파일 하나와 등록 줄 하나, 필터 파일의 `slack` 키가 는다. 보드와 답변 흐름은 바뀌지 않는다.

### 파일 (R6, R8, R9, D9~D12)

| 파일 | 단위 | 내용 |
| --- | --- | --- |
| `${XDG_CONFIG_HOME:-~/.config}/fos-skills/inbox.json` | 사람 | 켤 adapter, `intervalMinutes`(기본 5), `days`(기본 7), `signature`, `defaultBoard`(주 checkout 경로), adapter 별 값(두레이 웹 주소 등). 없으면 기능이 꺼진다 |
| `${XDG_STATE_HOME:-~/.local/state}/fos-skills/inbox/` | 사람 | 받은 항목 캐시와 받은 시각, 넘김 기록, 이름 캐시, 필터를 가진 저장소 목록 |
| `<orch 폴더>/config/notification.json` | 저장소 | adapter 별 키 아래 볼 범위. 두레이는 `projects`(id 나 코드)와 `channels`(id 나 이름), Slack 은 `channels` |

orch 폴더는 주 checkout 의 `.orch` 다(`ORCH_DIR` 이 있으면 그 값). 워크트리에서 불러도 같은 파일을 읽는다. 해석은 `orch/scripts/lib/paths.ts` 의 `orchDir` 이 소유한다.
`.orch/` 는 이 저장소와 ai-analysis 에서 git 이 무시해 사내 id 가 커밋되지 않는다.
「미분류」 는 필터 파일을 가진 저장소 가운데 어느 필터에도 들지 않는 항목이다. 보드가 받기를 부를 때 자기 저장소를 상태 폴더의 저장소 목록에 적는다.

### 받기와 표시 (R1, R7)

보드 훅은 1분마다 `node <플러그인 루트>/inbox/scripts/inbox.ts board --repo <주 checkout> --json` 을 부른다.
이 명령은 지금 캐시를 저장소 필터로 나눠 바로 낸다. 캐시가 `intervalMinutes` 보다 오래됐고 다른 세션이 받고 있지 않으면 `inbox.ts fetch` 를 따로 띄운다.
받기는 두레이 호출이 수십 번 들 수 있어 보드 훅의 시간 제한 안에서 기다리지 않는다. 그래서 처음 켠 직후의 첫 응답은 빈 목록이고 다음 호출부터 받은 항목이 보인다.
따로 띄운 받기는 잠금을 잡고 adapter 의 `fetch` 와 새 항목의 `answered`(한 번에 15개까지)를 부른 뒤 캐시를 쓴다. 잠금은 10분이 지나면 다른 세션이 다시 잡을 수 있고, 잡은 쪽만 푼다.
받기가 실패한 출처는 직전 항목을 그대로 두고 오류를 출처마다 남긴다.

### 답변 흐름 (R4, R10)

보드 훅은 모델에 직접 요청을 보내지 못해(`work-board/references/behavior.md` 「훅이 직접 보내지 않는 이유」) 입력란에 요청문을 채운다.
`1`~`9` 는 그 항목의 답변 요청문을, `i` 는 새 항목 전체를 훑어 답할 것과 넘길 것을 나누는 요청문을 채운다.
요청문은 맥락 읽기, 초안, 미리보기, 사용자 확인, `inbox.ts reply --yes` 순서를 담는다. 절차 문서는 `inbox` 스킬이 소유한다.

### 테스트

공통 모델, 필터, 캐시, 명령은 가짜 adapter 와 임시 폴더로 테스트한다. 두레이 adapter 의 변환은 공식 문서 예시와 dooray CLI 출력 필드를 본뜬 고정 응답으로 테스트한다.
보드 표시는 `claude plugin test` 의 화면 테스트로 본다. 실제 두레이 등록은 테스트에서 부르지 않는다.
R1, R5, R7 의 실제 동작은 `dooray stream list` 가 배포된 뒤 인수 검증에서 확인한다.
