# 결정 기록 샘플

아래는 가상 서비스의 작성 예시다. 정책·수치·승인·검증의 실제 증거가 아니다.
[ADR 규칙](adr-rules.md)으로 남길 필요부터 판단하고 [양식](../templates/adr.md)을 실제 결정으로 채운다.
예시 경로는 인라인 코드로 표시했다. 대상 저장소에서는 존재하는 원본으로 링크한다.

## architecture: 사용자별 Memory 접근 경계

- **status**: `accepted` (예시에서 합의한 것으로 가정)
- **decision-type**: `architecture`
- **areas**: `security, data`
- **현재 규칙의 원본**: `docs/contracts/memory-access.md`, 권한 필터 구현과 API 스키마
- **결정**: Memory 접근 권한은 실행 요청을 받는 서버가 강제한다. 에이전트에는 그 사용자가 읽을 수 있는 항목만 전달한다.
- **맥락**: 개인·공용 Memory 를 같은 저장소에서 제공한다. 프롬프트에 접근 금지를 적는 방식은 우회 가능하고 서버에서 거부 여부를 검증할 수 없다.
- **대안 기각**: 전체 Memory 를 주고 모델이 허용된 항목만 고르게 한다. 권한 밖 내용이 이미 전달되므로 응답을 가려도 접근 경계를 회복하지 못한다.
- **결과**:
  - 얻는 것: 모델과 프롬프트가 바뀌어도 같은 접근 경계를 유지한다.
  - 감당할 것: 서버가 사용자 식별·권한 필터를 소유하고 모든 조회 경로에 적용해야 한다.
- **확인 방법**: 다른 사용자 식별자로 조회해 응답·전달 문맥에 권한 밖 내용이 없는지 API 통합 테스트로 확인한다.

정책이 소유자와 공유 대상의 범위를 이미 정했다는 전제다. 누가 읽을 수 있는지 미정이면 spec 으로 돌아간다.
필드·토큰 형식 전체를 ADR 에 복사하지 않고 현재 계약을 연결한다.

## domain-policy: 예약 실행에 사용자별 상한을 둔다

- **status**: `accepted` (예시에서 사용자 확인을 받은 것으로 가정)
- **decision-type**: `domain-policy`
- **areas**: `cost, scheduling`
- **현재 규칙의 원본**: `docs/domain/scheduled-jobs.md` 의 `RULE-JOB-LIMIT`, 상한 값은 설정이 소유
- **결정**: 자동 예약 실행은 사용자별 상한을 적용한다. 상한을 넘은 회차는 실행하지 않고 건너뛴 이유를 남긴다.
- **맥락**: 반복 예약 하나가 사용량을 독점할 수 있다. 실행이 끝난 뒤 비용만 보여주면 이미 사용한 자원을 제한할 수 없다.
- **대안 기각**: 동시 실행 수만 제한한다. 짧은 실행이 연속으로 반복되면 하루 사용량은 제한되지 않는다.
- **결과**:
  - 얻는 것: 사용자 한 명의 잘못된 예약이 전체 사용량을 독점하는 위험을 줄인다.
  - 감당할 것: 상한을 넘긴 회차는 누락될 수 있어 상태와 사유를 사용자에게 보여줘야 한다.
- **확인 방법**: 상한 직전·동일·초과 사례와 사용자 간 독립성을 확인한다.

정책 결정은 spec 의 결정 표에서 확인받는다. 상한의 현재 값·허용 범위·건너뛰기 의미는 도메인 문서와 설정에 둔다.
허용 범위 안에서 설정 값만 조정하면 ADR 을 새로 쓰지 않는다. 집계 의미나 누락 정책이 바뀌면 결정 변경으로 판단한다.

## engineering-process: 인수 검증은 실제 사용 경계에서 한다

- **status**: `accepted` (예시에서 절차 변경을 합의한 것으로 가정)
- **decision-type**: `engineering-process`
- **areas**: `quality`
- **현재 규칙의 원본**: 해당 verify 절차 문서와 검증 결과 양식
- **결정**: 단위 테스트와 코드 리뷰 외에 사용자 인수 조건을 실제 API·CLI·화면 경계에서 확인한다. 실행하지 못한 필수 사례는 통과로 보고하지 않는다.
- **맥락**: 내부 테스트가 통과해도 잘못 연결된 실행 경로나 권한 설정은 실제 사용에서 실패할 수 있다.
- **대안 기각**: 테스트 개수와 리뷰어 PASS 만으로 완료한다. 사용자 흐름을 실행했다는 증거가 되지 않는다.
- **결과**:
  - 얻는 것: 사용자 동작과 완료 보고 사이의 근거를 추적할 수 있다.
  - 감당할 것: 검증 환경을 준비해야 하고 환경이 없으면 필수 사례가 미완료로 남는다.
- **확인 방법**: 실제 작업의 검증 결과에서 커밋·환경·기대값·실제값과 미실행 사례를 대조한다.

확정자는 [문서 소유권의 단계별 책임](../../spec/references/document-ownership.md#결정-기록의-단계별-책임)을 따른다. 이 예시는 사용자가 장기 절차 변경에 합의한 경우다. 제품 동작을 바꾸지 않으므로 기능 spec 을 새로 만들 필요는 없다.
실제 실행 명령과 통과 조건을 이 기록에도 복제하지 않고 현재 절차로 연결한다.

## 결정 변경과 현재 규칙 갱신

예를 들어 예약 실행의 초과 회차를 건너뛰는 대신 다음 시간대로 미루기로 정했다면 다음처럼 처리한다.

1. spec 에서 정책 변경과 인수 조건을 확인한다.
2. 새 `domain-policy` ADR 에 새 선택의 이유와 이전 ADR 링크를 남긴다.
3. 이전 ADR 의 결정 바로 아래에 대체한 부분과 새 ADR 링크를 붙인다. 당시 맥락·대안·결과는 보존한다.
4. 같은 PR 에서 도메인 문서·설정·구현·확인 사례를 맞춘다. 전체 대체의 상태·이동은 저장소 규약을 따른다.
5. verify 가 새 원본과 구현을 대조한다. docs-consolidate 는 새 정책을 대신 정하지 않는다.

## ADR 을 만들지 않는 예

| 요청 | 남길 자리 | 이유 |
| --- | --- | --- |
| 기존 패턴을 따르는 함수 추출 | 코드·PR | 독립적인 장기 선택이 없다 |
| 허용 범위 안에서 예약 상한 값 조정 | 설정과 변경 이력 | 정책의 의미를 바꾸지 않는다 |
| 단일 기능의 일시적인 화면 문구 | 기능 spec | 여러 기능이 참조할 장기 결정이 아니다 |
| 설치된 라이브러리 이름만 나열 | 의존성 파일 | 선택 이유를 더하지 않는다 |

반대로 특정 라이브러리의 복구 방식·권한 모델·라이선스 제약 때문에 대안을 기각했다면 그 장기 선택 이유는 `architecture` ADR 후보가 된다.
