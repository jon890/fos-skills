# docs-consolidate

**목표: 기능 문서를 현재 구현에 맞추고 실제로 반복되는 규칙만 공통화한다.**

[문서 소유권](../spec/references/feature-docs.md)을 읽는다.
`.claude/docs-consolidate-overlay.md`, 없으면 docs-check 오버레이와 저장소 지침에서 경로·검사 명령을 읽는다.

[문서 소유권](../spec/references/document-ownership.md)과 [문서 대조 양식](templates/document-review.md)을 먼저 읽는다.
계획 정리는 [계획 수명 규칙](../plan/references/plan-lifecycle.md)을 따른다.

## 기능 검증 뒤: 후보 추출

입력은 검증한 스펙, 변경 diff, verify 결과와 관련 기능·공유 계약이다.

1. 이번 기능의 문서가 검증한 구현과 맞는지 확인한다. 문서의 오타·누락은 해당 기능 범위에서 고친다.
   합의한 동작을 코드에 맞춰 바꾸지 않는다. 의미 차이는 spec, technical-design 또는 implementation 으로 돌려보낸다.
2. 이번 기능이 공통 흐름·권한·상태를 바꿨으면 해당 책임 문서도 대조한다. 필요한 정합성 수정을 공통화 후보로 미루지 않는다.
   새 공유 결정을 해야 하면 technical-design 으로 반환한다. 관련 없는 문서 감사로 범위를 넓히지 않는다.
3. 관련 스펙·계약만 읽고 중복·모순·공유 개념 후보를 찾는다. 저장소 전체 감사로 범위를 넓히지 않는다.
4. 후보마다 두 위치와 공통점·차이·제안할 소유 위치를 적는다. 없으면 검토 범위와 `후보 없음` 을 적는다.
5. 결과를 PR 본문이나 그 PR 의 증거 파일로 orch 에 넘긴다. 중앙 INDEX·진행표를 갱신하지 않는다.

이 모드에서 공유 계약을 새로 추출하거나 재구성하지 않는다.
기능 문서를 수정했으면 저장소 문서 검사를 실행하고 verify 에 문서 재검토를 요청한다.
코드·스펙의 동작 의미가 그대로면 제품 실행 테스트 전체를 반복하지 않는다.

## 후보가 모였을 때: 공통화

사용자 또는 orch 가 후보 묶음의 문서 정리를 작업 범위로 지정한 경우에만 수행한다.
후보가 생겼다는 이유로 현재 PR 의 범위를 자동 확장하지 않는다.

1. 후보의 실제 구현과 요구사항을 대조한다. 표현만 비슷하면 기각하고 아직 변동이 크면 보류한다.
2. 채택할 규칙의 소유 위치를 기존 계약 또는 `docs/contracts/<주제>.md` 로 정한다.
3. 공통 내용은 한곳으로 옮기고 기능 문서의 복제는 링크로 바꾼다. 기존 공통 계약이 있으면 새 사본을 만들지 않는다.
4. 관련 링크와 중복·의미 보존을 확인하고 저장소의 문서 검사를 실행한다.
5. 변경 범위와 채택·보류·기각 근거를 보고하고 별도 PR 처리는 orch 에 넘긴다.

제품 동작, 권한, 데이터 의미를 바꿔야 하면 문서 정리로 처리하지 않고 새 spec 작업으로 넘긴다.
문서 경로를 바꾸면 소비자와 링크도 함께 갱신한다. 원본이 정해진 API/DB 스키마를 문서로 복제하지 않는다.

## 완료 기준

후보 추출은 기능 문서가 구현과 맞고 후보의 근거 또는 후보 없음이 남으면 끝난다.
공통화는 지정한 후보들의 판정이 있고, 채택한 내용이 한곳에 있으며 문서 검증을 통과하면 끝난다.
공통화 후보가 남아 있어도 기능 완료를 막지 않는다. 실제 모순이 동작을 바꾸는 경우는 예외로 verify 에 돌려보낸다.
새 스케줄이나 상주 프로세스를 만들지 않는다. orch 가 관련 기능 묶음을 마쳤거나 후보 검토를 요청할 때 실행한다.
