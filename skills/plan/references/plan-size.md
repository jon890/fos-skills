# plan 하나는 PR 하나다

**plan 하나는 PR 하나로 끝나는 크기로 자른다. 대략 하루 안에 구현하고 머지까지 가는 일이다.**
더 큰 일은 plan 을 여럿으로 나누고, 지금 할 plan 만 자세히 쓴다.
뒤의 일은 목표 표나 그 저장소의 할 일 목록에 한 줄로 두고, 앞 PR 이 머지된 뒤 그때의 코드를 보고 계획한다.

## 이유

미리 써 둔 phase 문서는 앞 phase 를 하는 사이 낡는다.
크기가 크면 구현자가 draft PR 에서 멈추고, CI 실패와 충돌이 날 때마다 다시 맡겨야 한다.

## 어디서 판단하나

| 단계 | 판단 |
| --- | --- |
| 3 PR 범위 | 「이 변경이 어디까지 손대나」 에서 이번 PR 의 범위를 한 문장으로 정한다. 이 문장이 `index.json` 의 `pr_scope` 가 된다 |
| 4 task 작성 | phase 로 나누기 전에 범위가 PR 하나에 들어가는지 본다. 넘으면 plan 을 나누고 지금 할 것만 phase 로 쓴다. 뒤로 미룬 일은 `deferred` 에 적는다 |

PR 순서와 단위처럼 사용자가 정할 것은 spec 인터뷰가 묻고 스펙에 닫혀 있다. plan 은 그 결정을 따라 이번 PR 하나의 범위를 자른다.
스펙이 정한 단위가 아래 「검사 기준」 의 크기를 넘어 더 나눠야 할 때만 plan 이 사용자에게 어디서 자를지 묻는다. 앞 plan 이 끝나야 의미가 생기는 선을 고른다.

## 뒤로 미룬 일

뒤의 plan 은 phase 문서를 쓰지 않는다. 한 줄로 아래 세 가지만 남긴다.

| 칸 | 담는 것 |
| --- | --- |
| `what` | 무엇을 하나 |
| `why` | 왜 지금 이 plan 에 넣지 않나 |
| `after` | 앞 plan 의 무엇이 머지된 뒤에 하나 |

한 줄은 `index.json` 의 `deferred` 에 적고, 저장소에 목표 표나 할 일 목록이 있으면 거기에도 옮긴다.
`deferred` 가 가리키는 일은 그 PR 이 머지된 뒤 `plan` 을 다시 열어 계획한다.
`orch` 로 구현을 맡길 때 plan 하나는 worker 하나다. 뒤 plan 은 앞 PR 이 머지된 뒤 코디네이터가 새 지시서로 새 worker 에게 맡기고, 앞 worker 가 이어 맡지 않는다.

## 검사 기준

`verify_task.ts` 가 아래를 본다.

| 검사 | 결과 |
| --- | --- |
| phase 가 6개를 넘는다 | 위반. plan 을 나눈다 |
| 변경 파일이 40개를 넘는다 | 경고. 디렉터리 이동 같은 일괄 이동이면 `pr_scope` 에 그렇게 적는다 |
| 레포 설정의 「PR 변경 파일 상한」 을 넘는다 | 경고. 40개 기준 대신 쓰고, phase 별 변경 파일 수를 함께 내 나눌 선을 고르게 한다 |
| 수정할 파일이 레포 설정의 「파일 길이 상한」 의 95% 이상이다 | 경고. 더할 코드를 새 파일로 나눌지 계획에서 정한다 |
| 운영 코드 추정 줄 수가 레포 설정의 「PR 줄 수 상한」 의 80% 를 넘는다 | 경고. phase 별 추정을 보고 상한을 넘으면 자를 선을 미리 정한다 |
| 운영 코드 추정 줄 수가 레포 설정의 「PR 줄 수 상한」 을 넘는다 | 위반. 아래 「줄 수 상한을 넘을 때」 대로 plan 을 나눈다 |
| `pr_scope` 가 비었거나 한 문장이 아니다 | 위반 |
| `deferred` 칸이 없거나, 항목에 `what`, `why`, `after` 가 비었다 | 위반. 미룬 일이 없으면 빈 배열이다 |

레포 설정 값의 이름과 형식은 [레포 설정 탐색](monorepo.md#스크립트가-직접-읽는-값)이 정한다.
저장소의 크기 기준은 구현 뒤 PR 크기 측정에서야 걸리면 phase 커밋을 옮기고 계획을 다시 써야 해서, 계획 단계에서 같은 기준으로 본다.

`created_at` 이 2026-10-25 보다 이르거나 없는 옛 plan 은 같은 검사를 경고로만 낸다. 진행 중인 계획서를 다시 쓰게 하지 않는다.
「PR 줄 수 상한」 초과는 `created_at` 이 2026-11-20 이후인 plan 만 위반이고, 그 전 plan 은 경고다.

### 줄 수 상한을 넘을 때

phase 별 추정 줄 수를 보고 앞 plan 이 끝나야 의미가 생기는 선을 고른다. 뒤 phase 는 `deferred` 에 한 줄로 옮긴다.

| 경우 | 하는 일 |
| --- | --- |
| 스펙이 이 PR 의 단위를 정했다 | 그 단위를 더 나누는 것이라 사용자에게 어디서 자를지 묻는다. phase 별 추정을 함께 보인다 |
| 스펙이 PR 단위를 정하지 않았거나, 스펙 없는 계획이다 | plan 이 phase 경계에서 자르고 묻지 않는다. 자른 선과 phase 별 추정을 인계에 적는다 |

## 줄 수 추정

`verify_task.ts` 는 변경 파일 표로 PR 의 줄 수를 추정해 경고 한 줄로 알린다. 계수는 `scripts/pr_size.ts` 가 갖는다.

| 변경 | 세는 줄 |
| --- | --- |
| 수정 | 현재 줄의 20% |
| 삭제 | 현재 줄 전체. 운영 코드 파일을 통째로 지우면 운영 코드에서 빼고 전체에만 센다 |
| 이동(같은 이름의 삭제 행과 신규 행) | 둘 다 0줄 |
| 신규 운영 코드 파일 | 60줄 |
| 신규 테스트 코드 파일 | 130줄 |
| 신규 문서(`.md`) | 60줄 |
| 그 밖의 신규 파일(SQL, 설정, fixture) | 10줄 |

추정은 운영 코드, 테스트, 문서로 나눠 낸다. 「PR 줄 수 상한」 은 운영 코드에만 비교한다.
`.github/pr-size.json` 이 있으면 그 분류(`core`, `generated`, `tests`, `docs`)를 쓴다. 없으면 아래 순서로 처음 맞는 것을 고른다.

1. 레포 설정 「PR 줄 수 운영 코드」 의 glob 에 맞으면 운영 코드다. 저장소가 Markdown 같은 파일을 운영 코드로 셀 때 적는다
2. `.md`, `.mdx` 이거나 경로에 `docs` 폴더가 있으면 문서다
3. 경로에 `test`, `tests`, `__tests__`, `e2e` 폴더가 있거나 테스트 이름(`*.test.*`, `*.spec.*`, `*Test.java` 등)이면 테스트다
4. 나머지는 운영 코드다
의존 lock 파일(`pnpm-lock.yaml` 등), 빌드 결과물(`dist/`, `build/`, `.next/`, `coverage/`), 스냅샷과 압축·묶음 JS 는 설정이 없어도 세지 않는다.
glob 행과 읽지 못한 수정 파일은 「줄 수 미상」 으로 빼고 센다. 한 phase 에서 만들고 뒤 phase 에서 고친 파일은 신규로 센다.

`.github/pr-size.json` 의 `grades` 는 A·B·D 상한을 읽는다. A 이하면 A, A 초과는 B, B 초과는 C, D 초과는 D 이며 각 등급의 어느 항목이든 넘으면 그 기준을 넘은 것이다.

### 계수의 근거 (2026-11-20 실측)

fos-assistant 에서 계획서가 남은 기능 PR 12개(805, 809, 813, 817, 810, 780, 785, 786, 775, 808, 790, 759)를 비교했다.
계획서는 머지 때 지워져서 PR 브랜치 이력의 마지막 내용을 읽었다. 실제 줄 수는 그 저장소 `scripts/pr/pr-size.mjs` 의 분류로 센 추가와 삭제다.

- 신규 파일 하나의 실제 줄 수는 운영 코드 평균 70줄(중앙값 44줄, 112개), 테스트 약 135줄(63개), 문서 65줄(9개), SQL 8줄(6개)이었다.
- 계획서가 그 파일을 설명한 분량(인라인 코드 수, 글자 수)과 실제 줄 수의 상관계수는 0.22 에서 0.26 이었다. 설명 분량으로 계수를 바꾸지 않고 종류별 고정값을 쓴다.
- 수정 파일은 실제가 현재 줄의 12%(139개 합계, 파일 하나의 중앙값 8%)였다. 20% 는 파일 하나로는 크지만, 계획서에 없이 함께 바뀐 파일(PR 마다 0줄부터 273줄까지)을 메운다.
- 운영 코드 신규 계수를 PR 단위로 맞춰 봤다. 수정 20% 와 함께 쓸 때 결과는 아래와 같다.

| 신규 계수 | 실제 1,500줄 이하인데 추정이 1,500줄을 넘은 PR | 실제 1,500줄 초과인데 추정이 80% 이하인 PR | 추정/실제 기하평균 |
| --- | --- | --- | --- |
| 50줄 | 0개 | 0개 | 1.02 |
| 60줄 | 0개 | 0개 | 1.12 |
| 70줄 | 1개(813: 실제 1,163줄, 추정 1,654줄) | 0개 | 1.22 |

60줄로 정했다. 실제로 상한을 넘은 817(1,560줄)과 810(1,594줄)은 추정 1,432줄과 1,409줄로 80% 경고를 받는다. 50줄에서는 경고 폭에 겨우 걸린다.
1,000줄 넘는 PR 의 추정은 실제의 0.7배부터 1.5배까지라 상한 근처에서는 위반보다 경고가 먼저 알린다. 작은 PR(805, 775)은 2배 이상 크게 나오지만 상한과 멀어 결과에 영향이 없다.
