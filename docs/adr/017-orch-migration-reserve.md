# ADR-017: 마이그레이션 번호는 worker 가 만들기 전에 잠금을 걸고 예약한다

- **status**: `accepted`
- **결정**: worker 가 Flyway 마이그레이션 파일을 만들기 전에 `orch/scripts/reserve-migration.ts` 로 다음 번호를 예약한다.
  번호는 base 의 최고 번호, 다른 열린 PR 이 더한 번호, 다른 브랜치의 예약 번호 가운데 가장 큰 것의 첫 자리에 1 을 더한 값이다.
  예약은 `<orch 루트>/state/migration-reservations.json` 에 브랜치와 함께 남기고, 읽고 정하고 쓰는 일을 같은 폴더의 잠금 안에서 한다.
  같은 브랜치, 모듈, 설명으로 다시 부르면 같은 예약을 돌려준다. `--again` 은 그 예약을 버리고 새 번호를 받는다.
  그 브랜치의 PR 이 머지되거나 닫혔거나 브랜치가 원격과 로컬에 모두 없으면 다음 호출이 그 예약을 지운다.
  상주 루프의 자동 머지([ADR-016](016-orch-auto-merge.md))는 PR 이 아직 없는 다른 브랜치의 예약도 더 낮은 번호로 보고 높은 번호 PR 을 기다리게 한다.
  사용자 결정 2026-10-27: Flyway out-of-order 는 켜지 않는다. 적용 순서를 모든 환경에서 같게 두려는 것이다.
- **맥락**: 같은 모듈의 마이그레이션 번호를 PR 끼리 겹쳐 써 두 번째 PR 이 개발 서버 기동을 깨뜨렸다. 하루에 한 모듈의 같은 번호를 PR 네 개가 함께 쓴 일이 있었다.
  자동 머지가 겹침을 머지 전에 잡아도, 그때는 worker 가 이미 번호를 정해 파일과 테스트를 만든 뒤라 다시 정하는 비용이 크다.
- **대안 기각**:
  - out-of-order 를 켠다. 환경마다 적용 순서가 달라져, 개발 DB 에서 통과한 순서와 운영 DB 의 순서가 갈린다(사용자 결정).
  - 번호 대신 시각(`V20261027…`)을 쓴다. 이미 정수 번호를 쓰는 저장소의 정렬이 깨지고, 늦게 머지된 PR 의 이른 시각이 base 최고보다 작아 out-of-order 가 필요해진다.
  - 예약을 원격(브랜치나 이슈)에 둔다. 같은 PC 의 worker 끼리 겹치는 것이 문제였고, 원격 쓰기는 권한과 네트워크에 묶인다. 주 checkout 의 `.orch/` 는 모든 worktree 가 함께 본다.
  - 예약 없이 자동 머지의 겹침 알림만 둔다. 겹친 뒤에 알게 돼 worker 가 파일 이름, 테스트, 문서를 다시 고쳐야 한다.
  - 막힌 PR 의 파일 이름을 루프가 바꾼다. 이미 개발 DB 에 적용한 번호면 체크섬이 어긋난다. 사람이나 worker 가 `--again` 으로 다시 받는다.
- **결과**:
  - 얻는 것: 같은 PC 의 worker 들이 같은 모듈에 서로 다른 번호를 받는다. PR 을 열기 전의 번호도 자동 머지의 순서 판정에 든다.
  - 감당할 것: 예약만 하고 버린 브랜치의 번호는 그 브랜치가 원격과 로컬에서 사라질 때까지 남는다. 그동안 높은 번호 PR 이 기다리고 `MIGRATION-BLOCKED` 가 온다.
  - 감당할 것: 다른 PC 에서 만든 브랜치의 번호는 PR 을 열기 전까지 보이지 않는다. 열린 뒤에는 자동 머지의 겹침 판정이 잡는다.
- **적용 범위**: 예약 파일과 잠금은 `orch/scripts/lib/reservations.ts`, 명령은 `orch/scripts/reserve-migration.ts` 머리 주석, 지시서 문구 예시는 [`../../orch/references/spec-writing.md`](../../orch/references/spec-writing.md) 가 소유한다.
