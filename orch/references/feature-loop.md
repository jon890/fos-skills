# 기능 단위 개발 루프

orch 가 전체 루프를 조율한다. 단계별 판단과 산출물은 각 스킬이 소유한다.
입력은 기능 요청 또는 스펙 경로다. 기존 spec 필드 없는 plan 은 기존 worker 절차로 이어 간다.

| 순서 | 실행할 스킬 | 넘길 것 | 다음 단계 조건 |
| --- | --- | --- | --- |
| 1 | spec | 사용자 요청, 관련 코드와 공통 계약 | 필요한 결정과 인수 조건이 정리됨 |
| 2 | planning | 스펙 | 이번 PR 의 요구사항과 실행 계획이 검토됨 |
| 3 | build-with-teams | 스펙, plan, 작업 공간 | 구현과 개발 검증 완료 |
| 4 | verify | 같은 커밋, 스펙, plan, 개발 검증 | 이번 PR 필수 인수 조건과 독립 리뷰 통과 |
| 5 | docs-consolidate | 스펙, diff, 검증 결과 | 문서 대조와 후보 추출 완료. 후보 0건도 완료 |
| 6 | orch 의 기존 PR·머지·배포·정리 | 아래 인계 기록 | PR 반영과 필요한 원격 검증 완료 |

## 전이

- 구현 문제는 build, 요구사항·설계 누락은 spec/planning 으로 돌린다. 해결되지 않은 단계에서 다음으로 가지 않는다.
- 환경·권한 때문에 실행하지 못하면 필요한 것을 보고한다. 통과로 취급하지 않는다.
- spec 또는 코드가 바뀌면 영향받는 계획과 검증을 갱신한다. 이전 커밋의 결과를 새 변경에 그대로 쓰지 않는다.
- 공통 후보가 없거나 공통화가 보류돼도 기능 완료를 막지 않는다. 동작을 바꾸는 모순은 verify 에서 해결한다.
- 문서만 수정하면 verify 의 문서 검토만 다시 받는다. 원격 검증의 선행 조건이 채워지면 그 검증을 수행한다.

## worker 와 PR

새 기능 worker 지시서에 `spec → planning → build-with-teams → verify → docs-consolidate 후보 추출` 을 적는다.
스펙/계획이 이미 있으면 필요한 단계부터 시작한다. 단계를 나눠도 worker 의 완료 기준 PR 하나의 MERGED 는 유지한다.
build 의 구현 완료는 중간 상태다. worker_done 으로 dispatch 를 끝내지 않는다.
검증·후보 추출 뒤 PR 생성이 허락됐으면 worker 가 PR 을 열고, 아니라면 코디네이터가 허락 범위에 따라 처리한다.
머지와 작업 공간 정리는 기존 orch 절차가 맡는다. 여러 plan 이면 PR 하나가 머지된 뒤 다음 plan 을 구체화한다.

PR 을 열기 전에 스펙·요구사항 ID, verify 결과, 검증 커밋, 남은 원격 검증과 공통 후보를 본문에 보존한다.
계획서를 지우기 전에 `index.json` 의 `deferred` 전체(목표·이유·선행 조건)도 PR 본문에 옮긴다.
다음 worker 에게 앞 PR 의 이 목록과 스펙을 넘겨 다음 plan 을 만들게 한다. 중앙 진행표 갱신은 요구하지 않는다.
`remote-verification.md` 는 [기존 원격 검증 규칙](../../planning/references/task-create.md#원격-검증-목록)대로 시점·위치·명령·기대값을 옮긴다.
필수 `PR 전` 검증의 통과 결과가 없으면 PR 을 열지 않는다. 해당 검증이 없는 계획은 이 조건을 적용하지 않는다. `PR 뒤` 검증이 남았으면 머지/배포 뒤 실행하고 결과를 보존한다.
계획서는 검증과 기록 보존을 마친 뒤, 저장소 규칙대로 PR 안에서 제거한다. 스펙과 공유 계약은 남긴다.
계획서 삭제 같은 비제품 변경은 제품 검증을 반복하지 않지만 문서/링크 검사는 확인한다.
기준 브랜치 병합·충돌 해결·리뷰 수정으로 코드가 바뀌면 verify 를 다시 거친 뒤 머지한다.

마지막 PR 에서 스펙 전체의 요구사항 증거와 통합 동작을 확인한다.
부분 PR 의 PASS, MERGED 또는 보드 done 만으로 기능 전체 완료를 선언하지 않는다.
필요한 배포 후 검증이 남으면 기능 완료 보고에 미완료로 남긴다.

## 공통화 후속

후보는 PR 별 기록에서 읽는다. 공유 후보 목록에 worker 들이 동시에 쓰게 하지 않는다.
관련 기능 묶음을 마쳤거나 사용자가 정리를 요청하면 docs-consolidate 의 공통화 모드로 묶어 맡긴다.
제품 계약 변경이 필요하면 별도 spec 으로 돌린다. 공통화 PR 도 검토·문서 검증을 거쳐 기존 머지 절차를 따른다.

새 상태 머신이나 타이머를 추가하지 않는다. 스킬 인계로 한 기능을 끝내고 실제 사용에서 드러난 문제를 고친다.
