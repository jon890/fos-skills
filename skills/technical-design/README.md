# technical-design

확인한 기능 스펙을 기존 코드의 구조와 연결해요. 모듈 책임과 데이터 소유권을 먼저 정해 구현자가 경계를 임의로 만들지 않게 해요.

## 이럴 때 쓴다

- 스펙을 구현하기 전에 어느 모듈이 기능을 소유할지 정할 때
- 여러 서비스의 호출·상태 변경·실패 처리를 맞출 때
- 작은 기능이 기존 구조를 그대로 써도 되는지 확인할 때

## 사용 예시

사용자: “취소 스펙을 현재 작업 모듈과 스케줄러 구조에 맞게 기술 설계해 줘.”

스킬: 실제 코드를 읽고 상태 변경 주체와 취소·실행의 경쟁 처리를 정해요. 기존 계약과 대조하고 독립 검토를 받아요.

결과: 요구사항별 해결 방법과 검증 전략이 담긴 `design.md` 를 받아요. 작은 변경이면 스펙의 기술 설계 절에 짧게 남겨요.

장기 결정은 [ADR 작성 기준](references/adr-rules.md)으로 가리고 [세 종류의 샘플](references/adr-examples.md)처럼 이유와 현재 원본을 연결해요.

## 받는 것

기술 설계 경로, 주요 결정과 근거, 검사·독립 검토 결과를 받아요. 전체 시스템의 재설계나 PR 작업 분해는 포함하지 않아요.

## 함께 쓰는 스킬

`spec` 은 요구사항, `plan` 은 실행 작업, `implementation` 은 구현, `verify` 는 인수 검증을 맡아요.
