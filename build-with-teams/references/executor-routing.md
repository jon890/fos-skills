# 실행 형태와 등급

**`SKILL.md` 4단계에서 phase 마다 읽는다.**

## 목표

**phase 하나를 어느 엄격함으로 돌릴지 정한다.**

싼 경로는 작업이 명확하다는 것을 증명했을 때만 쓴다. 증명하지 못하면 더 엄격한 쪽을 고른다.
정하는 것은 둘이고 순서가 있다. 먼저 **실행 형태**(무엇을 증명했는가)를 판정하고,
그것을 하한으로 삼아 **실행 등급**(어느 모델로 돌리는가)을 고른다.

## 1. 실행 형태를 판정한다

| 실행 형태 | 의미 |
| --- | --- |
| `BOUNDED` | 실행 명세가 닫혀 있어 새로운 판단 없이 구현하고 검증할 수 있다 |
| `JUDGMENT_REQUIRED` | 일반적인 기술 판단이 필요하지만 설계나 데이터 위험은 높지 않다 |
| `HIGH_RISK` | 새 설계, 보안, 데이터, 호환성처럼 실패 비용이 큰 판단이 필요하다 |

**더 엄격한 판정이 항상 이긴다.**

- critic 판정과 team-lead 직접 점검이 다르면 더 엄격한 쪽을 고른다.
- 판정이 없거나 근거가 부족하면 `JUDGMENT_REQUIRED` 이상을 고른다.
- `execution_profile` 이 `deep` 이면 `HIGH_RISK` 다.

### `HIGH_RISK` 차단 조건

아래 중 하나라도 실제 변경 범위에 들어가면 `HIGH_RISK` 다.

- 새 아키텍처, 도메인 모델, 공용 추상화 설계
- 공개 API, 외부 이벤트, 저장 형식, 하위 호환성 변경
- 데이터 스키마, 마이그레이션, 영구 데이터 변환
- 인증, 권한, 비밀값, 보안 경계 변경
- 동시성, 트랜잭션, 분산 처리, 장애 복구 정책 변경
- 데이터 손실, 중단, 비용 과다 발생 가능성이 있는 작업
- 원인이 확정되지 않은 복합 장애나 성능 퇴행
- 여러 서비스, 저장소, 배포 경계를 넘는 변경

여러 구현안 중 하나를 골라야 하지만 위에 해당하지 않으면 `JUDGMENT_REQUIRED` 다.

### `BOUNDED` 자격

아래를 모두 만족해야 `BOUNDED` 다. 하나라도 확인할 수 없으면 `JUDGMENT_REQUIRED` 로 올린다.

- critic 이 전체 계획을 `APPROVE` 했다.
- 변경할 파일과 모듈, 완료 조건이 특정됐다.
- 기존 설계와 유틸리티와 코드 형태를 따라 구현할 수 있다.
- executor 가 제품, 설계, 공개 인터페이스 결정을 새로 내릴 필요가 없다.
- 잘못 구현해도 국소적으로 되돌릴 수 있다.
- 검증이 요청 동작과 주요 회귀를 실제로 감지한다.
- 위 `HIGH_RISK` 차단 조건에 해당하지 않는다.

### 판정에 쓰는 것

1. critic 이 코드와 문서와 phase 를 읽고 phase 별 실행 형태와 근거를 회신한다.
2. team-lead 가 phase 의 검증 명령과 `execution_profile` 을 직접 확인한다.
3. 오버레이의 반복 함정, 고위험 경로, 금지 패턴과 대조한다.

실행 형태는 `index.json` 에 저장하지 않는다. critic 회신과 phase 실행 보고에만 기록한다.

## 2. 실행 등급을 고른다

**출발값을 하나 고르고, 그 값을 하한으로 끌어올린다.** 둘은 성격이 달라 섞지 않는다.

**출발값**은 위에서부터 하나만 적용한다. 위가 있으면 아래를 보지 않는다.

1. phase 의 `execution_profile`
2. 옛 phase 의 `model` 값
3. 아래 규모별 기본 등급

**하한**은 1단계가 판정한 실행 형태의 최소 등급이다. 출발값이 이보다 낮으면 끌어올린다.

| 실행 형태 | 최소 등급 |
| --- | --- |
| `BOUNDED` | `fast` |
| `JUDGMENT_REQUIRED` | `standard` |
| `HIGH_RISK` | `deep` |

사용자가 특정 모델을 요청해도 이 하한 아래로는 내리지 않는다.

### 규모별 기본 등급

| 규모 | 무엇이 그런가 | team-lead | critic | executor | code-reviewer | docs-verifier |
|---|---|:---:|:---:|:---:|:---:|:---:|
| **소** | 버그 수정, 미세 조정 | standard | standard | standard | standard | standard |
| **중** | 기능 확장, 리팩토링 | standard | deep | standard | standard | standard |
| **대** | 새 아키텍처, 신규 도메인, 스키마 대규모 변경 | deep | deep | standard | standard | deep |

규모는 phase 개수가 아니라 **무엇을 바꾸는가**로 가른다.
phase 가 하나여도 스키마를 바꾸면 「대」 이고, 여러 개여도 같은 패턴 반복이면 「중」 이다.

**이 표는 기본값이지 하한이 아니다.** phase 가 `execution_profile` 로 등급을 지정했으면 그 값을 쓴다.
하한으로 읽으면 executor 가 전 규모 `standard` 라 `BOUNDED` 가 증명해 낸 `fast` 경로가 열리지 않는다.

세 등급의 의미는 `planning` 스킬의 `references/task-create.md` 「실행 등급 라우팅」 이 소유한다.
`model` 을 쓰는 옛 task 도 같은 세 값을 쓴다.

### 등급을 실제 모델로 옮기기

- team-lead 가 세 등급을 그 환경에 설치된 모델과 role 에 대응시킨다.
  정확히 맞는 것이 없으면 **더 엄격한 쪽으로만** 올려 잡는다. 아래로 내리는 폴백은 없다.
  실제 선택과 올려 잡은 사유를 실행 보고에 남긴다.
- **등급은 스폰 시점에 항상 명시 지정한다.** 생략했을 때 무엇이 적용되는지는 환경 설정이 정한다.
  스폰 도구의 계약은 「모델 인자를 생략하면 에이전트 정의의 모델을 쓰고, 그것도 없으면
  기본값을 쓴다. 그 기본값은 팀원 기본 모델이 설정되어 있으면 그 값이고, 없으면 team-lead 를 상속한다」 다.
  어느 쪽이 적용될지는 문서를 읽어서 알 수 없으므로 매번 명시한다.
- 모델과 effort 는 다른 축이다. 모델을 지정했다고 effort 까지 정해지지 않는다.
- 공용 스킬과 task 에는 실제 모델 id 를 적지 않는다. 세 등급으로만 적는다.

## 실행 중 승격

`BOUNDED` 로 시작한 executor 는 아래 상황에서 수정을 더 넓히지 않고 중단 보고한다.

- plan 범위 밖 파일이나 동작을 변경해야 한다.
- 요구사항이나 구현 방법을 두 가지 이상으로 해석할 수 있다.
- 새 추상화, 인터페이스, 데이터 형식 결정이 필요하다.
- 검증 실패 원인이 plan 과 다르거나 범위 밖에 있다.
- 수정한 뒤에도 같은 핵심 실패가 재현된다.
- `HIGH_RISK` 차단 조건을 새로 발견했다.

회신 형식이다.

```text
EXECUTOR_ESCALATE: <사유>
완료한 변경: <없음 | 범위>
미완료 조건: <남은 결정·검증>
권장 실행 형태: JUDGMENT_REQUIRED | HIGH_RISK
```

team-lead 는 승격 사유가 plan 을 바꾸면 critic 재평가로 돌아간다.
단순 실행 누락이면 같은 등급으로 한 번 재투입할 수 있다.
새로운 판단이 필요하면 더 엄격한 실행 형태로 승격한다.
검토가 설계나 명세 결함을 발견하면 재투입을 되풀이하지 않고 실행 형태를 승격한다.

## phase 실행 보고에 남길 것

- `execution_profile`
- 최종 실행 형태와 근거
- 실제로 쓴 role 과 모델, 올려 잡았으면 그 사유
- 승격 여부와 사유
