## 2.3.0

표의 열을 셀 때 이스케이프된 파이프를 구분자로 세던 오탐을 고쳤다.

`\|` 는 셀 안의 문자다. 그것을 세면 한 셀이 둘로 세어져 열 수가 실제보다 많아진다.
실측으로 두 자리가 걸렸다. 코드 스팬 안에 `\|` 를 적은 ADR 한 줄과
`` `[Ship\|Show\|Ask]` `` 를 적은 하네스 지침 한 줄이며, 둘 다 렌더링은 정상이었다.
열을 세기 전에 역슬래시 이스케이프를 지워 둘 다 통과한다.

**코드 스팬은 지우지 않는다.** GFM 은 인라인을 해석하기 전에 파이프로 셀을 가르므로
백틱 안의 맨 파이프도 구분자로 동작한다. 코드 스팬 전체를 지우면 그 어긋남을 놓친다.
그래서 이스케이프만 지운다.

세 자리를 `tests/` 에 표본으로 남겼다. 실측 오탐 둘, 백틱 안의 맨 파이프,
역슬래시 다음의 진짜 구분자다. 뒤의 둘은 지우는 범위가 넓어질 때 실패한다.

2단계에 오탐 처리 원칙을 넣었다.
걸린 자리가 오탐이면 통과 조건을 느슨하게 만들지 않고 그 자리에서 검사기를 고친다.
조건을 느슨하게 하면 진짜 위반도 함께 통과하고, 오탐은 남아 다음 감사에서 또 막는다.
오탐으로 판정하려면 렌더링 규격이 검사기와 다르다는 근거가 있어야 한다.

## 2.2.0

계획서를 번호로 가리킨 자리를 검사한다.

계획서는 구현이 끝나면 제거되므로, 문서가 번호로 가리킨 자리는 그때 깨진 참조가 된다.
`static_check.py` 가 `PLAN_REF` 로 위치를 뽑고, `references/six-axis.md` 가 유형과 예외를 정한다.

기본은 아무것도 적지 않는 것이다. 무엇이 언제 왜 바뀌었는지는 git 이력이 이미 추적한다.
결정의 근거가 필요하면 ADR 번호를, 변경의 이력이 필요하면 PR 번호를 적는다.
커밋 SHA 는 rebase 와 squash 로 값이 바뀌어 쓰지 않는다.

**계획서 번호를 시간 축으로 쓰지 않는다.** 번호가 계획서와 함께 사라져 판정이 불가능해진다.
날짜처럼 계획서 수명과 무관한 값을 쓴다.

예외 둘을 둔다. 기존 파일과 식별자의 이름, 측정 기록에 남은 실행 경로다.
앞쪽은 바꾸면 그 이름을 부르는 쪽도 함께 고쳐야 하고, 뒤쪽은 고치면 기록이 틀린 값이 된다.

완료 기준을 그 저장소가 정하게 했다. 기본값은 운영에 반영된 시점이다.
머지만 된 계획서는 아직 운영에 나가지 않아, 되돌릴 때 읽을 것이 남아 있어야 한다.

## 2.1.0

완료된 plan 을 제거 후보로 판정한다.

`tasks/` 의 계획서는 구현이 끝나면 역할이 끝난다.
남겨야 하는 것은 계획서가 아니라 그 계획이 내린 결정이고, 그 자리는 `docs/` 와 ADR 이다.

**무조건 제거로 판정하지 않는다.**
그 plan 의 결정이 `docs/` 나 ADR 에 남아 있는지 먼저 확인하고, 남아 있을 때만 후보로 올린다.
규율이 갖춰지지 않은 저장소에서는 계획서가 그 결정의 유일한 기록일 수 있다.

조사를 나눠 맡기고 메인은 셋만 한다.
무엇을 맡길지 나누는 것, 돌아온 보고를 종합하는 것, 승인을 받아 고치는 것이다.

**조사는 읽기만 시킨다.** 고칠 권한을 함께 주면 승인 절차를 거치지 않은 수정이 들어온다.
축이 여럿이면 축마다 하나씩 맡겨 한 번에 띄운다.
회신 형식을 리포트의 발견 하나와 같게 시켜, 모으면 그대로 리포트가 되게 했다.

조사자와 검토자는 다른 자리다. 한 사람에게 둘 다 맡기면 자기 발견을 자기가 확인하게 된다.

## 2.0.0

**목표: 문서가 현재 코드와 결정을 복원할 수 있는지 감사하고, 사용자가 승인한 것만 고친다.**

- 발견마다 그것을 증명한 코드나 명령이 있어야 한다.
- 사용자 승인 전에는 문서를 고치지 않는다.

실행은 6단계다. 단계마다 통과 조건과 읽을 문서가 정해져 있다.

| 단계 | 통과 조건 |
| --- | --- |
| 범위 판정 | 감사할 파일 목록과 ADR 디렉터리 경로가 정해졌다 |
| 정적 검사 | `static_check.py` 종료 코드 0, 검사한 Markdown 수가 1 이상 |
| 의미 검사 | 여섯 축을 대상 파일에 적용했고 발견마다 증명 근거가 있다 |
| 독립 검토 | 읽기 전용 검토자가 판정을 확인했다. 띄울 수 없으면 그 사실이 리포트에 있다 |
| 리포트와 승인 | 리포트가 나갔고 사용자가 고칠 항목을 정했다 |
| 수정과 재검증 | 승인 항목만 고쳤고 정적 검사와 코드 대조를 다시 통과했다 |

「범위 판정」 단계가 각 문서의 역할을 함께 정한다.
담을 것을 모르면 어느 문서가 소유해야 할 내용인지 가릴 수 없어
부패, 과대화, 중복을 판정하지 못한다. `planning` 이 관리하는 문서 다섯을 기본값으로 둔다.

여섯 축의 판정 기준은 `references/six-axis.md` 가 소유한다.
`status: superseded` 인 ADR 에 부패 축과 자명성 축을 적용하지 않는다.
`planning` 이 「ADR 은 지우지 않는다」 로 정하는데 세 축에 예외가 없어,
이력으로 남긴 ADR 이 부패와 폐기 후보로 잡히고 있었다.

정적 검사를 `scripts/static_check.py` 로 옮겼다.
awk 상태 머신 셋과 셸 함정 대응 주석 둘이 사라지고, 검출력 검사 21개가 붙었다.

옮기면서 결함 둘을 고쳤다.

- `git ls-files` 가 비ASCII 경로를 이스케이프해 내는데 그 문자열로 파일 존재를 확인하고 있었다.
  한글 이름 문서가 통째로 검사되지 않았고 검사 파일 수에도 잡히지 않았다. `-z` 로 받는다.
- 깨진 링크 검사가 `#` 로 시작하는 대상을 보지 않았다.
  목차가 헤딩과 어긋난 채 통과한 실측이 이 저장소 안에 있었다.
