# Task 생성 가이드

레포별 검증 명령과 레이어 구조는 레포 설정이 채운다. 찾는 순서는 `SKILL.md` 의 「레포 설정을 먼저 읽는다」 가 정한다.

반복 함정 목록은 레포 설정이 지정하면 그것을 따르고, **지정이 없으면 `docs/pitfalls/` 를 읽는다.**
그 디렉터리도 없으면 사전 확인 항목을 건너뛴다.
이 스킬은 그 목록에 새로 쓰지 않는다. 목록의 항목은 저장소 규칙으로 옮길 후보이고, 옮기는 일은 `build-with-teams` 의 마감 단계가 맡는다. 넣을 곳은 [`rule-placement.md`](rule-placement.md) 가 정한다.

## index.json 스키마

```jsonc
{
  "name": "plan{N}-{kebab-slug}",       // 디렉터리명과 일치. 접두사가 있으면 "fe-plan{N}-{kebab-slug}"
  "description": "한 줄 요약 — 무엇을 / 왜",
  "pr_scope": "이 plan 의 PR 이 끝내는 것 한 문장",
  "deferred": [                           // 뒤로 미룬 일. 없으면 빈 배열
    { "what": "무엇을", "why": "왜 이 plan 에 넣지 않나", "after": "앞 plan 의 무엇이 머지된 뒤" }
  ],
  "status": "pending",                    // 새 계획은 pending. 뒤의 값(completed, cancelled, failed)은 build-with-teams 가 정한다
  "created_at": "2026-01-01",             // YYYY-MM-DD
  "total_phases": 3,                      // phases 배열 길이와 일치
  "current_phase": 1,
  "phases": [
    {
      "number": 1,
      "file": "phase-01.md",
      "execution_profile": "standard"     // fast | standard | deep
    }
  ]
}
```

`pr_scope` 와 `deferred` 는 [`plan-size.md`](plan-size.md) 가 소유한다. 2026-10-25 이후에 만든 plan 은 둘이 없으면 `verify_task.py` 가 위반으로 센다.

## ADR(Architecture Decision Records) 구조 템플릿

파일명은 `docs/adr/NNN-<슬러그>.md` 다. 한 파일에 결정 하나만 담는다.

```markdown
## ADR-XXX: {제목. 결정의 한 줄 요약}

- **status**: `accepted`
- **결정**: {무엇을. 1~3문장}
- **맥락**: {왜 이 결정이 필요했는가. 제약·데이터·관찰}
- (조건부) **대체된 부분**: {이 ADR 의 어느 결정이 어느 ADR 에 뒤집혔는가. 링크 포함}
- **대안 기각**: {다른 옵션을 왜 선택하지 않았는가. 각 대안 1~2줄}
- **결과**: {이 결정 뒤로 무엇이 달라지는가}
  - 얻는 것: {가능해진 것}
  - 감당할 것: {비용·제약·앞으로 지켜야 할 것}
- (선택) **적용 범위**
```

`status` 는 둘뿐이다.

| 값            | 뜻                              |
| ------------ | ------------------------------ |
| `accepted`   | 현재 유효하다                        |
| `superseded` | 다른 ADR 이 이 결정을 뒤엎었다. 이력으로만 읽는다 |

`status` 가 없는 기존 ADR 은 `accepted` 로 읽는다.

**결과** 는 결정한 뒤에 생기는 트레이드오프를 적는다. 얻는 것과 감당할 것을 둘 다 적는다.

**ADR 은 지우지 않는다.**
결정 전체가 번복돼도 `status` 를 `superseded` 로 바꾸고 `대체된 부분` 에 대체한 ADR 을 가리킨다.
지우면 그때 그 판단을 왜 했는지가 사라진다.

- `superseded` 로 바꾼 파일은 `docs/adr/superseded/` 로 옮긴다. 파일 이름과 번호 또는 날짜 식별자는 바꾸지 않는다.
  현행 결정과 대체된 결정을 폴더만 보고 구분하려는 사용자 결정(2026-10-24)이다.
- 같은 변경에서 그 파일을 가리키는 상대 링크를 모두 고친다. 다른 ADR, docs, 코드 주석, README 와 옮긴 ADR 안의 상대 링크도 확인한다.
- 색인 파일(`INDEX.md` 등 저장소가 쓰는 것)은 「현행」 과 「대체됨」 으로 나눠 적는다.
- 일부만 대체돼 `accepted` 이면서 `대체된 부분` 이 있는 ADR 은 옮기지 않는다.
- `대체된 부분` 은 **결정 바로 아래**에 둔다. 결정만 읽고 지나가는 독자가 낡은 결론을 얻는 것을
막는 것이 목적이라, 문서 끝이나 대안 기각 안에 넣으면 의미가 없다.
- 대체한 쪽 ADR 에서도 원본을 링크해 양방향으로 찾을 수 있게 한다.
- 전체가 대체된 ADR 은 남은 본문 앞에 그것이 당시의 맥락임을 한 줄로 밝힌다.
- 코드와 경로는 결정을 가리키는 데 필요한 만큼만 인용한다. 구현 호출 방법, 작업 내역,
스택 규칙 반복은 넣지 않는다. 결정과 근거만 남긴다.
- **계획서를 번호로 가리키지 않는다.** ADR 은 계획서보다 오래 남는다.
  근거는 다른 ADR 번호나 PR 번호로 적고, 그것으로 부족하면 내용을 본문에 옮긴다.

## phase 파일 작성 규칙

**phase 하나는 테스트까지 통과한 커밋 하나로 끝낸다.**
코드를 바꾸는 phase 안에서 그 동작의 테스트를 만들거나 고치고 「검증」 절에서 실행한다.
테스트를 다음 phase 로 미루지 않는다. 작업 항목의 순서는 구현과 검증 의존에 맞게 정한다.
**한 phase 는 한 사람이 한 번에 붙잡고 끝낼 수 있는 크기로 둔다.**

**「검증」 절에는 작업 공간에서 커밋 전에 끝나는 검증만 둔다.**
push, 배포, 원격 호스트 접속이 있어야 끝나는 검증은 phase 에 두지 않는다.
그 검증을 끝내려면 먼저 커밋하고 push 해야 해서, 실패를 고친 커밋이 phase 밖에 생긴다.
원격 검증만 담은 phase 도 만들지 않는다. 그 phase 에는 커밋할 대상이 없다.
원격 검증은 아래 「원격 검증 목록」 에 모은다.

**느린 e2e 테스트는 phase 「검증」 절에 넣지 않는다.** 마지막 phase 의 검증 절이나 `build-with-teams` 6단계 통합 검증에서 한 번 돈다.
무엇이 느린 e2e 인지는 저장소 오버레이가 정한다. 오버레이가 없으면 브라우저나 외부 서비스가 필요한 테스트로 본다.
그 phase 의 검증 절에는 e2e 가 아닌 같은 phase 의 테스트 실행 명령을 그대로 둔다.

### phase 파일 구조

```markdown
# Phase NN. {제목}

**Execution profile**: standard

## 목표

무엇을 만드는가. 왜 필요한지 한 문장.

**범위 외**: 다른 phase 나 다른 plan 의 책임.

## 컨텍스트

이 대화를 보지 못한 구현자가 알아야 할 것.
기존 코드의 어느 패턴을 따르는지 경로로 짚는다.

**근거 문서**: `docs/flow.md` 의 「...」 절, `docs/adr/012-....md`
근거는 `docs/` 와 ADR 로만 적는다. 다른 계획서를 가리키면 그것이 제거된 뒤 읽을 수 없다.

## 의도 메모

- 기각한 옵션과 그 이유
- 앞으로 주의할 것

## Blocked 조건 (선택)

- 외부 의존성 부재 → `PHASE_BLOCKED: {이유}` 출력 후 종료

## 작업 항목

### 1. {파일} 의 변경 요약

구체적 변경. 함수 시그니처, 타입, 셀렉터, 이름. 기존 패턴 참조 경로.

### 2. 이 phase 를 검증하는 {테스트 파일}

무엇을 어떤 입력으로 확인하는지. 정상 경로 하나와 이 phase 가 다루는 실패 하나.

## 검증

실행할 명령과 기대값. 레포의 lint, type, test, build 명령과 구체 grep 기준을 적는다.
위에서 만든 테스트를 실행하는 명령을 함께 적는다.
**명령은 bash 코드 블록에 적는다.** `verify_task.py` 는 셸 코드 블록만 명령으로 읽는다. 목록이나 인라인 코드로 적은 명령은 없는 것으로 센다.

```bash
python3 -m unittest discover -s tests
```

검증 절의 각 줄은 저장소 루트에서 실행한다. 디렉터리가 필요하면 그 줄을 `cd <dir> && ...` 로 시작한다. 한 줄 안의 `&&` 체인은 같은 셸에서 실행한다.
커밋 전에 작업 공간에서 끝나는 명령만 적는다. push, 배포, ssh 가 필요한 검증은 원격 검증 목록으로 보낸다.

## 변경 파일

이 phase 의 커밋에 담을 파일을 저장소 root 기준 경로로 적는다. 모노레포면 `frontend/src/app.ts` 처럼 하위 프로젝트 디렉터리부터 적는다.

| 파일 | 변경 |
|---|---|
| `src/application.py` | 신규 |
| `tests/test_application.py` | 신규 |
```

### 변경 파일 작성

작업 항목의 변경 경로를 이 목록에 모은다. `build-with-teams` 는 커밋 전에 staged 파일과 대조한다.
목록에 없는 변경이 생기면 계획에 빠진 파일인지 무관한 변경인지 먼저 판정한다.
근거 문서 갱신도 목록에 포함한다.
phase 는 `tasks/` 를 바꾸지 않는다. 구현이 끝난 계획서는 `build-with-teams` 의 마감 단계가 지운다.

- 파일 경로를 `.../` 로 생략하지 않는다. 커밋 전 대조가 생략 경로를 실제 파일과 맞추지 못한다.
- `수정`과 `삭제`의 glob 은 일치하는 파일이 하나 이상 있어야 한다.
  `*`는 한 경로 조각, `**`는 하위 디렉터리까지 뜻한다.
- 신규 파일은 개별 경로를 적는다. 신규 glob 은 구체 파일의 부재를 확인하지 못하므로 경고한다.
- 신규로 적은 개별 파일이 커밋 전 staged 파일에 없으면 위반이다. 수정·삭제로 적은 파일이 없으면 경고한다.
- 앞 phase 가 만든 파일은 뒤 phase 에서 수정하거나 삭제할 수 있다. 앞 phase 의 신규 glob 에 맞는 경로도 같다.
  앞 phase 가 삭제한 파일을 뒤 phase 에서 수정할 수는 없다.
- 아직 머지되지 않은 다른 계획이 만들 파일을 고쳐야 하면 생성 검사가 위반으로 센다.
  그 계획이 머지된 뒤 기준 브랜치로 rebase 해 다시 돌리면 위반이 사라진다.

### 원격 검증 목록

push, 배포, 원격 호스트 접속이 있어야 끝나는 검증은 plan 디렉터리의 `remote-verification.md` 에 모은다.
`index.json` 의 `phases` 에 넣지 않는다. 원격 검증이 없으면 이 파일을 만들지 않는다.
`build-with-teams` 는 통합 검증 뒤 이 목록을 PR 본문의 확인 목록으로 옮기고, 계획서와 함께 지운다.

```markdown
# 원격 검증

| 선행 조건 | 시점 | 실행 위치 | 명령 | 기대값 |
|---|---|---|---|---|
| 없음 | PR 전 | dev 서버, 읽기 전용 | `ssh dev 'scripts/measure.sh --dry-run'` | 전체 배치 비용이 기준 이하 |
| push | PR 뒤 | 홈서버 임시 worktree | `scripts/verify.sh live` | 종료 코드 0 |
```

- **선행 조건**은 그 명령이 돌기 전에 끝나야 하는 것이다. `없음`, `push`, `머지`, `배포` 가운데 하나로 시작한다.
  원격 데이터를 읽기만 하는 추출과 측정은 이번 코드가 원격에 있을 필요가 없어 `없음` 이다.
- **시점**은 `PR 전` 또는 `PR 뒤` 다. `PR 전` 은 PR 을 열기 전에 결과가 있어야 하는 검증이다.
  `build-with-teams` 가 통합 검증 뒤, PR 을 만들기 전에 돌린다.
- `PR 전` 에는 원격 상태를 바꾸지 않는 읽기 전용 명령만 둔다. 상태를 바꾸는 검증은 사람이 시점을 고르게 `PR 뒤` 로 둔다.
  선행 조건이 `머지` 나 `배포` 면 `PR 전` 일 수 없다. 검사기가 위반으로 센다.
- 시점 열이 없는 옛 표는 모두 `PR 뒤` 로 읽고 경고만 한다.

### 검사기와 작성자가 확인할 범위

검사기가 잡는 것과 경고 문구는 `verify_task.py` 가 소유한다. 걸리면 출력이 고칠 방법을 알려준다.
아래는 작성할 때 먼저 지키면 재작성이 줄어드는 규칙이다.

- 검증 절에는 같은 phase 의 테스트를 실행하는 명령을 적는다. lint 나 grep 만으로는 통과하지 않는다.
- 테스트 파일을 직접 지정하는 명령은 작업 항목에 선언한 테스트를 포함한다.
- 테스트 출력을 `tee` 로 넘기면 `set -o pipefail` 을 함께 적는다.
- 보조 파일(fixture, helper, `conftest.py`)만 바꾸는 phase 도 그 파일을 쓰는 테스트를 실행하는 명령을 적는다.
- 저장소의 `scripts/check-*`, `scripts/verify.*`, `scripts/test-*` 를 검증에 쓰면
  그 파일을 직접 열어 테스트 범위와 실패 종료 코드를 확인한다.
- 설정이나 배포 구성만 바꾸는 phase 도 실행 가능한 검증 스크립트나 저장소 테스트 명령을 적는다.

검사기는 명령을 실행하거나 테스트가 목표 동작을 확인하는지 판단하지 않는다.
작성자는 다음을 직접 확인하고 필요한 내용을 작업 항목과 검증 절에 적는다.

| 확인할 것 | 남길 근거 |
| --- | --- |
| 테스트가 바꾼 동작을 확인한다 | 정상 입력과 이 phase 가 다루는 실패 입력, 기대 결과 |
| 저장소 전체 명령이 위 테스트를 실행한다 | 테스트 검색 경로, 모듈 범위, 제외 설정 |
| 스크립트가 실패를 숨기지 않는다 | 단언 방법과 실패 종료 코드 |
| 기존 식별자, 경로와 스키마가 docs와 코드에 맞는다 | 실제 정의를 읽고 일치시킨 이름과 타입 |
| 스키마, table, 설정의 개수를 상수로 단언하는 기존 테스트가 이 phase 의 변경에 깨지지 않는다 | 그 테스트를 변경 파일 표에 넣고 고칠 값을 작업 항목에 적는다. 레포의 테스트 프레임워크에서 개수를 단언하는 형태를 찾는다 |
| 테스트 명령에 필요한 환경값을 모두 적었다 | phase 마다 환경값 전체를 적는다. 앞 phase 를 가리키지 않는다. 구현자는 그 phase 만 읽는다 |
| 새로 만드는 키, 경로, 식별자가 기존 값과 겹치지 않는다 | 같은 종류의 기존 값을 `git grep` 으로 찾은 결과. 멱등 키나 설정 키가 다른 명령의 키와 같아지면 서로 덮어쓴다 |
| 시그니처를 바꾸는 phase 가 하위 클래스와 호출부를 모두 변경 파일에 넣었다 | `git grep -n "extends <클래스>\|new <클래스>("` 로 찾은 파일. 생성자 인자를 더하면 상속한 하위 클래스도 컴파일이 깨진다. 작업 항목에 바꾸는 함수를 `save()` 처럼 호출 형태로 적으면 검사기가 변경 파일에 없는 호출 파일을 경고로 낸다 |
| 여러 phase 에 걸친 이전이 각 phase 커밋에서 모든 호출부의 동작을 이전과 같게 둔다 | 기존 메서드를 새 메서드에 위임한다고 적기 전에 호출부를 `git grep` 으로 세고 반환 형식 차이를 확인한다. 중간 커밋에서 호출부 동작이 바뀌면 구현자가 멈춘다 |

`Critical Files`라는 기존 절 이름은 읽기 호환으로 받는다. 새 계획은 「변경 파일」을 쓴다.
검사기의 구현 후 문서 검사와 커밋 전 대조 인자는 `verify_task.py --help`가 설명한다.
