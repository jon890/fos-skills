- 대상 저장소는 {{REPO}} 다. 지정된 워크트리에서만 작업한다. 워크트리는 지시서의 `브랜치:` 이름으로 `origin/{{BASE}}` 최신 위에 만들어져 있다.
- 브랜치 이름을 바꾸지 않는다. push 는 `git push -u origin HEAD` 로 한다.
- 먼저 {{READ_FIRST}} 를 읽는다.
- 커밋은 관심사별로 나눈다. 제목 형식은 {{COMMIT_FORMAT}} 이다. 코드를 고친 뒤 `{{FORMAT_CMD}}` 를 돌린다.
- 커밋 메시지 끝에는 세션이 받은 attribution 지침(`Co-Authored-By` 줄)을 그대로 붙인다. 모델 이름은 이 파일에 적지 않는다. 지침이 없으면 그 줄을 붙이지 않는다.
- 구현이 docs 계약과 달라지면 같은 커밋에서 그 문서를 고친다. 고치기 전에 ask 로 알린다.
- 끝까지 진행하고 판단이 필요한 것만 ask 로 묻는다. 검증 명령(`{{VERIFY_CMD}}`)을 실제로 실행한다.
- 파일 수정은 `sed -i` 대신 Edit 나 python 으로 한다.
- 의존성이 필요하면 워크트리 안에서 lockfile 로 설치한다. 원래 저장소의 의존성 폴더를 링크로 걸지 않는다.
- **PR 생성은 지시서의 `허락:` 줄이 허락한 경우에만 한다. 허락이 없으면 push 까지만 하고 status 로 알린다.** base 는 {{BASE}} 다. 다른 PR 브랜치를 base 로 두지 않는다. 제목과 본문은 {{PR_FORMAT}} 을 따른다. 지시서가 정한 PR 만 연다.
- {{DRAFT_PR_RULE}}
- PR 을 연 뒤 리뷰가 달리면 `review-fix` 스킬로 반영한다. 리뷰 회신과 resolve 는 허용한다. 반영하지 않을 지적이 있으면 회신 전에 ask 로 묻는다.
- 머지는 하지 않는다. 코디네이터가 한다(워크트리 권한 설정이 `gh pr merge` 를 막는다). **그러나 PR 이 머지될 때까지 이 worker 가 맡는다.** 준비됨을 보낸 뒤에도 CI 실패, 충돌, 기준 브랜치 변경, 리뷰를 코디네이터의 지시를 기다리지 않고 직접 처리한다. 고쳐 push 하면 바뀐 head 로 `준비됨` 을 다시 보낸다.
- 하위 에이전트는 orca 명령을 쓰지 않는다. 스폰 프롬프트에 이 줄을 넣는다.
- 진행 보드(`board.json`)를 고치지 않는다. `board.ts step`, `mark`, `set` 을 부르지 않는다. 보드 단계는 스크립트가 PR, 머지, 배포로 끝내고 나머지는 코디네이터가 고친다. worker 가 단계를 체크하면 PR 전인데 끝난 것으로 보인다.
- 삭제처럼 되돌리기 어려운 쓰기는 하위 에이전트에 맡기지 않고 본체가 한다.
- `worker_done` 은 본체가 한 번만 보낸다. PR 을 여는 일은 그 PR 이 MERGED 가 된 것을 `gh pr view` 로 확인한 뒤 보낸다. PR 번호와 머지 커밋을 적는다. PR 이 없는 일(허락이 push 까지인 일)은 완료 기준을 채운 뒤 보낸다. 중간 진행(PR 생성, 준비됨)은 status 메시지로 보낸다.
- 권한 확인 창이나 거부로 막히면 우회하지 말고 ask 로 알린다. 터미널에만 적고 기다리지 않는다.
- 비밀값이 든 파일을 읽지 않고 비밀값을 출력하지 않는다. 공유 DB 에 마이그레이션을 적용하지 않는다.
- {{REMOTE_ACCESS_RULE}}
- 다른 worker 가 동시에 다른 일을 한다. 지시서 범위 밖의 파일은 고치지 않는다.
- 프로세스는 자기가 띄운 PID 로만 끈다. `pkill`, `killall` 은 다른 worker 의 호스트까지 꺼 쓰지 않는다(워크트리 권한 설정이 막는다). 스폰 프롬프트에 이 줄을 넣는다.
- 브라우저는 `BROWSER_EGO_SPACE` 를 자기 워크트리 이름(`basename "$(git rev-parse --show-toplevel)"`)으로 주고 연다. 다른 worker 와 같은 공간을 쓰면 탭이 섞이고 공간 한도가 찬다. 끝나면 실패해도 같은 이름으로 `browser-driver reset` 을 불러 탭과 공간을 함께 닫는다. 사용자 탭이 남아 공간이 닫히지 않으면 reset 이 그 사실을 알린다. `BROWSER_EGO_SPACE` 없이 부른 reset 은 기본 공간을 비우므로 browser-driver 가 거절한다.

## 판단이 필요할 때

- **기술 판단은 묻지 않고 권장안으로 진행한다.** 파일 위치, 테스트 방식, 마이그레이션 방식, 리뷰 하위 등급 지적의 반영 여부와 이유, 지시서 범위 안의 리팩터링 방식이 여기 해당한다. 고른 안과 이유를 status 메시지 한 줄과 PR 본문 「결정」 절에 남긴다.
- **아래만 ask 로 묻는다.** 화면이나 외부 API 계약 변경, 기록된 팀 결정을 뒤집는 것, 외부에 보이는 글, 공유 서버나 DB 에 쓰기, 비용이 드는 작업, 지시서 범위를 넘는 변경, 데이터 삭제.
- **ask 는 설치된 스킬의 `worker-ask` 로 보낸다.** 경로는 이 세션의 `CLAUDE_CONFIG_DIR`(없으면 `~/.claude`)에 설치된 `fos-skills@fos-skills` 에서 푼다. 코디네이터와 worker 의 프로필이 다를 수 있고 번들은 갱신되므로 경로를 지시서에 박지 않는다. Bash 호출마다 셸이 새로 뜨니 같은 호출 안에서 푼다.

  ```bash
  FROM=""
  QUESTION=""
  ORCH_SCRIPTS=$(node -e 'const fs=require("fs"),os=require("os");const d=process.env.CLAUDE_CONFIG_DIR||os.homedir()+"/.claude";const e=JSON.parse(fs.readFileSync(d+"/plugins/installed_plugins.json","utf8")).plugins["fos-skills@fos-skills"].sort((a,b)=>(a.scope!=="user")-(b.scope!=="user"))[0];console.log(e.installPath+"/orch/scripts")') && node --disable-warning=ExperimentalWarning "$ORCH_SCRIPTS/worker-ask.ts" --from "$FROM" --question "$QUESTION"
  ```

  위 블록은 `FROM` 과 `QUESTION` 을 채운 뒤 한 번에 붙여 넣는다. `FROM` 은 머리말의 `--from` 값이고 `QUESTION` 은 질문 문장이다. 값을 채우지 않고 돌리면 `worker-ask` 가 사용법 오류(종료 코드 2)로 끝난다. Claude 는 Bash 의 `run_in_background` 로 돌리고 완료 알림을 기다린다. 백그라운드 실행이 없으면 `--timeout-ms` 를 도구 시간 제한보다 짧게 준다. 답은 출력 첫 줄의 `answer: ` 뒤에 있다. 종료 코드 5 면 읽지 않은 코디네이터 메시지가 출력에 있으니 먼저 읽고, 그래도 물어야 하면 같은 명령을 다시 부른다(한 번 보여 준 메시지로는 다시 막지 않는다). 3 이면 첫 줄이 `answer: ` 일 때는 코디네이터가 status 로 보낸 답이고, 아니면 Run 메일함으로 대신 보낸 것이니 `orca orchestration check` 로 답을 읽는다. 4 면 출력의 메시지 ID 로 `--resume` 한다.
- **사용자가 정할 결정은 아래 형식으로 쓰고 `--decision` 을 붙인다.** 보드의 결정 필요 항목이 첫 줄을 제목으로, `권장:` 줄을 그 아래에 보인다. 형식이 어긋나면 `worker-ask` 가 묻지 않고 종료 코드 2 로 끝난다. 기술 질문과 막힘 보고는 형식 없이 묻는다.

  ```text
  결정: 무엇을 정하는지 한 줄
  배경: 왜 지금 정해야 하는지
  선택지:
  - 선택지 이름: 고르면 생기는 결과
  - 선택지 이름: 고르면 생기는 결과
  권장: 선택지 이름. 이유
  ```

- 기준 브랜치와 충돌하면 코디네이터가 후속 지시서를 보낸다. 그 지시대로 이 worker 가 푼다.

## 끝내기

1. 검증 명령을 돌려 통과를 확인한다.
2. 원격 브랜치를 pull 한 뒤 `git push -u origin HEAD` 로 push 한다.
3. PR 본문을 파일로 쓴다. 허락 줄이 PR 을 허락했으면 그 파일로 PR 을 연다. 본문 파일은 PR 이 열릴 때까지 지우지 않는다.
4. **게시가 막히면 묻지 않는다.** `gh pr create` 나 리뷰 회신이 거부되거나, 지금 실행의 지시가 GitHub 게시를 막는다고 판단되면 push 까지 하고 본문 파일(회신이면 스레드 id 와 회신 파일) 경로를 status 로 보낸다. 코디네이터가 그 파일로 연다.
5. PR 이 열리면 status 로 `준비됨 #<PR 번호>, head <40자리 SHA>` 한 줄을 보낸다. 4 로 넘겼으면 본문 파일 경로를 보내고 PR 이 열리면 이 줄을 보낸다. <!-- orch-rule: ready-status -->
6. **머지될 때까지 맡는다.** CI 실패, 충돌, 기준 브랜치 변경, 리뷰를 직접 처리하고 push 할 때마다 5 를 다시 보낸다. 코디네이터가 머지한다.
7. PR 이 MERGED 인 것을 확인한 뒤 `worker_done` 을 보낸다. PR 번호와 머지 커밋을 적는다. 머지 없이 닫혔으면 ask 로 알린다. <!-- orch-rule: done-after-merged -->

## 설계와 구현을 맡길 때

<!-- 지시서가 planning 이나 build-with-teams 를 쓰라고 하면 남긴다. 둘 다 쓰지 않으면 이 절을 지운다. -->

- `planning` 과 `build-with-teams` 는 사용자와 대화하는 세션을 전제로 한다. worker 는 사용자에게 묻지 못하므로 아래로 바꿔 읽는다.
- 사용자에게 확인하라는 단계는 위 「판단이 필요할 때」 의 기준으로 가른다. 기술 판단은 권장안으로 진행하고, ask 대상만 `worker-ask` 로 묻는다. `AskUserQuestion` 은 쓰지 않는다.
- 설계와 근거 문서는 `{{DESIGN_DIR}}` 에 둔다.
- plan 하나는 PR 하나다. 큰 일은 plan 을 나누고 계획서는 그 plan 을 구현한 PR 에서 지운다(`planning` 의 `plan-size.md` 가 소유).
- 세션 재시작, 계정 전환을 넘길 수 있는 일은 `planning` 으로 `tasks/` 를 만든다. 끊긴 뒤 다음 worker 가 계획과 phase 커밋으로 이어받는다.
- PR 하나로 끝나는 작은 일은 `tasks/` 를 만들지 않는다. 구현한 뒤 `build-with-teams` 의 「task 없이 리뷰부터 도는 경로」 로 이 지시서를 계획 입력으로 넘겨 리뷰와 PR 을 한다.
- 구현만 맡겼으면 `build-with-teams` 의 PR 단계는 위 공통 규칙(PR 생성은 허락 줄을 따름, 본문 파일, 머지하지 않음)을 따른다.
- 하위 에이전트는 `name` 없이 띄운다. 이름을 주면 팀원으로 등록되고 tmux pane 이 없는 worker 터미널에서 실패한다.
- 저장소에 `.claude/planning-overlay.md` 나 `.claude/build-with-teams-overlay.md` 가 있으면 경로는 그 파일을 따른다.
- 보고에서 phase 를 가리킬 때는 계획 이름을 붙인다(`plan12-login phase 3`). 계획이 둘 이상 돌면 phase 번호만으로는 어느 계획인지 알 수 없다.

## 스킬 개선 후보 보고

<!-- 스킬 개선 후보를 모으지 않으면 이 절을 지운다. -->

- 스킬과 이 지시서 체계를 쓰다가 아래를 만나면 그 자리에서 메모한다.
  - 지시대로 했는데 동작하지 않은 곳
  - 우회해야 했던 곳과 실제로 통한 방법
  - 스킬이 다루지 않아 물어야 했던 판단
  - 산문 대신 명령이나 스크립트로 바꿀 수 있는 곳
- 메모하기 전에 아래 세 가지를 모두 따져 하나라도 아니면 후보로 올리지 않는다.
  - 유의미한가: 고치면 다음 작업의 시간이나 실패가 실제로 줄어드는가. 한 번 겪고 끝날 일, 취향 차이는 올리지 않는다.
  - 단순 함정이 아닌가: 오타, 일시적인 네트워크나 권한 문제, 이 작업에만 있는 사정처럼 스킬을 고쳐도 재발을 못 막는 것은 올리지 않는다.
  - 구조로 막을 수 있는가: 스크립트, 검사기, 명령 한 줄, 문서 구조 변경처럼 다시 일어나지 않게 만드는 방법이 있어야 한다. 「주의한다」 같은 문장 추가로만 막을 수 있으면 올리지 않는다.
- 올릴 때는 세 항목에 대한 판단 근거를 한 줄씩 함께 적는다.
- 메모는 `{{FEEDBACK_DIR}}/<워크트리 이름>.md` 에 쌓는다(스킬 이름, 상황, 실제로 한 것, 개선 제안).
- `worker_done` 본문 끝에 「스킬 개선 후보 N건: <파일 경로>」 를 적는다. 없으면 「스킬 개선 후보 없음」.
- 스킬 파일은 직접 고치지 않는다. 코디네이터가 사용자와 정한 뒤 고친다.
