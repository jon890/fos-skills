# 마무리

「마무리」 단계에서 읽는다. resolve, 규칙 반영, 결과 보고를 이 순서로 한다.

## 리뷰 스레드 resolve

```bash
python3 scripts/review_threads.py list <owner> <repo> <N>
python3 scripts/review_threads.py resolve --repo <owner>/<repo> <THREAD_ID> ...
```

resolve 는 「이 지적을 처리했다」 는 표시다.
반영했거나 반영하지 않기로 판단하고 그 판단을 회신한 스레드만 resolve 한다.

**머지 전에 미해결 수가 0 인지 이 명령으로 확인한다.**

```bash
python3 scripts/review_threads.py list --count <owner> <repo> <N>
```

출력은 정수 하나다. 0 이 아니면 머지 가능으로 보고하지 않는다.
`list` 출력을 `grep` 으로 세지 않는다. 한 줄 JSON 에 여백이 없어 `"resolved": false` 패턴은 늘 0 이 나온다.

resolve 한 뒤 보호 규칙이 풀렸는지 본다.

```bash
gh pr view <N> --json mergeStateStatus
```

## 반복될 지적을 저장소 규칙으로 옮긴다

지적과 그 수정을 사건 기록으로 쌓지 않는다.
사건 목록은 다음 사람이 그 코드를 쓸 때 읽지 않아 같은 지적을 막지 못한다.
fix 가 끝났다고 항상 옮기지 않는다. **같은 실수가 다른 코드에서도 날 수 있는 지적**만 옮긴다.
1회성 오타, 특정 PR 맥락에서만 성립하는 지적, 칭찬과 단순 확인은 결과 보고에만 남긴다.

넣을 곳은 오버레이나 그 저장소 지침이 지정하면 그것을 따르고, 없으면 위에서부터 고른다.
모노레포면 지적이 달린 파일이 속한 하위 프로젝트의 것을 쓴다.

| 넣을 곳 | 고르는 때 |
| --- | --- |
| 검사 (lint 규칙, test, 검사 스크립트) | 자동 검사로 검출할 수 있다 |
| 코드 구조 (타입, 공용 helper, 모듈 경계) | 구조를 바꾸면 그 실수를 할 수 없게 된다 |
| 그 영역의 `docs/` 문서나 하네스 지침 파일의 규칙 문장과 이유 한 줄 | 위 둘로 막을 수 없다 |

**일반화할 곳이 없으면 넣지 않는다.** 결과 보고에만 남긴다.
규칙 문장에 PR 번호, 날짜, 지적 경위를 적지 않는다. 출처가 필요하면 커밋 메시지에 적는다.

**반복 함정 목록(`docs/pitfalls/` 나 오버레이가 지정한 경로)에는 새로 쓰지 않는다.**
저장소에 그 목록이 있으면 읽되, 각 항목은 위 표의 자리로 옮길 후보로 다룬다.
이번 지적에 걸린 항목을 옮겼으면 원래 항목을 지운다. 같은 규칙이 두 곳에 있으면 한쪽만 고쳐진다.

ADR 급 결정은 구조화 질문 도구가 있으면 그것으로 사용자에게 확인받는다.

규칙 커밋은 같은 fix PR 에 커밋 하나로 더한다. fix 커밋과 섞지 않는다. 한 번 호출하면 PR 하나다.

## 결과 보고

```
## 완료: PR #<N>

🔀 Conflict 해결 (<건수>)
  - <파일>: <결정 요약>
✅ 적용된 수정 (<건수>)
  - <파일>: <무엇을 수정했는지>
📋 이슈로 등록 (<건수>)
  - #<번호>: <범위가 커서 이슈로 추적>
💬 회신 완료 (<건수>, 스레드 <건수> / 인라인 <건수>)
🧵 스레드 resolve (<건수>)
⏭️ 건너뛴 항목 (<이유>)
📚 저장소 규칙 반영 (<건수>와 넣은 위치, 또는 「없음」)

커밋 (<건수>)
  - <해시> <메시지>
```

**커밋을 목록으로 낸다.** 지적별로 나뉘어 있어 하나가 아니다.
「커밋과 push」 단계가 만든 대응 표의 해시를 읽어 채운다.
규칙 커밋은 이 목록에 함께 적고, base 동기화 커밋은 fix 가 아니므로 「Conflict 해결」 절에서 다룬다.
