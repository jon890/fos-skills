# 실행 형태와 등급

**`SKILL.md` 4단계에서 phase 마다 읽는다.**

## 목표

**phase 하나를 어느 등급(`fast`, `standard`, `deep`)으로 돌릴지 정한다.**

먼저 **실행 형태**를 판정하고, 그것을 하한으로 삼아 등급을 고른다. 실제로 갈리는 곳은 둘이다.

- task 가 `fast` 를 적었는데 `BOUNDED` 가 아니면 `standard` 이상으로 올린다.
- task 가 `standard` 를 적었는데 `HIGH_RISK` 면 `deep` 으로 올린다.

**내리는 방향은 없다.**

## 1. 실행 형태를 판정한다

| 실행 형태 | 의미 |
| --- | --- |
| `BOUNDED` | 실행 명세가 닫혀 있어 새로운 판단 없이 구현하고 검증할 수 있다 |
| `JUDGMENT_REQUIRED` | 일반적인 기술 판단이 필요하지만 설계나 데이터 위험은 높지 않다 |
| `HIGH_RISK` | 새 설계, 보안, 데이터, 호환성처럼 실패 비용이 큰 판단이 필요하다 |

**더 엄격한 판정이 항상 이긴다.**

- critic 판정과 team-lead 직접 점검이 다르면 더 엄격한 쪽을 고른다.
  team-lead 는 phase 의 검증 명령과 오버레이의 반복 함정, 고위험 경로, 금지 패턴으로 점검한다.
- 판정이 없거나 근거가 부족하면 `JUDGMENT_REQUIRED` 이상을 고른다.
- `execution_profile` 이 `deep` 이면 `HIGH_RISK` 다.

### `HIGH_RISK` 차단 조건

아래 중 하나라도 실제 변경 범위에 들어가면 `HIGH_RISK` 다.

- 새 아키텍처, 도메인 모델, 공용 추상화 설계
- 공개 API, 외부 이벤트, 저장 형식, 하위 호환성 변경
- 데이터 스키마, 마이그레이션, 영구 데이터 변환
- 인증, 권한, 비밀값, 보안 경계 변경
- 동시성, 트랜잭션, 분산 처리, 장애 복구 정책 변경
- 데이터 손실, 중단, 비용 과다 발생 가능성이 있는 작업
- 원인이 확정되지 않은 복합 장애나 성능 퇴행
- 여러 서비스, 저장소, 배포 경계를 넘는 변경

여러 구현안 중 하나를 골라야 하지만 위에 해당하지 않으면 `JUDGMENT_REQUIRED` 다.

### `BOUNDED` 자격

아래를 모두 만족해야 `BOUNDED` 다. 하나라도 확인할 수 없으면 `JUDGMENT_REQUIRED` 로 올린다.

- 변경할 파일과 모듈, 완료 조건이 특정됐다.
- 기존 설계와 유틸리티와 코드 형태를 따라 구현할 수 있다.
- executor 가 제품, 설계, 공개 인터페이스 결정을 새로 내릴 필요가 없다.
- 잘못 구현해도 국소적으로 되돌릴 수 있다.
- 검증이 요청 동작과 주요 회귀를 실제로 감지한다.
- 위 `HIGH_RISK` 차단 조건에 해당하지 않는다.

## 2. 실행 등급을 고른다

**출발값**은 위에서부터 하나만 적용한다. 위가 있으면 아래를 보지 않는다.

1. phase 의 `execution_profile`
2. 옛 phase 의 `model` 값. 그 값이 무엇이든 `standard` 로 읽는다
3. 계획 검토 단계에서 판정한 규모의 기본 등급 (아래 표)

**하한**은 위에서 판정한 실행 형태의 최소 등급이다. 출발값이 이보다 낮으면 끌어올린다.

| 실행 형태 | 최소 등급 |
| --- | --- |
| `BOUNDED` | `fast` |
| `JUDGMENT_REQUIRED` | `standard` |
| `HIGH_RISK` | `deep` |

사용자가 특정 모델을 요청해도 이 하한 아래로는 내리지 않는다.

### 규모별 기본 등급

| 규모 | 해당하는 변경 | team-lead | critic | executor | code-reviewer | docs-verifier |
|---|---|:---:|:---:|:---:|:---:|:---:|
| **소** | 버그 수정, 미세 조정 | standard | standard | standard | standard | standard |
| **중** | 기능 확장, 리팩토링 | standard | deep | standard | standard | standard |
| **대** | 새 아키텍처, 신규 도메인, 스키마 대규모 변경 | deep | deep | standard | standard | deep |

규모는 phase 개수가 아니라 **무엇을 바꾸는가**로 가른다.
phase 가 하나여도 스키마를 바꾸면 「대」 이고, 여러 개여도 같은 패턴 반복이면 「중」 이다.

### 등급과 실제 모델의 대응

- team-lead 가 세 등급을 그 환경에 설치된 모델과 role 에 대응시킨다.
  정확히 맞는 것이 없으면 **더 엄격한 쪽으로만** 올려 잡는다. 아래로 내리는 폴백은 없다.
  실제 선택과 올려 잡은 사유를 실행 보고에 남긴다.
- **등급은 스폰 시점에 항상 명시 지정한다.**
  생략하면 에이전트 정의의 모델, 팀원 기본 모델, team-lead 상속 중 무엇이 적용될지 환경 설정이 정한다.
- 모델과 effort 는 따로 지정한다.

## 승격 보고 처리

executor 가 중단 보고하는 조건과 형식은 [`role-executor.md`](role-executor.md)가 소유한다.
받은 뒤 team-lead 가 아래에서 하나를 고른다.

| 사유 | 대응 |
| --- | --- |
| plan 을 바꿔야 한다 | `SKILL.md` 3단계 critic 재평가로 돌아간다 |
| 단순 실행 누락이다 | 같은 등급으로 재투입한다 |
| 새로운 판단이 필요하다 | 실행 형태를 올리고 그 최소 등급으로 다시 스폰한다 |
| code-reviewer 나 docs-verifier 가 설계와 명세 결함을 발견했다 | 같음 |

## team-lead 가 phase 마다 남길 기록

- 출발값과 최종 실행 형태, 그렇게 판정한 근거
- 실제로 쓴 role 과 모델, 올려 잡았으면 그 사유
- 승격 여부와 사유
