# orch: 보드의 다음 단계를 코디네이터가 지시 없이 이어 간다

확인: 2026-11-10

## 목표

보드 항목의 앞 단계가 끝나고 다음 단계가 미리 허락된 일이면, 사용자가 다시 지시하지 않아도 코디네이터가 그 단계를 띄운다. 사용자가 정할 단계는 코디네이터가 바로 묻고, 배포나 회차 같은 조건을 기다리는 단계는 조건이 채워질 때까지 깨우지 않는다.

- 배경(사용자 2026-11-10): 「board 에 올라온 작업은 단계가 끝나면 다음 단계도 진행해야 하는데 멈춰 있는 경우가 꽤 있다. ai-analysis 에서 특히 그렇다」.
- 코디네이터 조사(2026-11-10): ai-analysis 보드에서 앞 단계는 끝났고 다음 단계가 남은 항목이 14개였다. 사람과 외부를 기다리는 것(기획 답, real 19:00 회차 결과)과 스스로 넘어갈 수 있던 것(audit-admin-view 「PR3: 선행 조건 충족 → worker」, trait-memory 「PR3~10」 연속 PR)이 섞여 있었다.

## 범위

이번 범위:

- 보드 단계 줄의 표시 세 가지(미리 허락됨, 사용자가 정함, 조건을 기다림)와 읽는 규칙
- 상주 루프가 표시를 읽어 코디네이터를 깨우는 알림
- 코디네이터가 알림을 받고 따르는 규칙(띄우기, 묻기, 한도, 보고, 멈추기)

범위 밖:

- 루프가 worker 를 직접 띄우는 것. 지시서를 쓰고 띄우는 일은 코디네이터가 한다
- worker 가 보드를 고치는 것. 공통 지시서의 「worker 는 보드를 고치지 않는다」 를 그대로 둔다
- 표시가 없는 옛 단계 줄을 한꺼번에 고치는 것
- 보드 화면(work-board)에서 표시를 아이콘으로 바꾸는 것. 화면은 표시 글을 그대로 보여 준다

## 사용자 답(1라운드, 2026-11-10)

- 묻지 않고 이어 가도 되는 일: 확인받은 계획의 다음 PR, 스펙 확인 뒤 설계와 계획, 배포·회차 뒤 정리와 다시 재기, 리뷰 지적 반영과 머지.
- 자동으로 띄우면 안 되는 일: real 에 닿는 일(real 배포, real 데이터와 운영 설정 변경), 외부로 나가는 글(Dooray 댓글과 업무, 메신저, 메일, 사내 회신), 범위가 바뀌는 일(스펙과 계획에 없던 새 일, 계획을 나누는 결정). 「비용이 큰 일」 은 고르지 않았다.
- 알림: 띄울 때마다 그 턴의 답에 「다음 단계 자동 진행: 무엇을, 어느 모델로, 왜 묻지 않았는지」 한 줄. 따로 메시지를 보내지 않는다.

## 요구사항과 인수 조건

용어: 「첫 미완료 단계」 는 항목 `details` 에서 번호로 시작하고 끝나지 않은 첫 단계 줄이다. 「참고:」, 「대기:」, 「남은 일:」, 「중간 과정:」 처럼 번호 없는 줄은 단계가 아니다(`board.md`).

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 꼬리표 없는 수동 단계 줄의 번호 뒤 맨 앞에 `[auto]`, `[ask]`, `[wait]`, `[wait: <조건>]` 중 하나를 붙일 수 있다. 사건 단계(`[pr]`, `[merge]`, `[deploy]`, `[release]`)에는 붙이지 않는다. 붙이는 것은 코디네이터다. worker 는 계획에서 나눈 PR 목록을 `worker_done` 에 적어 넘기고 보드를 고치지 않는다 | `2. [auto] PR4 회차 추이 API (계획: <경로>)` 처럼 쓴 줄을 orch 가 표시와 본문으로 나눠 읽는다. 표시가 없거나 모르는 표시(`[maybe]`)인 줄은 표시 없는 줄로 읽는다. 기존 사건 꼬리표와 줄 끝 `(#N 사건)` 은 지금과 같이 동작한다. 리뷰 반영과 머지는 지금 규칙(review-fix, 머지 큐, 자동 머지 설정)대로 코디네이터가 한다 |
| REQ2 | `[auto]` 는 DECISION1 의 일이고 DECISION2 의 일이 아닐 때만 붙인다. 줄에 근거를 괄호로 적는다: `(스펙: <경로>)`, `(계획: <경로>)`, 또는 앞 사건 `(앞 사건: #N merge)`. 앞 사건 근거는 줄 끝 사건 꼬리표 `(#N 사건)` 과 다른 꼴로 적는다. 줄 끝 꼬리표는 그 사건이 일어나면 그 줄을 끝내므로, 근거로 쓰면 띄우기 전에 `[auto]` 줄이 끝나 버린다 | orch 규칙 문서(`board.md`)에 붙여도 되는 일, 안 되는 일, 근거 꼴이 있다. 근거 없는 `[auto]` 줄을 받은 코디네이터는 띄우지 않고 `[ask]` 로 바꿔 묻는다. `2. [auto] PR4 (앞 사건: #665 merge)` 는 #665 가 머지돼도 끝나지 않고 첫 미완료 단계로 남아 `STEP-READY` 대상이 된다 |
| REQ3 | 코디네이터는 `[auto]` 단계를 띄우기 직전에 근거를 확인한다. 스펙 근거면 그 파일이 있고 `확인: YYYY-MM-DD` 줄이 있어야 한다. 계획 근거면 그 파일이 있어야 한다. 경로가 절대경로면 그 자리(다른 워크트리 포함), 상대경로면 저장소 기본 checkout 기준이다. 앞 사건 근거(`(앞 사건: #N 사건)`)면 보드에서 그 PR 의 그 사건 단계 줄이 이미 끝나 있으면 된다. 아니면 `[ask]` 로 바꿔 묻는다 | 규칙 문서에 이 확인 순서가 있다. 확인 줄 없는 스펙을 근거로 단 `[auto]` 는 띄우지 않고 사용자에게 묻는다. 머지 안 된 앞 PR 워크트리의 계획을 절대경로로 적은 연속 PR 은 이어진다 |
| REQ4 | 상주 루프는 status 가 doing 이나 wait 인 항목의 첫 미완료 단계를 본다. worktree·branch 칸이 비어 있어도 본다. todo, decide, done, goal 항목은 보지 않는다. 첫 미완료 단계가 `[auto]` 이고 그 항목의 워크트리·브랜치에 살아 있는 worker 가 없고 그 항목의 열린 PR 이 없으면, 또는 첫 미완료 단계가 `[ask]` 면(worker·PR 과 관계없이), 그 틱에 주 Run 으로 `STEP-READY` 를 보낸다. 본문은 항목 id, 표시, 단계 글이다. 코디네이터를 깨우는 알림이다. 루프는 항목 status 를 바꾸지 않는다 | 머지로 `[merge]` 단계가 끝나 다음 줄이 `[auto]` 가 된 항목에, 다음 틱 안에 `STEP-READY <항목> auto <단계 글>` 이 한 번 온다. 같은 항목·같은 단계 글로는 루프를 다시 띄운 뒤에도 다시 오지 않는다(REQ9 의 다시 알림은 예외). 단계 글이 바뀌면 다시 온다. `[auto]` 는 worker 가 살아 있거나 PR 이 열려 있으면 오지 않는다. PR 이 열린 동안의 `[ask]` 는 바로 온다 |
| REQ5 | 표시가 붙은 단계에는 처음에 `STAGE-STALLED` 를 보내지 않는다. `[wait]` 단계는 깨우지 않는다. 다만 자동으로 한 번 띄운 `[auto]` 단계가 다시 「살아 있는 worker 도 열린 PR 도 없음」 이 되면, 표시 없는 줄처럼 30분(`pipeline.idle_min`) 뒤 `STAGE-STALLED` 를 보낸다. 표시 없는 단계는 지금처럼 30분 뒤 `STAGE-STALLED` 다 | `[wait]` 가 첫 미완료인 항목은 몇 시간이 지나도 알림을 받지 않는다. 자동으로 띄운 worker 가 끝났는데 줄이 그대로인 항목은 30분 뒤 `STAGE-STALLED` 를 한 번 받는다. 표시 없는 단계의 알림은 지금과 같다 |
| REQ6 | `[wait]` 줄 끝의 `(#N 사건)` 은 지금처럼 그 PR 사건에 끝난다. `[wait: YYYY-MM-DD HH:MM]` 은 그 시각(루프가 도는 머신의 로컬 시간)이 지나면 루프가 그 줄을 끝낸다. 항목 status(doing, wait)와 관계없다. 그 밖의 조건 글은 루프가 끝내지 않고 코디네이터나 사용자가 끝낸다 | 시각이 지난 뒤 첫 틱에 그 줄이 done 이 되고, 다음 줄이 `[auto]` 면 REQ4 의 알림이 온다. wait 항목에서도 같다. 꼴이 틀린 시각(`[wait: 내일 아침]`)은 글 조건으로 보고 끝내지 않는다 |
| REQ7 | 코디네이터는 `STEP-READY auto` 를 받거나 머지·배포로 다음 단계가 `[auto]` 가 된 것을 보면 같은 턴에 지시서를 쓰고 그 단계를 띄운다. `STEP-READY ask` 면 결정 질문 형식으로 사용자에게 묻는다 | orch 규칙 문서(`waiting.md`, `replying.md`)에 이 처리가 있다 |
| REQ8 | 자동으로 띄우면 그 턴의 답에 `다음 단계 자동 진행: <무엇을>, <agent·모델>, <묻지 않은 이유(근거)>` 한 줄을 남긴다. 따로 메시지를 보내지 않는다 | 규칙 문서에 이 줄의 꼴이 있다 |
| REQ9 | 자동으로 띄우는 한도: 살아 있는 worker 수로는 미루지 않는다. 최근 30분 안에 `WORKER-LIMITED` 를 받았으면 자동으로 띄우지 않고 사용자에게 알린다. 루프는 마지막 `WORKER-LIMITED` 뒤 30분이 지나면 그 사이 미룬 단계에 `STEP-READY` 를 한 번 더 보낸다. 한 단계는 한 번만 자동으로 띄운다. 자동으로 띄운 worker 가 일을 끝내지 못하면(`worker_done` 의 failed, 끝난 터미널, 사용자가 멈춤) 다시 띄우지 않고 그 단계를 `[ask]` 로 바꿔 묻는다. | REQ10 | 표시 없는 옛 줄은 지금처럼 다룬다. 한꺼번에 고치지 않고, 코디네이터가 그 항목의 단계를 새로 쓰거나 고칠 때 표시를 붙인다. 저장소별 켜기 설정은 없다. 표시를 붙이는 것이 켜기다 | 플러그인을 갱신하고 루프를 다시 띄워도 표시 없는 보드의 알림과 동작이 그대로다 |
| REQ11 | 멈추기: 단계 하나는 사용자가 멈추라고 하면 코디네이터가 그 worker 를 기존 절차로 중지하고 그 단계를 `[ask]` 로 바꾼다. 저장소 전체는 `.orch/config.json` 의 `board.auto_advance` 를 `false` 로 둔다. 그러면 루프가 `STEP-READY` 를 보내지 않고 코디네이터도 자동으로 띄우지 않는다. `[auto]`·`[ask]` 줄은 표시 없는 줄처럼 30분 뒤 `STAGE-STALLED` 를 받는다. `[wait]` 는 그대로 깨우지 않고 시각 wait 도 그대로 끝낸다. 기본은 `true` 다 | `board.auto_advance: false` 인 저장소에서 `[auto]` 가 첫 미완료여도 `STEP-READY` 가 오지 않고 30분 뒤 `STAGE-STALLED` 가 온다. `[wait]` 항목에는 알림이 쏟아지지 않는다. 값이 boolean 이 아니면 설정 오류다 |
| REQ12 | 다른 저장소 코디네이터(ai-analysis 등)도 같은 규칙을 쓴다. 규칙은 orch 스킬 문서와 루프에 두고 저장소 오버레이에 옮겨 적지 않는다 | 플러그인을 갱신하고 그 저장소 루프를 다시 띄우면 표시를 붙인 항목부터 REQ4~REQ9 가 동작한다 |
