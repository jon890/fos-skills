# planning

**목표: 사용자와 합의한 것을 `docs/` 에 남기고, 그것만 읽고 구현할 수 있는 `tasks/` 를 만든다.**

- 의사결정과 서비스의 흐름은 `docs/` 에 남는다. 구현이 끝난 뒤에도 읽는다.
- `tasks/plan{N}-{slug}/phase-*.md` 는 구현자가 이 대화를 보지 못해도 실행할 수 있어야 한다.
- 구현된 것이 합의한 것과 같아야 한다.

이 워크플로가 관리하는 문서는 다섯이다. 파일 이름이 담을 것을 정한다.


| 파일                          | 담는 것                                                                                       | 정하는 단계       |
| --------------------------- | ------------------------------------------------------------------------------------------ | ------------ |
| `docs/prd.md`               | 제품 요구사항. 무엇을 만들고 무엇은 만들지 않는가, 무엇을 관측하면 요구가 충족되는가                                           | 7 (영향만 판정)   |
| `docs/flow.md`              | 흐름도나 시퀀스 다이어그램. mermaid 로 그린다. 정상 경로와 분기, 실패와 빈 상태와 동시 요청에서 갈리는 지점 | 3            |
| `docs/code-architecture.md` | 모듈 책임과 배치. 어느 경로에 무엇이 앉고 어느 쪽이 어느 쪽을 부르는가                                                  | 4, 6         |
| `docs/data-schema.md`       | 저장 모델. 필드와 타입, 키와 유니크 제약, 지울 때 함께 지워지는 것                                                   | 6            |
| `docs/adr/NNN-<슬러그>.md`     | 결정 하나와 그 근거. 맥락, 버린 대안, 얻는 것과 감당할 것                                                        | 결정할 때마다 새 파일 |


## 레포 설정을 먼저 읽는다

레포 고유의 값은 아래 순서로 찾는다. 앞에서 찾으면 뒤를 보지 않는다.

1. `<repo-root>/.claude/planning-overlay.md`
2. 그 저장소의 하네스 지침 파일. `AGENTS.md` 와 `CLAUDE.md` 를 본다
3. 어디에도 없으면 사용자에게 확인한다

검증 명령, 레이어 구조, 도메인 변형, 추가 문서가 여기 해당한다.
실측으로 오버레이 없이 `CLAUDE.md` 만 둔 저장소가 셋이다.

## 8단계 실행 절차

각 단계는 진입 시 해당 reference 를 읽고 수행한다. 단계를 표기하고, 아래 통과 조건을 확인한 뒤 다음으로 간다.


| 단계  | 이름                            | 정해야 하는 것                        | reference                                                 |
| --- | ----------------------------- | ------------------------------- | --------------------------------------------------------- |
| 1   | 구현 가능성 (역할: CTO)              | 되는가, 무엇을 재사용하나, 무엇이 위험한가        | `references/step-1-feasibility.md`                        |
| 2   | 기술 스택                         | 기존 스택으로 되는가, 새 의존이 정당한가         | `references/step-2-tech-stack.md`                         |
| 3   | 호출·사용자 흐름 (역할: 워크플로/UX)       | 정상 흐름과 실패·빈 상태·동시 충돌            | `references/step-3-flow.md`                               |
| 4   | 인터페이스 설계                      | 사용자와 호출자가 마주하는 표면               | `references/step-4-interface.md`                          |
| 5   | API·함수 설계                     | 엔드포인트·시그니처·요청과 응답 스키마           | `references/step-5-api.md`                                |
| 6   | 데이터·코드 구조 (역할: 데이터 모델러 겸 CTO) | 스키마·상태와 디렉터리 배치                 | `references/step-6-data-code.md`                          |
| 7   | docs 영향과 기술 결정 기록             | 책임 문서 판정과 실제 갱신                 | `references/step-7-docs.md`                               |
| 8   | task 파일 생성과 커밋                | 대화를 못 본 executor 가 읽고 실행할 phase | `references/step-8-tasks.md`, `references/task-create.md` |


### 단계는 하나씩 순차로 진행한다

1. **단계 기록 생성**: planning 시작 시 밟을 단계를 각각 할 일로 만들고,
   단계를 통과할 때마다 완료 처리한다. 할 일 목록 도구가 있으면 그것을 쓴다.
2. **단계에 진입하면 해당 reference 문서를 읽고 그 문서의 「정할 것」 을 정한다.**
3. **통과 조건**: 아래 둘이 모두 참이어야 다음 단계로 간다.
   - **남은 질문이 없다.** 그 단계의 「물어서 확정할 것」 을 하나씩 짚었고, 답이 열어 놓은 후속 질문도 닫혔다.
   - **사용자만 답할 결정이 남지 않았다.** 취향, 범위, 되돌리기 어려운 것, 트레이드오프 판단이 여기 해당한다.
     선택지와 트레이드오프를 붙여 묻고 확정받는다.
     구조화 질문 도구가 있으면 그것을 쓰고, 없으면 번호를 붙여 묻는다.

8단계에는 조건이 하나 더 붙는다.
**phase 가 인용한 식별자와 스키마와 경로가 `docs/` 에 적힌 것과 같아야 한다.**
어긋나면 구현자가 phase 만 읽고 합의와 다른 것을 만든다.

## task 생성과 마감

### plan 을 나눌지 정한다

8단계 task 를 만들기 전에 정한다.
**한 plan 은 한 번에 검토할 수 있는 크기로 둔다.** 

### task 를 만든 직후 확인한다

task 파일을 만든 직후, 사용자에게 보고하기 전에 둘을 한다.

1. **스크립트를 돌린다.** 종료 코드 0 이어야 한다.
  ```bash
   # cwd: 타깃 레포 root
   python3 scripts/verify_task.py plan{N}-{slug}
  ```
2. **스크립트가 잡지 못하는 것을 확인한다.**
   phase 를 처음 읽는 사람이 되물어야 실행할 수 있는 곳,
   반복 함정 목록의 패턴에 걸리는 곳이다.

위반을 찾으면 임의로 고치지 않고 사용자에게 확인받는다.
