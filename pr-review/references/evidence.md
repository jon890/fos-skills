# 근거 확보

리뷰에서 가장 비싼 실수는 못 찾은 버그가 아니라 **틀린 지적**이다.
작성자가 확인하고 반박하고 되돌리는 데 드는 시간이, 내가 한 번 더 재는 시간보다 훨씬 크다.

## 세 가지 주장과 각각의 증명

| 주장의 종류 | 필요한 근거 | 없으면 |
| --- | --- | --- |
| 동작 주장 ("이 경로는 실행되지 않는다") | `file:line` 인용 | 쓰지 않는다 |
| 비용 주장 ("느리다", "메모리를 쓴다") | 실측값 | 등급을 내리거나 질문형으로 |
| 관례 주장 ("다른 곳은 이렇게 한다") | 그 다른 곳의 인용 | 쓰지 않는다 |

**이름에서 추론한 것은 근거가 아니다.** 메서드 이름이 `getFile` 이라고 파일 하나만 받아온다고 단정하지 않는다.
주석도 근거가 아니다. 주석과 코드가 다른 경우가 실제로 있다.

## 실측 방법

### 소켓 대기와 CPU 분포

돌고 있는 JVM 에 붙일 수 있다. 코드를 고치지 않고 에이전트도 필요 없다.

```bash
jcmd -l | grep <애플리케이션 클래스>
jcmd <pid> JFR.start name=probe settings=profile filename=/tmp/probe.jfr duration=180s
jfr summary /tmp/probe.jfr
jfr print --events jdk.SocketRead /tmp/probe.jfr
jfr print --events jdk.ExecutionSample /tmp/probe.jfr
```

`jdk.SocketRead` 는 `host`, `port`, `eventThread`, `duration` 을 준다.
**대상별로 묶고 스레드별로도 묶는다.** 어느 스레드에 몰렸는지가 병목의 위치를 알려준다.

`jdk.ExecutionSample` 은 표본이라 "이 메서드가 몇 ms" 는 나오지 않는다. 어디에 몰렸는지만 본다.

### 특정 구간의 시간

전체 프로파일보다 그 구간만 떼어 재는 편이 정확하다.
접속 시간을 알고 싶으면 같은 프로토콜로 접속만 반복해 잰다.

### 쿼리 횟수와 시간

SQL 로그가 있으면 구문별로 센다. 건수와 합계를 같이 낸다.
건당 시간이 네트워크 왕복과 비슷하면 **쿼리가 아니라 호출 횟수가 문제**다. 왕복을 따로 재서 확인한다.

```bash
# 대상 호스트로 TCP 연결 왕복을 20 번 재서 중앙값을 낸다
python3 - <<'PY'
import socket, statistics, time
HOST, PORT = "db.example.internal", 5432
d = []
for _ in range(20):
    s = socket.socket(); t = time.perf_counter()
    s.connect((HOST, PORT)); d.append((time.perf_counter() - t) * 1000); s.close()
print(f"중앙값 {statistics.median(d):.2f}ms  최소 {min(d):.2f}ms  최대 {max(d):.2f}ms")
PY
```

### 인덱스

느리다고 쓰기 전에 인덱스가 있는지 본다. 엔티티 선언이 아니라 **DB 의 실제 인덱스**를 본다.
둘이 다른 경우가 있다. 사용자에게 `SHOW INDEX FROM <table>` 을 부탁해도 된다.

## 실측이 주장을 뒤집는 일은 흔하다

기록해 둘 만한 실제 사례다. 다섯 번 재서 다섯 번 다 처음 주장이 틀렸다.

| 처음 주장 | 실측 결과 |
| --- | --- |
| 파싱을 옮기면 메모리가 준다 | 정상 상태는 지금이 더 낮았다 |
| 이 새로고침은 정확성에 필요하다 | 충돌은 이미 감수하도록 되어 있었다 |
| 재로그인이 느리다 | 페이지 처리 시간의 1\~3% 였다 |
| 함수로 감싼 컬럼이라 전체 훑기가 된다 | 다른 인덱스가 있어 영향이 작았다 |
| 이 필드가 비어 있다 | 내 조회 경로가 틀렸다 |

마지막 줄이 특히 흔하다. **내 확인 방법이 틀린 것을 코드 문제로 오인한다.**
값이 비어 보이면 코드를 의심하기 전에 내가 본 경로가 맞는지 먼저 확인한다.

## 확신이 없을 때 쓰는 문형

단정하지 않고 여지를 남기되, 무엇을 확인하지 못했는지 밝힌다.

- `~로 읽었는데 제가 놓친 의존이 있으면 알려주세요`
- `이 경우가 실제로 발생하는지는 확인하지 못했습니다`
- `측정하지 못해 영향 범위는 모르겠습니다`

확인하지 못한 것을 확인한 것처럼 쓰지 않는다.
반대로, 확인한 것은 어떻게 확인했는지 한 줄로 적는다. 작성자가 같은 방법으로 재현할 수 있다.
