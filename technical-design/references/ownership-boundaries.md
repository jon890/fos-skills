# 소유 경계 검토

새 업무 영역의 기술 설계에서 읽는다. 기존 저장소의 분리 판단 기준을 유지한다.

**소유 경계의 분리 신호**는 다음과 같다. 새 영역을 기존 모듈에 넣을 때 하나씩 대조한다.

- 쓰는 사람이 다르다.
- 배포 환경이 다르다.
- 데이터 생명주기가 다르다.
- 기존 운영 코드가 새 영역의 데이터를 거꾸로 읽게 된다.

하나라도 걸리면 어디에 둘지를 `사용자` 결정으로 올리고, 아래 「소유 경계 ADR 초안」 을 쓴다.
하나도 걸리지 않으면 작성자가 대조한 근거를 결정 표에 남기고 기존 모듈에 둔다. 기능마다 모듈 질문을 만들어 내지 않으려는 것이다.

### 소유 경계 ADR 초안

모듈 배치는 나중에 옮기려면 코드와 데이터를 함께 바꿔야 하는 결정이다. 그래서 질문 블록 하나로 끝내지 않고 ADR 초안으로 남긴다.

- 초안에는 선택지와 선택지마다의 영향, 권장안과 이유를 쓴다. 선택지는 기존 모듈에 둠, 새 모듈이나 서비스로 나눔, 공유 라이브러리로 뺌처럼 실제로 갈리는 것만 둔다.
- 걸린 분리 신호를 근거 경로와 함께 적는다.
- ADR 위치와 형식은 대상 저장소 지침과 오버레이를 따른다. 지정이 없으면 plan 의 [ADR 구조 템플릿](../../plan/references/task-create.md#adrarchitecture-decision-records-구조-템플릿)을 쓴다.
- 초안은 사용자가 고르기 전까지 제안 상태로 둔다. 결정 표의 그 행 근거에 초안 경로를 적는다.

**ADR 초안을 쓴 기능은 설계 관문이 열린 것으로 본다.**
이때만 결정을 올리기 전에 대화를 모르는 하위 에이전트 하나에게 architect 관점으로 초안을 한 번 검토받는다.
빠진 선택지, 낮게 잡은 영향, 근거가 약한 권장안을 찾게 하고, 발견은 초안에 반영한 뒤 올린다.
위임 방식은 [팀원 위임 계약](../../implementation/references/team-spawn.md)을 따른다. 독립 검토를 실행할 수 없는 환경이면 미완료로 보고한다. 자기 점검으로 통과 처리하지 않는다.
