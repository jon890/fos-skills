# Step 7. docs 영향 종합과 기술 결정 기록

**역할**: 문서 관리자. 여섯 달 뒤 이 코드를 처음 보는 사람이 무엇을 알아야 하는지로 판단한다.
**통과시키지 않는 것**: 코드만 봐도 아는 내용을 적은 문서, "왜" 가 빠진 결정 기록, 갱신을 phase 로 미루는 것.

규모와 무관하게 항상 수행한다.

## 정할 것

- 이번에 내린 기술 결정 목록과 각각의 "왜".
- 필수 다섯 전체의 영향 판정. 영향이 없는 문서는 본문을 건드리지 않고 근거만 단계 결과에 남긴다.
- 영향을 받는 문서의 실제 갱신 diff 와 ADR 번호.
  없는 문서는 이번 변경이 그 내용을 실제로 소유할 때만 만든다. 장기 기술 결정이 없으면 빈 ADR 을 만들지 않는다.
- 레포 설정이 지정한 추가 문서의 영향 판정과 갱신 diff.
- 같은 정보를 두 문서에 쓰지 않는다. 필요하면 링크한다.

ADR 형식과 supersede 처리는 `task-create.md` 가 소유한다.

## 계획서를 가리키지 않는다

`docs/` 는 계획서보다 오래 남는다. 계획서는 구현이 끝나 운영에 반영되면 제거된다.
`docs/` 가 계획서를 번호로 가리키면 그때 깨진 참조가 된다.

- **기본은 아무것도 적지 않는다.** 무엇이 언제 왜 바뀌었는지는 git 이력이 이미 추적한다.
- 결정의 근거가 필요하면 ADR 번호를 적는다.
- 변경의 이력이 필요하면 PR 번호를 적는다.
- 커밋 SHA 는 적지 않는다. rebase 와 squash 로 값이 바뀌어 같은 변경을 다시 찾을 수 없다.
- 계획서 번호를 시간 축으로 쓰지 않는다. 번호가 계획서와 함께 사라져 어느 쪽이 최근인지 판정할 수 없다.
  날짜처럼 계획서 수명과 무관한 값을 쓴다.

**내용을 계획서에 맡기지 않는다.** 계획서를 읽으라고 적는 것은 그 내용을 아직 옮기지 않았다는 뜻이다.
책임 문서가 그 내용을 소유해야 계획서를 지울 수 있다.

## 물어서 확정할 것

- 이 결정이 ADR 감인가. 아래 둘 중 하나를 만족할 때만 남긴다.
    - 되돌리는 비용이 크다. 지금 바꾸면 이미 쓴 코드나 데이터를 함께 바꿔야 한다.
    - 시스템의 핵심 개념을 정한다. 자료 구조, 동기와 비동기, 동시성 전략, 트랜잭션 경계다.
    - 둘 다 아니면 남기지 않는다. 라이브러리나 제품 선택은 교체 비용이 커도 핵심 개념을 바꾸지 않으면
      ADR 이 아니다. 그런 것을 쌓으면 정작 구조를 정한 결정이 목록에서 묻힌다.
- 기존 ADR 이나 문서와 충돌하거나 중복하거나 대체되는 지점.
- 제품 범위, 흐름, 모듈 책임, 저장 계약 중 어느 책임 문서에도 반영되지 않은 합의.
- 공유 인덱스 편집이 동시에 도는 다른 planning 과 충돌할 위치.

## 문서 우선 절차

1. 합의와 기각과 미결을 정리하고 미결이 0인지 확인한다.
2. 각 합의의 책임 문서와 기존 설명의 충돌 여부를 판정한다.
   소규모 변경은 전량 정독 대신 판정 한 줄로 갈음한다.
3. 영향을 받는 문서와 필요한 ADR 을 실제로 갱신한다. task 나 phase 에 문서 결정을 미루지 않는다.
4. `git diff -- docs/` 로 변경을 읽고 용어와 상태와 API 와 저장 모델이 서로 일치하는지 확인한다.
5. 영향이 없는 문서와 그 근거를 단계 결과에 남긴다.
