# 보드 항목이 기능 하나의 단계를 끝까지 잇고, 사건이 오면 대기를 푼다

확인: 2026-11-27

## 목표

보드 항목 하나가 기능 하나를 스펙부터 구현, 검증까지 따라간다. 코디네이터가 기억해 직접 이어 붙이던 곳(설계 PR 머지 뒤 구현 항목, 보드 항목 없이 뜬 worker, 「dev 평가 끝나면」 같은 대기)을 보드와 루프가 맡는다.
근거: 요청 R39(ai-analysis, 2026-11-27) 의 1·2·5번. 실측: 설계 PR 머지로 항목이 done 이 됐는데 구현 PR 이 계속됐다(세 건), 구현 worker 두 개가 보드 항목 없이 떴다, 대기 조건 두 개를 코디네이터가 직접 풀었다.

## 범위

이번 범위:

- 보드 항목과 기능 폴더(`docs/features/<기능>/`)의 연결, 단계 PR 머지 뒤 다음 단계 줄.
- `orch worker launch` 의 보드 항목 찾기와 거부.
- 대기 줄의 사건 이름과 저장소 오버레이의 사건 확인 명령.

범위 밖:

- R39 의 3·4·6번(PR 없는 일의 보고 받기 단계, 숫자로 시작하는 단계 글, 열린 worker 폴더 지키기). 별도 버그 수정 PR 이 맡는다.
- 다음 단계 worker 를 자동으로 띄우는 일.

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 기능 단위 항목 | 보드 항목은 기능 폴더 하나에 하나다. 항목에 기능 폴더 경로를 두고, 두레이 업무가 있으면 task-ref 도 둔다. 기능이 아닌 일(버그 수정, 정리)은 지금처럼 지시서의 항목 id 로 만든다 |
| REQ2 | 단계 머지 뒤 다음 단계 | 기능 항목의 한 단계 PR 이 머지되면 루프가 feature-loop 순서(spec → technical-design → plan·implementation → verify → docs-consolidate)로 다음 단계 줄을 더하고 항목을 doing 으로 둔다. 마지막 단계가 끝날 때만 done 이 된다. 코디네이터에게 「다음 단계 차례」 를 알린다. worker 는 띄우지 않는다 |
| REQ3 | 항목 찾기 | `worker launch` 는 지시서에 `보드 항목 id:` 가 없으면 브랜치, task-ref, 지시서가 가리키는 기능 폴더로 기존 항목을 찾아 붙인다. 못 찾으면 띄우지 않고, 항목 id 를 적거나 `보드 항목 없음: <이유>` 를 적으라고 알린다 |
| REQ4 | 사건 대기 | 대기 줄에 사건 이름을 달 수 있다. 저장소 오버레이가 사건 이름마다 확인 명령을 둔다(끝났으면 종료 코드 0). 루프가 틱마다 대기 줄의 사건 명령을 시간 상한 안에서 돌리고, 끝났으면 대기를 풀고 코디네이터에게 알린다. 명령이 없거나 실패하면 대기를 그대로 두고 오류를 한 번 알린다 |
| REQ5 | 테스트 | 보드 파일을 흉내 낸 단위 테스트로 본다. REQ2 는 「설계 PR 머지 → 항목이 doing 으로 남고 구현 단계 줄이 생긴다」 를 확인한다 |
