# docs-check

**목표: 문서가 현재 코드와 결정을 복원할 수 있는지 감사하고, 사용자가 승인한 것만 고친다.**

- 발견마다 그것을 증명한 코드나 명령이 있어야 한다.
- 사용자 승인 전에는 문서를 고치지 않는다.
- 현재 사실은 책임 문서 한곳에만 남긴다.

## 레포 오버레이

`<repo-root>/.claude/docs-check-overlay.md` 가 있으면 **먼저 읽고** 코어보다 우선한다.
오버레이는 문서 경계, 검증 명령, 저장소 특화 코드 대조 grep 을 소유한다.
없으면 그 저장소의 하네스 지침 파일(`AGENTS.md`, `CLAUDE.md`)에서 문서 경계와 검증 명령을 찾는다.

## 실행 절차

각 단계는 진입 시 해당 reference 를 읽고 수행한다. 통과 조건을 확인한 뒤 다음으로 간다.


| 단계  | 이름      | 통과 조건                                           | reference                 |
| --- | ------- | ----------------------------------------------- | ------------------------- |
| 1   | 범위 판정   | 감사할 파일 목록과 ADR 디렉터리 경로가 정해졌다                    | 오버레이                      |
| 2   | 정적 검사   | `static_check.py` 종료 코드 0, 검사한 Markdown 수가 1 이상 | `scripts/static_check.py` |
| 3   | 의미 검사   | 여섯 축을 대상 파일에 적용했고 발견마다 증명 근거가 있다                | `references/six-axis.md`  |
| 4   | 독립 검토   | 읽기 전용 검토자가 판정을 확인했다. 띄울 수 없으면 그 사실이 리포트에 있다     |                           |
| 5   | 리포트와 승인 | 리포트가 나갔고 사용자가 고칠 항목을 정했다                        |                           |
| 6   | 수정과 재검증 | 승인 항목만 고쳤고 정적 검사와 코드 대조를 다시 통과했다                |                           |


### 1. 범위 판정

사용자가 지정한 범위를 우선한다.
지정이 없으면 현재 경로와 변경 파일에서 가장 좁은 범위를 추론한다.

**각 문서가 무엇을 담기로 했는지 함께 정한다.**
담을 것을 모르면 부패, 과대화, 중복을 판정할 수 없다.
어느 문서가 소유해야 할 내용인지 가릴 기준이 없기 때문이다.

그 저장소가 문서의 역할을 선언했으면 그것을 따른다.
선언이 없으면 아래를 기본값으로 쓴다. `planning` 이 관리하는 문서 다섯이고, 그 스킬이 규약을 소유한다.

| 파일 | 담는 것 |
| --- | --- |
| `docs/prd.md` | 제품 요구사항. 무엇을 만들고 무엇은 만들지 않는가, 무엇을 관측하면 요구가 충족되는가 |
| `docs/flow.md` | 흐름도나 시퀀스 다이어그램. 정상 경로와 분기, 실패와 빈 상태와 동시 요청에서 갈리는 지점 |
| `docs/code-architecture.md` | 모듈 책임과 배치. 어느 경로에 무엇이 앉고 어느 쪽이 어느 쪽을 부르는가 |
| `docs/data-schema.md` | 저장 모델. 필드와 타입, 키와 유니크 제약, 지울 때 함께 지워지는 것 |
| `docs/adr/NNN-<슬러그>.md` | 결정 하나와 그 근거. 맥락, 버린 대안, 얻는 것과 감당할 것 |

여기에 범위의 `README.md` 와 책임 문서, `docs/adr/INDEX.md` 를 더한다.

**문서 목록을 고정하지 않는다.** 실제 파일과 그것을 소비하는 코드를 함께 확인한다.
위 다섯을 쓰지 않는 저장소도 있다. 없는 파일을 만들라고 제안하지 않는다.

### 2. 정적 검사

검사 대상 저장소 루트에서 실행한다.

```bash
python3 scripts/static_check.py <ADR_DIR> <scope>
```


| 종료 코드 | 뜻                       |
| ----- | ----------------------- |
| 0     | 위반 없음                   |
| 1     | 위반 있음. 위반 라인이 표준 출력에 있다 |
| 2     | 검사가 돌지 못함               |


**표준 오류에 표시된 검사 파일 수가 0이면 통과로 보지 않는다.**
ADR 디렉터리가 여러 개면 각각 실행하되 결과를 한 리포트에 합친다.

오버레이가 지정한 코드 대조 명령도 실행한다.
플레이스홀더, 잘못된 작업 디렉터리, 자기참조 때문에 검사가 죽어 있지 않은지 확인한다.

### 3. 의미 검사

코드와 문서의 실제 소비 관계를 읽고 여섯 축을 판정한다.
세부 판정 기준은 `references/six-axis.md` 가 소유한다.


| 축      | 판정하는 것                             |
| ------ | ---------------------------------- |
| 부패     | 제거하거나 바꾼 코드, 경로, 정책이 현재 사실처럼 남았는가  |
| 과대화    | 문서가 구현 절차와 파일 목록을 복제해 작은 변경에도 낡는가  |
| 추론성    | 결정의 맥락, 선택한 것과 기각한 대안을 복원할 수 있는가   |
| 중복     | 같은 정의를 여러 문서가 소유하는가                |
| 자명성    | 코드와 설정만 보면 아는 내용을 ADR 이 반복하는가      |
| 구조 무결성 | 링크, 표, 코드 펜스, 헤딩과 ADR Index 가 올바른가 |


**줄 수만으로 과대화를 판정하지 않는다.**
고정 개수와 목록은 계약인지 단순 복제인지 코드와 대조한다.

### 4. 독립 검토

검토자를 **읽기 전용으로 띄운다.** 검토자의 판정도 코드와 실행 결과에 대조한다.

띄울 수 없으면 메인이 직접 검사하고 그 사실을 리포트에 남긴다.

### 5. 리포트와 승인

각 발견에 아래를 담는다.

```
[<축>] <Critical | Warning>  <파일>:<줄>
현재 사실: <문서가 뭐라고 적었고 실제는 무엇인가>
증명: <대조한 코드, 명령, 단일 소스>
수정안: <가장 작은 수정>
대안: <유지할 수 있는 선택지. 없으면 「없음」>
```

리포트는 `Critical`, `Warning`, `안전` 으로 나누고
검사 범위, 정적 검사 결과, 검증 공백을 함께 적는다.

### 6. 수정과 재검증

- 현재 사실은 책임 문서 한곳에만 남기고 나머지는 그것을 가리킨다.
- ADR 에는 코드로 자명하지 않은 장기 결정, 맥락, 기각한 대안만 남긴다.
- 구현 경로와 실행 명령은 책임 문서나 코드로 옮기고 ADR 은 그 위치를 짧게 가리킨다.
- 대체된 ADR 은 지우지 않는다. `status` 를 `superseded` 로 바꾸고
  `대체된 부분` 을 결정 바로 아래에 두어 대체한 ADR 을 가리킨다. 규약은 `planning` 이 소유한다.
- ADR 파일과 `INDEX.md` 를 함께 고친다.
- 고친 Markdown 에 그 저장소의 표현과 가독성 검사를 실행한다.

수정 뒤 정적 검사와 코드 대조를 다시 실행하고, 승인받지 않은 변경이 없는지 확인한다.
