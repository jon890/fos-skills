# 같은 PR 의 머지 큐 중복 막기 기술 설계

스펙 문서는 두지 않는다. 사용자에게 보이는 동작이 아래 REQ1 하나이고, 지시서가 그 동작을 정했다.
배경은 2026-11-20 fos-assistant 에서 같은 PR 에 `orch queue merge` 프로세스가 둘 뜬 일이다.
상주 루프의 자동 머지가 이미 건 PR 을 코디네이터가 다시 걸었다.
PR 558 은 파일 잠금 여러 개(맡기 기록, 맡기 확인, 마무리 pid 주인 판단)로 이것을 막으려 했고, 리뷰마다 새 경합이 나와 이 설계로 뺐다.

## 요구사항 연결

| ID | 요구사항 | 해결 방법 |
| --- | --- | --- |
| REQ1 | 같은 PR 을 두 번 큐에 넣어도 머지와 마무리가 한 번만 돈다 | PR 마다 실행권 하나를 원자적으로 만든다. 머지 큐 실행과 마무리가 각각 실행권을 쥔 프로세스 하나에서만 돈다 |
| REQ2 | 두 번째 호출은 이미 진행 중이라는 것과 진행 중인 쪽을 알리고 끝난다 | 실행권의 owner 에 pid, 시작 시각, 명령과 Run 을 적어 `QUEUE-DUP` 줄로 낸다 |
| REQ3 | 일시 실패로 걸지 못한 PR 은 다음에 다시 걸린다 | 걸지 못한 호출은 아무것도 시작하지 않고 끝나고, 자동 머지는 그 PR 의 시도 기록을 지운다 |

## 책임과 경계

**한 PR 의 머지 큐 실행은 그 PR 의 실행권을 쥔 프로세스 하나가 맡는다.**
실행권은 `lib/pr-claim.ts` 가 소유한다. 종류는 둘이고 쥐는 프로세스와 쥐는 기간이 다르다.

| 실행권 | 쥐는 프로세스 | 쥐는 기간 | 막는 것 |
| --- | --- | --- | --- |
| `queue-<PR>` | `orch queue merge`(merge-with-finish.ts). 직접 부른 `orch queue run` 은 merge_queue.ts | 큐가 그 PR 을 맡고 있는 동안. 큐를 건 호출이 끝나거나 큐가 그 PR 을 보류로 뺄 때까지 | 같은 PR 을 든 두 번째 큐가 마무리를 띄우고, 앞 큐 뒤에 그 PR 을 다시 판정하는 것 |
| `finish-<PR>` | finish-pr.ts | 마무리가 끝날 때까지(배포 대기 포함) | 같은 PR 의 마무리 둘이 함께 도는 것 |

둘을 하나로 묶지 않는 이유는 수명이 달라서다.
마무리는 큐가 그 PR 을 보류한 뒤에도 머지를 180분까지 기다리고, 그 사이 새 큐가 같은 PR 을 다시 걸어 도는 마무리를 그대로 쓴다.

호출 경로는 그대로다. 상주 루프의 자동 머지와 코디네이터가 모두 merge-with-finish.ts 를 띄우고, 그 프로세스가 실행권을 잡는다.
누가 띄웠는지는 구분하지 않는다. 먼저 잡은 쪽이 맡는다.

- merge-with-finish.ts 는 마무리를 띄우기 전에 인자의 PR 모두에 `queue-<PR>` 을 잡는다. 번호가 낮은 PR 부터 잡고, 다른 쪽이 쥔 첫 PR 에서 멈춰 잡은 것을 놓고 끝난다.
- merge_queue.ts 는 부모가 넘긴 token(`ORCH_QUEUE_CLAIM_TOKEN`)의 실행권을 제 것으로 읽는다. 직접 부른 큐는 스스로 잡는다.
- merge_queue.ts 는 보류, 충돌, 묶음으로 뺀 PR 의 실행권을 그 자리에서 놓는다. 정리 전에 한 번 다시 판정할 PR 은 그 판정 뒤에 놓는다.
  큐는 뺀 PR 을 다시 보지 않는다. 큐가 끝날 때까지 쥐면 보류가 풀린 PR 을 다시 걸어도 거절돼 아무도 맡지 않는다(독립 리뷰에서 나온 순서).
  다시 건 큐는 저장소 잠금을 기다렸다가 앞 큐 뒤에 돈다.
- finish-pr.ts 는 `--pid-file` 을 받으면 시작할 때 `finish-<PR>` 을 스스로 잡는다. 띄우는 쪽(merge-with-finish, `orch followup done`)의 pid 파일 확인은 안내용이다.
- 상주 루프의 자동 머지는 실행권을 잡지 않는다. 띄운 큐의 로그에서 걸지 못한 것을 읽어 시도 기록만 고친다.

저장소의 큐 잠금(`state/merge-queue.lock`)은 그대로 둔다. 서로 다른 PR 을 든 큐가 차례를 기다리는 일은 그 잠금이 맡는다.

## 인터페이스와 데이터

실행권은 `<orch 루트>/state/pr-claims/<종류>-<PR>` 디렉터리다. 형식은 [docs/data-schema.md](../../data-schema.md) 의 `state/pr-claims/` 행이 소유한다.
만들기, 죽은 실행권 회수, 놓기는 `lib/owner-lock.ts` 의 디렉터리 rename 규칙을 그대로 쓴다.

- **잡기**: owner 파일을 쓴 임시 디렉터리를 실행권 이름으로 rename 한다. 이미 있으면 실패한다. 기다리지 않는다.
- **살아 있는지**: owner 의 pid 가 살아 있고 시작 시각·명령줄(`lib/process.ts` 의 `identity`)이 같아야 살아 있다. pid 가 다른 프로세스에 다시 쓰인 실행권은 죽은 것이다.
- **회수**: 죽은 실행권을 그 실행권만의 묘비 이름으로 rename 한다. 같은 죽은 실행권을 늦게 회수하는 쪽은 새 주인의 실행권을 옮기지 못한다.
- **놓기**: 쥔 프로세스가 끝날 때 놓는다. 놓지 못하고 죽어도 다음에 잡는 쪽이 회수하므로 정리 절차가 따로 없다.

새 출력 줄과 종료 코드는 merge-with-finish.ts 와 merge_queue.ts 가 같다.

| 상황 | 출력 | 종료 코드 | 부른 쪽이 할 일 |
| --- | --- | --- | --- |
| 다른 큐가 그 PR 을 맡았다 | `QUEUE-DUP <PR> 이미 진행 중이다: pid <pid> <시작 시각> <명령과 Run>`. 처음 막힌 PR 하나만 낸다 | 4 | 다시 걸지 않는다. 진행 중인 쪽이 머지와 마무리를 끝낸다. 다른 PR 도 함께 걸었으면 겹친 PR 을 빼고 다시 부른다 |
| 쥔 쪽이나 이 프로세스의 시작 시각을 읽지 못했다(ps 실패). 회수 경합이 20번을 넘은 때도 같다 | `QUEUE-CLAIM-FAIL <이유>` | 1 | 같은 명령을 다시 부른다 |
| 같은 PR 의 마무리가 돈다 | 마무리 로그에 `FINISH-RUNNING <PR> pid <pid>` | 0 | 없음 |

마무리의 pid 파일(`finish-<PR>.pid`)은 형식과 읽는 쪽이 그대로다. 실행권을 쥔 동안에만 쓰고 지운다.
다시 돌기 표시는 `state/finish-rerun/<PR>` 에 둔다. 로그 폴더를 따로 준 마무리와 `orch followup done` 이 같은 자리를 보게 하려는 것이다. 규칙은 `lib/finish-claim.ts` 머리 주석이 소유한다.
실행권과 표시의 PR 번호는 정수로 바꿔 쓴다. `0568` 과 `568` 은 같은 실행권이다.

## 실패와 일관성

PR 558 리뷰가 재현한 순서마다 이 구조에서 일어나는 일이다.

| 재현된 순서 | 이 구조에서 |
| --- | --- |
| 두 호출이 동시에 기록이 없는 것을 보고 각자 마무리를 띄운다 | 확인하고 쓰는 두 단계가 없다. rename 하나가 성공한 쪽만 마무리를 띄운다 |
| 맡기 확인 잠금을 잡지 못하면 확인 없이 큐를 건다 | 기다리는 잠금이 없다. 확인하지 못하는 경우는 ps 실패뿐이고 그때는 아무것도 걸지 않는다 |
| 잠금을 넘겨받다 죽은 프로세스의 표시가 남는다 | 회수는 rename 하나라 도중 상태가 없다. 묘비만 남고 다음 호출이 잡는다 |
| 앞 큐의 보류 기록이 새 큐의 맡기 기록을 가린다 | 맡은 PR 을 차례 기록에서 추리지 않는다. 쥔 프로세스가 살아 있는지만 본다 |
| 끝나는 마무리가 새 마무리의 pid 파일을 지운다 | pid 파일은 실행권을 쥔 동안에만 지운다. 놓은 뒤에는 건드리지 않는다 |
| 마무리가 pid 를 쓰기 전에 다른 마무리가 뜬다 | 늦게 뜬 마무리는 실행권을 잡지 못해 `FINISH-RUNNING` 으로 끝난다. pid 파일을 덮어쓰지 않는다 |
| 끝나는 마무리와 `followup done` 이 겹쳐 다시 돌기 요청을 잃는다 | 표시를 쓴 뒤에 실행권이 쥐어진 것을 본 요청은, 쥔 쪽이 놓은 뒤 표시를 한 번 더 볼 때 반드시 보인다 |
| 걸지 못한 자동 머지의 시도 기록이 남아 다시 걸리지 않는다 | 로그의 `QUEUE-DUP`, `QUEUE-CLAIM-FAIL` 을 읽어 그때 건 PR 의 `tried` 를 모두 지운다 |
| inode 를 읽고 owner 를 읽는 사이에 정상 종료와 새 시작이 끼어, 새 주인의 실행권을 회수한다(PR 568 리뷰) | owner 를 읽은 뒤 inode 가 그대로인지 다시 본다. 바뀌었으면 처음부터 읽는다 |

**남는 경합**

- **큐를 건 프로세스만 SIGKILL 로 죽고 자식 머지 큐가 살아남은 경우.** 실행권은 죽은 것으로 읽혀 다른 호출이 같은 PR 을 걸 수 있다.
  새 큐는 저장소 잠금을 기다렸다가 살아남은 큐 뒤에 돈다. 머지된 PR 은 건너뛰므로 머지는 두 번 일어나지 않고, 보류된 PR 의 판정과 알림이 한 번 더 나갈 수 있다.
  SIGTERM 과 SIGINT 는 자식 큐에 넘기고 끝나기를 기다린 뒤 놓으므로 해당하지 않는다.
- **묘비 보존 시간.** 회수하다 한 시간 넘게 멈춘 프로세스가 다시 움직이면 새 주인의 실행권을 옮길 수 있다. `lib/owner-lock.ts` 가 이미 가진 한계다.
- **큐를 건 프로세스가 다른 신호로 죽은 경우.** SIGTERM, SIGINT, SIGHUP 밖의 신호(SIGQUIT 같은 것)는 SIGKILL 과 같다.
- **`QUEUE-DUP` 으로 물러난 자동 머지.** 그때 건 PR 의 `tried` 를 모두 지운다. PR 을 쥔 큐가 그 PR 을 보류로 끝내면 루프가 같은 HEAD 를 한 번 더 걸어 worker 에게 같은 보류 알림이 두 번 갈 수 있다.
  `tried` 를 두면 쥔 큐도 다른 PR 에서 막혀 물러났을 때 아무도 그 PR 을 맡지 않는다(PR 568 리뷰). 맡는 쪽이 없는 것보다 알림이 한 번 더 가는 쪽을 골랐다.
- **죽은 pid 가 남은 pid 파일.** 큐가 거절돼 끝낸 마무리와 SIGKILL 로 죽은 마무리의 pid 파일은 남는다. 그 pid 가 다른 프로세스에 다시 쓰이면 pid 파일만 읽는 곳(띄우는 쪽의 안내 확인, 보드 동기화, 루프 갱신)이 도는 것으로 읽는다. 마무리 자신의 겹침 판단은 실행권의 시작 시각 대조라 영향이 없다.
- **마무리의 ps 실패.** 마무리는 시작 시각을 읽지 못하면 세 번까지 다시 본 뒤 1 로 끝난다. 그때는 정리의 `FINISH-MISSING` 알림이 받친다.
- **`--pid-file` 없이 직접 부른 `orch queue finish`.** 실행권을 잡지 않는다. 지금처럼 겹쳐 돌 수 있다.

**호환**

- 머지되기 전에 뜬 옛 큐와 옛 마무리는 실행권이 없다. 그 프로세스가 끝날 때까지는 지금 동작(저장소 잠금 대기, pid 파일 확인)으로 돌아간다.
- `QUEUE-DUP` 과 종료 코드 4 는 새 값이다. 종료 코드 4 를 다른 뜻으로 쓰던 곳은 없다.

## 검증 전략

- REQ1, REQ2: 임시 저장소에서 가짜 머지 큐를 붙잡아 둔 채 같은 PR 을 다시 거는 테스트(`merge-with-finish.spec.ts`). 동시에 건 경우, 일부만 겹친 경우, 직접 부른 큐, 죽은 프로세스의 실행권 회수를 본다. 실제 GitHub 머지는 부르지 않는다.
- 실행권 자체: 여러 프로세스가 같은 실행권을 다투는 테스트와 회수 경합(`lib-pr-claim.spec.ts`).
- 마무리의 겹침: 끝나는 마무리와 새 마무리, 다시 돌기 표시의 순서를 단계별로 고정한 테스트(`lib-finish-claim.spec.ts`, `finish-pr.spec.ts`).
- REQ3: 걸지 못하고 끝난 큐 뒤의 틱이 같은 HEAD 를 다시 거는 테스트(`orch-loop-auto-merge.spec.ts`).

**버린 대안**

- **코디네이터의 `queue merge` 는 루프에 요청만 넣고 루프가 실행한다.** 루프가 없는 저장소에서는 직접 실행하는 길이 그대로 남아, 두 길이 만나는 곳에 같은 원자적 확인이 또 필요하다.
  `orch queue merge` 는 `MERGED`, `STOP` 줄과 종료 코드를 부른 쪽에 바로 돌려주는데, 요청으로 바꾸면 이 출력 계약이 사라진다. PR 표시(`!`, `~`), 묶음, 머지 전 명령도 요청에 담아 옮겨야 한다.
- **맡은 PR 기록과 그것을 지키는 잠금(PR 558).** 기록을 읽고 고르고 쓰는 단계가 나뉘어 잠금이 필요했고, 잠금을 못 잡았을 때와 넘겨받다 죽었을 때의 처리가 각각 새 경합이 됐다.
- **프로세스 목록(ps)으로 같은 PR 의 큐를 찾는다.** 명령줄을 읽는 것과 큐를 띄우는 것 사이가 비고, ps 가 실패하면 판단할 수 없다. 지금 자동 머지가 쓰는 이 확인은 걸기 전의 앞 단계로만 남긴다.
- **운영체제가 풀어 주는 잠금(flock).** node 에 내장 API 가 없어 perl 같은 바깥 도구에 기대야 한다. 쥔 쪽이 누구인지도 따로 적어야 한다.

**루프가 없는 저장소.** 같은 구조로 돈다. 실행권은 큐를 건 프로세스가 잡으므로 루프가 있든 없든 두 번째 호출은 `QUEUE-DUP` 으로 끝난다.
