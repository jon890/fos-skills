# 같은 일을 두 모델에 맡겨 비교하기

**같은 계열의 새 세대가 아닌 새 모델은 같은 지시서를 지금 모델과 함께 맡겨 비교하고, 사용자가 승인한 뒤에만 모델 표를 바꾼다.**
자동 시작이나 두 worker 를 묶어 관리하는 코드는 없다. 코디네이터가 지금의 `orch worker launch` 로 이 절차를 따른다(사용자 결정 2026-11-23).
결정값의 원본은 스펙 [model-auto-routing](../../../docs/features/model-auto-routing/spec.md) 의 「결정」 표다. 이 문서는 그 값을 쓰는 순서만 갖는다.
같은 계열의 새 세대는 비교하지 않는다. `launch-worker` 가 바로 새 세대로 띄운다([`agent-selection.md`](agent-selection.md) 「새 모델과 새 세대」).

## 비교 시작

1. 상주 루프가 보드에 올린 「새 모델 <모델>」 항목을 보고 비교할 모델을 정한다. 첫 비교 대상은 `gpt-6.2-astra` 다(보드 항목 `model-new-gpt-6-2-astra`).
2. 모델 설명과 등급으로 비교할 행을 고른다. 어느 행이든 된다.
   evidence 의 「같은 일 두 모델 비교」 절에 같은 모델과 행의 판단이 이미 있으면 다시 비교하지 않는다.
3. 비교 id 를 `compare-<모델>-<행>` 꼴로 정한다. 점은 붙임표로 바꾼다(예: `compare-gpt-6-2-astra-design`).
   두 worker 지시서의 `보드 항목 id:` 줄에 이 id 를 적어 보드 항목 하나로 모은다.
4. evidence 에 [`templates/model-compare-record.md`](../templates/model-compare-record.md) 를 복사해 비교 절을 만들고 사용자에게 「비교 시작 <모델> <행>」 을 한 줄 알린다.
   사용자가 멈추라고 하면 남은 건을 띄우지 않고 기록 절에 중단과 날짜를 적는다.
5. 그 행에 새 일이 올 때마다 아래 「두 worker 띄우기」 로 한 건씩 맡긴다. 고른 행마다 5건이다.

## 두 worker 띄우기

지시서 본문은 하나로 쓰고 두 파일로 복사한다. 두 파일은 아래 줄만 다르다.

| 줄 | 지금 모델 | 후보 모델 |
| --- | --- | --- |
| `브랜치:` | `<브랜치>-base` | `<브랜치>-cand` |
| `worker 선택:` | 행의 값 그대로. 끝에 `후보 밖: 비교 기준, <후보 모델> 대조(사용자 결정 2026-11-20)` | 후보 모델과 행의 effort. 끝에 `후보 밖: 비교, <지금 모델> 대조(사용자 결정 2026-11-20)` |

- 두 줄 모두 `후보 밖:` 을 적는다. 그래야 사용량 판정([`agent-selection.md`](agent-selection.md) 「Claude 사용량이 남을 때」)과 세대 판정이 제공자와 모델을 바꾸지 않는다. astra 는 「기본 후보에서 뺀 모델」 이라 이 줄이 없으면 고를 수 없다.
- `비교:` 칸과 `experiment:` 줄은 쓰지 않는다. `후보 밖:` 뒤의 「비교」 는 이유 문장이라 `spec-lint` 가 받는다.
- 두 지시서의 `허락:` 줄은 PR 열기까지 같게 쓴다. 머지는 코디네이터가 한다.
- 담당 경로가 같으므로 두 번째 띄우기는 `--lint-ack "모델 비교: 같은 지시서를 두 모델에"` 를 준다. 워크트리 이름(`--name`)도 `-base`, `-cand` 로 나눈다.

## 숨긴 리뷰

두 PR 이 모두 준비됨을 보내면 평소 리뷰(PR 자동 리뷰나 리뷰 worker)와 별도로 숨긴 리뷰를 맡긴다.

1. 섞을 순서를 정한다. `node -e "console.log(Math.random() < 0.5 ? 'base=A' : 'base=B')"` 의 결과를 `"$(orch paths root)/handoff/compare-keys/<비교 id>-<건 번호>.txt"` 에 적는다.
2. 리뷰 폴더 `"$(orch paths root)/handoff/<비교 id>-<건 번호>/"` 에 `gh pr diff <PR>` 출력을 `A.diff`, `B.diff` 로 둔다. 커밋 메시지, PR 번호, 브랜치 이름은 넣지 않는다. 커밋 끝 줄과 브랜치가 모델을 드러낸다.
3. [`templates/spec-compare-review.md`](../templates/spec-compare-review.md) 로 Claude 리뷰어와 Codex 리뷰어의 지시서를 하나씩 써서 띄운다. 리뷰어는 리뷰 폴더만 읽는다. 지시서에 순서 파일 경로를 적지 않는다.
4. 두 리뷰어가 같은 쪽을 고른 건만 그 쪽의 이김으로 센다. 다르면 갈림이다.

## 머지와 건의 결과

- 두 리뷰어가 같은 쪽을 골랐으면 그 PR 을 머지한다.
- 숨긴 리뷰가 갈리면 평소 리뷰의 P1·P2 수가 적은 쪽을 머지한다. 숨긴 리뷰는 무승부로 센다.
- 한쪽 worker 가 실패하면(PR 을 준비하지 못했거나 abandon) 다른 쪽을 머지하고, 실패한 쪽의 나쁜 건으로 센다.
- 머지하지 않은 PR 은 `gh pr close` 로 닫고, 그 worker 에게 「비교에서 다른 쪽을 머지해 닫았다. worker_done 을 보내고 끝낸다」 를 보낸다. 터미널과 워크트리는 [`cleanup.md`](cleanup.md) 대로 정리한다.

## 건마다 기록할 값

두 PR 이 머지되거나 닫힌 뒤 `<orch 루트>/state/routing-log.jsonl` 에서 PR 번호로 줄을 찾아 기록 표에 옮긴다. 리뷰 결과는 리뷰어의 worker_done 에서 옮긴다.

| 칸 | 출처 |
| --- | --- |
| 리뷰 P1·P2 | `first_review` 의 P1, P2 |
| 첫 CI | `ci_failures` 가 0 이면 통과, 아니면 실패 |
| 리뷰 뒤 고친 커밋 | `fix_commits_after_review` |
| 막힘·재시도 | `escalations` 와 `retry_of` 가 있는 dispatch 수 |
| 준비까지 분 | `minutes_to_ready` |
| 토큰 | `tokens` 를 [`agent-selection.md`](agent-selection.md) 「실측 기록」 의 집계와 같은 가격으로 바꾼 값 |
| 숨긴 리뷰 | 두 리뷰어의 선택과 순서 파일로 푼 결과(지금, 후보, 갈림) |

**나쁜 건**은 후보가 리뷰 P1·P2, 첫 CI 실패, 리뷰 뒤 고친 커밋, 막힘, 재시도 가운데 하나라도 지금 모델보다 많은 건이다. 실패한 쪽도 나쁜 건이다.

## 5건 뒤 판단

순서대로 본다. 앞 관문을 넘지 못하면 「지금 모델 유지」 다.

1. 문제: 후보의 나쁜 건이 5건 중 1건 이하다.
2. 시간: 후보의 준비까지 분의 중앙값이 지금 모델의 1.5배 이하다. 숨긴 리뷰에서 후보가 3건 이상 이겼으면 2배 이하다.
3. 비용: 후보의 토큰 비용 합이 낮거나 같으면 「후보로 바꿈」 이다. 후보가 비싸면 숨긴 리뷰에서 3건 이상 이겼을 때만 「후보로 바꿈」 이다.

판단과 근거를 기록 절의 「판단」 에 적는다.

## 표 바꾸기

- 「후보로 바꿈」 이면 기록 절을 미리보기로 `orch board approval add <비교 id> --title "모델 표 바꾸기 <모델> <행>" --kind spec --preview <미리보기> --then "모델 표를 바꾸는 worker 를 띄운다"` 로 승인 대기를 올린다. 승인 처리는 [`replying.md`](replying.md) 「보드 승인」 을 따른다.
- 승인되면 [`agent-selection.md`](agent-selection.md) 「모델」 표의 그 행을 바꾸는 worker 를 띄운다. 행 `simple-apply` 의 작은 문서 수정이다.
- 거절이나 「지금 모델 유지」 면 기록 절에 결과만 남긴다. 표는 바꾸지 않는다.
