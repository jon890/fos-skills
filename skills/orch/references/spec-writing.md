# 2. 지시서 쓰기

**지시 본문은 대상 저장소의 git 이 무시하는 폴더에 쓰고, `--spec` 에는 그 경로만 준다.** `--spec` 에 들어갈 한 줄은 `spec-line` 이 만든다([`launch.md`](launch.md) 의 `--spec` 절).
긴 지시는 앞부분도 중간도 잘려 도착한다.
지시서에 적지 않은 일이 빠진 채 완료로 보고되는 것을 막으려면 해야 할 일과 완료 기준을 지시서에 적는다. 후속 지시도 짧게 보내거나 새 파일로 준다.

지시서 폴더의 기본은 `<repo>/.orch/specs/` 다(`orch paths specs`). 오버레이가 다른 폴더를 정하면 그것을 따른다.

- 파일 이름은 `spec-<worktree 이름>.md` 로 한다. 공통 지시서는 `spec-common.md` 다. `orch cleanup sweep` 이 지시서 폴더(`--specs-dir`)에서 이 이름과, 지시서의 `브랜치:` 줄이 가리키는 머지된 브랜치를 보고 머지 뒤 지시서를 지운다. 후속 지시서처럼 이름이 워크트리와 달라도 `브랜치:` 줄이 있으면 지워진다. 그 줄이 없는 지시서는 이름이 워크트리 이름과 같아야 지워진다.
- 폴더는 `orch paths --ensure specs` 로 만든다. 만들면서 `.orch/` 를 로컬 전용 `.git/info/exclude` 에 더해 git 이 무시하게 한다. 다른 폴더를 쓰면 `git -C "$REPO" check-ignore -q` 로 무시되는지 본다.
- scratchpad 에 쓰지 않는다. **실측으로** 코디네이터 세션이 다시 시작되면서 scratchpad 가 정리돼 전날 쓴 지시서가 사라졌다. worker 는 받은 경로를 계속 읽으므로, 도중에 사라지면 읽을 곳을 잃는다.

**개별 지시서의 첫 줄은 `# <업무 목적 한 문장>` 이다.** `launch-worker` 가 이 줄을 보드 항목 제목으로 쓴다.
고르는 순서와 업무 연결 줄의 꼴은 `lib/board.ts` 의 `specTitle` 이 소유하고, `spec-lint` 가 제목 줄도 `보드 항목 id:` 도 없는 지시서에 `제목` 경고를 낸다.

**worker 마다 같은 규칙은 공통 지시서 한 파일에 두고, 개별 지시서는 제목 줄 다음 줄에서 그 파일을 가리킨다.**
틀은 [`../templates/spec-common.md`](../templates/spec-common.md) 다. 저장소마다 한 번 복사해 `{{...}}` 를 채운다.
`<!-- orch-rule: ... -->` 표지는 지우지 않는다. `spec-lint` 가 이 표지와 표지가 붙은 항목의 본문으로 공통 지시서가 틀보다 낡았는지 본다. 틀의 그 항목이 바뀌면 저장소 사본도 옮겨야 경고가 사라진다.
`공통` 경고가 나면 `orch spec sync-common` 으로 항목별 diff 를 먼저 보고 `orch spec sync-common --apply` 로 반영한다.
기본 대상은 orch 지시서 폴더의 `spec-common.md` 이고, 다른 폴더는 `--specs-dir` 로 준다.
표지 없는 저장소 고유 항목은 바꾸지 않는다.
저장소가 일부러 바꾼 항목은 `<!-- orch-rule: 이름 keep -->` 로 표시한다.
동기화는 그 항목을 보존하고 lint 도 본문 경고를 내지 않는다.
다시 틀을 따르려면 `keep` 을 지운다.
틀의 `{{...}}` 에 저장소 값을 채운 항목은 그대로 둔다.
본문까지 낡아서 채운 값을 확정할 수 없거나, 빠진 항목에 자리표시자가 있으면 `SYNC-MANUAL` 로 남기고 종료 코드 1 을 낸다.
`--apply` 는 나머지 안전한 항목만 반영한다.
이 항목은 직접 맞춘다.
표지가 하위 항목에 있거나 교체 범위에 저장소의 하위 목록이 있으면 부모와 하위 규칙을 지키도록 `SYNC-MANUAL` 로 남긴다.
빠진 표지는 틀의 다음 표지 항목 앞에 넣고, 뒤에 있는 표지가 없으면 파일 끝에 넣는다.
`migration` 과 `adr` 은 `spec-lint` 와 같은 설정 조건으로 추가한다.
이미 있는 조건부 항목은 조건과 무관하게 비교한다.

**실행기 경로는 채우지 않는다.** `orch` 가 PATH 에 없으면 틀의 명령이 worker 세션의 `CLAUDE_CONFIG_DIR/plugins/installed_plugins.json` 에서 `fos-skills@fos-skills` 의 `installPath` 를 읽어 `bin/orch` 를 푼다. 캐시 폴더 이름은 해시라 `ls | tail -1` 이나 `ls -t` 로 고르면 설치되지 않은 번들을 집는다. 코디네이터가 그때의 캐시 경로를 박으면 번들이 갱신되거나 worker 가 다른 프로필에서 돌 때 옛 스크립트를 가리킨다. 저장소 체크아웃 경로도 박지 않는다. 그 체크아웃이 다른 브랜치에 있으면 main 과 다른 스크립트가 돈다.
같은 항목이 `user` 와 `project` 범위로 여러 개면 `user` 범위를 쓴다.
`{{DRAFT_PR_RULE}}` 는 오버레이가 draft 로 CI 를 미루는 저장소면 「PR 은 `gh pr create --draft` 로 연다. ready 로 바꾸는 것은 코디네이터가 한다」 이고, 아니면 그 줄을 지운다.
`{{DESIGN_DIR}}` 는 worker 가 `spec`, `technical-design` 으로 만든 요구사항·설계 문서를 둘 폴더다(예: `docs/<분야>/`). 두 스킬을 쓰게 하지 않으면 그 절을 지운다.
저장소 고유 규칙(검증 명령, 원격 접속, 비밀값)은 오버레이에 두고 공통 지시서가 가리키게 한다.

## 넣을 것

- 브랜치 이름을 `` 브랜치: `feature/x` `` 형식의 줄로 적는다. 백틱 안이 이름이고, 같은 줄에 다른 말이 있어도 된다.
  `make-worktree` 가 이 줄을 읽어 워크트리를 만들고, 6단계가 push 한 원격 브랜치를 이 값과 대조한다.
  예전에 머지된 PR 의 브랜치 이름은 다시 쓰지 않는다. 스크립트가 원격에 남은 같은 이름은 거부하지만, 지워진 옛 이름은 알지 못한다
- 다른 PR 의 배포 뒤에 머지할 PR 처럼 루프가 자동으로 머지하면 안 되는 지시서에는 `- 머지 보류: <이유>` 줄을 넣는다
- DB 마이그레이션 번호 예약 규칙은 공통 지시서 틀의 `migration` 표지 항목이 소유한다. Flyway 마이그레이션이 있는 저장소의 공통 지시서에 그 항목을 그대로 옮긴다.
  worker 가 번호를 직접 정하면 다른 worktree 의 파일과 번호가 겹친다. orch 설정에 `migrations` 가 있는데 항목이 없으면 `spec-lint` 가 `공통` 경고를 낸다
- ADR 번호 예약 규칙은 공통 지시서 틀의 `adr` 표지 항목이 소유한다. orch 설정에 `adr.dirs` 를 둔 저장소의 공통 지시서에 그 항목을 그대로 옮긴다.
  병렬 PR 이 같은 폴더에 같은 ADR 번호를 고르면 INDEX 충돌과 번호 인용 수정이 뒤따른다. `adr.dirs` 가 있는데 항목이 없으면 `spec-lint` 가 `공통` 경고를 낸다
- `## 할 일` 제목을 두고 그 아래 첫 줄에 기능 루프를 쓰는지 적는다. 모든 개별 지시서에 필수이고, 지침만으로는 바쁠 때 건너뛰어 `spec-lint` 가 `루프` 발견으로 막는다.
  꼴과 예, 고르는 기준, 예외는 [`feature-loop.md`](feature-loop.md) 의 「루프를 쓸지 정한다」 가, 판정 규칙은 `spec-lint.ts` 머리 주석의 「루프」 가 소유한다
- 담당 범위, 기대하는 이득, 선행 결과, 결정하지 못한 사항
- Ownership 에 「구현이 docs 계약과 달라지면 같은 커밋에서 그 절을 고친다. 고치기 전에 ask 로 알린다」.
  docs 를 범위에서 빼면 구현 중 계약이 바뀔 때마다 worker 가 docs 검사에 걸려 `ask` 로 멈춘다
- 승인이 필요한 작업이면 「발견 목록을 먼저 내고 멈춘다」.
  그 회신이 `worker_done` 으로 바로 오면 절차 위반으로 본다
- 사용자가 허락한 외부 동작을 `허락:` 으로 시작하는 줄에 적는다. PR 을 열게 하는지와 관계없이 모든 지시서에 필수다.
  `launch-worker` 가 이 줄이 없으면 거부한다. 예: 「허락: push 와 draft PR 생성(base main)은 사용자가 허락했다.」
  허락한 것이 없으면 「허락: 없음. push 까지만 한다.」 를 적는다.
  codex worker 의 기본 지침은 GitHub 게시를 막아, 지시서에 「PR 을 연다」 만 있으면 승인을 다시 묻는다.
  `spec-line` 이 이 줄을 `--spec` 의 첫 지시 줄에 붙인다
- 고른 worker 를 `worker 선택:` 으로 시작하는 줄 하나에 적는다. 모든 개별 지시서에 필수다.
  형식은 「worker 선택: `<에이전트>` `<모델>` effort `<effort>`. 행: <id>. [high 근거: ….] 비교: <다른 후보>. 이유: <고른 이유>.」 다.
  `행:` 은 모든 새 지시서에 모델 표의 id 를 적는다. `high 근거:` 는 `agent-selection.md` 「Opus `high`」 가 요구할 때만 적고, 꼴은 「high 근거: medium 실패 <dispatch id>」 나 「high 근거: 사용자 지정 YYYY-MM-DD」 다. effort 를 지정하지 않는 행(Haiku)은 effort 를 `기본` 으로 적는다.
  예: 「worker 선택: `codex` `gpt-6.1-sol` effort `low`. 행: impl-planned. 비교: Claude Sonnet 5.5. 이유: 계획서가 수정 위치를 정했고 CI 리뷰가 Claude 라 제공자를 나눈다.」
  후보와 고르는 규칙은 [`agent-selection.md`](agent-selection.md) 가 소유한다. 비교 없이 익숙한 제공자로 기우는 것을 막으려고 줄을 강제한다.
  `선택` 발견과 거부 조건은 `spec-lint.ts` 와 `launch-worker.ts` 머리 주석이 소유한다. `--lint-ack` 으로 넘기지 못한다.
- 비교 실험은 다음처럼 `experiment:` 줄 하나를 더한다. 후보는 `/` 로 나누며 둘 이상이고 중복 없이 agent, model, effort 를 적는다. `worker 선택:` 은 후보 중 하나여야 한다.

  ```text
  experiment: review-fix-small. 후보: `claude` `claude-sonnet-5-5` effort `medium` / `codex` `gpt-6.1-sol` effort `medium`.
  ```

  배정 규칙은 `launch-worker.ts` 머리 주석이 소유한다. 실험 후보인 Opus 높은 effort 는 별도 high 근거 없이 허용한다.
- PR 을 열게 하면 「PR 본문 파일은 worker 세션 임시 폴더(scratchpad, 없으면 `$TMPDIR`)에 쓰고 PR 이 열릴 때까지 지우지 않는다. 경로는 status 나 `worker_done` 에 적는다」 도 적는다. 권한 거부로 worker 가 PR 을 못 열면 코디네이터가 그 경로의 파일로 연다. 저장소의 `.orch/` 에는 두지 않는다
- PR 을 열게 하면 「PR 은 기준 브랜치를 base 로 따로 연다. 다른 PR 브랜치를 base 로 두지 않는다」 도 적는다.
  앞 PR 브랜치를 base 로 연 PR 은 앞 PR 을 `--delete-branch` 로 머지하면 자동으로 닫히거나 앞 브랜치로 머지된다
- 지시서 하나는 PR 하나로 쓴다([`SKILL.md`](../SKILL.md) 원칙). 설계 문서만 따로 PR 로 올리지 않고 설계와 구현을 한 PR 에 담는다(사용자 결정 2026-10-26). PR 이 둘 이상 필요한 일은 지시서를 나누고, 뒤 지시서는 앞 PR 이 머지된 뒤 쓴다.
  **완료 기준은 PR 하나의 MERGED 다.** 계획이 PR 여럿이면 지시서에 「이 지시서는 PR1 만 맡는다. 뒤 PR 은 코디네이터가 새 지시서로 띄운다」 와 뒤 PR 목록(참고)을 `## 완료 기준` 밖의 참고 절에 적는다. 완료 기준에 PR 둘 이상을 적으면 `spec-lint` 가 `완료` 경고를 낸다. worker 하나가 PR 여럿을 이어 맡으면 머지 알림과 완료 기준이 어긋나 worker 가 멈춘다
- 소계획으로 나누는 일을 맡기면 「worker 를 띄우지 않는다. 소계획마다 `ready:` status 메시지를 보낸다」 와 그 형식을 적는다.
  worker 는 다시 worker 를 띄우지 못한다(`nested_worker_depth_exceeded`)
- CI 고침, 리뷰 반영, 충돌 해결처럼 기존 PR 을 마무리하는 지시서에는 `중간 과정: PR #N` 줄을 첫 `##` 제목 앞, 브랜치 줄 근처에 넣는다.
  `launch-worker` 는 첫 `##` 제목 앞에서만 이 줄을 찾는다. 할 일 본문에 같은 글이 인용돼도 중간 과정으로 읽지 않게 하려는 것이다.
  `launch-worker` 가 이 줄을 보고 보드 항목을 새로 만들지 않고, 그 PR 의 기존 항목에 줄 하나만 남긴다([`board.md`](board.md) 의 「갱신 담당」).
  빠뜨리면 같은 워크트리의 항목을 이어 쓰거나 새 항목을 만들어, 한 PR 의 중간 과정이 마일스톤 항목처럼 보드에 쌓인다
- 보드 항목의 단계는 「할 일」 이 아니라 저장소의 마일스톤 단계(`board.steps`, 없으면 PR, 머지)다. 이 일만 다른 단계가 필요하면 `## 보드 단계` 절에 꼬리표 붙은 번호 줄을 적는다.
  꼬리표와 우선순위는 [`board.md`](board.md) 의 「마일스톤 단계」 가 소유한다. 「할 일」 은 worker 가 읽는 구현 세부라 보드에 올리지 않는다
- PR 은 머지될 때까지 만든 worker 가 맡는다. 충돌과 CI 실패도 그 worker 가 풀고 코디네이터는 worker 브랜치에서 직접 풀지 않는다([`replying.md`](replying.md) 의 「충돌과 리뷰 반영은 만든 worker 가 이어 받는다」 가 정한다). 지시서 크기는 `plan` 의 plan 크기 기준을 따른다

**기술 판단과 사용자 판단을 나눠 적는다.**
파일 위치, 테스트 방식, 리뷰 하위 등급 반영 여부처럼 되돌리기 쉬운 기술 판단은 묻지 않고 권장안으로 진행하게 하고, 고른 안을 status 와 PR 본문 「결정」 절에 남기게 한다.
외부 계약 변경, 팀 결정을 뒤집는 것, 외부에 보이는 글, 공유 서버나 DB 쓰기, 비용이 드는 작업, 범위를 넘는 변경, 데이터 삭제만 ask 로 묻게 한다.
나누지 않으면 worker 가 사소한 것마다 묻고 멈추거나, 사용자가 정할 것을 스스로 정한다.

**같은 파일이나 화면, 문서를 고치는 일은 동시에 맡기지 않는다.** 먼저 머지된 쪽 때문에 뒤 PR 이 충돌하고, 충돌을 합치다 다시 깨진다.
겹치는 일은 앞 PR 이 머지된 뒤 그 위에서 시작하게 지시서에 적는다.

## 띄우기 전 검사

**지시서를 다 쓰면 띄우기 전에 `spec-lint` 로 한 번에 검사한다.** 이번에 띄울 지시서를 모두 넘긴다. 공통 지시서는 넘기지 않는다.
지시서끼리 담당 파일이 겹치거나, 가리킨 함수가 없거나, 금지 명령을 요구하는 것을 띄운 뒤에 알면 worker 가 ask 로 멈추거나 뒤 PR 이 충돌한다.

```bash
orch spec lint --check-overlay "$SPECS_DIR"/spec-a.md "$SPECS_DIR"/spec-b.md
```

`launch-worker` 도 띄우기 전에 같은 검사를 한 번 더 한다(차례는 `launch-worker.ts` 머리 주석이 소유한다). 아직 띄우지 않은 지시서끼리의 겹침은 이 단계의 한 번에 검사하는 호출이 잡는다.
종료 코드 1 이면 발견 줄을 보고 지시서를 고친다. `루프` 발견이면 스펙을 확인받거나, `스펙: 새로 쓴다` 로 spec 단계부터 맡기거나, 루프를 쓰지 않을 일이면 `루프 없이: <이유>` 로 고친다. 의도한 겹침이면 `launch-worker --lint-ack "<이유>"` 로 넘기고, 이유는 worker 기록에 남는다. `경로` 경고는 새로 만들 파일이면 그대로 둔다.
**`공통` 경고가 나오면 저장소 공통 지시서가 틀보다 낡았다.** 표지가 빠졌다는 경고면 틀에서 그 `<!-- orch-rule: ... -->` 표지가 붙은 항목을 옮기고, 규칙이 틀과 다르다는 경고면 그 줄 번호의 항목을 틀의 항목으로 바꾼 뒤 띄운다. 저장소가 그 규칙을 일부러 바꿨으면 경고를 그대로 둔다.
**`임시` 경고는 지시서가 임시 폴더의 파일을 가리킨다는 뜻이다.** 필요한 내용을 지시서 본문에 옮기거나 저장소나 orch 폴더에 둔다. **`완료` 경고는** 지시서를 PR1 만 맡게 줄이고 뒤 PR 은 참고 절로 옮긴다. 두 경고 모두 종료 코드에는 넣지 않는다.
`오버레이` 발견은 오버레이나 `.orch/config.json` 이 `origin/<기준 브랜치>` 에 없는 파일을 가리킨다는 뜻이라 그 파일을 고친다. 기준 브랜치가 main 이 아니면 `--base` 로 준다.
담당 범위는 지시서에 `` 담당: `src/a/**`, `docs/a.md` `` 줄로 적는다. 그 줄이 없으면 겹침 검사가 그 지시서를 건너뛴다.
금지 문구가 든 줄이 정말 필요하면 그 줄을 `예외:` 로 시작한다.
코디네이터 소유 경로, 소유 계약, 저장소의 금지 문구는 오버레이의 `## spec-lint` 절에 둔다. 형식은 스크립트 머리 주석이 소유한다.

## 리뷰 worker 지시서

남의 PR 을 읽고 리뷰만 쓰는 worker 의 지시서에는 아래 두 줄을 첫 `##` 제목 앞에 둔다.

```markdown
리뷰 PR: #1137
브랜치: `review/pr-1137`
```

**`launch-worker` 가 `리뷰 PR:` 줄을 보고 PR head 를 받아 워크트리를 그 커밋에 detached 로 둔다.** 받는 일은 코디네이터 쪽 `launch-worker` 프로세스가 주 checkout 에서 하고, 받을 때 쓴 임시 ref 는 바로 지운다. 워크트리를 만들 때 `브랜치:` 줄의 `review/pr-<N>` 로컬 브랜치가 생기고, 정리가 지운다.
지시서에는 「worker 는 fetch 하지 않고 준비된 HEAD 를 리뷰한다. 브랜치를 만들거나 `git fetch origin pull/N/head` 를 부르지 않는다」 를 적는다.
worker 의 fetch 는 SSH 별칭 원격에서 인증으로 막히고, worker 가 만든 `pr-N` 브랜치는 정리가 PR 로 찾지 못해 쌓인다.
PR head 를 받지 못해 멈추면 원인을 고친 뒤 같은 지시서로 `--worktree` 를 주어 다시 띄운다. 그때 다시 받아 옮긴다. 이미 PR head 에 놓인 워크트리면 준비 명령을 다시 돌리지 않는다.
파일 이름은 `spec-review-pr-<N>.md` 로 하고, 같은 PR 을 다시 리뷰하면 `spec-review-pr-<N>-<꼬리>.md` 와 `review/pr-<N>-<꼬리>` 로 쓴다.

**생성물이 있어야 테스트가 도는 저장소는 `config.json` 의 `review.prepare` 에 준비 명령을 둔다.** `launch-worker` 가 PR head 를 꺼낸 뒤 그 워크트리에서 한 번 돌리고 `REVIEW-PREPARE <종료 코드>` 를 낸다.
명령은 저장소마다 달라 스킬은 자리만 둔다. 무거운 생성이면 명령 안에서 `heavy-slot` 으로 감싼다. 감싸는 방법은 [`overlay.md`](overlay.md) 의 「저장소 스크립트에서 orch 부르기」 를 따른다.
준비가 실패해도 worker 는 뜬다. 코디네이터는 0 이 아니면 지시서나 후속 지시로 「생성물이 없어 서비스 테스트는 돌지 않는다」 를 알린다.

**리뷰가 끝난 뒤의 정리는 스크립트가 한다.** 리뷰 워크트리는 `orch cleanup worktree --delete-branch` 로 지운다. detached 워크트리여도 그것을 만든 `review/pr-<N>` 을 함께 지운다.
남은 리뷰 워크트리, 리뷰 브랜치와 리뷰 지시서는 `cleanup-sweep` 이 지운다. 지우는 조건은 스크립트 머리 주석의 「리뷰 흔적」 이 소유한다.

## 스킬 개선 후보를 모으게 할 때

worker 가 스킬을 쓰다 막힌 곳을 모으게 하려면 공통 지시서 틀의 「스킬 개선 후보 보고」 절을 남긴다. 그 절의 표지가 빠지면 `spec-lint` 가 `공통` 경고를 낸다.
후보는 worker 가 아니라 코디네이터가 사용자와 정한 뒤 반영한다. worker 가 스킬 파일을 직접 고치면 같은 스킬을 쓰는 다른 worker 의 절차가 도중에 바뀐다.
쌓인 후보를 다시 보는 주기와 판정 기준은 [`feedback-review.md`](feedback-review.md) 가 소유한다.

worker 가 판단을 정한 일반 기술 개념을 공부 후보로 적게 하려면 「공부 후보 보고」 절을 남긴다. 표지가 빠지면 같은 `공통` 경고가 난다. 후보 기준과 글로 잇는 법은 [`study-candidates.md`](study-candidates.md) 가 소유한다.
