# spec

**목표: 기능 하나의 제품 결정이 닫히고 사용자가 확인한 스펙이 남아, technical-design 이 구조와 책임을 설계할 수 있다.**

먼저 [기능 문서와 단계 인계](references/feature-docs.md)를 읽는다.
대상 저장소 지침과 `.claude/spec-overlay.md` 를 읽고, docs 경로는 [plan 의 탐색 규칙](../plan/references/monorepo.md)을 따른다.

- **묻기 전에 읽는다.** 코드와 문서로 답할 수 있는 것은 묻지 않는다. 이미 정한 것을 다시 묻지 않는다.
- **정했다고 넘기지 않는다.** 사용자 동작, 권한, 데이터 보존, 호환, 운영에 닿는 결정은 작성자가 답을 알아도 사용자에게 확인받는다.
- **사용자가 확인하기 전에는 기술 설계·계획·구현을 시작하지 않는다.**

## 워크플로우 개요

| 단계 | 이름 | 통과 조건 | reference |
| --- | --- | --- | --- |
| 1 | 탐색 | 관련 코드, 기존 스펙, 공유 계약, 도메인 문서, ADR 을 읽었고 근거 경로를 적었다 | |
| 2 | 결정 목록 | 점검 축마다 결정 또는 「해당 없음과 이유」 가 결정 표 초안에 있다. 도메인 규칙을 바꾸면 변경할 규칙과 확정 상태가, 바꾸지 않으면 그 사실이 스펙에 있다 | [`interview.md`](references/interview.md) |
| 3 | 질문 라운드 | 결정 표에서 「누가」 가 `사용자` 인 행이 모두 답을 받았다 | [`interview.md`](references/interview.md) |
| 4 | 모호함 0 판정 | `check_feature.py --draft` 와 `run_doc_checks.py` 종료 코드가 0 이고, 독립 검토자의 발견이 모두 결정 표에 반영됐다 | [`interview.md`](references/interview.md) |
| 5 | 사용자 확인 | 사용자가 스펙을 확인했고 스펙 머리에 `확인: YYYY-MM-DD` 줄이 있다. `check_feature.py` 와 `run_doc_checks.py` 종료 코드가 0 이다 | |

3~4 에서 새 결정이 나오면 결정 표에 더하고 3으로 돌아간다.
확인 뒤 plan·verify 가 새 사용자 결정을 찾아 되돌려 보내면, 그 결정만 3부터 다시 돌고 확인을 다시 받는다.

작성 전에 [스펙 양식](templates/spec.md)을 읽는다. 양식의 예시는 실제 사용자 결정·확인 날짜가 아니다.
PRD 가 필요하고 기존 양식이 없을 때만 [제품 요구사항 양식](templates/product-requirements.md)을 쓴다.
문서별 책임은 [문서 소유권](references/document-ownership.md)을 따른다.

## 1. 탐색

이번 기능이 닿는 코드와 문서를 읽는다. 기능의 목표를 사용자 말로 한 문장 적는다.
여러 기능이 섞여 있으면 나누고 지금 구현할 기능만 상세화한다.

## 2. 결정 목록

[인터뷰 절차](references/interview.md)의 점검 축으로 결정 표를 만든다.
결정마다 `사용자` 가 정할지 `작성자` 가 근거를 남기고 정할지 나눈다. 나누는 기준은 같은 문서가 정한다.
여러 기능이 참조하는 도메인 규칙은 기존 규칙을 RULE ID 로 참조하고, 바꿀 규칙은 스펙의 「도메인 규칙 변경」 표에 적는다. 원본은 [문서 소유권의 「단계별 책임」](references/document-ownership.md#단계별-책임)이다.

## 3. 질문 라운드

첫 라운드는 요청을 되짚고 목표와 범위의 빈칸을 열린 질문으로 묻는다.
다음 라운드부터는 결정을 한 번에 최대 4개씩, 선택지와 영향, 권장과 이유를 붙여 묻는다.
질문 형식, 라운드 상한, 「그만 묻고 진행」 출구는 [인터뷰 절차](references/interview.md)가 정한다.

**사용자에게 직접 묻지 못하는 세션(orch worker)이면** 같은 문서의 「직접 묻지 못할 때」 를 따른다.

## 4. 모호함 0 판정

요구사항과 인수 조건을 쓰고 결정 표를 스펙의 `## 결정` 절에 둔다. 템플릿은 [기능 문서](references/feature-docs.md#스펙-템플릿)에 있다.
그다음 아래 검사를 돌리고, 대화를 모르는 독립 검토자에게 스펙을 읽힌다. 검토자에게 줄 지시는 [인터뷰 절차](references/interview.md)의 「독립 검토자 검사」 에 있다.

`$PLAN_SKILL_DIR` 은 이 번들의 형제 `plan` 디렉터리다. cwd 는 대상 저장소 루트이고 `$SPEC` 은 그 루트 기준 상대경로다.

```bash
python3 "$PLAN_SKILL_DIR/scripts/check_feature.py" "$SPEC" --draft
python3 "$PLAN_SKILL_DIR/scripts/run_doc_checks.py" --skill spec "$SPEC"
```

`--draft` 는 확인 줄을 요구하지 않는다. 이 검사는 형식만 보고 의미 검토와 사용자 합의를 대신하지 않는다.
`run_doc_checks.py` 는 레포 설정의 「문서 검사 명령」(예: ADR 링크 규칙을 보는 저장소 문서 검사)을 돌린다. 값이 없으면 건너뛰고 0 으로 끝난다.
저장소 문서 검사를 이 단계에서 돌리지 않으면 구현 phase 커밋에서야 걸려 문서 수정이 구현 커밋에 섞인다.

## 5. 사용자 확인

스펙 경로와 함께 목표, 범위 밖, 요구사항 표, 결정 표를 메시지 본문에 그대로 보이고 확인을 받는다.
도구 출력은 화면에서 접혀 사용자가 못 볼 수 있어 본문에 싣는다.
고칠 점이 나오면 고치고 다시 보인다. 확인을 받으면 스펙 제목 아래 `확인: YYYY-MM-DD` 줄을 적고 `--draft` 없이 검사한다.

```bash
python3 "$PLAN_SKILL_DIR/scripts/check_feature.py" "$SPEC"
python3 "$PLAN_SKILL_DIR/scripts/run_doc_checks.py" --skill spec "$SPEC"
```

스펙 경로와 결정 요약을 technical-design 이나 orch 에 넘긴다. 구현은 시작하지 않는다.

## 완료 기준

결정 표가 모두 닫혔고, 요구사항마다 관측할 인수 조건이 있으며, 사용자가 확인한 날짜가 스펙에 있다.
그렇지 않으면 남은 결정과 이유를 보고한다. 모든 예외를 미리 설계하려고 범위를 넓히지 않는다.
