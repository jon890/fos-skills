# 기능 문서와 단계 인계

## 문서 소유권

docs 경로는 [planning 의 탐색 규칙](../../planning/references/monorepo.md)과 프로젝트 오버레이를 따른다.
기본은 `docs/features/<feature-id>/spec.md` 다. 기능 ID 는 내용이 드러나는 슬러그로 정하고 기존 경로와 겹치지 않는지 확인한다.
전역 순번과 수동 기능 색인을 만들지 않는다. 기존 기능을 바꾸면 새 사본 대신 그 스펙을 수정한다.

- `spec.md`: 목표, 범위, R1 같은 기능 내부 요구사항 ID, 관측 가능한 인수 조건, 필요한 설계, 미결정.
- `design.md`: 설계가 길어졌을 때만 분리한다. 스펙에서 상대 링크로 참조한다.
- `docs/contracts/`: 둘 이상의 기능이 실제로 공유하는 계약. 기능 문서는 링크로 참조한다.
- 기존 API 스키마, 마이그레이션, ADR: 각 원본이 소유한다. 필드 전체를 기능 문서에 복제하지 않는다.
- `tasks/<plan>/`: PR 하나의 임시 실행 계획. 지속할 계약을 여기에만 두지 않는다.
- 검증 결과와 공통 후보: PR 본문 또는 그 PR 의 증거 파일. 모든 worker 가 중앙 진행표를 수정하지 않는다.

기존 전역 문서를 일괄 이동하지 않는다. 이번 기능이 바꾸는 부분만 책임 문서로 옮기고 원래 자리는 링크로 바꾼다.
별도 계약이 없는 새 기능은 전역 flow/data-schema/code-architecture 를 함께 수정할 필요가 없다.
공유 권한이나 상태 의미가 구현을 좌우하면 스펙 단계에서 먼저 합의한다. 공통화 후보로 미루지 않는다.

## 스펙 템플릿

```markdown
# 작업 취소

## 목표
소유자가 실행을 취소할 수 있다.

## 범위
이번 범위와 범위 밖의 동작.

## 요구사항과 인수 조건
| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| R1 | 소유자만 취소할 수 있다 | 타 사용자의 요청은 거부되고 실행 상태가 바뀌지 않는다 |
| R2 | 반복 요청은 안전하다 | 반복해도 취소 부작용이 중복되지 않는다 |

## 설계
필요한 API, 데이터/상태, 실패 동작, 테스트 방법을 요구사항 ID 에 연결한다.
공유 계약과 정확한 스키마의 원본은 링크로 참조한다. 해당하지 않는 설계는 이유만 적는다.

## 미결정
없음
```

`미결정` 이 없다는 선언만으로 설계가 완전하다고 보지 않는다. 스펙 작성자가 코드와 사용자 의도를 대조한다.
기존 관례로 정할 내부 이름과 배치는 작성자가 정한다. 사용자 동작, 권한, 데이터 보존이나 호환성을 바꿀 결정만 묻는다.
스펙은 구현 전에는 합의한 목표다. 완료 보고는 인수 검증 뒤에만 하며 진행 로그를 스펙에 계속 덧붙이지 않는다.

## 인계

| 단계 | 전달하는 것 | 다음으로 가는 기준 |
| --- | --- | --- |
| spec | 스펙 경로, 해결한 결정 | 구현 결과를 바꿀 미결정이 없고 요구사항마다 인수 조건과 검증 방법이 있다 |
| planning | 스펙 경로, plan, 이번 PR 의 요구사항 ID | 실행 가능한 작업과 검사 명령이 있고 계획 검토를 통과했다 |
| build-with-teams | 작업 공간, 기준/검증 커밋, plan, 변경 파일, 개발 검증 결과 | 담당 구현과 개발 검증이 끝났다. 기능 완료 선언은 하지 않는다 |
| verify | 같은 변경에 대한 인수 조건별 증거, 코드/문서 검토 결과 | 이번 PR 의 필수 조건을 확인했고 완료를 막는 발견과 필수 미검증이 없다 |
| docs-consolidate | 이번 기능의 문서 대조 결과, 공통 후보 또는 없음 | 문서가 구현과 맞고 후보가 근거와 함께 남았다. 공통화는 필요할 때 별도 작업으로 한다 |

각 단계는 `완료: <산출물과 증거>` 또는 `미완료: <이유와 돌아갈 단계>` 로 회신한다.
명령 실행 실패와 환경 부재를 통과로 보고하지 않는다. 별도 상태 머신이나 자동 재시도 정책은 두지 않는다.

기능이 여러 PR 이면 이번 PR 의 요구사항만 검증하고 전체 완료와 구분한다.
orch 는 모든 요구사항의 인수 증거와 남은 원격 검증을 모아 기능 완료를 판단한다.
같은 요구사항을 여러 PR 이 나눠 구현하면 각 PR 의 부분 증거와 마지막 통합 증거를 구분한다.

- Superpowers: 스펙과 구현 계획을 나누고 각 작업을 검증 가능한 결과로 자른다. https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md
- gstack: 설계의 테스트 계획을 실제 API/브라우저/작업 검증으로 이어 간다. https://github.com/garrytan/gstack/blob/main/docs/skills.md
