# spec

**목표: 기능 하나를 구현하고 검증할 수 있도록 필요한 의사결정을 끝낸다.**

먼저 [기능 문서와 단계 인계](references/feature-docs.md)를 읽는다.
대상 저장소 지침과 `.claude/spec-overlay.md` 를 읽고, docs 경로는 [planning 의 탐색 규칙](../planning/references/monorepo.md)을 따른다.
기존 코드와 관련 스펙·공유 계약을 먼저 읽는다. 이미 정한 것을 다시 묻지 않는다.

## 절차

1. 기능의 목표와 범위, 관측 가능한 인수 조건을 요구사항 ID 로 정리한다.
2. 이번 기능에 필요한 API·데이터·상태·실패 동작과 테스트 방법을 함께 설계한다. 기존 스키마와 공통 규칙은 링크한다.
3. 사용자 의도에 따라 결과가 달라지는 결정만 묻고 닫는다. 코드에서 정할 수 있는 내부 구현은 합리적인 선택과 근거를 남긴다.
4. 기능 폴더에 스펙을 쓰고 사용자 요청과 대조한다. 여러 기능이면 나누되 지금 구현할 기능만 상세화한다.
5. 아래 형식 검사를 실행하고 스펙 경로와 결정 요약을 orch 에 넘긴다.

`$PLANNING_SKILL_DIR` 은 이 번들의 형제 `planning` 디렉터리다. cwd 는 대상 저장소 루트다.

```bash
python3 "$PLANNING_SKILL_DIR/scripts/check_feature.py" "$SPEC"
```

이 검사는 형식과 연결만 본다. 의미 검토와 사용자 결정 완료를 대신하지 않는다.
합의한 스펙은 planning 으로 넘기고 구현은 시작하지 않는다.

## 완료 기준

범위와 인수 조건이 명확하고 필요한 설계·검증 방법이 있으며, 구현 결과를 바꿀 미결정이 없다.
그렇지 않으면 남은 결정과 이유를 보고한다. 모든 예외를 미리 설계하려고 범위를 넓히지 않는다.
