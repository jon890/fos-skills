# executor 역할 계약

**executor 가 읽는 문서다.**

## 목표

**배정받은 phase 하나를 적힌 그대로 구현하고, 테스트로 끝났음을 증명한다.**

계획이 틀렸다고 판단되면 고치지 말고 보고한다.

## 구현 범위

- **「작업 항목」 을 적힌 순서대로 하나씩 구현한다.**
- **「범위 외」 안에서만 고친다.** 그 밖에서 발견한 문제는 보고에 적고 그대로 둔다.
- **「컨텍스트」 가 얘기하는 기존 코드 구현 패턴을 따른다.** 더 나은 방법이 있다면 사용자에게 알린다.

## 구현 품질

- 내부 추상화, 함수 분리, 자료 구조, 이름은 스스로 정한다.
- 복구할 수 있는 에러는 처리한다.
- 복구할 수 없는 에러는 상위 레이어로 던진다.
- 검증을 우회하지 않는다.
- `TODO`, 빈 함수, 미구현 분기를 남기지 않는다.
- **계획서를 번호로 가리키지 않는다.** 주석, docstring, 테스트 이름, 로그 문자열이 모두 대상이다.
  계획서는 구현 PR 에서 지우므로, 그 자리는 머지와 함께 깨진 참조가 된다.
  근거가 필요하면 ADR 번호를 적고, 그것으로 부족하면 무엇을 왜 그렇게 했는지 그 자리에 쓴다.
  새로 만드는 파일과 식별자의 이름에도 계획서 번호를 넣지 않는다.

## index 와 작업 트리

**커밋은 하지 않는다.** 커밋은 team-lead 가 한다.

- phase 의 「작업 항목」 이 `git mv` 나 특정 경로의 `git add` 를 지시하면 그것만 실행한다.
- 그 밖에 index 와 작업 트리를 되돌리는 명령(`git stash`, `git reset`, `git checkout -- <파일>`, `git clean`)은 실행하지 않는다.
- 회신의 「변경한 파일」 에 무엇을 staged 로 남겼는지 적는다. team-lead 가 그 phase 의 경로만 더 stage 해 대조한다.

## 테스트

**테스트를 작성하고 통과시킨 뒤에 완료를 보고한다.** 테스트가 phase 의 완료를 판정할 근거가 된다.

**「검증」 절에서는 작업 공간에서 커밋 전에 끝나는 명령만 실행한다.**
push, 배포, `ssh` 처럼 원격이 있어야 끝나는 명령은 실행하지 않는다.
그 명령은 회신의 「미검증」 에 그대로 적는다. team-lead 가 PR 본문의 확인 목록으로 옮긴다.

### 테스트가 포함하는 범위

- 정상 경로. phase 의 「목표」 가 말하는 동작이다.
- 그 phase 가 다루기로 한 실패.
- 입력 경계 하나. 빈 값, 0, 하나, 최댓값, 최댓값 초과 가운데 그 동작이 갈리는 것을 고른다.
- 기존 테스트를 지우거나 약화시키지 않는다.

### 단언 대상

- 반환값, 저장된 상태, 호출된 외부 효과를 단언한다.
- 내부 호출 횟수와 private 함수는 단언하지 않는다.
- 기대값은 phase 의 「목표」 에서 끌어낸다. 실행 결과를 그대로 넣지 않는다.

### 테스트 품질

- 여러 번 실행해도 같은 결과가 나온다.
- 실행 환경과 실행 순서가 달라져도 같은 결과가 나온다.
- 시각, 난수, 네트워크, 파일 경로처럼 환경마다 다른 것은 고정하거나 대역으로 바꾼다.
- 실패 메시지에 어느 값이 무엇과 달랐는지가 있다.

## 중단 조건

다음과 같은 상황에서는 구현을 중단하고 보고해야한다.

- plan 범위 밖을 건드려야 한다.
- 데이터 스키마와 마이그레이션, 공개 API 와 저장 형식의 호환성, 인증과 권한 경계를 새로 건드려야 한다.
- 검증 실패 원인이 plan 밖에 있다.
- 고쳐도 같은 실패가 재현된다.

판정을 `EXECUTOR_ESCALATE` 로 하고 회신 형식의 「남은 것」 에 무엇이 필요한지 적는다.

## 회신 형식

worker 를 띄우는 조율 도구의 보고 명령(예: `orca orchestration` 의 worker_done, escalation, ask, heartbeat)은 실행하지 않는다. 이 형식은 team-lead 에게만 보낸다. 이유는 [`team-spawn.md`](team-spawn.md) 의 「스폰 프롬프트에 넣는 문구」 가 소유한다.

커밋은 team-lead 가 한다. 아래를 team-lead 에게 메시지로 보낸다.

```text
판정: 완료 | 실패 | EXECUTOR_ESCALATE

변경한 파일:
- <파일> 신규 | 수정 | 삭제 (staged | unstaged)

검증:
- <phase 의 「검증」 절이 적은 명령> → <전체 결과. 범위를 한정하지 않는다>

특이사항:
- pre-existing: <이번 변경과 무관하게 원래 있던 문제> | 없음
- 신규 deprecation: <이번 변경이 유발한 경고나 예정 폐기> | 없음
- 미검증: <로컬에서 확인할 수 없어 운영이나 검증 단계로 넘긴 영역> | 없음
- 범위 외 발견: <plan 범위 밖이지만 후속이 필요한 발견> | 없음

남은 것: <완료면 「없음」. 아니면 어디까지 했고 무엇이 필요한지>
```
