# 하네스 감사 축

각 축에서 발견한 항목은 파일 위치, 측정값, 실행 결과와 함께 판정표에 기록한다.
축마다 붙인 예는 찾을 모양을 보인다. 표면 형태보다 그 모양이 왜 문제인지를 현재 대상에 대입한다.

이 문서는 무엇을 찾을지를 소유한다.
찾은 것을 유지할지 지울지는 [`references/judgment.md`](judgment.md)가 소유한다.

## 소유권 중복

같은 지시가 여러 파일에 본문으로 존재하면 어느 문서가 소유자인지 확인한다.
링크나 짧은 포인터는 중복으로 보지 않는다.
독립적으로 수정될 수 있는 반복 문구는 정책이 갈라질 위험이 있다.

**소유자에는 실행 파일도 들어간다.** 스크립트의 docstring, `--help` 출력, 코드 주석이
사용법과 내부 동작을 소유한다. 산문이 그것을 다시 적었는지 본다.

- 예: `SKILL.md` 절차와 참조 파일에 같은 문구가 함께 있다.
- 예: 스크립트 docstring 이 가진 인자 기본값, 페이지 크기, 엔드포인트를 `SKILL.md` 가 다시 적는다.

**형제 스킬도 소유자다.** 어떤 단계가 다른 스킬을 부른다면 그 스킬의 절차와 함정은 그쪽이 소유한다.
부르는 쪽에는 넘길 값과 언제 부르는지만 둔다.

- 예: 게시 단계가 호출 대상 스킬의 게시 전 점검 항목과 인증 실패 복구 명령을 다시 적는다.

## 죽은 검출

검출 명령이 존재한다는 사실과 검출력이 살아 있다는 사실을 구분한다.
입력 경로와 작업 디렉터리를 먼저 검증하고 대조 표본으로 검출력을 확인한다.
이 과정이 없으면 0건이 거짓 통과가 될 수 있다.

**문서가 준 명령이 도는지도 같은 자리에서 본다.** 검출 명령만 보지 않는다.
실행 가능한 블록을 전부 돌리고, 상대경로가 어느 디렉터리를 전제하는지 함께 본다.

- 예: 리팩터링으로 내용이 다른 파일로 옮겨졌는데 검출 명령이 옛 진입점 파일을 계속 가리킨다.
- `git grep` 은 git 에 추가되기 전 파일을 보지 못한다. 새로 만든 파일을 대상으로 삼는 검사는 추적 상태를 함께 본다.
- 예: 셸 변수를 `export` 없이 두고 뒤따르는 스크립트가 환경 변수로 읽어, 그대로 실행하면 반드시 실패한다.

## 값 하드코딩

모델 식별자, 버전, 단계 범위, 개수, 목록처럼 다른 곳이 소유해야 할 값을 산문이 복제하는지 찾는다.
문서에는 값 자체보다 값을 읽을 경로와 판정 방법을 둔다.

- 예: 문서의 모델 식별자가 실제 설정과 다르다. 그 문서를 믿으면 잘못된 역량 기준으로 지시를 판정한다.
- 예: 같은 캐시 파일 목록이 여러 문서에 서로 다른 개수로 적혀 있다. 문서끼리 비교해서는 무엇이 옳은지 가릴 수 없다.

목록을 지우기 전에 그것이 유일한 출처인지 먼저 판정한다. 절차는 `judgment.md` 에 있다.

## 지시 충돌

같은 절차를 두 문서가 반대로 규정하는지 찾는다.
문서끼리 비교해서는 어느 쪽이 맞는지 정할 수 없으므로 실행 경로를 실측해 판정한다.

- 예: 한 문서는 검증 순서를 타입 검사 다음 린트로, 오버레이는 그 반대로 적는다. CI 설정의 단계 순서를 읽어 판정한다.
- 예: 역할 정의는 레이어 직접 참조를 금지하고 프로젝트 지침은 일부를 허용한다.

**한 문서 안도 본다.** 그 문서가 비용, 위험, 금지를 적어 둔 자리를 찾고,
같은 문서의 다른 절이 그것을 요구하는지 확인한다.
비용을 적어 둔 절이 그 비용을 쓰라고 시키는 자리가 대표적이다.

- 예: 조회 한 번의 비용이 크다고 적어 둔 단계가 연결 테스트로 같은 조회를 시킨다.

## 스킬 경계

형제 스킬 사이의 경계를 본다. 스킬 하나만 읽어서는 보이지 않는다.

- **정책 어긋남:** 같은 주제(PR 분할, 승인 기준, 정리 대상)를 두 스킬이 다르게 정했는지 찾는다.
  한쪽만 최근에 바뀌었으면 옛 쪽이 정책 잔존이다. 어느 쪽이 맞는지는 커밋 기록의 순서와 실행 경로로 판정한다.
- **트리거 겹침:** 두 스킬의 description 이 같은 요청 문구를 트리거로 갖는지, 서로를 가리키는 경계 문장이 있는지 본다.
  경계 문장이 없으면 같은 요청을 두 스킬이 가져가거나, 하나만 불려 다른 스킬의 일을 즉흥으로 처리한다.

설치된 스킬의 description 은 세션의 스킬 목록에서 읽는다. 다른 저장소의 스킬도 대조 대상이지만 교정은 그 저장소에서 한다.
사용 기록 모드를 돌렸으면 같은 세션에서 두 스킬이 함께 불린 기록이 근거가 된다.

- 예: 설계 스킬과 조율 스킬의 PR 분할 정책이 어긋난다. PR 작성 스킬과 미리보기 스킬의 승인 기준이 다르다.
- 예: 업무 조회 스킬과 업무 작성 스킬의 description 에 경계 문장이 없어 한 세션에서 함께 불린다.

## 계층 분리

매 실행에 필요한 오케스트레이션과 특정 조건에서만 필요한 복구 절차를 분리한다.
조건부 세부를 참조 파일로 옮길 때는 본문에 발동 조건과 읽을 경로를 남긴다.

- 예: 충돌이 생겼을 때만 필요한 절차가 참조 파일 없이 본문에 있어 매 실행 컨텍스트를 차지한다.

## 스킬 구조와 유지보수성

개인 스킬은 사용자와 에이전트가 함께 읽고 고치는 작업 문서다.
목표와 책임 범위가 먼저 보이고, 서로 다른 목표가 한 스킬에 섞였는지 확인한다.
면접 연습, 문서 작성, 배포처럼 완료 조건과 실행 리듬이 다르면 스킬이나 단계 책임을 분리한다.

정적 검사는 산문으로 반복하지 않고 실행할 스크립트와 실패 대응을 확인한다.
검사 결과 0건을 통과로 단정하는 문장은 `죽은 검출` 축으로 다시 본다.

스킬 문서의 층과 배치, 단계별 reference 를 두는 기준은 사용자 전역 `~/.claude/references/skill-structure.md`가 소유한다.
한국어 표현과 사람이 읽는 문서 구조의 판정은 `korean-check` 스킬의
[`references/`](../../../export-only-skills/korean-check/references)가 소유한다.
공개 저장소 문서에는 `~/` 밖의 사용자 고유 절대 경로를 쓰지 않는다.

## 정책 잔존

새 정책의 선언을 찾은 다음, 이전 정책이 실행 절차 가까이에 남았는지 검색한다.

- 예: 자율 진행 정책으로 바뀐 뒤에도 단계 절차 옆에 사용자 확정을 요구하는 옛 문구가 남아 매 단계를 멈춘다.
- 예: 이미 해결된 사건의 확인 지시가 남아 있다. 가리키는 설정이 들어가 있으면 지금 필요한 대응으로 바꾼다.
## 런타임 동작 변화

하네스 자체가 바뀌어 지침의 전제가 더는 참이 아닌 경우를 찾는다.
모델 역량이 아니라 **도구·런타임의 동작**이 바뀐 것이라, 실행해 보거나 공식 문서를 읽어야 드러난다.
문서끼리 비교해서는 절대 보이지 않는다.

찾는 방법은 셋이다.

- 지침이 전제하는 동작을 **실제로 재현**해 본다.
- 도구 설명 원문과 대조한다. 도구 계약은 1차 자료다.
- 공식 문서에서 그 동작이 언제 어떻게 바뀌었는지 확인한다.

- 예: 「팀원은 idle 직후 스스로 종료하니 재스폰한다」 는 지침. 공식 문서가 idle 팀원이 계속 돌며 이름으로 부를 수 있다고 적으면 재스폰은 컨텍스트만 버린다.
- 예: 스폰 인자가 「받아들이되 무시」 로 바뀌어, 그 인자의 유무로 갈리던 우선순위 표가 뜻을 잃는다.
- 예: 기본 표시 모드가 바뀌어, 옛 기본값에서만 나던 실패를 다루는 가드가 발동할 수 없다.

근거 없이 "요즘은 안 그럴 것" 이라고 지우지 않는다.
바뀌었다는 것을 확인한 만큼만 고치고, 옛 관측이 거짓이었다고 단정하지 않는다.

## 모델 교체

세션 모델이 지침을 쓸 때와 다르거나 사용자가 새 모델을 언급했을 때 이 축을 적용한다.
지시가 실제 세션에서 어떻게 작동했는지 근거가 필요하면 [`usage-audit.md`](usage-audit.md) 의 사용 기록 모드를 쓴다.
현재 세션의 시스템 프롬프트와 도구 설명에 먼저 대조한다.
모델 설명 자료는 다음 순서로 읽는다.

1. claude-api 스킬의 `shared/` 아래에서 대상 모델 절의 `Behavioral shifts` 와
   `prompt-audit.md` 의 `Group 1d(Fossils)` 와 keep list 를 읽는다.
   번들 버전마다 경로가 바뀌므로 고정 경로를 적지 않는다.
   대상 모델 절이 다시 테스트할 목록을 앞 모델 절로 넘기면 그 절의 `Behavioral shifts` 까지 읽는다.
2. 해당 모델의 발표문과 시스템 카드의 alignment 절을 읽는다.
   시스템 카드 PDF 가 10MB 를 넘으면 웹 페이지를 가져오는 도구가 실패하므로 내려받아 `pdftotext` 로 변환해 검색한다.

다음 문장을 찾는다.

- 시스템 프롬프트가 이미 지시하는 문장
- 모델 행동 관측을 근거로 둔 문장
- 모델 이름과 버전을 명시한 문장

모델 행동 관측을 근거로 둔 문장은 `judgment.md` 의 「10. 실측의 관측 대상: 도구 동작과 모델 행동」 축으로 판정한다.

이전 모델에 맞춘 지시는 바로 지우지 않는다.
마이그레이션 가이드가 출발점으로 두고 다시 테스트하라고 하면 보류로 두고 다시 테스트할 후보로 적는다.
시스템 카드가 새 모델의 약점으로 적은 행동에 맞선 지시는 유지 근거로 적는다.

**가이드는 제거를, 시스템 카드는 유지를 가리키면 보류로 두고 두 근거를 함께 적는다.**
같은 약점을 산출물에 남는 형태로 막는 대안이 있으면 그것을 선택지로 함께 낸다.
예: 하위 에이전트에게 최종 확인을 맡기는 절이면, 검토자를 없애고 완료 보고에 실행한 명령과 결과를 적게 하는 안을 함께 낸다.

## 사용 이력 0

한 번도 실행되지 않은 절차가 필요한 안전장치인지 판단한다.
호출 수를 세야 하면 [`usage-audit.md`](usage-audit.md) 의 사용 기록 모드로 센다.
발동할 수 없는 죽은 단계인지도 구분한다.
생략 조건과 호출 패턴을 먼저 대조한다.
대체 경로와 도입 근거도 함께 확인한다.

- 예: 선택 단계의 생략 기준이 일반적인 호출을 모두 포함해, 규칙을 지킬수록 그 단계가 매번 생략된다.
