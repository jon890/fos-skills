# plan

사용자가 확인한 기능 스펙과 기술 설계를 구현자가 실행할 PR 하나의 작업으로 나눈다. 제품 동작과 결정은 spec 이 인터뷰로 정하고, 여기서는 구현 순서와 변경 파일, 검증 명령에 집중한다.

## 이럴 때 쓴다

- 확인한 스펙으로 task 를 만들 때(「계획 세워줘」, 「PR 로 나눠줘」)
- 큰 기능에서 지금 구현할 PR 만 상세화할 때
- 기능 루프 밖의 긴 정리·이전 작업을 세션이 끊겨도 이어받게 계획서로 남길 때

「이 기능 설계해 보자」 처럼 동작을 정하는 요청은 `spec` 이 받는다.

## 사용 예시

> “docs/features/run-cancel/spec.md 의 구현 계획을 만들어 줘.”
> 스펙과 기술 설계를 검사하고, 이번 PR 의 요구사항을 골라 테스트까지 포함한 phase 를 만든 뒤 critic 이 계획을 검토한다.
> 계획 중 사용자 결정이 새로 나오면 묻지 않고 spec 으로 돌려보낸다.

## 받는 것

- 스펙·설계·REQ1 같은 요구사항 ID 가 연결된 기능 폴더의 `tasks/<계획>/index.json`
- phase 별 작업·변경 파일·검증 명령
- 뒤 PR 의 목표와 선행 조건

## 함께 쓰는 스킬

- `spec`: 사용자를 인터뷰해 요구사항을 확정한다
- `technical-design`: 모듈 책임과 데이터 소유권, 검증 전략을 확정한다
- `implementation`: 계획을 구현한다
- `verify`: 인수 조건을 확인한다
