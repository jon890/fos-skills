# orch: 보드 항목 고치기를 `orch board` 명령으로 부른다

확인: 2026-11-10

## 목표

코디네이터가 보드 항목의 상태와 단계 줄을 `orch board` 명령 한 줄로 고친다. 플러그인 캐시의 버전 경로를 찾지 않고, 인자 꼴을 외우지 않고, `board.json` 을 직접 고치지 않는다. 고친 결과는 한 줄로 돌려받아 호출마다 드는 토큰을 줄인다.

- 배경(넘김 문서 `.orch/handoff-board-cli/README.md`, 2026-11-10): ai-analysis 세션에서 보드 고치기 호출 약 30회 가운데 대부분을 python 으로 `board.json` 을 직접 고쳤다. 플러그인 버전이 하루에 여러 번 올라(14.22.0 → 14.27.0 → 14.28.0) `board.ts` 경로가 바뀌고, `detail-add` 는 `--detail` 이 아니라 위치 인자인 것처럼 꼴이 달라 호출마다 명령이 2~3번 더 돌았다.
- 배경(ai-analysis 코디네이터 요청 2026-11-10): PR 이 머지돼도 직접 쓴 단계 줄이 끝나지 않아 사용자가 「머지됐는데 보드가 왜 안 바뀌냐」 고 물었다. 같은 날 loop.log 로 원인을 가렸다(아래 「조사한 사실」).

## 조사한 사실

| 대상 | 사실 | 근거 |
| --- | --- | --- |
| 지금 `orch board` | `sync`, `release`, `goal` 만 있다. 항목 상태나 단계 줄을 고치는 동작이 없다 | `skills/orch/scripts/lib/commands.ts` 의 board 묶음 |
| 보드를 고치는 도구 | `extensions/work-board/bin/board.ts` 가 `set`, `step`, `mark`, `detail-add`, `detail-edit`, `steps`, `list`, `del` 을 갖는다. 항목 검사(doing 은 진행률 필요)와 저장 꼴(들여쓰기 한 칸, 끝 줄바꿈 없음)도 갖는다. 루프의 `board-sync` 와 `launch-worker` 가 이 도구를 부른다 | `board.ts` 머리 주석, `skills/orch/scripts/lib/board.ts` 의 `BOARD_BIN` |

| 마지막 PR 뒤 남은 단계 | 줄 앞 사건 표시도 줄 끝 꼬리표도 없는 항목은 마지막 PR 이 머지되면 `board-sync` 가 끝나지 않은 단계를 모두 끝내고 `done` 으로 바꾼다. `finish-pr` 는 단계를 보지 않고 `done` 으로 바꾸고 `next` 의 줄을 지운다. 「real 활성화」 처럼 머지와 무관한 줄도 끝난 것으로 바뀐다. 마일스톤 항목은 이미 끝나지 않은 수동 단계가 남으면 `done` 으로 바꾸지 않는다 | `board-sync.ts` 머리 주석(「마지막이면 남은 단계를 끝내고 항목을 done 으로 바꾼다」)과 옛 꼴 항목 분기, `finish-pr.ts` 의 `setBoardDone`, `core/milestones.ts` 머리 주석의 「done 지점」, ai-analysis 코디네이터의 개선 후보 조사(2026-11-10) |
| 보드 자동 진행 스펙 | 단계 줄 번호 뒤에 `[auto]`, `[ask]`, `[wait: 조건]` 을 붙이는 스펙이 확인됐다(2026-11-10). 아직 main 에 머지되지 않았다 | `origin/docs/board-auto-advance-spec` 브랜치의 `docs/features/board-auto-advance/spec.md` |

## 범위

이번 범위:

- `orch board` 의 새 동작 넷: `set`, `step`, `add-step`, `show`
- 단계를 줄 앞 번호로 고르고, 단계 글을 바꾸거나 더하는 규칙, 줄 끝 사건 꼬리표를 붙이는 `--on`
- 보드 자동 진행 표시(`[auto]`, `[ask]`, `[wait: 조건]`)를 붙이고 바꾸는 `step` 의 전용 동작
- 한 줄 출력과 종료 코드
- 보드 파일 찾기를 orch 규칙으로 맞추기
- `board.ts` 에 읽기부터 쓰기까지 파일 잠금 더하기. 호출자가 미리 읽은 목록으로 줄을 통째로 저장하는 쓰기(`board-sync`, 중간 과정 기록)가 앞 수정을 지우지 않게 하기
- `finish.board` 를 `boardPath` 가 읽게 해 새 명령, `sync`, `release`, `goal`, 루프, 마무리가 모두 같은 보드 파일을 쓰게 하기
- 머지는 반영됐는데 끝낼 줄을 못 정한 항목을 알리기
- 마지막 PR 이 머지돼도 끝나지 않은 단계가 남은 항목을 `done` 으로 바꾸지 않기

범위 밖:

- `set` 으로 제목, PR, 담당 워크트리 같은 칸을 고치는 것. 그 칸은 `board.ts` 로 고친다
- 새 항목을 만드는 것. `launch-worker` 와 `board.ts set` 이 맡는다
- `mark` 번호(번호 없는 참고 줄까지 센 줄 순서)로 줄을 고르는 것
- `board.ts` 를 없애거나 규칙을 orch 로 옮기는 것
- worker 가 이 명령으로 보드를 고치는 것을 코드로 막는 것. 공통 지시서의 글 규칙으로 지킨다
- `finish-pr` 가 마지막 PR 인지 판정하지 못할 때 중간 PR 로 보는 규칙을 바꾸는 것(다른 기능의 계약이다)
- 꼬리표 없이 줄 글의 PR 번호를 읽어 줄을 끝내는 것. 알림 뒤에도 놓치는 경우가 남는지 보고 따로 정한다
- `[auto]` 의 근거(스펙, 계획, 앞 사건)가 맞는지 이 명령이 확인하는 것. 띄우기 직전 확인은 자동 진행 스펙의 코디네이터 규칙이다

구현 순서: 표시를 다루는 `step` 전용 동작(REQ10)은 자동 진행 스펙의 구현이 머지된 뒤에 연다. 그 밖의 동작은 먼저 낼 수 있다. PR 을 어떻게 나눌지는 plan 이 정한다.

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | `orch board set <항목> <상태>`, `orch board step <항목> <번호> <동작>`, `orch board add-step <항목> "<글>"`, `orch board show <항목>` 을 부를 수 있다. 상태는 `goal`, `decide`, `doing`, `wait`, `done` 이다. 플러그인 경로를 적지 않고 어느 폴더에서 불러도 같다 | 플러그인 버전이 오른 뒤에도 `orch board set` 이 같은 꼴로 돈다. `orch board --help` 와 명령 표(`lib/commands.ts`)가 네 동작을 보인다. 상태가 다섯 값이 아니면 종료 코드 1 이고 stderr 에 허용 값이 나온다 |
| REQ2 | 보드 파일은 orch 의 규칙으로 찾는다. `--board <파일>` 이 있으면 그것, 없으면 `config.json` 의 `finish.board`, 없으면 주 checkout 의 `.omc/board.json`(옛 `.omc/handoffs/board.json` 이 있으면 그것)이다. `--board` 의 상대경로는 주 checkout 기준이다. `--repo` 를 주면 그 폴더가 속한 저장소의 보드를 쓴다(워크트리를 주면 그 워크트리의 보드) | `--repo` 없이 워크트리 안에서 `orch board set` 을 불러도 주 checkout 의 보드가 바뀌고 워크트리에 보드 사본이 생기지 않는다. `orch board sync` 가 읽는 파일과 같다. `finish.board` 로 기본과 다른 파일을 정한 저장소에서 새 명령, `sync`, `release`, `goal`, 루프의 동기화와 보드 확인, 마무리가 모두 그 파일을 쓴다. 기본 보드와 지정 보드의 내용이 다를 때 지정 보드만 바뀌고, 지정 보드만 있고 기본 보드가 없을 때 루프가 동기화를 건너뛰지 않는다 |
| REQ3 | `step` 은 줄 앞 번호로 단계를 고른다. 「9.」, 「9)」, 「9 」 로 시작하는 줄이 9번이다. 글 일치로는 찾지 않는다. 번호가 없으면 거절하고 지금 있는 단계 번호를 알려 준다. details 에 단계가 있으면 details 를, 없으면 next 를 쓴다(`board.ts step` 과 같다). 같은 번호의 줄이 둘 이상이면 거절한다. 번호 뒤에 공백이 없는 글(`9.머지`)은 단계 줄이 아니다 | 단계가 1~3번인 항목에 `step <항목> 9 done` 을 부르면 종료 코드 1 이고 stderr 에 「9 번 단계가 없다. 있는 번호: 1 2 3」 이 나온다. 보드 파일은 바뀌지 않는다 |
| REQ4 | `step <항목> <번호> done` 은 그 단계를 끝낸 것으로, `undo` 는 끝나지 않은 것으로 표시한다. `text "<글>"` 은 줄 전체(번호 포함)를 새 글로 바꾼다. 그 단계가 있는 쪽(details 또는 next)의 줄을 고친다. 새 글이 같은 번호로 시작하지 않으면 거절한다. 새 글에 앞 표시(`✓`, `[x]`, `[ ]`, `▶`, `◇` 중 하나)가 없으면 끝냄 상태는 그대로다. 옛 줄에 사건 꼬리표(줄 앞 `[merge]` 따위나 줄 끝 `(#N 사건)`)가 있는데 새 글에 없으면 조용히 끝나지 않게 되므로 거절한다. `undo` 는 항목 상태를 바꾸지 않는다(`board.ts` 와 같다). `decide` 항목의 줄이 모두 끝나면 항목이 `done` 이 된다(`board.ts` 의 자동 전환) | `step <항목> 9 text "9. 머지 확인"` 이 9번 줄 글만 바꾸고 끝냄 상태는 그대로 둔다. `step <항목> 9 text "10. 머지"` 는 종료 코드 1 이다. `(#1455 merge)` 가 든 줄을 꼬리표 없는 글로 바꾸면 종료 코드 1 이다. next 에만 단계가 있는 항목에도 같은 호출이 듣는다. `decide` 항목의 마지막 미완료 줄을 `done` 으로 하면 출력 줄 끝에 `status=done` 이 붙는다 |
| REQ5 | `add-step <항목> "<글>"` 은 details 끝에 줄 하나를 더한다. 글에 번호가 없으면 가장 큰 단계 번호에 1을 더한 번호를 앞에 붙이고, 번호를 직접 쓰면 그대로 쓰되 이미 있는 번호면 거절한다. 새 줄은 끝나지 않은 단계이고 단계가 있는 쪽(details 또는 next)에 더한다. `done` 항목에는 더하지 않고 거절한다. 항목에 `progress` 칸(N/M)이 있으면 그 값이 단계 수보다 앞서 새 줄이 진행률에 안 보이므로 stderr 에 한 줄로 알린다 | 단계가 1~9번인 항목에 `add-step <항목> "리뷰 반영"` 이 「10. 리뷰 반영」 을 더한다. `add-step <항목> "9. 중복"` 은 종료 코드 1 이다. 단계가 next 에만 있는 항목은 next 에 줄이 더해진다. `done` 항목에 부르면 종료 코드 1 이다 |
| REQ6 | `add-step` 과 `step text` 는 `--on "<PR 번호> <사건>"` 을 받아 줄 끝에 `(#1455 merge)` 꼴 꼬리표를 붙인다. 사건은 `pr`, `merge`, `deploy`, `release` 다.
