# planning

새 기능·변경을 구현하기 전, 모호함을 모두 없애고 문서를 정비한 뒤 실행(build)으로 넘기는 8단계 설계 워크플로.

## 레포 오버레이 로딩 (필수 첫 단계)

`<repo-root>/.claude/planning-overlay.md` 가 있으면 **먼저 읽고** 코어보다 우선한다.

오버레이는 아래 필수 관리 문서를 빼거나 다른 문서로 대체할 수 없다. 저장소 특성에 맞는 추가 문서와 더 강한 검증만 더할 수 있다.

## 필수 관리 문서 — 공용 고정 계약

모든 planning은 다음 다섯 문서를 관리한다.

- `docs/prd.md` — 제품 목표, 사용자 가치, 범위와 제외 범위를 소유한다.
- `docs/flow.md` — 사용자·호출 흐름, 상태 전이, 오류와 부분 성공을 소유한다.
- `docs/code-architecture.md` — 모듈 책임, 파일 배치, 의존 방향과 실행 경계를 소유한다.
- `docs/data-schema.md` — 저장 모델 전체의 필드·키·제약·삭제 규칙과 구조화 형식을 소유한다.
- `docs/adr/` — 코드로 자명하지 않은 장기 기술 결정의 이유, 대안, 결과와 대체 관계를 소유한다.

책임 문서 판정, 없는 문서의 생성 조건, 규모별 완화는 7단계가 소유한다 (`references/step-7-docs.md`).

문서 갱신과 문서 간 계약 일치 검증이 끝나기 전에는 8단계 task를 만들 수 없다.
완료 여부는 7단계의 문서 diff 로 판정하며, 어느 문서도 영향받지 않는다는 판정을 남긴 경우도 통과로 본다.

## 핵심 원칙

- **모호함 제로**: 조금이라도 모호하면 사용자와 논의. 넘어가지 않는다.
- **AI 에이전트 관점**: 최종 문서는 AI 가 읽고 phase 로 구현 가능할 만큼 명확.
- **선택지는 질문 도구로**: 추천안 첫 번째, label 끝 `(추천)`, 트레이드오프. long-form 나열 금지.
- **질문 규율**: 깊은 모호함은 하나씩. 사실(파일·git·도구)은 직접 조회, 사용자에겐 결정만 묻는다.

## 모호함 능동 발굴 (모든 단계 필수)

각 단계는 산출물만 뽑고 넘어가지 않는다.
그 단계 reference 의 "캐낼 모호점" 을 하나씩 짚어, 명시 안 됐거나 해석이 갈리는 지점을 찾아낸다.
"알아서 됐겠지" 로 지나가지 않는다.

이게 planning 의 핵심 가치다 — 구현 전에 모호함을 다 태워 없앤다.

## 단계 강제 (필수) — 뭉개기·건너뛰기 방지

과거 실패: 단계를 이름 없이 섞어 진행해 3·4단계(흐름·인터페이스)를 놓치고, 확정 전에 청사진·실행으로 앞서갔다. 아래로 강제한다.

1. **단계 기록 생성** — planning 시작 시 `TaskCreate` 로 밟을 단계를 각각 task 로 만든다(규모에 따라 1~8 중 선택). 미완 단계가 눈에 남아 뭉개기를 막는다.
2. **단계 표기** — 매 응답 첫 줄에 `지금 N단계: <이름>` 표기. 사용자가 진행·누락을 본다.
    - 한 턴에 여러 단계를 진행해도 된다. 밟은 단계를 순서대로 모두 표기하고, 단계마다 턴을 끊지 않는다.
3. **단계 진입 = reference 로드** — 각 단계 진입 시 `references/step-N-*.md` 를 읽고 **그 역할로** 수행. 코어의 한 줄 요약만 보고 진행하지 않는다.
4. **통과 조건** — 그 단계의 모호점이 **0** 이어야 완료(task completed)된다. 판정 기준은 모호점 유무이고, 사용자 응답 횟수가 아니다.
    - **모호점이 남아 있으면 멈춘다** — 사용자만 답할 결정(취향·범위·되돌리기 어려운 것·트레이드오프 판단)은 `AskUserQuestion` 으로 확정받고 나서 진행한다.
    - **모호점이 0 이면 확정을 기다리지 않고 다음 단계로 넘어간다.** 무엇을 어떤 근거로 정했는지 단계 표기에 남긴다 — 사용자가 그 기록을 보고 되짚을 수 있다.
    - 사실로 확인 가능한 것(파일·git·도구·실측)은 **직접 조회해 스스로 정한다.** 사용자에게 묻지 않는다.
    - **모호함을 안고 앞서가는 것은 여전히 금지다** — 미해결 모호점이 있는 상태에서 전체 청사진·docs 작성·task 생성·실행으로 넘어가지 않는다.
5. **합치기·건너뛰기는 규모 작을 때만, 사유 명시** — "이 변경은 작아 3·4 병합" 처럼 단계 표기에 밝힌다. 7단계(docs)만은 규모 무관 항상 수행.

막아야 할 것은 **모호함을 안고 앞서가는 것**이지 단계를 연달아 통과하는 것이 아니다.
건너뛰기 방지는 1~3번(단계 기록·단계 표기·reference 로드)이 담당한다.

## 동시성 안전 (여러 planning 병행 시)

여러 세션이 동시에 planning 하면 번호·문서·push 가 충돌한다. 방지:

- **branch-per-plan** — planning 을 main 이 아니라 **`plan{N}-<slug>` 브랜치**에서 한다.
    - docs 와 tasks 를 그 브랜치에 커밋·push 한다.
    - 충돌은 merge 시점에 드러난다 — 조용히 묻히지 않는다.
    - 레포 branch 정책이 따로 있으면 오버레이를 우선한다.
    - **planning 은 PR 을 만들지 않는다** — 이 브랜치는 기획에서 끝나지 않고 **구현이 이어 붙는 같은 브랜치**다.
        - 실행 스킬이 이 브랜치에서 worktree 를 분기해 phase 커밋을 쌓는다.
        - 기획 커밋과 구현 커밋을 담은 **PR 1개**를 마지막에 연다 — plan 1개 = PR 1개는 여기서 지켜진다.
- **번호 선점** — 번호를 부여하기 전에 원격까지 스캔하고, 정한 번호는 **브랜치를 즉시 만들어 확보**한다.
    - `git fetch` 후 `git branch -a` 와 `gh pr list --state open` 로 plan·ADR 번호를 훑는다.
    - 읽기만 하고 끝내면 두 세션이 같은 번호를 집는다.
- **공유 문서는 끝에 덧붙이는 편집만** — 새 ADR·phase 파일은 서로 충돌하지 않는다.
    - README·data-schema 같은 공유 인덱스는 **끝에 행을 추가**하기만 한다.
    - 기존 행을 재배열하거나 중간에 끼워 넣지 않는다 — merge 가 깔끔해진다.
- **ADR 번호** — 브랜치로 claim 안 되니 시작 시 원격까지 스캔, 충돌 나면 merge 때 재번호(최후).

## 실행 절차 (8단계)

각 단계는 진입 시 해당 reference 를 읽고 그 역할로 수행 → 단계 표기 → 모호점 0 확인 → 다음.

| 단계 | 이름 | 무엇을 정하는가 | reference |
|---|---|---|---|
| 1 | 구현 가능성 (역할: CTO) | 되는가, 무엇을 재사용하나, 무엇이 위험한가 | `references/step-1-feasibility.md` |
| 2 | 기술 스택 | 기존 스택으로 되는가, 새 의존이 정당한가 | `references/step-2-tech-stack.md` |
| 3 | 호출·사용자 흐름 (역할: 워크플로/UX) | 정상 흐름과 실패·빈 상태·동시 충돌 | `references/step-3-flow.md` |
| 4 | 인터페이스 설계 | 사용자와 호출자가 마주하는 표면 | `references/step-4-interface.md` |
| 5 | API·함수 설계 | 엔드포인트·시그니처·요청과 응답 스키마 | `references/step-5-api.md` |
| 6 | 데이터·코드 구조 (역할: 데이터 모델러 겸 CTO) | 스키마·상태와 디렉터리 배치 | `references/step-6-data-code.md` |
| 7 | docs 영향과 기술 결정 기록 | 책임 문서 판정과 실제 갱신 | `references/step-7-docs.md` |
| 8 | task 파일 생성과 커밋 | 대화를 못 본 executor 가 읽고 실행할 phase | `references/step-8-tasks.md`, `task-create.md` |

## 의사결정 누적 → 논의 완료 시 docs 반영

논의 중 결정은 대화 컨텍스트에 누적한다. 최종 docs 에 즉시 쓰지 않는다(중간 결정은 바뀔 수 있어 재작성·미확정 혼입). 논의가 끝나면 누적 최종 결정만 한 번에 docs 반영(7단계).

## 규모 분할 점검 — plan 1개 = PR 1개

7단계 결정이 끝나고 8단계 task를 만들기 전에 예상 변경 범위를 판정한다.

- 하나의 plan은 정확히 하나의 구현 브랜치와 하나의 PR에 대응시킨다.
- 독립된 검토·검증 단위가 둘 이상이면 phase를 계속 늘리지 말고 여러 plan으로 나눈다.
- 생성 파일을 제외한 예상 변경이 약 25개 파일, 800줄 또는 5개 phase를 넘으면 분할 검토를 반드시 수행한다. 수치는 경고선이며 변경 이유를 한 번에 설명할 수 있는지가 최종 기준이다.
- DB·저장 계약, backend 처리와 API, frontend 연결, skill·tooling처럼 자체 완료 기준을 갖는 경계를 우선 분할 후보로 삼는다.
- 각 분할 plan에 목표, 범위 외, 검증 기준을 지정한다. 여러 plan을 한 브랜치나 한 PR에 합치지 않는다.
- 분할안을 사용자에게 **실행 순서**와 각 PR의 검토 초점과 함께 제시하고 확정받은 뒤 번호를 선점하고 task를 만든다. 순서는 보고로 전달하며 task 파일에 의존 관계 필드로 남기지 않는다.
- 7단계 docs 갱신분은 plan별로 쪼개지 않고 첫 plan 브랜치에 함께 커밋한다.
- 후속 plan 브랜치는 번호를 확보하려고 지금 만들되, 실행 직전 **최신 `main` 위로 rebase** 한다.
  만든 시점 그대로 두면 앞선 plan 의 docs 가 빠진 base 위에서 구현하게 된다.

```bash
git fetch origin && git switch plan{N}-<slug>
git rebase origin/main
git push --force-with-lease
```

rebase 는 **PR 생성 전에만** 한다 — PR 이 열린 뒤에는 리뷰 코멘트가 커밋에 묶여 있어 히스토리를 다시 쓰면 사라진다.

분할하지 않는다면 경고선 이하라는 이유만 쓰지 말고 하나의 원자적 변경으로 묶여야 하는 근거를 단계 기록에 남긴다.

## 자체 검토와 task 검증 (생성 직후, 필수)

task 파일을 만든 직후, 커밋하기 전에 세 가지를 순서대로 한다.

1. **자체 검토** — `task-create.md` 의 "자체 검토" 절차를 따른다.
2. **자동 검증** — 스크립트가 잦은 실수 5가지를 찾는다. 출력이 0 줄이어야 통과.

    ```bash
    # cwd: 타깃 레포 root
    ~/.claude/skills/planning/scripts/verify-task.sh plan{N}-{slug}
    ```

3. **사람 판단 4 패턴** — 도메인 의존이라 스크립트가 못 잡는다. `task-create.md` 의 목록을 따른다.

위반을 찾으면 임의로 고치지 않고 질문 도구로 사용자에게 확인한다.
계획의 수치·범위는 사용자 의도가 담긴 값이라, 조용히 바꾸면 합의가 뒤집힌다.

## 완료 후 (필수)

1. **브랜치를 확인한다** — 오버레이 정책을 따르고, 기본은 `plan{N}-slug` 브랜치다.
2. **plan별로 커밋하고 push 한다** — 오버레이에 커밋 규칙이 있으면 그쪽을 우선한다.
3. **실행 기록 한 줄 추가** — `docs/retrospectives/RUNS.md` 에 이번 planning 결과를 남긴다.
   스킬은 `planning`, 대상은 plan 이름, 개입 열에는 사용자에게 되물은 횟수를 적는다.
   중단된 planning 도 기록한다. 형식은 `~/.claude/skills/build-with-teams/references/run-record.md` 를 따른다.
9. 사용자에게 plan 순서와 plan별 실행 명령을 보고한다 (형식은 오버레이).

**실제 phase 실행은 사용자가 실행 명령을 호출할 때 시작.** planning 은 task 생성과 push 까지.
보고에는 각 plan 의 **브랜치 이름**을 함께 적는다 — 실행 스킬이 그 브랜치에서 worktree 를 분기하므로, 이름이 곧 핸드오프 인자다.

예외: 논의만(docs·task 없음) → commit 생략 고지. main 직접 push 금지 — 산출물은 plan 브랜치에만 둔다.
이미 push 한 커밋을 **고쳐 쓰지 않는다** — 수정은 새 커밋으로. 단 실행 직전 base rebase 는 예외이며 `--force-with-lease` 로 한다(위 규모 분할 점검 참조).

## plan 네이밍

- 번호 선점은 위 "동시성 안전" 참조(fetch → 원격 스캔 → 브랜치 claim).
- 서브넘버: 동일 기능 확장·동일 도메인 후속은 `plan003-2` 식으로 묶고, 독립 실행 가능하면 새 번호.
