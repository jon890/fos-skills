# Task 생성 가이드

레포별 검증 명령과 레이어 구조는 레포 설정이 채운다. 찾는 순서는 `SKILL.md` 의 「레포 설정을 먼저 읽는다」 가 정한다.

반복 함정 목록은 레포 설정이 지정하면 그것을 따르고, **지정이 없으면 `docs/pitfalls/` 를 읽는다.**
그 디렉터리도 없으면 사전 확인 항목을 건너뛴다.

## index.json 스키마

```jsonc
{
  "name": "plan{N}-{kebab-slug}",       // 디렉터리명과 일치
  "description": "한 줄 요약 — 무엇을 / 왜",
  "status": "pending",                    // pending | in_progress | completed | failed
  "created_at": "2026-01-01",             // YYYY-MM-DD
  "total_phases": 3,                      // phases 배열 길이와 일치
  "current_phase": 1,
  "phases": [
    {
      "number": 1,
      "file": "phase-01.md",
      "execution_profile": "standard"     // fast | standard | deep
    }
  ]
}
```

## ADR(Architecture Decision Records) 구조 템플릿

파일명은 `docs/adr/NNN-<슬러그>.md` 다. 한 파일에 결정 하나만 담는다.

```markdown
## ADR-XXX: {제목. 결정의 한 줄 요약}

- **status**: `accepted`
- **결정**: {무엇을. 1~3문장}
- **맥락**: {왜 이 결정이 필요했는가. 제약·데이터·관찰}
- (조건부) **대체된 부분**: {이 ADR 의 어느 결정이 어느 ADR 에 뒤집혔는가. 링크 포함}
- **대안 기각**: {다른 옵션을 왜 선택하지 않았는가. 각 대안 1~2줄}
- **결과**: {이 결정 뒤로 무엇이 달라지는가}
  - 얻는 것: {가능해진 것}
  - 감당할 것: {비용·제약·앞으로 지켜야 할 것}
- (선택) **적용 범위**
```

`status` 는 둘뿐이다.

| 값            | 뜻                              |
| ------------ | ------------------------------ |
| `accepted`   | 현재 유효하다                        |
| `superseded` | 다른 ADR 이 이 결정을 뒤엎었다. 이력으로만 읽는다 |

`status` 가 없는 기존 ADR 은 `accepted` 로 읽는다.

**결과** 는 결정한 뒤에 생기는 트레이드오프를 적는다. 얻는 것과 감당할 것을 둘 다 적는다.

**ADR 은 지우지 않는다.**
결정 전체가 번복돼도 `status` 를 `superseded` 로 바꾸고 `대체된 부분` 에 대체한 ADR 을 가리킨다.
지우면 그때 그 판단을 왜 했는지가 사라진다. 당시 정보로는 옳았던 결정이 대부분이다.

- `대체된 부분` 은 **결정 바로 아래**에 둔다. 결정만 읽고 지나가는 독자가 낡은 결론을 얻는 것을
막는 것이 목적이라, 문서 끝이나 대안 기각 안에 넣으면 의미가 없다.
- 대체한 쪽 ADR 에서도 원본을 링크해 양방향으로 찾을 수 있게 한다.
- 전체가 대체된 ADR 은 남은 본문 앞에 그것이 당시의 맥락임을 한 줄로 밝힌다.
- 코드와 경로는 결정을 가리키는 데 필요한 만큼만 인용한다. 구현 호출 방법, 작업 내역,
스택 규칙 반복은 넣지 않는다. 결정과 근거만 남긴다.

## phase 파일 작성 규칙

phase 는 자기완결이어야 하므로 **마지막 작업 항목을 테스트로 둔다.**
그 phase 가 끝났는지는 테스트로 판정한다.
**한 phase 는 한 사람이 한 번에 붙잡고 끝낼 수 있는 크기로 둔다.**

### phase 파일 구조

```markdown
# Phase NN. {제목}

**Execution profile**: standard

## 목표

무엇을 만드는가. 왜 필요한지 한 문장.

**범위 외**: 다른 phase 나 다른 plan 의 책임.

## 컨텍스트

이 대화를 보지 못한 구현자가 알아야 할 것.
기존 코드의 어느 패턴을 따르는지 경로로 짚는다.

**근거 문서**: `docs/flow.md` 의 「...」 절, `docs/adr/012-....md`

## 의도 메모

- 기각한 옵션과 그 이유
- 앞으로 주의할 것

## Blocked 조건 (선택)

- 외부 의존성 부재 → `PHASE_BLOCKED: {이유}` 출력 후 종료

## 작업 항목

### 1. {파일} — 변경 요약

구체적 변경. 함수 시그니처, 타입, 셀렉터, 이름. 기존 패턴 참조 경로.

### N. {테스트 파일} — 이 phase 를 검증하는 테스트

무엇을 어떤 입력으로 확인하는지. 정상 경로 하나와 이 phase 가 다루는 실패 하나.

## 검증

실행할 명령과 기대값. 레포의 lint, type, test, build 명령과 구체 grep 기준을 적는다.
위에서 만든 테스트를 실행하는 명령을 함께 적는다.

## Critical Files

검토자가 보는 색인이다. 위 작업 항목이 건드린 파일을 모은다.

| 파일 | 변경 |
|---|---|
| `...` | 신규 / 수정 / 삭제 |
```
