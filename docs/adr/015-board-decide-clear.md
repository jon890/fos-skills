# ADR-015: 보드의 결정 필요는 남은 줄과 남은 질문만 세고, 중간 과정은 보드 항목을 만들지 않는다

- **status**: `accepted`
- **결정**: 보드의 결정 필요 수는 decide 항목의 끝나지 않은 줄(줄이 없으면 항목 하나)과 답하지 않은 worker 질문만 센다.
  답한 줄은 `board.ts mark` 로 끝내고, decide 항목의 줄이 모두 끝나면 그 항목은 done 이 된다.
  worker 질문은 그 thread 에 worker 쪽으로 간 메시지가 있으면 답한 것으로 본다. 보낸 사람이 Run 인지 코디네이터 터미널인지는 보지 않는다.
  같은 worker 의 미답변 질문은 가장 최근 것 하나로 센다.
  지시서에 `중간 과정: PR #N` 줄이 있으면 worker 를 띄울 때 보드 항목을 만들지 않고, 그 PR 의 기존 항목 하위 줄에 한 줄만 남긴다.
  `보드 항목 id:` 로 정한 항목이 done 이면 새 worker 를 띄울 때 doing 으로 다시 연다. 지난 단계는 완료로 두고 새 단계를 다음 번호부터 이어 붙이며, `pr` 필드의 머지된 PR 은 `merged-pr` 의 맨 앞으로 옮긴다. 남은 `progress` 값은 지워 단계 수로 센다.
  이미 있는 항목에 worker 를 다시 띄우면 제목을 바꾸지 않고, 끝나지 않은 항목에는 단계도 더하지 않는다. 이어 띄운 지시서의 머리줄이 마일스톤 제목을 덮었다(사용자 지적 2026-10-27).
  상주 루프의 충돌 후속 지시서는 PR 마다 `spec-conflict-<PR>.md` 하나이고 base 가 움직이면 덮어쓴다. 마무리(`finish-pr.ts`)가 머지 뒤 그 지시서를 지운다.
  사용자 요청 2026-10-26.
- **맥락**: board-decide 가 답을 받아도 줄과 항목이 남아 결정 필요 수가 줄지 않았다. `board.ts list` 와 `steps` 가 번호 없는 줄을 보이지 않아,
  코디네이터가 줄이 있는 모음 항목을 빈 항목으로 잘못 읽었다.
  코디네이터 터미널에서 `orca orchestration reply` 로 답하면 회신의 보낸 사람이 `term_*` 이고, `--from run:<Run>` 은 터미널 증명 때문에 거절된다.
  창은 Run 이 보낸 회신만 답으로 셌고, 질문을 보낸 터미널의 inbox 만 읽었다. 회신은 `dispatch:<그 터미널의 dispatch>` 로 가서 그 조회에 나오지 않는다.
  그래서 답한 질문 4건이 계속 결정 필요로 남았고, 그중 2건은 worker 가 답을 못 받아 다시 보낸 것이었다.
  done 항목에 같은 id 로 새 worker 를 띄우면 워크트리와 제목만 바뀌고 done 으로 남아 창에서 사라졌다. `pr` 필드에 머지된 PR 이 남아 보드 동기화가 다시 done 으로 바꿀 수도 있었다.
  충돌 해결처럼 PR 하나를 마무리하려는 worker 가 「PR #N 의 base 충돌 풀기」 같은 새 항목을 만들었고, base 가 움직일 때마다 지시서가 새로 생겨 한 PR 에 9벌이 쌓였다.
- **대안 기각**:
  - `steps` 의 JSON 에 번호 없는 줄을 더한다. `board-sync.ts` 와 `launch-worker.ts` 가 그 목록의 길이와 번호로 단계를 판정해, 참고 줄만 있는 항목을 단계가 있는 항목으로 읽는다.
    그래서 JSON 은 그대로 두고 단계가 아닌 줄은 stderr 에 낸다.
  - `step` 이 번호 없는 줄도 끝내게 한다. 단계 번호와 줄 번호가 섞여 `step 3` 이 어느 줄인지 정할 수 없다.
  - 회신을 전체 inbox 에서 찾는다. 기록이 수천 건이라 창이 45초마다 읽기에는 무겁다. 질문마다 그 worker 의 handle 만 읽는다.
  - 다시 보낸 질문을 본문 비교로 묶는다. worker 가 앞 질문을 줄이거나 덧붙여 다시 보내 본문이 같지 않다. `ask` 는 답을 받을 때까지 막히므로 worker 하나에 열린 질문은 하나다.
  - 중간 과정을 지시서 제목이나 파일 이름으로 판정한다. 코디네이터가 쓰는 CI 고침과 리뷰 반영 지시서는 제목이 정해져 있지 않다. 줄 하나로 명시한다.
  - done 항목에 붙일 때 새 항목을 만든다. 같은 업무의 단계가 두 항목으로 갈리고, 지시서가 정한 항목 id 를 지키지 못한다.
  - 다시 열 때 옛 단계를 지운다. 이미 끝낸 일이 진행률에서 사라진다.
  - 충돌 지시서를 base SHA 마다 남긴다. 앞 지시서는 다음 base 에서 쓸모가 없고, 마지막 PR 판정이 남은 지시서를 셀 때 섞인다.
- **결과**:
  - 얻는 것: 답한 결정과 질문이 다음 조회에서 창에서 빠진다. 코디네이터가 `list` 만으로 모음 항목의 줄과 완료 여부를 본다.
  - 얻는 것: 보드에는 사용자가 정한 마일스톤 항목만 남는다. 충돌 지시서는 PR 마다 하나다.
  - 감당할 것: worker 쪽으로 간 메시지는 모두 답으로 센다. 코디네이터가 답 대신 상태만 물어도 그 질문은 빠진다.
  - 감당할 것: 같은 worker 가 서로 다른 질문을 `send --type question` 으로 연달아 보내면 마지막 하나만 보인다. 창은 「다시 보냄 n」 으로 묶인 수를 알린다.
  - 감당할 것: 코디네이터가 중간 과정 지시서에 `중간 과정:` 줄을 빠뜨리면 예전처럼 같은 워크트리의 항목을 이어 쓰거나 새 항목을 만든다.
  - 감당할 것: 마무리가 `pr` 필드를 비우고 done 으로 바꾼 항목은 `merged-pr` 에 옛 PR 이 없다. 다시 연 항목의 새 worker 가 옛 브랜치 이름을 그대로 쓰면 보드 동기화가 옛 머지 PR 을 다시 찾아 done 으로 되돌릴 수 있다. 새 브랜치 이름으로 띄운다.
  - 감당할 것: `중간 과정:` 줄은 그 worker 가 끝난 뒤에도 항목이 done 이 될 때까지 남는다. 다음 중간 과정이 그 줄을 바꿔 쓴다.
- **적용 범위**: 줄 명령은 `work-board/bin/board.ts`, 창의 질문 판정은 `work-board/hooks/register.js` 의 `queryQuestions` 와 `parseQuestions`,
  orch 질문 감시(`watch-questions`, `orch-loop` 의 재알림)의 같은 판정은 `orch/scripts/lib/questions.ts` 의 `unanswered` 와 `snapshot`,
  중간 과정은 `orch/scripts/lib/board.ts` 의 `registerBoard`, 충돌 지시서는 `orch/scripts/lib/conflicts.ts`, 지우기는 `orch/scripts/finish-pr.ts` 머리 주석이 소유한다.
