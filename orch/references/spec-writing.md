# 2. 지시서 쓰기

**지시 본문은 대상 저장소의 git 이 무시하는 폴더에 쓰고, `--spec` 에는 그 경로만 준다.** `--spec` 에 들어갈 한 줄은 `spec-line` 이 만든다([`launch.md`](launch.md) 의 `--spec` 절).
긴 지시는 앞부분도 중간도 잘려 도착한다.
지시서에 적지 않은 일이 빠진 채 완료로 보고되는 것을 막으려면 해야 할 일과 완료 기준을 지시서에 적는다. 후속 지시도 짧게 보내거나 새 파일로 준다.

지시서 폴더의 기본은 `<repo>/.orch/specs/` 다(`orch_paths.ts specs`). 오버레이가 다른 폴더를 정하면 그것을 따른다.

- 파일 이름은 `spec-<worktree 이름>.md` 로 한다. 공통 지시서는 `spec-common.md` 다. `cleanup-sweep.ts --specs-dir` 가 이 이름을 보고 머지 뒤 지시서를 지운다.
- 폴더는 `node --disable-warning=ExperimentalWarning "$SKILL_DIR/scripts/orch_paths.ts" --repo "$REPO" --ensure specs` 로 만든다. 만들면서 `.orch/` 를 로컬 전용 `.git/info/exclude` 에 더해 git 이 무시하게 한다. 다른 폴더를 쓰면 `git -C "$REPO" check-ignore -q` 로 무시되는지 본다.
- scratchpad 에 쓰지 않는다. **실측으로** 코디네이터 세션이 다시 시작되면서 scratchpad 가 정리돼 전날 쓴 지시서가 사라졌다. worker 는 받은 경로를 계속 읽으므로, 도중에 사라지면 읽을 곳을 잃는다.

**worker 마다 같은 규칙은 공통 지시서 한 파일에 두고, 개별 지시서는 첫 줄에서 그 파일을 가리킨다.**
틀은 [`../templates/spec-common.md`](../templates/spec-common.md) 다. 저장소마다 한 번 복사해 `{{...}}` 를 채운다.
**스크립트 경로는 채우지 않는다.** 틀의 명령이 worker 세션의 `CLAUDE_CONFIG_DIR/plugins/installed_plugins.json` 에서 `fos-skills@fos-skills` 의 `installPath` 를 읽어 `orch/scripts` 를 푼다. 캐시 폴더 이름은 해시라 `ls | tail -1` 이나 `ls -t` 로 고르면 설치되지 않은 번들을 집는다. 코디네이터가 그때의 캐시 경로를 박으면 번들이 갱신되거나 worker 가 다른 프로필에서 돌 때 옛 스크립트를 가리킨다. 저장소 체크아웃 경로도 박지 않는다. 그 체크아웃이 다른 브랜치에 있으면 main 과 다른 스크립트가 돈다.
같은 항목이 `user` 와 `project` 범위로 여러 개면 `user` 범위를 쓴다.
`{{DRAFT_PR_RULE}}` 는 오버레이가 draft 로 CI 를 미루는 저장소면 「PR 은 `gh pr create --draft` 로 연다. ready 로 바꾸는 것은 코디네이터가 한다」 이고, 아니면 그 줄을 지운다.
`{{DESIGN_DIR}}` 는 worker 가 `planning` 으로 만든 설계 문서를 둘 폴더다(예: `docs/<분야>/`). 두 스킬을 쓰게 하지 않으면 그 절을 지운다.
worker 가 직접 `orca orchestration ask` 를 부르면 답을 기다리는 동안 도구 호출이 시간 초과되고, 끝난 Dispatch 에서는 ask 자체가 거절된다. `worker-ask` 가 두 경우를 종료 코드로 가른다.
저장소 고유 규칙(검증 명령, 원격 접속, 비밀값)은 오버레이에 두고 공통 지시서가 가리키게 한다.

## 넣을 것

- 브랜치 이름을 `` 브랜치: `feature/x` `` 형식의 줄로 적는다. 백틱 안이 이름이고, 같은 줄에 다른 말이 있어도 된다.
  `make-worktree` 가 이 줄을 읽어 워크트리를 만들고, 6단계가 push 한 원격 브랜치를 이 값과 대조한다.
  예전에 머지된 PR 의 브랜치 이름은 다시 쓰지 않는다. 스크립트가 원격에 남은 같은 이름은 거부하지만, 지워진 옛 이름은 알지 못한다
- 「push 는 `git push -u origin HEAD` 로 한다. 브랜치 이름을 바꾸지 않는다」.
  워크트리는 지시서의 이름으로 만들어져 있고, 다른 이름으로 올리면 6단계 대조에서 걸린다
- 담당 범위, 기대하는 이득, 선행 결과, 결정하지 못한 사항
- effort 가 `low` 나 `medium` 이면 「끝까지 진행하고 판단만 ask 로 묻는다. 검증 명령을 실행한다」 를 넣는다. 중간에 멈추거나 검증을 건너뛴 채 보고하는 것을 막는다
- Ownership 에 「구현이 docs 계약과 달라지면 같은 커밋에서 그 절을 고친다. 고치기 전에 ask 로 알린다」.
  docs 를 범위에서 빼면 구현 중 계약이 바뀔 때마다 worker 가 docs 검사에 걸려 `ask` 로 멈춘다
- 승인이 필요한 작업이면 「발견 목록을 먼저 내고 멈춘다」.
  그 회신이 `worker_done` 으로 바로 오면 절차 위반으로 본다
- 사용자가 허락한 외부 동작을 `허락:` 으로 시작하는 줄에 적는다. PR 을 열게 하는지와 관계없이 모든 지시서에 필수다.
  `launch-worker` 가 이 줄이 없으면 거부한다. 예: 「허락: push 와 draft PR 생성(base main)은 사용자가 허락했다.」
  허락한 것이 없으면 「허락: 없음. push 까지만 한다.」 를 적는다.
  codex worker 의 기본 지침은 GitHub 게시를 막아, 지시서에 「PR 을 연다」 만 있으면 승인을 다시 묻는다.
  `spec-line` 이 이 줄을 `--spec` 의 첫 지시 줄에 붙인다
- PR 을 열게 하면 「`gh pr create` 나 리뷰 회신이 거부되면 push 한 뒤 본문 파일 경로(회신이면 스레드 id 와 회신 파일)를 status 로 보낸다. 묻지 않고 다음 일을 계속한다」 도 적는다.
  지시서의 승인은 worker 세션의 권한 분류기에 전달되지 않아, 같은 요청이 세션마다 허용되기도 하고 거부되기도 한다.
  받은 뒤의 처리는 [`replying.md`](replying.md) 의 「PR 생성과 리뷰 회신을 대신 한다」 가 정한다
- PR 을 열게 하면 「PR 본문 파일은 PR 이 열릴 때까지 지우지 않는다」 도 적는다. 코디네이터가 그 파일로 PR 을 연다
- PR 을 열게 하면 「PR 은 기준 브랜치를 base 로 따로 연다. 다른 PR 브랜치를 base 로 두지 않는다」 도 적는다.
  앞 PR 브랜치를 base 로 연 PR 은 앞 PR 을 `--delete-branch` 로 머지하면 자동으로 닫히거나 앞 브랜치로 머지된다
- PR 을 몇 개로 나눌지는 worker 가 정하고, 머지 순서는 코디네이터가 정해 지시서에 적는다. 뒤 PR 이 앞 PR 의 코드에 기대면 머지 순서와, 앞 PR 머지 뒤 뒤 브랜치를 기준 브랜치 위로 다시 맞출 담당(worker 또는 코디네이터)을 적는다.
  base 를 따로 열라는 규칙과 부딪혀 worker 가 순서를 스스로 정하게 된다
- 「파일 수정은 `sed -i` 대신 Edit 나 python 으로 한다」.
  macOS `sed` 는 `-i ''` 가 필요하고 줄바꿈 치환이 실패한다
- 의존성이 필요한 검사를 시키면 「워크트리 안에서 lockfile 로 설치한다(`npm ci`, `pnpm install --frozen-lockfile`)」 를 적는다. 원래 저장소의 `node_modules` 를 심볼릭 링크로 걸게 하지 않는다.
  링크를 지우는 `rm` 이 워크트리 밖 경로로 풀려 권한 확인 창이 뜨고, worker 가 그 자리에서 멈춘다
- 「삭제처럼 되돌리기 어려운 쓰기는 하위 에이전트에 맡기지 않고 본체가 한다」.
  하위 에이전트가 받은 지시는 사용자 승인으로 인정되지 않아 권한 분류기가 막는다
- 소계획으로 나누는 일을 맡기면 「worker 를 띄우지 않는다. 소계획마다 `ready:` status 메시지를 보낸다」 와 그 형식을 적는다.
  worker 는 다시 worker 를 띄우지 못한다(`nested_worker_depth_exceeded`)
- 「하위 에이전트는 orca 명령을 쓰지 않는다. 스폰 프롬프트에 이 줄을 넣는다」 와 「PR 을 열면 status 로 `준비됨 #PR, head SHA` 를 보내고, 머지될 때까지 CI 실패, 충돌, 기준 브랜치 변경을 직접 처리하며, MERGED 를 확인한 뒤 `worker_done` 을 본체가 한 번만 보낸다」.
  하위 에이전트는 worker 와 같은 터미널 핸들로 보내서, Orca 는 누가 보낸 `worker_done` 인지 구분하지 못한다.
  이 규칙은 예방이고, 완료 판정은 6단계가 git 으로 한다
- 「권한 확인 창이나 거부로 막히면 우회하지 말고 ask 로 알린다. 터미널에만 적고 기다리지 않는다」.
  터미널에만 적으면 코디네이터의 `check --wait` 가 깨어나지 않아 worker 가 stale 로 남는다
- PR 은 머지될 때까지 만든 worker 가 맡는다. 기준 브랜치와 충돌하거나 CI 가 실패하면 그 worker 가 푼다. 코디네이터는 worker 브랜치에서 직접 풀지 않는다. 지시서 하나는 PR 하나로 끝나는 크기로 쓴다(`planning` 의 plan 크기 기준). 더 큰 일은 지시서를 나누고 앞 PR 이 머지된 뒤 다음 지시서를 쓴다.
  [`replying.md`](replying.md) 의 「충돌과 리뷰 반영은 만든 worker 가 이어 받는다」 가 정한다

**기술 판단과 사용자 판단을 나눠 적는다.**
파일 위치, 테스트 방식, 리뷰 하위 등급 반영 여부처럼 되돌리기 쉬운 기술 판단은 묻지 않고 권장안으로 진행하게 하고, 고른 안을 status 와 PR 본문 「결정」 절에 남기게 한다.
외부 계약 변경, 팀 결정을 뒤집는 것, 외부에 보이는 글, 공유 서버나 DB 쓰기, 비용이 드는 작업, 범위를 넘는 변경, 데이터 삭제만 ask 로 묻게 한다.
나누지 않으면 worker 가 사소한 것마다 묻고 멈추거나, 사용자가 정할 것을 스스로 정한다.

**같은 파일이나 화면, 문서를 고치는 일은 동시에 맡기지 않는다.** 먼저 머지된 쪽 때문에 뒤 PR 이 충돌하고, 충돌을 합치다 다시 깨진다.
겹치는 일은 앞 PR 이 머지된 뒤 그 위에서 시작하게 지시서에 적는다.

## 띄우기 전 검사

**지시서를 다 쓰면 띄우기 전에 `spec-lint` 로 한 번에 검사한다.** 이번에 띄울 지시서를 모두 넘긴다. 공통 지시서는 넘기지 않는다.
지시서끼리 담당 파일이 겹치거나, 가리킨 함수가 없거나, 금지 명령을 요구하는 것을 띄운 뒤에 알면 worker 가 ask 로 멈추거나 뒤 PR 이 충돌한다.

```bash
node --disable-warning=ExperimentalWarning "$SKILL_DIR/scripts/spec-lint.ts" --repo "$REPO" --check-overlay "$SPECS_DIR"/spec-a.md "$SPECS_DIR"/spec-b.md
```

종료 코드 1 이면 발견 줄을 보고 지시서를 고친다. `경로` 경고는 새로 만들 파일이면 그대로 둔다.
`오버레이` 발견은 오버레이나 `.orch/config.json` 이 `origin/<기준 브랜치>` 에 없는 파일을 가리킨다는 뜻이라 그 파일을 고친다. 기준 브랜치가 main 이 아니면 `--base` 로 준다.
담당 범위는 지시서에 `` 담당: `src/a/**`, `docs/a.md` `` 줄로 적는다. 그 줄이 없으면 겹침 검사가 그 지시서를 건너뛴다.
금지 문구가 든 줄이 정말 필요하면 그 줄을 `예외:` 로 시작한다.
코디네이터 소유 경로, 소유 계약, 저장소의 금지 문구는 오버레이의 `## spec-lint` 절에 둔다. 형식은 스크립트 머리 주석이 소유한다.

## 스킬 개선 후보를 모으게 할 때

worker 가 스킬을 쓰다 막힌 곳을 모으게 하려면 공통 지시서 틀의 「스킬 개선 후보 보고」 절을 남긴다.
후보는 worker 가 아니라 코디네이터가 사용자와 정한 뒤 반영한다. worker 가 스킬 파일을 직접 고치면 같은 스킬을 쓰는 다른 worker 의 절차가 도중에 바뀐다.
