# docs-consolidate

**목표: 기능 문서를 현재 구현에 맞추고 실제로 반복되는 규칙만 공통화한다.**

모드마다 실행 시점과 통과 조건이 달라 표를 따로 둔다.

| 모드 | 언제 | 끝났다고 볼 때 |
| --- | --- | --- |
| 후보 추출 | 기능 검증 뒤 | 기능 문서가 구현과 맞고 후보의 근거 또는 `후보 없음` 이 남았다 |
| 공통화 | 사용자나 orch 가 모인 후보의 문서 정리를 작업 범위로 지정했을 때 | 지정한 후보마다 판정이 있고 채택한 내용이 한곳에 있으며 문서 검증을 통과했다 |

[기능 문서와 단계 인계](../spec/references/feature-docs.md)와 [문서 소유권과 변경](../spec/references/document-ownership.md), [문서 대조 양식](templates/document-review.md)을 먼저 읽는다.
plan 번들의 `scripts/overlay_paths.ts --skill docs-consolidate` 를 대상 저장소 루트에서 실행하고 출력의 `search` 순서대로 경로·검사 명령을 읽는다.
감사 범위가 정해졌으면 그 파일 경로도 인자로 넘긴다. 모노레포 판정, 종료 코드, 자기 오버레이가 없을 때 읽는 순서는 [오버레이 탐색 규칙](../plan/references/monorepo.md)을 따른다.

계획 정리는 [계획 수명 규칙](../plan/references/plan-lifecycle.md)을 따른다.

## 기능 검증 뒤: 후보 추출

입력은 검증한 스펙, 변경 diff, verify 결과와 관련 기능·공유 계약, 그리고 implementation·review-fix 가 PR 본문이나 결과 보고에 적은 저장소 규칙 후보다.

| 단계 | 이름 | 통과 조건 |
| --- | --- | --- |
| 1 | 기능 문서 대조 | `document-review.md` 의 문서 정합성 표에서 기능 문서 행마다 처리 결과가 정합, 문구 수정, 앞 단계 반환 중 하나다 |
| 2 | 공통 책임 문서 대조 | 이번 기능이 공통 흐름·권한·상태를 바꿨으면 그 책임 문서 행에 결과가 있다. 바꾸지 않았으면 영향 없음의 근거가 있다 |
| 3 | 후보 찾기 | 관련 스펙·계약만 읽었고 중복·모순·공유 개념 후보와 받은 규칙 후보를 가렸다 |
| 4 | 후보 기록 | 후보마다 두 위치, 공통점·차이, 제안할 소유 위치가 있다. 없으면 검토 범위와 `후보 없음` 이 있다 |
| 5 | 인계 | 결과가 PR 본문이나 그 PR 의 증거 파일에 있다 |

1. **기능 문서 대조.** 이번 기능의 문서가 검증한 구현과 맞는지 확인한다. 문서의 오타·누락은 해당 기능 범위에서 고친다.
   합의한 동작을 코드에 맞춰 바꾸지 않는다. 의미 차이는 spec, technical-design 또는 implementation 으로 돌려보낸다.
2. **공통 책임 문서 대조.** 이번 기능이 공통 흐름·권한·상태를 바꿨으면 해당 책임 문서도 대조한다. 필요한 정합성 수정을 공통화 후보로 미루지 않는다.
   변경한 ADR 과 현재 원본의 연결·중복·대체 관계도 [결정 기록의 단계별 책임](../spec/references/document-ownership.md#결정-기록의-단계별-책임)으로 대조한다. 새 정책은 spec, 새 구조 결정은 technical-design 으로 반환한다. 관련 없는 문서 감사로 범위를 넓히지 않는다.
3. **후보 찾기.** 관련 스펙·계약만 읽고 중복·모순·공유 개념 후보를 찾는다. 저장소 전체 감사로 범위를 넓히지 않는다.
   도메인 규칙 변경이 있었으면 갱신 누락, 중복, 상충을 마지막으로 확인한다. 현재 기준의 갱신은 해당 PR 의 책임이라 여기서 대신 정하지 않는다.
   누락을 찾으면 정책을 직접 정하지 않고 spec 이나 해당 기능 PR 로 돌려보낸다. 여러 스펙에 흩어진 같은 규칙은 도메인 문서로 옮길 공통화 후보로 적는다.
   기준은 [문서 소유권의 「단계별 책임」](../spec/references/document-ownership.md#단계별-책임)이 정한다.
   implementation·review-fix 가 적은 저장소 규칙 후보(반복될 실패를 일반화한 규칙 한 줄과 제안한 넣을 곳)도 여기서 모아 다음 단계의 후보로 넘긴다.
4. **후보 기록.** 후보마다 두 위치와 공통점·차이·제안할 소유 위치를 적는다. 없으면 검토 범위와 `후보 없음` 을 적는다.
5. **인계.** 결과를 PR 본문이나 그 PR 의 증거 파일로 orch 에 넘긴다. 중앙 INDEX·진행표를 갱신하지 않는다.

이 모드에서 공유 계약을 새로 추출하거나 재구성하지 않는다. 저장소 규칙 파일도 고치지 않는다.
기능 문서를 수정했으면 저장소 문서 검사를 실행하고 verify 에 문서 재검토를 요청한다.
코드·스펙의 동작 의미가 그대로면 제품 실행 테스트 전체를 반복하지 않는다.
공통화 후보가 남아 있어도 기능 완료를 막지 않는다. 실제 모순이 동작을 바꾸는 경우는 예외로 verify 에 돌려보낸다.

## 후보가 모였을 때: 공통화

사용자 또는 orch 가 후보 묶음의 문서 정리를 작업 범위로 지정한 경우에만 수행한다.
후보가 생겼다는 이유로 현재 PR 의 범위를 자동 확장하지 않는다.

| 단계 | 이름 | 통과 조건 |
| --- | --- | --- |
| 1 | 후보 판정 | 지정한 후보마다 채택, 보류, 기각 중 하나와 근거가 있다 |
| 2 | 소유 위치 결정 | 채택한 규칙마다 소유 위치(기존 계약, `docs/contracts/<주제>.md`, 도메인 문서, 저장소 규칙의 넣을 곳)가 하나다 |
| 3 | 옮기기 | 공통 내용이 소유 위치 한곳에 있고 기능 문서의 복제가 링크로 바뀌었다 |
| 4 | 문서 검증 | 링크와 중복·의미 보존을 확인했고 저장소의 문서 검사가 통과했다 |
| 5 | 보고 | 변경 범위와 채택·보류·기각 근거가 나갔고 별도 PR 처리가 orch 에 넘어갔다 |

1. **후보 판정.** 후보의 실제 구현과 요구사항을 대조한다. 표현만 비슷하면 기각하고 아직 변동이 크면 보류한다.
2. **소유 위치 결정.** 채택할 규칙의 소유 위치를 기존 계약 또는 `docs/contracts/<주제>.md` 로 정한다. 여러 기능이 참조하는 도메인 규칙이면 도메인 문서가 소유 위치다.
   implementation·review-fix 가 적은 저장소 규칙 후보와 반복 함정 목록의 항목은 [plan 의 `references/rule-placement.md`](../plan/references/rule-placement.md) 로 넣을 곳(검사, 코드 구조, 규칙 문장)을 고른다.
3. **옮기기.** 공통 내용은 한곳으로 옮기고 기능 문서의 복제는 링크로 바꾼다. 기존 공통 계약이 있으면 새 사본을 만들지 않는다.
4. **문서 검증.** 관련 링크와 중복·의미 보존을 확인하고 저장소의 문서 검사를 실행한다.
5. **보고.** 변경 범위와 채택·보류·기각 근거를 보고하고 별도 PR 처리는 orch 에 넘긴다.

제품 동작, 권한, 데이터 의미를 바꿔야 하면 문서 정리로 처리하지 않고 새 spec 작업으로 넘긴다.
문서 경로를 바꾸면 소비자와 링크도 함께 갱신한다. 원본이 정해진 API/DB 스키마를 문서로 복제하지 않는다.

orch 가 관련 기능 묶음을 마쳤거나 후보 검토를 요청할 때 실행한다.
