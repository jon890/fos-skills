# orch: 「머지해도 되나」 판단을 하나로 모은다

확인: 2026-11-24

## 목표

머지 관문(`orch queue gate`), 머지 큐, 루프 자동 머지가 같은 PR 에 같은 답을 낸다. 지금은 셋이 조건을 따로 확인해서, 보드 보류는 루프만 보고 통합 테스트·비공개 낱말은 관문만 보는 식으로 어긋나 있다.
근거: 아키텍처 검토(2026-11-24)의 1번 후보와 조건 조사. 같은 개념을 고칠 때마다 관문, 루프, finish-pr 을 함께 고쳤다(예: 커밋 6c2340d2, PR 619 의 Codex 지적 3건).

## 범위

이번 범위:

- PR 하나의 상태를 받아 막히는 이유를 종류와 함께 모두 돌려주는 판단을 하나로 모은다. 관문, 머지 큐, 루프 자동 머지가 이 판단을 쓴다. finish-pr 은 머지 뒤라 고치지 않는다.
- 아래 REQ2~REQ5 의 동작 변경.
- 「draft 로 CI 미루기」 저장소 옵션과 딸린 것(`ci-ready.ts`, `orch queue ready`, `--skipped-is-missing`, 오버레이 표의 그 행과 지시 문구, doctor·설정 검증)을 없앤다. 옛 오버레이나 설정에 그 옵션이 남아 있으면 doctor 가 경고한다.

범위 밖:

- work-board 가 이 판단 결과를 받게 바꾸는 일(3번 후보). 루프가 남기는 대기 문구 형식은 그대로 둔다.
- 여러 PR 의 마이그레이션 번호 순서 조정. 루프에 그대로 둔다.
- 머지 큐만 하는 일(base 최신화, 겹침 판정, 합친 사본 검사, before-merge 이벤트).

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 같은 PR 에 같은 답 | 같은 PR 상태를 주면 관문, 머지 큐, 루프가 같은 조건 목록으로 판단한다. 루프는 가벼운 범위(충돌 여부, 통합 테스트 기록, 비공개 낱말 댓글 검사를 뺀 범위)만 묻고, 관문과 머지 큐는 전체 범위를 묻는다. 범위에 든 조건의 판단 결과는 호출부와 관계없이 같다 |
| REQ2 | 보류는 머지 단계에서 막는다 | 판단은 「준비됨을 알려도 되나」 와 「지금 머지해도 되나」 두 단계다. 지시서 보류, PR 본문 보류, 보드 보류는 머지 단계에서 막는다. 사람이 `orch queue merge` 로 직접 머지해도 보드 보류가 있으면 막힌다. worker 가 쓰는 `orch queue gate` 는 보류를 `HOLD` 줄로 알리고 통과한다 |
| REQ3 | draft 는 준비 안 됨 | draft PR 은 `orch queue gate` 가 GATE-FAIL 로 낸다. 예외 없음: draft 를 통과시키는 저장소 설정을 두지 않는다 |
| REQ4 | 체크가 없으면 준비 안 됨 | 필수 체크 설정과 관계없이 PR 에 CI 체크가 하나도 없으면 준비 안 됨이다. CI 가 없는 저장소는 설정 값으로 이 조건을 끈다 |
| REQ5 | 리뷰 설정이 없으면 자동 머지하지 않는다 | `queue.auto_review` 에 `trusted_bots` 도 `review_checks` 도 없으면 루프는 어떤 PR 도 자동 머지하지 않고 그 이유를 대기 문구로 남긴다. 기능 PR 과 일반 PR 의 구분은 없앤다. 코디네이터의 직접 머지는 막지 않는다 |
| REQ6 | 지금 커밋 기준 | 판단 중에 PR HEAD 가 바뀌면 그 판단은 통과로 보지 않는다(루프 포함) |
