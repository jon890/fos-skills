# plan 하나는 PR 하나다

**plan 하나는 PR 하나로 끝나는 크기로 자른다. 대략 하루 안에 구현하고 머지까지 가는 일이다.**
더 큰 일은 plan 을 여럿으로 나누고, 지금 할 plan 만 자세히 쓴다.
뒤의 일은 목표 표나 그 저장소의 할 일 목록에 한 줄로 두고, 앞 PR 이 머지된 뒤 그때의 코드를 보고 계획한다.

## 이유

미리 써 둔 phase 문서는 앞 phase 를 하는 사이 낡는다.
phase 14개짜리 plan 에서 앞 phase 를 하는 동안 다른 리팩터가 디렉터리를 옮겨, 뒤 phase 일곱 개의 경로가 모두 틀렸다.
크기가 크면 구현자가 draft PR 에서 멈추고, CI 실패와 충돌이 날 때마다 다시 맡겨야 한다.

## 어디서 판단하나

| 단계 | 판단 |
| --- | --- |
| 1 구현 가능성 | 「이 변경이 어디까지 손대나」 에서 이번 PR 의 범위를 한 문장으로 정한다. 이 문장이 `index.json` 의 `pr_scope` 가 된다 |
| 8 task 파일 생성 | phase 로 나누기 전에 범위가 PR 하나에 들어가는지 본다. 넘으면 plan 을 나누고 지금 할 것만 phase 로 쓴다. 뒤로 미룬 일은 `deferred` 에 적는다 |

사용자에게 묻는 것은 어디서 자르는가뿐이다. 앞 plan 이 끝나야 의미가 생기는 선을 고른다.

## 뒤로 미룬 일

뒤의 plan 은 phase 문서를 쓰지 않는다. 한 줄로 아래 세 가지만 남긴다.

| 칸 | 담는 것 |
| --- | --- |
| `what` | 무엇을 하나 |
| `why` | 왜 지금 이 plan 에 넣지 않나 |
| `after` | 앞 plan 의 무엇이 머지된 뒤에 하나 |

한 줄은 `index.json` 의 `deferred` 에 적고, 저장소에 목표 표나 할 일 목록이 있으면 거기에도 옮긴다.
`deferred` 가 가리키는 일은 그 PR 이 머지된 뒤 `planning` 을 다시 열어 계획한다.

## 검사 기준

`verify_task.py` 가 아래를 본다. 기준은 저장소 7곳의 plan 517개를 측정해 정했다.

| 측정 | p50 | p90 | p95 | 최대 |
| --- | --- | --- | --- | --- |
| phase 수 | 3 | 5 | 6 | 19 |
| 변경 파일 수(`docs/` 와 `tasks/` 제외) | 12 | 50 | 77 | 530 |

| 검사 | 결과 |
| --- | --- |
| phase 가 6개를 넘는다 | 위반. plan 을 나눈다 |
| 변경 파일이 40개를 넘는다 | 경고. 디렉터리 이동 같은 일괄 이동이면 `pr_scope` 에 그렇게 적는다 |
| `pr_scope` 가 비었거나 한 문장이 아니다 | 위반 |
| `deferred` 칸이 없거나, 항목에 `what`, `why`, `after` 가 비었다 | 위반. 미룬 일이 없으면 빈 배열이다 |

phase 6개 선은 p95 다. 이 선을 넘는 plan 은 5% 이하이고 대부분 디렉터리 이동처럼 앞 phase 가 뒤 phase 의 경로를 바꾸는 일이었다.
`created_at` 이 2026-10-25 보다 이르거나 없는 옛 plan 은 같은 검사를 경고로만 낸다. 진행 중인 계획서를 다시 쓰게 하지 않는다.

계획서를 만든 날부터 지운 날까지의 길이는 기준으로 쓰지 않았다.
지운 날이 PR 머지가 아니라 나중의 일괄 정리 커밋인 plan 이 섞여, 머지까지 걸린 시간을 알 수 없다.
