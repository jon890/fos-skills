# 감사 축

「의미 검사」 단계에서 읽는다.

## ADR 상태를 먼저 본다

`status: superseded` 인 ADR 은 이력이다. 부패 축과 자명성 축을 적용하지 않는다.
당시의 코드와 경로를 가리키는 것이 정상이고, 대체됐다는 사실 자체가 남길 이유다.

**대신 대체 표기와 위치, 링크·색인 갱신 규약을 지켰는지 본다.** 어긋난 자리가 발견이다.
`status` 가 없는 ADR 을 어떻게 읽는지를 포함해 규약은
[technical-design 의 adr-rules.md](../../technical-design/references/adr-rules.md) 가 소유한다.

## 완료된 plan 은 제거 후보다

[계획 수명 규칙](../../plan/references/plan-lifecycle.md)으로 보존 정책과 실제 완료 여부를 먼저 판정한다.
머지된 PR 또는 completed 계획 중 삭제 정책에 해당하는 것만 검토한다. 진행 중인 계획과 보존 정책의 계획은 제거 후보가 아니다.
결정·검증 절차·기대값·실제 증거가 책임 문서 또는 PR 에 남았는지 대조한다. 없으면 제거하지 않고 빠진 기록을 보고한다.
제거 후보도 docs-audit 의 기존 승인 절차를 따른다. 유일한 결정·증거를 자동 삭제하지 않는다.

## 계획서를 번호로 가리키지 않는다

계획서가 제거되므로, 문서와 코드가 계획서를 번호로 가리킨 자리는 그때 깨진 참조가 된다.

**기본은 아무것도 적지 않는 것이다.** 무엇이 언제 왜 바뀌었는지는 git 이력이 이미 추적한다.
근거가 필요할 때만 아래를 적는다.

| 남길 것 | 무엇을 적나 |
| --- | --- |
| 결정의 근거 | ADR 번호 |
| 변경의 이력 | PR 번호 |
| 그 밖 | 적지 않는다 |

커밋 SHA 는 적지 않는다. rebase 와 squash 로 값이 바뀌어 같은 변경을 다시 찾을 수 없다.

### 유형별 처리

`static_check.py` 가 `PLAN_REF` 로 위치를 뽑는다. 처리는 유형이 정한다.

| 유형 | 예 | 처리 |
| --- | --- | --- |
| 출처 표기 | 결정 문장 끝에 계획서 번호를 괄호로 붙인 것 | 지운다 |
| 내용 위임 | 내용을 적지 않고 계획서를 읽으라고 한 것 | 내용을 책임 문서로 옮기고 지운다 |
| 시간 축 | 계획서 번호를 시간 순서로 쓰는 판정 기준 | 날짜로 바꾼다 |
| 절차 설명 | 계획서를 만드는 방법을 설명한 것 | 유지한다 |

**계획서 번호를 시간 축으로 쓰지 않는다.**
번호는 계획서와 함께 사라지므로, 사라진 뒤에는 어느 쪽이 최근인지 판정할 수 없다.
날짜처럼 계획서 수명과 무관한 값을 쓴다.

### 예외

아래 둘은 발견으로 올리지 않는다.

- **기존 파일과 식별자의 이름.** 이름은 참조가 아니라 식별자다.
  바꾸면 그 이름을 부르는 쪽도 함께 고쳐야 해서 비용이 참조 하나보다 크다.
  새로 만드는 이름에는 계획서 번호를 넣지 않는다.
- **측정 기록에 남은 실행 경로.** 그 시점의 실행 환경을 적은 것이라, 고치면 기록이 틀린 값이 된다.

## A. 부패

코드가 docs 와 맞는가. 제거된 엔티티가 docs 에 남아있지 않은가.

- 제거된 함수·컴포넌트·엔드포인트명이 docs 에 남아있다.
- DB 스키마와 스키마 문서의 테이블·필드가 불일치한다.
- 디렉터리·파일 경로가 실제와 다르다.
- "제거 완료" ADR 의 제거 대상이 여전히 코드에 존재한다.
- 미갱신 환경변수 표, 실재하지 않는 경로.

> 레포 특화 부패 검사(스키마 파일 경로·라우트·config 키 대조)는 오버레이의 grep 명령을 따른다.

### 설정 값과 도메인 문서의 어긋남

판정 값의 원본이 버전 관리되는 설정(룰 설정, DB 사전)이면 도메인 문서는 그 의미와 근거를 설명한다. 둘이 어긋난 자리가 발견이다.

- 숫자가 같은지를 보지 않는다. 문서가 설명한 규칙의 의미, 허용 범위와 설정 값이 맞는지, 문서가 가리키는 설정 키가 실제로 있는지를 본다.
- 문서가 설정 값을 복제해 두었으면 중복 축의 발견으로 함께 올린다. 값은 설정이 원본이다.
- 허용 범위 안의 값 조정은 설정 변경 이력이 맡는다. 의미가 바뀐 변경인데 스펙과 문서 갱신이 없으면 발견이다.

## B. 과대화

ADR·docs 가 구현 세부로 비대해졌는가.

**ADR 에 무엇을 담는지는 [technical-design 의 adr-rules.md](../../technical-design/references/adr-rules.md) 「담는 것과 담지 않는 것」 이 소유한다.** 이 축은 그 문서를 적용해 감사한다.

- ADR 본문이 「담지 않는 것」 에 든 내용(긴 코드 블록, 파일·디렉터리 복제, 이름을 줄 단위로 나열한 표, 스택 규칙 반복, 작업 내역)을 담았으면 발견이다.
- 중간 단계를 남기고 최종 상태와 이유를 흐렸으면 발견이다.

### ADR 이 현재 규칙의 원본 노릇을 한다

**지금 따를 도메인 규칙이나 기준값을 ADR 에서만 읽을 수 있으면 발견이다.**
ADR 이 도메인 모델이나 정책을 고른 이유를 담는 것은 발견이 아니다. 경계는 [spec 의 문서 소유권 「ADR 과 도메인 문서」](../../spec/references/document-ownership.md#adr-과-도메인-문서)가 소유한다.

- 판정 질문: 이 규칙을 지금 적용하려는 사람이 ADR 을 열어야만 기준을 알 수 있는가? 그렇다면 원본 노릇이다.
- ADR 과 도메인 문서가 같은 규칙을 다르게 적었으면 부패 축의 `Critical` 이다. 도메인 문서가 없거나 링크가 없으면 `Warning` 이다.
- 수정안은 현재 규칙을 도메인 문서로 옮기고 ADR 과 서로 링크하는 것이다. 기존 ADR 은 전부 다시 쓰지 않고 이번 감사 범위가 건드리는 영역만 제안한다.
- `superseded` ADR 은 이력이다. 그 안의 규칙이 아직 유효한데 도메인 문서에 없을 때만 발견이다.

## C. 의사결정 추론성

ADR 이 "왜" 를 담고 있는가. "결정 / 맥락 / 대안 기각" 구조가 있는가.

검출 대상:

- "결정" 만 있고 "맥락·이유·대안" 이 없는 ADR
- 맥락이 "요구사항 추가" 같은 순환 설명
- 대안 기각이 없거나 "기각" 만 있고 근거가 없음

## D. 중복

같은 내용이 여러 docs 에 본문으로 반복되는가.

검출 대상:

- 같은 필드 목록이 ADR 과 스키마 문서 양쪽에 있음
- 흐름 요약이 PRD 와 flow 문서 양쪽에 있음
- 그 저장소 지침의 스택 규칙이 아키텍처 문서에 복사됨

원칙: **정의는 1곳, 다른 문서는 링크 또는 짧은 참조.**

## E. ADR 자명성

**ADR 을 남길지의 기준은 [technical-design 의 adr-rules.md](../../technical-design/references/adr-rules.md) 「남길 조건」 과 「코드로 자명한 결정은 남기지 않는다」 가 소유한다.** 이 축은 그 문서의 폐기 후보 판정을 적용해 감사한다.

그 문서의 자명성 질문이 모두 맞으면 폐기 후보로 보고, 연결 문서와 외부 참조를 확인한 뒤 판정한다.
