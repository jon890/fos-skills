# 하네스 감사 축

각 축에서 발견한 항목은 파일 위치, 측정값, 실행 결과와 함께 판정표에 기록한다.
사례의 표면 형태보다 왜 기존 감사가 실패했는지를 현재 대상에 대입한다.

이 문서는 무엇을 찾을지를 소유한다.
찾은 것을 유지할지 지울지는 [`references/judgment.md`](judgment.md)가 소유한다.

## 소유권 중복

같은 지시가 여러 파일에 본문으로 존재하면 어느 문서가 소유자인지 확인한다.
링크나 짧은 포인터는 중복으로 보지 않는다.
독립적으로 수정될 수 있는 반복 문구는 정책이 갈라질 위험이 있다.

**소유자에는 실행 파일도 들어간다.** 스크립트의 docstring, `--help` 출력, 코드 주석이
사용법과 내부 동작을 소유한다. 산문이 그것을 다시 적었는지 본다.

- **실측 사례:** 어떤 스킬의 `SKILL.md` 절차와 참조 파일에 같은 문구가 함께 남았다.
  두 파일이 같은 행동을 소유한 상태였다.
- **실측 사례:** 셸 스크립트 여섯을 Python 으로 옮기자 각 파일이 docstring 을 갖게 됐는데
  `SKILL.md` 가 인자 기본값과 페이지네이션 크기와 엔드포인트를 그대로 다시 적고 있었다.
  26줄을 지웠고 판단이 바뀐 것은 없었다.

**형제 스킬도 소유자다.** 어떤 단계가 다른 스킬을 부른다면 그 스킬의 절차와 함정은 그쪽이 소유한다.
부르는 쪽에는 넘길 값과 언제 부르는지만 둔다.

- **실측 사례:** 한 스킬의 게시 단계가 게시 전 공개 점검 3항목, 인증 실패 복구 명령,
  반환 주소 둘 중 어느 것을 전달할지를 모두 적고 있었다. 셋 다 호출 대상 스킬이 이미 소유한 것이었다.
  넘길 값 표와 호출 시점만 남기니 18줄이 9줄이 됐다.
- **실측 사례:** 같은 스킬이 지식 기반에 결과를 되돌리는 절차를 적고 있었는데
  그 절차는 지식 기반 스킬이 소유한다. 부르는 쪽이 적을 이유가 없었다.

## 죽은 검출

검출 명령이 존재한다는 사실과 검출력이 살아 있다는 사실을 구분한다.
입력 경로와 작업 디렉터리를 먼저 검증하고 대조 표본으로 검출력을 확인한다.
이 과정이 없으면 0건이 거짓 통과가 될 수 있다.

**문서가 준 명령이 도는지도 같은 자리에서 본다.** 검출 명령만 보지 않는다.
실행 가능한 블록을 전부 돌리고, 상대경로가 어느 디렉터리를 전제하는지 함께 본다.

- **실측 사례:** 리팩터링으로 진입점 파일이 60줄로 줄었다.
  검출 명령 7건은 그 파일을 계속 가리켜 실제 대상을 보지 않았다.
- **실측 사례:** `git grep` 은 git 에 추가되기 전 파일을 보지 못한다.
  새로 만든 검사 파일이 자기 선언을 위반으로 잡는 문제가 있었는데,
  그 파일이 아직 추적되지 않아 로컬에서는 0건으로 통과했다.
  커밋한 뒤에 드러났다. 새로 만든 파일을 대상으로 삼는 검사는 추적 상태를 함께 본다.
- **실측 사례:** 그대로 실행하면 반드시 실패하는 명령이 둘 있었다.
  셸 변수를 `export` 없이 두고 뒤따르는 Python 이 환경 변수로 읽어 `KeyError` 가 났고,
  없는 속성을 찍어 `AttributeError` 가 났다.
  둘 다 즉시 예외로 죽어 결과가 틀리지는 않지만, 문서가 준 명령이 동작하지 않는다.

## 값 하드코딩

모델 식별자, 버전, 단계 범위, 개수, 목록처럼 다른 곳이 소유해야 할 값을 산문이 복제하는지 찾는다.
문서에는 값 자체보다 값을 읽을 경로와 판정 방법을 둔다.

- **실측 사례:** 문서의 모델 식별자가 실제 설정과 달랐다.
  감사자는 잘못된 역량 기준으로 지시를 판정했다.
- **실측 사례:** 같은 캐시 파일 목록이 네 문서에 각각 다른 개수로 적혀 있었다.
  어느 것도 실제와 맞지 않았고, 문서끼리 비교해서는 무엇이 옳은지 가릴 수 없었다.

목록을 지우기 전에 그것이 유일한 출처인지 먼저 판정한다. 절차는 `judgment.md` 에 있다.

## 지시 충돌

같은 절차를 두 문서가 반대로 규정하는지 찾는다.
문서끼리 비교해서는 어느 쪽이 맞는지 정할 수 없으므로 실행 경로를 실측해 판정한다.

- **실측 사례:** 한 문서는 검증 순서를 타입 검사 다음 린트로, 오버레이는 그 반대로 적었다.
  지속적 통합 설정의 단계 순서를 읽어 판정했다.
- **실측 사례:** 한 하네스의 역할 정의는 레이어 직접 참조를 금지했고
  프로젝트 지침은 일부 경우를 허용했다. 같은 코드에 정반대 판정이 나올 수 있었다.

**한 문서 안도 본다.** 그 문서가 비용, 위험, 금지를 적어 둔 자리를 찾고,
같은 문서의 다른 절이 그것을 요구하는지 확인한다.
비용을 적어 둔 절이 그 비용을 쓰라고 시키는 자리가 대표적이다.

- **실측 사례:** 2단계가 조회 한 번에 21,870 이 나간다고 기록해 두고,
  바로 그 2단계가 연결 테스트로 같은 조회를 시켰다.
  4단계는 「빈도 상위 시그니처 두셋은 반드시 시간순 추적으로 판별한다」고 못박아
  같은 조회를 세 번 부르게 했다. 지시대로 실행하면 약 11시간분이 나간다.
  실제로 그 연결 테스트 한 번으로 잔량이 음수가 되어 3시간을 쓰지 못했다.

## 계층 분리

매 실행에 필요한 오케스트레이션과 특정 조건에서만 필요한 복구 절차를 분리한다.
조건부 세부를 참조 파일로 옮길 때는 본문에 발동 조건과 읽을 경로를 남긴다.

- **실측 사례:** 366줄인 스킬에 참조 파일이 하나도 없었다.
  충돌이 생겼을 때만 필요한 절차 45줄이 매 실행 컨텍스트를 차지했다.

## 스킬 구조와 유지보수성

개인 스킬은 사용자와 에이전트가 함께 읽고 고치는 작업 문서다.
목표와 책임 범위가 먼저 보이고, 서로 다른 목표가 한 스킬에 섞였는지 확인한다.
면접 연습, 문서 작성, 배포처럼 완료 조건과 실행 리듬이 다르면 스킬이나 단계 책임을 분리한다.

단계별로 필요한 context만 읽게 되어 있는지 확인한다.
`SKILL.md`는 목표, 진행 순서와 발동 조건을 소유하고, 세부 절차와 예시는 해당 단계의 reference가 소유한다.
끝의 참고 자료 목록보다 사용하는 단계 옆의 파일 참조가 유지보수하기 쉽다.

정적 검사는 산문으로 반복하지 않고 실행할 스크립트와 실패 대응을 확인한다.
검사 결과 0건을 통과로 단정하는 문장은 `죽은 검출` 축으로 다시 본다.

사람이 읽는 문서 구조도 감사 대상이다.
문단은 작업 주제별로 나누고, 순서가 있으면 번호 목록을 쓰며, 같은 속성을 비교할 때만 표를 쓴다.
강조는 목표와 중요한 판단 조건에만 쓴다.
파일 참조는 사람이 열 수 있는 Markdown 링크로 두고, 실행 명령의 경로는 복사 가능한 코드 원문으로 둔다.

스킬 문서의 층과 배치는 사용자 전역 `~/.claude/references/skill-structure.md`가 소유한다.
한국어 표현과 문서 구조의 판정은 `korean-check` 스킬의
[`references/`](../../korean-check/references/)가 소유한다.
공개 저장소에 환경 특정 절대 경로를 노출하지 않도록 주의한다.

## 정책 잔존

새 정책의 선언을 찾은 다음, 이전 정책이 실행 절차 가까이에 남았는지 검색한다.
모델은 멀리 있는 원칙보다 당장 실행하는 단계 옆의 구체적인 문구를 따르기 쉽다.

- **실측 사례:** 자율 진행 정책으로 바뀐 뒤에도 단계 절차 옆에 옛 문구가 남았다.
  사용자 확정을 요구하는 문구가 매 단계 실행을 멈췄다.
- **실측 사례:** 이미 해결된 사건의 확인 지시가 남아 있었다.
  가리키는 설정이 이미 들어가 있었으므로, 확인이 아니라 실제로 필요한 대응으로 바꿔야 했다.

## 런타임 동작 변화

하네스 자체가 바뀌어 지침의 전제가 더는 참이 아닌 경우를 찾는다.
모델 역량이 아니라 **도구·런타임의 동작**이 바뀐 것이라, 실행해 보거나 공식 문서를 읽어야 드러난다.
문서끼리 비교해서는 절대 보이지 않는다.

찾는 방법은 셋이다.

- 지침이 전제하는 동작을 **실제로 재현**해 본다.
- 도구 설명 원문과 대조한다. 도구 계약은 1차 자료다.
- 공식 문서에서 그 동작이 언제 어떻게 바뀌었는지 확인한다.

- **실측 사례:** "팀원은 idle 직후 스스로 종료하니 재스폰해야 한다" 는 지침이 있었다.
  공식 문서는 "hidden, not stopped", "stays running and addressable" 라고 적고 있었고,
  이름으로 메시지를 보내면 컨텍스트를 유지한 채 재개됐다.
  그 지침을 따랐다면 매번 재스폰해 컨텍스트를 버렸을 것이다.
- **실측 사례:** 스폰 인자 하나가 특정 버전부터 "받아들이되 무시" 로 바뀌었다.
  그 인자의 유무로 갈리던 3단계 우선순위 표가 통째로 무의미해져 있었다.
- **실측 사례:** 기본 표시 모드가 바뀌어, 옛 기본값에서만 나던 스폰 실패를 다루는 가드가
  발동할 수 없는 상태로 남아 있었다.

근거 없이 "요즘은 안 그럴 것" 이라고 지우지 않는다.
바뀌었다는 것을 확인한 만큼만 고치고, 옛 관측이 거짓이었다고 단정하지 않는다.

## 모델 교체

세션 모델이 지침을 쓸 때와 다르거나 사용자가 새 모델을 언급했을 때 이 축을 적용한다.
현재 세션의 시스템 프롬프트와 도구 설명에 먼저 대조한다.
모델 설명 자료는 다음 순서로 읽는다.

1. claude-api 스킬의 `shared/` 아래에서 대상 모델 절의 `Behavioral shifts` 와
   `prompt-audit.md` 의 `Group 1d(Fossils)` 와 keep list 를 읽는다.
   번들 버전마다 경로가 바뀌므로 고정 경로를 적지 않는다.
   대상 모델 절이 재시험 목록을 앞 모델 절로 넘기면 그 절의 `Behavioral shifts` 까지 읽는다.
2. 해당 모델의 발표문과 시스템 카드의 alignment 절을 읽는다.
   시스템 카드 PDF 가 10MB 를 넘으면 WebFetch 가 실패하므로 내려받아 `pdftotext` 로 변환해 검색한다.

다음 문장을 찾는다.

- 시스템 프롬프트가 이미 지시하는 문장
- 모델 행동 관측을 근거로 둔 문장
- 모델 이름과 버전을 명시한 문장

실측으로, 진행할 수 있을 때 묻지 말라는 지침은 시스템 프롬프트와 도구 설명에 이미 있었다.
특정 모델을 권고의 이름으로 명시한 문장은 모델이 바뀐 뒤에 낡았다.
`judgment.md` 의 10번 축으로 모델 행동 관측을 근거로 둔 문장을 찾았다.

이전 모델에 맞춘 지시는 바로 지우지 않는다.
마이그레이션 가이드가 출발점으로 두고 다시 시험하라고 하면 보류로 두고 재시험 후보로 적는다.
시스템 카드가 새 모델의 약점으로 적은 행동에 맞선 지시는 유지 근거로 적는다.

**가이드는 제거를, 시스템 카드는 유지를 가리키면 보류로 두고 두 근거를 함께 적는다.**
같은 약점을 산출물에 남는 형태로 막는 대안이 있으면 그것을 선택지로 함께 낸다.
실측으로, 하위 에이전트에게 최종 확인을 맡기는 절이 그랬다.
가이드는 검증을 맡기는 지시가 과검증을 부른다고 했고, 시스템 카드는 부분 확인을 전체로 보고하는 경향을 약점으로 적었다.
검토자를 없애고 완료 보고에 실행한 명령과 결과를 적게 하는 대안을 사용자가 골랐다.

## 사용 이력 0

한 번도 실행되지 않은 절차가 필요한 안전장치인지 판단한다.
발동할 수 없는 죽은 단계인지도 구분한다.
생략 조건과 호출 패턴을 먼저 대조한다.
대체 경로와 도입 근거도 함께 확인한다.

- **실측 사례:** 선택 단계의 생략 기준이 일반적인 호출을 모두 포함했다.
  규칙을 지킬수록 그 단계가 매번 생략됐다.
