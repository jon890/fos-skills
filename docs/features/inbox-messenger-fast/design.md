# inbox 출처별 받기 설계

[스펙](spec.md)의 REQ2~REQ6을 이 PR에서 구현한다. 보드는 활성 상태에서 1분마다 캐시를 읽고, 두레이 조회는 별도 프로세스에서 이어 간다.

## 출처별 주기와 저장

- adapter는 활성 출처를 알려 주고 요청받은 출처 하나만 읽는다. 두레이는 업무와 메신저를 따로 받으며, `messenger: false`면 메신저를 띄우지 않는다.
- 설정 `messengerIntervalMinutes`의 기본은 1분이다. 업무는 `taskIntervalMinutes`를 쓰고, 기존 `intervalMinutes`도 업무 주기로 읽는다. 두 값이 모두 없으면 지난 업무 커서로 이어 받을 수 있을 때 1분, 커서가 없거나 읽을 수 없을 때 5분을 쓴다.
- 출처마다 마지막 시도 시각, 성공 커서, 오류를 저장한다. 전체 조회 실패 시 시도 시각과 오류만 갱신하고, 항목과 커서는 유지한다. 일부 대화방만 실패했을 때는 기존처럼 해당 방을 다음 주기에 다시 읽는다.
- 기존 캐시와 커서는 처음 읽을 때 이어받고, 새 상태는 별도 파일에 쓴다. 업데이트 전에 열린 보드가 예전 캐시를 갱신해도 새 상태가 보존된다. 보드 JSON 형식과 최신 조회 시각은 유지한다.

## 업무 커서와 기존 CLI

설치된 CLI 0.33.0에서 `stream list`는 최근 시각을 주면 페이지를 일찍 멈췄다. 기존 inbox는 15일 전을 넘겨 피드 전체를 읽었다. 지난 커서부터 받으면 호출이 줄어들므로 CLI 버전 대신 업무 커서 유무로 주기를 정한다.

CLI 0.33.0의 `--since`는 경계 페이지에서 시각 없는 댓글을 버린다. 업무 커서가 있으면 `stream list --size 200`의 JSON과 다음 페이지 커서를 읽고, 필요하면 `--before`로 이어 간다. 피드에서 원소 순서가 수십 초씩 어긋날 수 있어 지난 커서보다 1분 이전인 페이지까지 포함한다. 받은 항목은 기존과 같이 ID로 합친다. 업무 커서가 없거나 잘못됐으면 기존과 같이 15일 전부터 읽는다. 다음 페이지를 찾을 수 없는데 원소가 더 있을 수 있으면 피드 전체를 받고, 이어 받기가 다시 성공할 때까지 기본 5분 주기를 쓴다.

## 잠금과 보드

동시에 받은 결과와 답함 표시를 덮어쓰지 않도록, 두레이 조회 중에는 출처별 받기 잠금만 쥐고 캐시를 갱신할 때 짧은 쓰기 잠금을 잡는다. 원격 호출이 끝난 뒤 쓰기 잠금 안에서 캐시를 다시 읽고 해당 출처만 합친다. 받기 프로세스가 끝나면 다음 받기가 잠금을 회수한다.

보드는 이미 받고 있는 출처를 건너뛰고 주기가 지난 출처마다 자식 프로세스를 따로 띄운다. 받기를 띄울 때 보드가 주기를 확인한 시각을 넘겨 다음 1분 호출에서 자식 프로세스 시작 시간만큼 밀리지 않게 한다. 보드는 띄우기 전에 읽은 결과를 반환한다.

## 구현과 확인 순서

1. 출처 선택과 캐시 쓰기를 나눈다. 기존 상태를 읽고 출처 하나가 실패했을 때 다른 출처의 항목과 커서가 남는지 테스트한다.
2. 업무 커서와 출처별 잠금을 적용한다. 시각 없는 댓글이 있는 경계 페이지, 커서 유무에 따른 주기, 업무 받기 중 메신저 받기, 보드의 즉시 반환을 확인한다.
3. 읽기 전용 두레이 호출과 임시 캐시로 실제 장비에서 두 주기가 다르게 움직이는지 확인한다. 메시지를 보내고 표시 시간을 재는 REQ7은 후속 검증에서 수행한다.
