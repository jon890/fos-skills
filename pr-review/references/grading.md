# 등급

등급은 **근거의 강도**로 정한다. 느낌의 세기로 정하지 않는다.

표기는 본문 첫 줄에 괄호로 둔다. 사용자가 목록에서 바로 알아볼 수 있게 하려는 것이다.

```
(P3)

안녕하세요 @작성자 님!
...
```

## 판정표

| 등급 | 조건 | 근거로 필요한 것 |
| --- | --- | --- |
| P1 | 데이터가 사라지거나 서비스가 멈춘다 | 재현 경로. 어떤 입력에서 무엇이 깨지는지 |
| P2 | 결과가 틀린다. 사용자가 잘못된 값을 본다 | 코드 인용으로 입증 |
| P3 | 실측된 비용이 있거나, 한 번 굳으면 코드 수정으로 못 푸는 상태가 된다 | 측정값 또는 상태가 굳는 경로 |
| P4 | 구조와 관례. 성능 영향이 측정되지 않았다 | 저장소 안의 다른 사례 인용 |
| P5 | 취향. 지금 형태로 가도 아무 문제가 없다 | 없어도 된다 |

## 자주 틀리는 자리

**측정하지 않은 성능 지적은 P3 가 아니다.** P4 다.
"느려 보인다" 는 등급을 올리는 근거가 아니다. 재고 나서 올린다.

**구조 개선은 기본이 P4 다.** 테스트하기 어렵다, 응집도가 낮다, 관심사가 섞였다는 모두 P4 다.
P3 으로 올리려면 그 구조 때문에 생기는 구체적 비용을 재야 한다.

**한 번 굳으면 못 푸는 상태는 P3 이다.** 실패 횟수가 임계치를 넘어 영구 스킵이 되는데
그 스킵을 푸는 경로가 없는 경우가 그렇다. 지금 당장 안 나도 P3 다.

**드물게 발생한다고 등급을 내리지 않는다.** 대신 빈도를 본문에 적는다.
작성자가 판단할 수 있게 하는 편이, 내가 등급으로 눌러 표현하는 것보다 정확하다.

## 등급을 내리는 경우

실측이 예상보다 작게 나왔으면 **등록 전에 내린다.** 이미 등록했으면 답글로 밝힌다.

```
실측해 보니 제가 적은 것보다 비중이 작았습니다.
페이지 처리 시간의 1~3% 라 (P4) 가 맞았습니다.
```

등급을 올리는 방향의 재조정은 하지 않는다. 새 근거가 나왔으면 새 리뷰로 낸다.

## 개수 제한

한 번에 P4, P5 를 다섯 개 넘게 올리지 않는다. 넘으면 요약에 개수만 적는다.
사소한 지적이 많으면 중요한 지적이 묻힌다.

재리뷰에서는 더 좁힌다. **두 번째 리뷰부터는 P3 이상만 낸다.**
한 줄 수정이 일곱 번째 왕복까지 가는 것을 막는다.

## 저장소가 등급을 재정의할 수 있다

레포 오버레이나 `REVIEW.md` 가 "이 저장소에서 P2 는 무엇인가" 를 다시 정할 수 있다.
문서 저장소나 프로토타입은 기준이 다르다. 오버레이가 있으면 그쪽을 따른다.
