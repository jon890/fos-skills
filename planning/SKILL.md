# planning

**목표: 구현에 들어가기 전에 모호함을 0 으로 만들고, 그 결정을 문서에 남기고,
남은 일을 phase 단위로 쪼개 실행으로 넘긴다.**

그리고 각 작업이 `tasks/plan{N}-{slug}/phase-*.md` 로 쪼개져 있어야 한다. 구현자가 이 논의 내용을 산출물로만으로도 파악하고 구현할 수 있어야한다.

이 워크플로가 관리하는 문서는 다음과 같다.


| 대상       | 파일                          | 갱신 시점              |
| -------- | --------------------------- | ------------------ |
| 기술적 의사결정 | `docs/adr/NNN-<슬러그>.md`     | 결정할 때마다 새 파일       |
| 실행 흐름    | `docs/flow.md`              | 3단계에서 정하고 7단계에서 반영 |
| 코드 아키텍처  | `docs/code-architecture.md` | 6단계에서 정하고 7단계에서 반영 |
| 데이터 스키마  | `docs/data-schema.md`       | 5단계에서 정하고 7단계에서 반영 |
| 제품 범위    | `docs/prd.md`               | 7단계에서 영향만 판정한다     |

각 단계는 진입 시 해당 reference 를 읽고 그 역할로 수행 → 단계 표기 → 모호점 0 확인 → 다음.

| --- | ----------------------------- | ------------------------------- | --------------------------------------------------------- |
| 1   | 구현 가능성 (역할: CTO)              | 되는가, 무엇을 재사용하나, 무엇이 위험한가        | `references/step-1-feasibility.md`                        |
| 2   | 기술 스택                         | 기존 스택으로 되는가, 새 의존이 정당한가         | `references/step-2-tech-stack.md`                         |
| 3   | 호출·사용자 흐름 (역할: 워크플로/UX)       | 정상 흐름과 실패·빈 상태·동시 충돌            | `references/step-3-flow.md`                               |
| 4   | 인터페이스 설계                      | 사용자와 호출자가 마주하는 표면               | `references/step-4-interface.md`                          |
| 5   | API·함수 설계                     | 엔드포인트·시그니처·요청과 응답 스키마           | `references/step-5-api.md`                                |

| 7   | docs 영향과 기술 결정 기록             | 책임 문서 판정과 실제 갱신                 | `references/step-7-docs.md`                               |
| 8   | task 파일 생성과 커밋                | 대화를 못 본 executor 가 읽고 실행할 phase | `references/step-8-tasks.md`, `references/task-create.md` |


### 단계 강제: 뭉개기·건너뛰기 방지

1. **단계 기록 생성**: planning 시작 시 `TaskCreate` 로 밟을 단계를 각각 task 로 만든다.
2. **단계 표기**: 매 응답 첫 줄에 `지금 N단계: <이름>` 표기. 사용자가 진행·누락을 본다.
3. **단계 진입 = reference 로드**: 각 단계 진입 시 `references/step-N-*.md` 를 읽고 **그 역할로** 수행한다.
4. **통과 조건**: 그 단계의 모호점이 **0** 이어야 완료(task completed)된다. 판정 기준은 모호점 유무이고, 사용자 응답 횟수가 아니다.
  - **모호점이 남아 있으면 멈춘다**: 사용자만 답할 결정(취향·범위·되돌리기 어려운 것·트레이드오프 판단)은 `AskUserQuestion` 으로 확정받고 나서 진행한다.
    - **모호점이 0 이면 확정을 기다리지 않고 다음 단계로 넘어간다.** 무엇을 어떤 근거로 정했는지 단계 표기에 남긴다: 사용자가 그 기록을 보고 되짚을 수 있다.
    - 사실로 확인 가능한 것(파일·git·도구·실측)은 **직접 조회해 스스로 정한다.** 사용자에게 묻지 않는다.

## 공통 규칙

### 핵심 원칙

- **모호함 제로**: 조금이라도 모호하면 사용자와 논의. 넘어가지 않는다.
- **능동 발굴**: 각 단계에서 그 reference 의 "캐낼 모호점" 을 하나씩 짚어, 명시 안 됐거나 해석이 갈리는 지점을 찾아낸다. "알아서 됐겠지" 로 지나가지 않는다.
- **AI 에이전트 관점**: 최종 문서는 AI 가 읽고 phase 로 구현 가능할 만큼 명확.

### 공용 필수 관리 문서

각 문서는 답하는 물음이 하나씩이다. **없으면 미완인 것**이 그 문서를 판정하는 기준이다.


| 문서                          | 답하는 물음                  | 없으면 미완                |
| --------------------------- | ----------------------- | --------------------- |
| `docs/prd.md`               | 무엇을 왜 만드는가              | 범위와 제외 범위, 됐다고 말할 기준  |
| `docs/flow.md`              | 어떻게 흐르는가                | 정상 흐름, 그리고 실패와 빈 상태   |
| `docs/code-architecture.md` | 무엇이 어디에 있고 누가 무엇을 책임지는가 | 디렉터리 배치, 모듈 책임, 의존 방향 |
| `docs/data-schema.md`       | 무엇을 어떤 모양으로 저장하는가       | 필드와 키, 제약, 삭제 규칙      |
| `docs/adr/`                 | 왜 그렇게 정했는가              | 결정, 맥락, 대안 기각, 결과     |


절의 이름과 나누는 축은 저장소가 정한다. 실측으로 세 저장소의 `flow.md` 는
처리 경로, 명령별, 사용자 탐색으로 각각 다르게 나뉘어 있고 줄 수도 47부터 578까지 갈린다.
강제하는 것은 축이 아니라 위의 「없으면 미완」 이다.

**필수 다섯이 담지 않는 산출물은 오버레이가 소유 문서를 정한다.**
REST 요청과 응답 계약이 그렇다. `data-schema.md` 는 저장 모델만 소유하므로 API 계약이 갈 곳이 없다.
실측으로 한 저장소는 `docs/api-spec.md` 를 따로 두어 해결했다.
오버레이에 지정이 없으면 5단계에서 어디에 남길지 사용자에게 확인한다.

`**docs/` 는 `tasks/` 를 가리키지 않는다.**
plan 번호와 phase 파일은 구현 뒤 다시 읽지 않는 일회용 산출물이다.
문서 제목이나 본문에 `plan057` 같은 번호를 적으면, 그 task 를 정리하는 순간
오래 남아야 할 문서가 없는 곳을 가리킨다. 무엇이 어떻게 동작하는지만 적는다.

책임 문서 판정, 없는 문서의 생성 조건, 규모별 완화는 7단계가 소유한다 (`references/step-7-docs.md`).

문서 갱신과 문서 간 계약 일치 검증이 끝나기 전에는 8단계 task를 만들 수 없다.
완료 여부는 7단계의 문서 diff 로 판정하며, 어느 문서도 영향받지 않는다는 판정을 남긴 경우도 통과로 본다.

## task 생성과 마감

### 규모 분할 점검: plan 1개 = PR 1개

7단계 결정이 끝나고 8단계 task를 만들기 전에 예상 변경 범위를 판정한다.

- 하나의 plan은 정확히 하나의 구현 브랜치와 하나의 PR에 대응시킨다.
- 독립된 검토·검증 단위가 둘 이상이면 여러 plan 으로 나눈다.
- 생성 파일을 제외한 예상 변경이 약 25개 파일, 800줄 또는 5개 phase를 넘으면 분할 검토를 반드시 수행한다. 수치는 경고선이며 변경 이유를 한 번에 설명할 수 있는지가 최종 기준이다.
- DB·저장 계약, backend 처리와 API, frontend 연결, skill·tooling처럼 자체 완료 기준을 갖는 경계를 우선 분할 후보로 삼는다.
- 각 분할 plan에 목표, 범위 외, 검증 기준을 지정한다. 여러 plan을 한 브랜치나 한 PR에 합치지 않는다.
- 분할안을 사용자에게 **실행 순서**와 각 PR의 검토 초점과 함께 제시하고 확정받은 뒤 번호를 선점하고 task를 만든다. 순서는 보고로 전달하며 task 파일에 기계 판독용 의존 관계 필드를 만들지 않는다.
  - 다만 **선행 plan 의 산출물을 전제하는 phase 는 그 전제를 phase 본문에 적는다.**
  "이 phase 는 plan{M} 이 만드는 `<경로>` 를 전제한다. 미머지면 base 를 확인하고 멈춘다" 형태다.
  - 전제를 적지 않으면 실행자가 현재 `origin/main` 에 없는 경로를 찾다 헤매고, 그 원인이 task 어디에도 남지 않는다.
  - 전제가 없는 phase 는 현재 base 에 실재하는 것만 인용한다.
- 7단계 docs 갱신분은 plan별로 쪼개지 않고 한 곳에 함께 남긴다.
앞선 plan 의 docs 가 빠진 상태에서 뒤 plan 을 구현하면 근거 없이 구현하게 된다.

한 plan 으로 두기로 했으면 하나의 원자적 변경으로 묶여야 하는 근거를 단계 기록에 남긴다.

### 자체 검토와 task 검증 (생성 직후, 필수)

task 파일을 만든 직후, 커밋하기 전에 세 가지를 순서대로 한다.

1. **자체 검토**: `references/task-create.md` 의 "task 검증" 절차를 따른다.
2. **자동 검증**: 스크립트가 기계로 판정되는 task 위생을 찾는다. 종료 코드 0 이어야 통과.
  ```bash
    # cwd: 타깃 레포 root
    python3 scripts/verify_task.py plan{N}-{slug}
  ```
3. **사람 판단 4 패턴**: 도메인 의존이라 스크립트가 못 잡는다. `references/task-create.md` 의 목록을 따른다.

위반을 찾으면 임의로 고치지 않고 질문 도구로 사용자에게 확인한다.
계획의 수치·범위는 사용자 의도가 담긴 값이라, 조용히 바꾸면 합의가 뒤집힌다.
