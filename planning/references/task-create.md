# Task 생성 가이드

레포별 검증 명령과 레이어 구조는 레포 설정이 채운다. 찾는 순서는 `SKILL.md` 의 「레포 설정을 먼저 읽는다」 가 정한다.

반복 함정 목록은 레포 설정이 지정하면 그것을 따르고, **지정이 없으면 `docs/pitfalls/` 를 읽는다.**
그 디렉터리도 없으면 사전 확인 항목을 건너뛴다.

## index.json 스키마

```jsonc
{
  "name": "plan{N}-{kebab-slug}",       // 디렉터리명과 일치
  "description": "한 줄 요약 — 무엇을 / 왜",
  "status": "pending",                    // pending | in_progress | completed | failed
  "created_at": "2026-01-01",             // YYYY-MM-DD
  "total_phases": 3,                      // phases 배열 길이와 일치
  "current_phase": 1,
  "phases": [
    {
      "number": 1,
      "file": "phase-01.md",
      "execution_profile": "standard"     // fast | standard | deep
    }
  ]
}
```

## ADR(Architecture Decision Records) 구조 템플릿

파일명은 `docs/adr/NNN-<슬러그>.md` 다. 한 파일에 결정 하나만 담는다.

```markdown
## ADR-XXX: {제목. 결정의 한 줄 요약}

- **status**: `accepted`
- **결정**: {무엇을. 1~3문장}
- **맥락**: {왜 이 결정이 필요했는가. 제약·데이터·관찰}
- (조건부) **대체된 부분**: {이 ADR 의 어느 결정이 어느 ADR 에 뒤집혔는가. 링크 포함}
- **대안 기각**: {다른 옵션을 왜 선택하지 않았는가. 각 대안 1~2줄}
- **결과**: {이 결정 뒤로 무엇이 달라지는가}
  - 얻는 것: {가능해진 것}
  - 감당할 것: {비용·제약·앞으로 지켜야 할 것}
- (선택) **적용 범위**
```

`status` 는 둘뿐이다.

| 값            | 뜻                              |
| ------------ | ------------------------------ |
| `accepted`   | 현재 유효하다                        |
| `superseded` | 다른 ADR 이 이 결정을 뒤엎었다. 이력으로만 읽는다 |

`status` 가 없는 기존 ADR 은 `accepted` 로 읽는다.

**결과** 는 결정한 뒤에 생기는 트레이드오프를 적는다. 얻는 것과 감당할 것을 둘 다 적는다.

**ADR 은 지우지 않는다.**
결정 전체가 번복돼도 `status` 를 `superseded` 로 바꾸고 `대체된 부분` 에 대체한 ADR 을 가리킨다.
지우면 그때 그 판단을 왜 했는지가 사라진다. 당시 정보로는 옳았던 결정이 대부분이다.

- `대체된 부분` 은 **결정 바로 아래**에 둔다. 결정만 읽고 지나가는 독자가 낡은 결론을 얻는 것을
막는 것이 목적이라, 문서 끝이나 대안 기각 안에 넣으면 의미가 없다.
- 대체한 쪽 ADR 에서도 원본을 링크해 양방향으로 찾을 수 있게 한다.
- 전체가 대체된 ADR 은 남은 본문 앞에 그것이 당시의 맥락임을 한 줄로 밝힌다.
- 코드와 경로는 결정을 가리키는 데 필요한 만큼만 인용한다. 구현 호출 방법, 작업 내역,
스택 규칙 반복은 넣지 않는다. 결정과 근거만 남긴다.
- **계획서를 번호로 가리키지 않는다.** ADR 은 계획서보다 오래 남는다.
  근거는 다른 ADR 번호나 PR 번호로 적고, 그것으로 부족하면 내용을 본문에 옮긴다.

## phase 파일 작성 규칙

**phase 하나는 테스트까지 통과한 커밋 하나로 끝낸다.**
코드를 바꾸는 phase 안에서 그 동작의 테스트를 만들거나 고치고 「검증」 절에서 실행한다.
테스트를 다음 phase 로 미루지 않는다. 작업 항목의 순서는 구현과 검증 의존에 맞게 정한다.
**한 phase 는 한 사람이 한 번에 붙잡고 끝낼 수 있는 크기로 둔다.**

### phase 파일 구조

```markdown
# Phase NN. {제목}

**Execution profile**: standard

## 목표

무엇을 만드는가. 왜 필요한지 한 문장.

**범위 외**: 다른 phase 나 다른 plan 의 책임.

## 컨텍스트

이 대화를 보지 못한 구현자가 알아야 할 것.
기존 코드의 어느 패턴을 따르는지 경로로 짚는다.

**근거 문서**: `docs/flow.md` 의 「...」 절, `docs/adr/012-....md`
근거는 `docs/` 와 ADR 로만 적는다. 다른 계획서를 가리키면 그것이 제거된 뒤 읽을 수 없다.

## 의도 메모

- 기각한 옵션과 그 이유
- 앞으로 주의할 것

## Blocked 조건 (선택)

- 외부 의존성 부재 → `PHASE_BLOCKED: {이유}` 출력 후 종료

## 작업 항목

### 1. {파일} 의 변경 요약

구체적 변경. 함수 시그니처, 타입, 셀렉터, 이름. 기존 패턴 참조 경로.

### 2. 이 phase 를 검증하는 {테스트 파일}

무엇을 어떤 입력으로 확인하는지. 정상 경로 하나와 이 phase 가 다루는 실패 하나.

## 검증

실행할 명령과 기대값. 레포의 lint, type, test, build 명령과 구체 grep 기준을 적는다.
위에서 만든 테스트를 실행하는 명령을 함께 적는다.

## 변경 파일

이 phase 의 커밋에 담을 파일을 저장소 root 기준 경로로 적는다.

| 파일 | 변경 |
|---|---|
| `src/application.py` | 신규 |
| `tests/test_application.py` | 신규 |
```

### 변경 파일 작성

작업 항목의 변경 경로를 이 목록에 모은다. `build-with-teams` 는 커밋 전에 staged 파일과 대조한다.
목록에 없는 변경이 생기면 계획에 빠진 파일인지 무관한 변경인지 먼저 판정한다.
마지막 phase 가 바꾸는 `tasks/` 의 완료 상태와 근거 문서 갱신도 목록에 포함한다.

- 파일 경로를 `.../` 로 생략하지 않는다. 「변경 파일」 절의 생략 경로는 생성 검사와 커밋 전 대조 모두 위반이다.
  기존 `Critical Files` 절의 생략 경로만 생성 검사에서 경고로 둔다.
- `수정`과 `삭제`의 glob 은 일치하는 파일이 하나 이상 있어야 한다.
  `*`는 한 경로 조각, `**`는 하위 디렉터리까지 뜻한다.
- 신규 파일은 개별 경로를 적는다. 신규 glob 은 구체 파일의 부재를 확인하지 못하므로 경고한다.
- 신규로 적은 개별 파일이 커밋 전 staged 파일에 없으면 위반이다. 수정·삭제로 적은 파일이 없으면 경고한다.
- 앞 phase 가 만든 파일은 뒤 phase 에서 수정하거나 삭제할 수 있다. 앞 phase 의 신규 glob 에 맞는 경로도 같다.
  앞 phase 가 삭제한 파일을 뒤 phase 에서 수정할 수는 없다.

### 검사기와 작성자가 확인할 범위

검사기는 검증 절의 테스트 실행 명령과 코드 변경에 대응하는 같은 phase 의 테스트 작업을 대조한다.
제목에 「테스트」가 있어도 lint나 grep만 실행하면 통과하지 않는다.
`npx`, `uv run`, `poetry run`, `pipenv run`, `bundle exec` 같은 접두어와 패키지 관리자의 작업 공간 옵션은 벗겨서 판정한다.
검사기가 모르는 실행기만 있으면 위반 대신 경고로 알린다. 그 명령이 테스트를 실행하는지 작성자가 확인한다.
테스트 파일을 직접 지정하는 명령은 작업 항목에 선언한 테스트를 포함해야 한다.
저장소의 `scripts/check-*`, `scripts/verify.*`, `scripts/test-*`를 검증에 쓰면
그 파일을 직접 열어 테스트 범위와 실패 종료 코드를 확인한다.
설정이나 배포 구성만 바꾸는 phase 도 실행 가능한 검증 스크립트나 저장소 테스트 명령을 적는다.

검사기는 명령을 실행하거나 테스트가 목표 동작을 확인하는지 판단하지 않는다.
작성자는 다음을 직접 확인하고 필요한 내용을 작업 항목과 검증 절에 적는다.

| 확인할 것 | 남길 근거 |
| --- | --- |
| 테스트가 바꾼 동작을 확인한다 | 정상 입력과 이 phase 가 다루는 실패 입력, 기대 결과 |
| 저장소 전체 명령이 위 테스트를 실행한다 | 테스트 검색 경로, 모듈 범위, 제외 설정 |
| 스크립트가 실패를 숨기지 않는다 | 단언 방법과 실패 종료 코드 |
| 기존 식별자, 경로와 스키마가 docs와 코드에 맞는다 | 실제 정의를 읽고 일치시킨 이름과 타입 |

`Critical Files`라는 기존 절 이름은 읽기 호환으로 받는다. 새 계획은 「변경 파일」을 쓴다.
검사기의 구현 후 문서 검사와 커밋 전 대조 인자는 `verify_task.py --help`가 설명한다.
