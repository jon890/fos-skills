# Step 7 — docs 영향 종합 + 기술 결정 기록

**역할**: 문서 관리자. 6개월 뒤 이 코드를 처음 보는 에이전트가 무엇을 알아야 하는지 기준으로 판단하는 사람.
**통과시키지 않는 것**: 코드만 봐도 아는 내용을 적은 문서, "왜" 가 빠진 결정 기록, 갱신을 phase 로 미루는 것.

규모와 무관하게 **항상 수행**한다 (문서 drift 방지).

## 목적

이번에 내린 기술 결정을 목록화하고 "왜"를 남긴다. 공용 필수 관리 문서를 먼저 현재 상태로 갱신하고 문서 사이의 계약을 맞춘다.

## 필수 산출물

- 기술 결정 목록 + 각 결정의 "왜".
- 공용 필수 관리 문서 `docs/prd.md`, `docs/flow.md`, `docs/code-architecture.md`, `docs/data-schema.md`, `docs/adr/` 전체의 영향 판정.
- 영향을 받는 필수 문서의 실제 갱신 diff + ADR 위치·번호. 없는 문서는 이번 변경이 그 내용을 실제로 소유할 때만 생성한다.
- 영향이 없는 필수 문서는 본문을 건드리지 않고 근거만 단계 결과에 기록한다. 장기 기술 결정이 없으면 빈 ADR을 만들지 않는다.
- 오버레이가 지정한 추가 문서의 영향 판정과 필요한 실제 갱신 diff.
- **단일 소스 원칙** — 같은 정보를 두 문서에 쓰지 않는다. 필요하면 링크.
- **ADR 내용 기준** — 결정·맥락·대안 기각만 담는다.
    - 코드 블록·경로 나열·호출 방법·`CLAUDE.md` 규칙 반복은 넣지 않는다.
    - 분량은 내용에 맞추고 채우기용 섹션이나 중복 요약을 덧붙이지 않는다.

## 캐낼 모호점 (능동 발굴 → 사용자 확정)

- 이 결정이 ADR 감인가, 아니면 자명해서 안 남길 것인가(자명한 건 ADR X).
- 기존 ADR·문서와 **충돌·중복·supersede** 되는 지점.
- 제품 범위, 흐름, 모듈 책임, 저장 계약 중 어느 책임 문서에도 반영되지 않은 합의.
- 공유 문서(인덱스) 편집이 동시 planning 과 충돌할 위치 → append 편집으로.

## 문서 우선 절차

1. `합의`, `기각`, `미결`을 정리하고 `미결`이 0인지 확인한다.
2. 각 합의의 책임 문서와 기존 설명의 충돌·대체 여부를 판정한다. 소규모 변경은 전량 정독 대신 판정 한 줄로 갈음한다(SKILL.md 규모별 완화).
3. 영향을 받는 문서와 필요한 ADR을 실제로 갱신한다. task나 phase에 문서 결정을 미루지 않는다.
4. `git diff -- docs/prd.md docs/flow.md docs/code-architecture.md docs/data-schema.md docs/adr`로 변경을 읽고 용어·상태·API·저장 모델이 서로 일치하는지 확인한다.
5. 영향이 없는 문서와 그 근거를 단계 결과에 남긴다.

## 게이트 통과

최종 결정이 필수 관리 문서와 필요한 ADR에 실제 반영되고, 문서 diff 검증이 끝나고, 모호점 **0** → 8단계. 문서 계획만 작성했거나 갱신을 phase로 미뤘다면 통과하지 못한다.
