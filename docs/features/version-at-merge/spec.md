# 스킬 버전과 변경 이력을 머지 때 정한다

확인: 2026-11-04

## 목표

같은 스킬을 고치는 PR 이 여럿이어도 버전 줄과 CHANGELOG 절 때문에 서로 충돌하지 않는다.
PR 은 무엇이 바뀌었는지만 조각 파일로 적고, 새 버전 번호와 CHANGELOG 절은 main 에 머지될 때 workflow 가 정한다.

## 범위

이번 범위(PR1, 계획 하나):

- PR 이 변경 이력을 적는 자리(스킬 폴더의 조각 파일)와 형식, 등급 표시.
- main push 마다 도는 workflow 가 main 의 조각을 읽어 스킬 `metadata.version` 과 CHANGELOG 절을 올리고 조각을 지우는 동작.
- 조각 형식을 검사하는 `check-skill-docs.py` 갱신과 테스트.
- 내보내기에서 조각 폴더 제외.
- README 「버전과 변경 이력」, `docs/flow.md`, `docs/code-architecture.md`, orch 공통 지시서 틀의 갱신과 새 ADR.
- 옛 방식(PR 이 버전과 CHANGELOG 를 직접 올림)으로 열린 PR 이 머지돼도 깨지지 않는 전환 규칙.

범위 밖:

- 플러그인 version 의 등급 규칙 자체([ADR-019](../../adr/019-plugin-version-auto-bump.md) 유지). 새 기록이 그 입력이 되도록 잇기만 한다.
- 조각 없는 스킬 변경을 CI 가 막는 검사.
- major 를 조각으로 받는 것. major 는 PR 이 직접 올린다.
- 팀 저장소 내보내기의 버전 방향 보호 규칙, git 태그와 릴리스.

## 용어

- 조각: `skills/<이름>/changes/<슬러그>.<등급>.md`. `extensions/work-board`, `export-only-skills/<이름>` 도 같은 꼴(`<스킬 폴더>/changes/`)이다. 내용은 CHANGELOG 항목(`- ` 줄) 1~5개다.
- 등급: 파일 이름 접미 `.patch.md` 또는 `.minor.md` 둘뿐이다.

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 스킬을 고치는 PR 은 `metadata.version` 과 CHANGELOG 를 건드리지 않고 조각 파일로 이력을 남긴다 | 같은 스킬에 조각을 하나씩 더한 두 브랜치를 차례로 병합하면 충돌 없이 합쳐진다(임시 저장소 테스트) |
| REQ2 | 머지 workflow 가 main 트리의 조각마다 새 버전을 정해 SKILL.md 와 CHANGELOG 에 반영하고 조각을 지운다 | 조각 1건이 `metadata.version` 의 patch 또는 minor 한 단계 상승, CHANGELOG 맨 위 `## X.Y.Z (실행일)` 절(조각 항목 그대로), 조각 파일 삭제가 된다 |
| REQ3 | 한 번에 조각이 여럿이거나 스킬이 여럿이어도 모두 반영된다 | 스킬 둘에 조각 셋을 둔 테스트에서 버전이 조각마다 하나씩 올라가고, 같은 스킬의 조각은 main 에 들어온 순서대로 번호를 받는다 |
| REQ4 | 옛 방식으로 올린 변경은 건드리지 않는다 | 조각이 없는 스킬은 workflow 가 버전과 CHANGELOG 를 건드리지 않는다. PR 이 직접 올린 버전·절은 그대로 남고 플러그인 등급은 지금과 같이 정해진다. 한 PR 이 같은 스킬에서 직접 올림과 조각을 섞지 않는다(README 에 적는다) |
| REQ5 | 플러그인 version 은 조각에서도 오른다 | 조각이 있으면 플러그인이 minor 이상으로 오르고 플러그인 CHANGELOG 줄에 「스킬 새버전」 이 적힌다 |
| REQ6 | 형식이 틀린 조각은 PR 의 CI 에서 걸린다 | 접미가 `.patch.md`, `.minor.md` 가 아니거나, `- ` 줄이 아닌 줄이 있거나, 항목이 5개를 넘거나, 내용이 빈 항목이나 160자를 넘는 항목이나 `호환성:` 항목이 있으면 `check-skill-docs.py` 가 파일과 이유를 내고 종료 코드 1 이다 |
| REQ7 | 팀 저장소 내보내기가 조각을 가져가지 않는다 | `export-to-team.sh` 점검에서 `changes/` 아래 파일이 어긋남으로 나오지 않는다 |
| REQ8 | 문서가 새 관례를 안내한다 | README 「버전과 변경 이력」, `docs/flow.md`, `docs/code-architecture.md` 가 조각 방식과 major·옛 방식 예외를 적고, 저장소 문서에 PR 이 버전과 CHANGELOG 를 직접 올리라는 옛 문장이 남지 않는다(`grep` 으로 확인) |

## 설계 메모(작성자 결정의 근거)

- `## Unreleased` 절은 충돌을 없애지 못한다. 두 PR 이 CHANGELOG 맨 위의 같은 위치에 더해 CONFLICT 가 났다(2026-11-04 임시 git 저장소 실측). 그래서 파일을 PR 마다 나눈다.
- workflow 는 push 범위가 아니라 main 트리에 남은 조각 전부를 처리한다. 머지가 겹쳐 실행 하나가 빠져도(GitHub 은 대기 중인 같은 그룹 실행을 최신 하나만 남긴다) 다음 실행이 이어서 올린다.
- 조각 순서는 main 에 그 조각을 넣은 커밋의 순서다. 같은 이름을 지웠다 다시 쓰면 다시 넣은 커밋이다(같으면 파일 이름). CHANGELOG 절 날짜는 workflow 실행일이다.
- 플러그인 등급: 조각이 하나라도 있으면 minor, 조각이 없고 옛 방식 신호도 없으면 patch, `호환성:` 이 든 옛 방식 줄이 있으면 major(지금과 같다).
- 같은 스킬에서 다른 PR 의 직접 올림과 조각이 만나면 조각을 지금 version 위에 올린다(직접 올림이 7.11.0 이면 조각은 7.12.0). 조각이 있는 스킬만 처리하고, 조각이 없는 스킬은 건드리지 않는다.
- 한 번의 실행은 플러그인을 한 번만 올린다(조각이 몇 개든 minor 한 번, 플러그인 CHANGELOG 한 줄). 옛 방식의 `호환성:` 줄이 push 범위에 함께 있으면 major 다.
- 플러그인 CHANGELOG 줄은 조각마다 만든 새 버전을 모두 적고(`plan 5.5.1, plan 5.6.0`) 지금처럼 PR 번호를 붙인다.
- 형식이 틀린 조각은 workflow 가 그 조각만 건너뛰고 경고를 낸다. 나머지 조각은 처리한다. 틀린 조각은 main 에 남아 다음 실행에도 경고를 낸다. 형식은 REQ6 과 같다: 조각 끝 빈 줄은 허용하고 그 밖에 `- ` 줄이 아닌 줄(제목, 문단)은 오류다.
- CHANGELOG 절 날짜는 한국 시간(Asia/Seoul) 실행일이다. 이 저장소의 지금 이력 날짜가 작성자의 한국 날짜라서 맞춘다.
- 이 PR 자체는 옛 방식으로 버전을 올린다. 새 workflow 는 머지된 뒤에야 돈다.
