# 문서 소유권과 변경

## 양식 사용

문서를 쓰는 스킬이 양식 한 벌을 소유한다. 작성 전에 해당 양식을 읽고 실제 기능의 값으로 바꾼다.
양식의 필수 항목은 유지하고 조건부 항목은 필요할 때만 쓴다. 예시의 결정·날짜·명령은 합의나 실행 증거가 아니다.
기존 저장소의 PRD·flow·ADR 양식이 있으면 우선한다. 기존 문서를 새 양식으로 일괄 재작성하지 않는다.
필수 정보와 연결은 검사기, 의미·결정·실행 증거는 독립 검토가 확인한다. 제목만 채운 문서는 완료가 아니다.

| 문서 | 양식 원본 | 갱신할 때 |
| --- | --- | --- |
| 기능 스펙 | [spec](../templates/spec.md) | 기능 요구사항·인수 조건이 바뀜 |
| 기술 설계 | [technical-design](../../technical-design/templates/design.md) | 모듈 책임·상호작용·검증 전략이 바뀜 |
| 실행 계획 | [index](../../plan/templates/index.json), [phase](../../plan/templates/phase.md) | PR 의 범위·작업·개발 검증이 바뀜 |
| 인수 검증 계획 | [plan](../../plan/templates/verification-plan.md) | 준비 조건·실행 절차·기대값이 바뀜 |
| 인수 검증 결과 | [verify](../../verify/templates/verification-result.md) | 같은 커밋의 실제 실행 결과를 기록 |
| 문서 대조·공통 후보 | [docs-consolidate](../../docs-consolidate/templates/document-review.md) | 기능 검증 뒤 정합성과 후보를 기록 |
| PRD | [spec 기본 양식](../templates/product-requirements.md) | 제품 목적·대상·주요 시나리오·범위가 바뀜 |
| flow | [기술 설계 기본 양식](../../technical-design/templates/system-flow.md) | 시스템 공통 상호작용이 바뀜 |
| ADR | [기술 설계 기본 양식](../../technical-design/templates/adr.md) | 장기 결정의 맥락·대안·선택 이유를 기록·대체 |
| 도메인 문서 | [spec 기본 양식](../templates/domain.md) | 여러 기능이 참조하는 현재 도메인 규칙이 바뀜 |
| 출력 계약 | [기술 설계 기본 양식](../../technical-design/templates/output-contract.md) | 결과 필드의 의미·허용 값·누락 처리가 바뀜 |

## 사실은 한곳에

PRD 는 제품 목적·범위를, 기능 spec 은 상세 요구사항을 소유한다. PRD 에 모든 요구사항과 진행률을 복제하지 않는다.
flow 는 시스템 공통 흐름을, 기능 design 은 상세 상호작용을 소유한다. 공통 문서에는 필요한 상세 링크를 둔다.
정확한 API/DB 스키마는 원본 코드·스키마가 소유한다. 다른 문서는 동작·이유와 원본 링크를 남긴다.
ADR 은 현재 구조의 전체 목록이 아니다. 결정을 뒤집으면 현재 사실의 책임 문서를 함께 맞춘다. 대체 관계와 당시 맥락의 보존은 [ADR 규칙](../../technical-design/references/adr-rules.md)이 소유한다.

## ADR 과 도메인 문서

**ADR 은 「왜 이렇게 결정했나」, 도메인 문서는 「지금 무엇을 따라야 하나」 를 담는다.**
ADR 은 결정의 배경, 대안, 영향을 담는다. 종류에 따라 구조, 도메인 정책, 개발 절차의 선택 이유를 기록한다.
ADR 이 현재 규칙의 원본 노릇을 하게 두지 않는다. 현재 원본은 종류와 범위로 정한다. 단일 기능 정책은 spec, 여러 기능의 도메인 규칙은 도메인 문서, 개발 절차는 해당 절차 문서, 정확한 값은 설정이 소유한다. ADR 과 현재 원본은 서로 링크한다.
결정의 배경과 현재 적용 규칙을 한 문서에 섞지 않는다.

### 결정 기록의 단계별 책임

결정의 종류·남길 조건·수명은 [ADR 규칙](../../technical-design/references/adr-rules.md#결정-종류와-관심-영역)이 소유한다.
기존 단계 안에서 처리하며 별도 ADR 단계를 만들지 않는다. 기록할 장기 결정이 없으면 ADR 은 만들지 않는다.

| 단계 | 책임 | 통과 조건 |
| --- | --- | --- |
| spec | 제품·도메인 정책을 결정하고, 장기 선택 이유를 기록할 필요와 현재 규칙의 원본을 식별한다 | 정책 결정과 확정 근거가 있고, 기록이 필요하면 종류·원본·선택 이유가 인계됐다 |
| technical-design | 구조 결정을 정하고 기존 결정과 대조한다. ADR 이 필요하면 종류·원본·대안·영향을 기록한다 | 정책을 대신 정하지 않았고 구조 결정이 닫혔으며 필요한 결정 기록이 식별됐다 |
| plan | 확정한 결정의 기록·원본 갱신·확인 사례를 같은 PR 의 작업으로 묶는다 | 새 결정을 구현자에게 미루지 않았고 필요한 문서와 검증 작업이 있다 |
| implementation | 코드·설정과 현재 책임 문서, 합의한 ADR 을 같은 PR 에 반영한다 | 결정·원본·구현의 의미가 같고 대체가 있으면 양방향 연결을 반영했다 |
| verify | 변경한 결정과 원본, 구현·평가 사례를 대조한다 | 일치 여부와 증거가 있고 새 정책은 spec, 구조 결정은 technical-design 으로 반환했다 |
| docs-consolidate | 원본 연결·중복·대체 관계의 누락을 찾고 공통 후보를 추출한다 | 정책을 새로 정하거나 과거 결론을 덮어쓰지 않았고 의미 차이는 해당 단계로 반환했다 |

`engineering-process` 의 장기 절차 결정은 사용자가 확정한다. 저장소 지침에 권한을 위임받은 결정자가 명시돼 있으면 그 사람이 확정한다. 에이전트는 제안과 근거 정리를 맡고, 위임 근거 없이 스스로 확정하지 않는다.
이미 확인받거나 위임 범위 안에서 확정한 결정은 근거를 인계하고 다시 묻지 않는다. 기존 결정을 바꾸지 않는 문구 수정·구현 선택에 별도 승인을 추가하지 않는다. 제품 동작을 바꾸지 않는 절차·문서 작업에 기능 spec 을 억지로 만들지 않는다.
그 작업의 plan·구현·검증 안에서 같은 기록·원본 대조를 수행한다. docs-audit 는 감사와 수정 제안만 맡고 결정 주체를 대신하지 않는다.

### 문서 자리

아래는 기본 자리다. 저장소 지침이나 오버레이가 다른 자리를 정하면 그것을 따른다.

| 문서 | 기본 자리 | 소유하는 것 |
| --- | --- | --- |
| 도메인 문서 | `docs/domain/<영역>.md` | 여러 기능이 함께 참조하는, 지금 유효한 도메인 개념과 판단 규칙, 상태 의미 |
| 출력 계약 | `docs/contracts/<출력>.md` | 결과를 쓰는 쪽과의 계약. 필드 의미, 필수 여부, 허용 값, 누락 처리 |
| 기능 스펙 | `docs/features/<기능>/spec.md` | 기능별 요구의 원본. 기능이 끝나도 과거 기록이 되지 않는다 |
| 기술 설계 | `docs/features/<기능>/design.md` | 규칙을 구현하는 방법 |
| 버전 관리되는 설정 | 저장소의 룰 설정이나 DB 사전 | 실제 판정 값의 원본 |

- 도메인 문서는 처음에 영역 하나에 파일 하나로 둔다. 규칙마다 파일을 만들지 않는다. 구성은 [도메인 문서 양식](../templates/domain.md)을 따른다.
- 여러 기능에 걸치는 공통 규칙만 도메인 문서가 소유한다. 한 기능에만 쓰는 규칙은 그 기능 스펙에 둔다.
- 같은 개념도 자리를 나눈다. 등급의 의미는 도메인 문서, 응답 필드에 넣는 등급 값은 출력 계약, 모델에게 등급을 어떻게 쓰라고 지시하는지는 프롬프트가 소유한다.
- 판정 값이 설정에 있으면 문서에 값을 복제하지 않는다. 설정이 값의 원본이고, 문서는 의미와 근거를 설명하며 설정을 가리킨다.
- 작은 변경도 스펙의 최소 절과 REQ1 인수 조건을 유지하고 결정 표를 짧게 쓴다. 공통 규칙이 아니면 도메인 문서를 새로 만들지 않는다.

### 단계별 책임

규칙 변경이 있을 때만 적용한다. 기준은 도메인 문서에 diff 가 있느냐가 아니라 변경이 필요한 곳에 빠짐없이 반영됐느냐다.
각 스킬에는 아래 행의 행동과 통과 조건만 짧게 두고, 규칙은 이 절이 소유한다.

| 단계 | 하는 일 | 통과 조건 |
| --- | --- | --- |
| spec | 도메인 규칙 결정을 소유한다. 기존 규칙은 RULE ID 로 참조하고, 바꿀 규칙을 스펙의 「도메인 규칙 변경」 표에 적어 사용자 확인을 받는다 | 변경할 규칙과 확정 상태가 명시되어 있다. 변경이 없으면 그 사실을 적었다 |
| technical-design | 규칙을 적용할 자리(코드, 프롬프트, 설정, 출력 계약)와 값의 원본을 정한다 | 변경 규칙의 적용 위치와 값의 원본이 정해져 있다 |
| plan | 도메인 문서와 출력 계약을 고치는 작업, 규칙별 확인 사례를 넣는다 | 필요한 문서·구현·검증 작업이 포함되어 있다 |
| implementation | 코드, 프롬프트, 설정, 평가 사례와 같은 PR 에서 도메인 문서를 고친다 | 변경 규칙이 관련 문서와 실제 적용 위치에 함께 반영되어 있다 |
| verify | 문서, 코드와 지시문, 평가 사례가 같은 규칙을 따르는지 규칙 ID 별로 확인한다 | 변경 규칙별 일치 여부와 실행 근거가 있다 |
| docs-consolidate | 갱신 누락, 중복, 상충을 마지막으로 확인하고 여러 스펙에 흩어진 규칙의 공통화 후보를 추출한다 | 누락을 찾으면 정책을 직접 정하지 않고 spec 이나 해당 기능 PR 로 돌려보냈다 |

현재 기준의 갱신은 해당 PR 의 책임이다. docs-consolidate 로 미루지 않는다.
기능 없이 기준만 바뀌어도(기획 피드백, 운영 중 결정) 목표·범위·REQ1 과 관측할 인수 조건·결정 표를 짧게 둔 작은 스펙과 PR 하나로 처리한다. 별도 축약 스키마는 만들지 않는다.

### 운영 설정의 변경

| 변경 | 처리 |
| --- | --- |
| 기존 정책이 허용한 범위 안의 값 조정 | 설정 변경 이력으로 관리한다. 스펙을 만들지 않는다 |
| 분류 의미, 판단 방식, 행동이 달라지는 변경 | 작은 스펙(결정 표)과 PR 로 기준을 바꾼다 |

설정을 바꿀 때는 도메인 문서에 영향이 있는지 확인한다. 숫자가 같은지가 아니라 규칙의 의미, 허용 범위, 설정 참조가 유효한지를 본다.

### 규칙의 결정 상태

도메인 문서의 규칙과 스펙의 「도메인 규칙 변경」 표는 결정 상태를 네 칸으로 나눠 적는다. 「AI 결정」 같은 상태 값을 쓰지 않는다.

| 칸 | 값 |
| --- | --- |
| 결정 상태 | `제안`, `확인 대기`, `확정` |
| 제안자 | AI, 기획, 회의처럼 처음 제안한 쪽 |
| 확정 근거 | 확정한 사람과 날짜. 예: `사용자 위임 2026-11-03` |
| 외부 검토 | `기획 확인 대기`, `기획 확인 완료`, `해당 없음` |

예를 들어 AI 가 제안하고 사용자가 위임해 확정했지만 기획 확인이 남은 규칙은 「확정, AI, 사용자 위임 2026-11-03, 기획 확인 대기」 로 적는다.

외부 검토가 남아 있어도 사용자가 적용을 위임해 확정했다면 진행할 수 있다. 외부 확인이 적용의 선행 조건이면 확정으로 쓰지 않고 확인 대기로 두며 구현을 막는다. 검사기는 변경 표의 확정 여부와 근거를 보고, 실제 위임과 외부 검토의 의미는 독립 검토가 확인한다.

### 기존 ADR

기존 ADR 은 전부 다시 쓰지 않는다. 앞으로 건드리는 영역부터 현재 규칙을 도메인 문서로 옮기고 ADR 과 서로 링크한다.

## 변경 순서와 충돌

technical-design 에서 이번 기능이 바꾸는 책임 문서만 식별한다. 영향이 없는 전역 문서는 수정하지 않는다.
이번 기능이 공유 권한·상태·호출 의미를 바꾸면 구현 전에 그 결정을 해결하고 해당 구현 PR 에 책임 문서를 맞춘다.
docs-consolidate 는 검증한 구현과 문서를 대조하고, 의미 변경은 spec/technical-design/implementation 으로 반환한다.
현재 사실의 필수 수정은 후속 공통화까지 미루지 않는다. 반복 표현 정리·관련 없는 낡은 문서는 후속 후보로 남긴다.

orch 는 동시에 진행할 계획의 변경 파일과 책임 문서를 대조한다. 같은 공유 문서를 바꾸면 담당을 한 worker 로 모으거나 순차 실행한다.
공유 계약을 먼저 바꿔야 하면 선행 PR 을 머지한 뒤 소비 기능의 계획을 구체화한다. 파일 잠금 시스템·중앙 진행표는 추가하지 않는다.
각 worker 는 자기 기능·계획 문서를 소유하고, 같은 전역 파일을 모두 갱신하게 하지 않는다.

## 계획과 증거의 수명

[계획 수명 규칙](../../plan/references/plan-lifecycle.md)이 보존·삭제와 증거 인계를 소유한다.
문서 점검은 이 규칙으로 완료 계획을 분류한다. 진행 중인 계획이나 유일한 결정·증거를 자동 삭제하지 않는다.
