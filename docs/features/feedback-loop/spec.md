# 스킬 피드백 반영 루프

확인: 2026-11-20

## 목표

여러 저장소의 worker 와 코디네이터가 남긴 스킬 개선 후보를 fos-skills 세션에서 한 번에 모아 판정하고, 고친 결과를 후보를 남긴 저장소에 알린 뒤 후보 파일을 지운다.
사용자는 보드의 단축키 하나로 이 흐름을 시작하고, 요청문을 직접 타이핑하지 않는다.

지금은 후보가 저장소마다 `.orch/feedback/` 에 따로 쌓이고 그 저장소 세션이 각자 판정한다([`feedback-review.md`](../../../skills/orch/references/feedback-review.md)).
2026-11-20 에 7개 저장소에서 후보 43개를 확인했다. 그 가운데 12개는 반영 PR(#504~#516)이 모두 머지됐는데도 지워지지 않았고, 후보를 남긴 저장소는 고쳐졌다는 사실을 모른다.
후보 11개 가운데 3개는 fos-skills 스킬이 아니라 다른 저장소의 스킬(ai-sdt 의 create-pr 검사기, ai-analysis 의 analysis-audit) 몫이었다.

## 범위

이번 범위:

- `orch feedback add` 에 「대상」 칸(core 스킬, 이 저장소)을 더하고 공통 지시서 틀이 고르는 기준을 설명한다.
- fos-skills 세션에서 Orca 에 등록된 모든 저장소의 열린 후보를 모아 보는 명령.
- 판정에 「core 에 필요한가」 확인을 더하고, 저장소 몫으로 본 후보는 원래 저장소에 돌려준다.
- 반영된 후보와 기각한 후보를 원래 저장소에 알리고, 원래 저장소에서 알림을 보인 뒤 휴지통으로 옮긴다.
- 보드에 `f` 단축키(피드백 반영)를 더한다.

범위 밖:

- 지금 쌓인 core 후보 6건(검사기 오탐 2건, worker 가 멈추는 문제 2건, plan 의 깨질 테스트 경고, ADR 번호 예약 설정 알림)의 수정. 이 루프와 별개로 각각 PR 을 연다.
- 다른 저장소의 스킬을 fos-skills 세션이 직접 고치는 것.
- Orca 에 등록되지 않은 저장소의 후보.
- 공부 후보(`.orch/study/`)의 같은 흐름.

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 후보를 적을 때 대상을 고른다 | `orch feedback add` 에 대상 값(core 스킬, 이 저장소)이 없거나 다른 값이면 저장하지 않고 이유를 낸다. 저장한 파일에 대상 칸이 있다. 공통 지시서 틀의 「스킬 개선 후보 보고」 절이 「다른 저장소에서도 같은 스킬을 쓰면 나는 문제면 core 스킬, 이 저장소의 스킬·설정·코드 때문이면 이 저장소」 를 기준으로 적는다. 대상 칸이 없는 옛 파일은 대상 「확인 필요」 로 읽힌다 |
| REQ2 | fos-skills 세션에서 모든 저장소의 후보를 모아 본다 | fos-skills 에서 모아 보기 명령을 돌리면 `orca repo list` 의 저장소마다 열린 후보(후보, 보류)가 저장소 이름, 대상, 상태, 제목과 함께 나온다. 대상이 이 저장소인 후보는 「저장소 몫」 으로, 대상이 「확인 필요」 인 옛 파일은 판정할 core 쪽 후보로 묶인다. 알림을 보낼 수 있는 후보(REQ4 조건이 찬 것), 버전을 기다리는 후보, 반영 PR 이 머지되지 않고 닫힌 후보도 따로 묶어 낸다. 후보 폴더가 없는 저장소는 줄 없이 건너뛰고, 폴더를 읽지 못한 저장소는 저장소 이름과 이유를 한 줄 낸다. 이 명령은 후보 파일을 바꾸지 않고 메시지도 보내지 않는다. 마지막 분류 결과는 `.orch/state` 에 남긴다 |
| REQ3 | 판정에서 core 몫인지 확인한다 | 판정 절차가 기존 세 기준 앞에 「core 에 필요한가」 를 확인하게 한다. 저장소 몫으로 판정하면 파일은 원래 저장소에 그대로 남고, 그 저장소의 doctor 가 할 일로 센다. core 몫 후보와 대상이 「확인 필요」 인 옛 파일은 원래 저장소의 doctor 가 할 일로 세지 않는다(fos-skills 자신은 예외로, 모든 저장소의 core 몫을 센다). 저장소 몫 후보는 그 저장소의 반영 PR 이 머지되면 doctor 가 한 번 보이고 휴지통 폴더로 옮긴다 |
| REQ4 | 반영과 기각을 원래 저장소에 표시한다 | 알림 보내기 명령을 돌리면, 채택한 후보 가운데 PR 이 머지되고 그 PR 이 든 플러그인 버전이 main 에 올라간 것은 원래 파일 상태가 PR 번호와 버전을 담은 「반영됨」 으로, 기각한 후보는 이유를 담은 기각 상태로 바뀐다. PR 은 머지됐지만 버전이 아직 올라가지 않았으면 바꾸지 않는다. 중복으로 기각한 후보는 대표 후보가 반영됨이 될 때 대표의 PR 과 버전을 담아 함께 바뀐다. 알림 보내기는 사용자에게 묻지 않고 돌고, 보낸 목록을 보고한다 |
| REQ5 | 원래 저장소에 일하는 코디네이터가 있으면 바로 알린다 | REQ4 로 상태를 바꿀 때 그 저장소에 메인 코디네이터가 있으면, 한 번 돌릴 때 저장소마다 메시지 한 통이 간다. 메시지에는 후보마다 「무엇이 고쳐졌는지(제목, PR, 버전)」 나 「기각 이유」 가 있고, 고쳐진 것이 있으면 「플러그인 갱신 필요」 한 줄이 있다. 메시지가 가면 그 후보 파일은 바로 휴지통 폴더로 옮겨진다. 메인이 없거나 보내기가 실패하면 상태 표시만 남고 오류로 멈추지 않는다 |
| REQ6 | 메시지를 받지 못한 저장소는 doctor 가 보인 뒤 지운다 | 원래 저장소에서 orch 를 열 때 doctor 가 반영됨·기각 상태로 남은 후보를 제목과 PR, 버전, 이유와 함께 보이고 그 파일을 휴지통 폴더(기본 `~/.Trash/orch-feedback/`)로 옮긴다. 같은 알림은 메시지와 doctor 를 합쳐 한 번만 보인다 |
| REQ7 | 보드의 단축키로 흐름을 시작한다 | 지금 할 수 있는 일이 있으면 보드 단축키 상자에 「f: 피드백 반영 (개수)」 가 보이고, 없으면 보이지 않는다. 개수는 판정할 후보(상태가 후보인 것)와 지금 보낼 수 있는 알림, 보일 알림이다. 보류와 버전을 기다리는 후보는 세지 않는다. fos-skills 의 보드는 모든 저장소의 core 몫과 fos-skills 자기 몫, fos-skills 가 받은 알림을, 다른 저장소의 보드는 그 저장소 몫과 받은 알림을 센다. `f` 를 누르면 입력란에 요청문이 채워지고 Enter 를 눌러야 보내진다 |
| REQ8 | 이미 반영된 옛 후보도 같은 흐름을 탄다 | 이 기능이 들어간 뒤 첫 모아 보기에서, 반영 PR 이 머지되고 버전이 올라간 기존 `채택 #PR` 후보 12개가 REQ4~REQ6 대로 알려지고 원래 저장소에서 지워진다 |

## 도메인 규칙 변경

도메인 규칙 변경 없음: 여러 기능이 참조하는 도메인 규칙을 바꾸지 않는다. 바뀌는 것은 orch 의 후보 판정 절차와 후보 파일 형식이다.
