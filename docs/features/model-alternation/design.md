# 같은 등급의 모델을 번갈아 띄우는 설계

## 요구사항 연결

| ID | 해결 방법 |
| --- | --- |
| REQ1 | 지시서의 행에서 등급을 찾고, 그 등급의 차례로 제공자를 정한다 |
| REQ2 | 저장소 밖의 장비 상태에서 다음 제공자를 읽고, 잠금 안에서 다음 차례로 바꾼다 |
| REQ3 | 차례의 모델과 짝을 기존 한도 검사에 넘긴다. 한 쪽이 소진되면 짝으로 띄우고, 둘 다 소진되면 기존 초기화 안내를 낸다 |
| REQ4 | 기존 선택 줄 형식을 유지한다. 같은 행의 두 조합을 지시서와 CLI에서 허용하고 실제 선택과 이유를 실행 출력 및 이력에 남긴다 |
| REQ5 | 후보 밖 모델은 지시서에서 받은 설정으로 한도 검사부터 진행한다 |
| REQ6 | 리뷰는 구현 브랜치의 최근 실행 이력에서 실제 제공자를 읽어 기존 리뷰 등급의 반대 제공자를 고른다 |
| REQ7 | Task 재시도와 relaunch는 차례를 쓴다. resume과 터미널 이어 쓰기는 세션을 잇는다 |
| REQ8 | 행에는 등급과 모델 쌍을 표시한다. 실행 코드는 한도 표의 등급 표시와 대응 모델을 읽는다 |

## 책임과 경계

[모델 표](../../../skills/orch/references/agent-selection.md#모델)가 작업에 맞는 등급과 effort를 정한다. [한도 표](../../../skills/orch/references/agent-selection.md#사용-한도에-걸렸을-때)에서 등급을 표시한 행의 두 제공자를 짝으로 읽는다. 같은 등급의 다른 대응 모델은 직접 고른 모델과 리뷰의 기존 한도 대체에 쓴다.

`selection.ts`는 조합을 검사하고, `model-turn.ts`는 다음 제공자를 저장한다. `launch-worker.ts`는 차례, 세대, 한도, 실행 가능 여부를 순서대로 확인한다. 기존 한도 판정에 후보 목록만 넘기므로 사용량을 해석하는 규칙은 한곳에 있다.

`orch spec review`는 구현 브랜치의 가장 최근 이력에서 `effective.agent`를 먼저 읽는다. 옛 이력은 최상위 `agent`를 쓴다. 리뷰 시작은 이 지시서의 제공자를 사용하고, 소진 시 기존 한도 대응을 따른다.

## 인터페이스와 데이터

`~/.cache/orch/model-turns.json`에 등급별로 다음 제공자를 적는다. `ORCH_MACHINE_DIR`을 정했으면 그 폴더에 둔다. 처음에는 Codex 차례로 시작하고, 같은 등급의 여러 행은 같은 키를 쓴다. 실행 설정의 `alternation`에 등급, 차례의 제공자, CLI가 받은 설정, `번갈아: <등급> 차례`를 적는다. 최상위 실행 설정에는 실제로 띄운 값을, 한도로 모델을 바꿨으면 `candidateOverride`에 그 이유를 적는다.

## 실패와 일관성

기존 `withOwnerLock`으로 읽기와 쓰기를 감싸고, 같은 폴더에 쓴 임시 파일을 rename 한다. 잠금이나 파일 읽기·쓰기에 실패하면 시작 전에 거절한다. 예약한 차례는 한도에 걸리거나 시작에 실패해도 계속 진행해, 다른 실행에서 이미 받은 차례를 되돌리지 않는다. 계정 재확인에서 한도를 다시 읽어도 이미 잡은 차례를 쓴다.

단독 `--preflight`도 차례를 잡고 실행 후보를 출력한다. relaunch는 abandon 전 사전 검사에서 잡은 차례를 최종 호출에 넘겨 두 번 세지 않는다. 차례 파일 없이도 처음부터 시작할 수 있어 기존 이력을 변환할 필요가 없다.

## 검증 전략

- 단위 테스트로 각 행의 짝과 effort, 두 제공자의 지시서 허용, 잠금이 막는 동시 차례 중복을 본다.
- 가짜 Orca로 시작과 이력, 소진 대체와 거절, 리뷰, 재시도, relaunch, 터미널 이어 쓰기를 확인한다. resume의 기존 모델 보존 테스트도 돌린다.
- 장비의 계정으로 같은 등급의 `--preflight`를 연속 호출해 실제 후보가 달라지는지 본다.
