# 여섯 감사 축

「의미 검사」 단계에서 읽는다.

## ADR 상태를 먼저 본다

`status: superseded` 인 ADR 은 이력이다. 부패 축과 자명성 축을 적용하지 않는다.
당시의 코드와 경로를 가리키는 것이 정상이고, 대체됐다는 사실 자체가 남길 이유다.

**대신 대체 표기와 위치, 링크·색인 갱신 규약을 지켰는지 본다.** 어긋난 자리가 발견이다.
`status` 가 없는 ADR 을 어떻게 읽는지를 포함해 규약은
[plan 의 task-create.md](../../plan/references/task-create.md) 가 소유한다.

## 완료된 plan 은 제거 후보다

[계획 수명 규칙](../../plan/references/plan-lifecycle.md)으로 보존 정책과 실제 완료 여부를 먼저 판정한다.
머지된 PR 또는 completed 계획 중 삭제 정책에 해당하는 것만 검토한다. 진행 중인 계획과 보존 정책의 계획은 제거 후보가 아니다.
결정·검증 절차·기대값·실제 증거가 책임 문서 또는 PR 에 남았는지 대조한다. 없으면 제거하지 않고 빠진 기록을 보고한다.
제거 후보도 docs-check 의 기존 승인 절차를 따른다. 유일한 결정·증거를 자동 삭제하지 않는다.

## 계획서를 번호로 가리키지 않는다

계획서가 제거되므로, 문서와 코드가 계획서를 번호로 가리킨 자리는 그때 깨진 참조가 된다.

**기본은 아무것도 적지 않는 것이다.** 무엇이 언제 왜 바뀌었는지는 git 이력이 이미 추적한다.
근거가 필요할 때만 아래를 적는다.

| 남길 것 | 무엇을 적나 |
| --- | --- |
| 결정의 근거 | ADR 번호 |
| 변경의 이력 | PR 번호 |
| 그 밖 | 적지 않는다 |

커밋 SHA 는 적지 않는다. rebase 와 squash 로 값이 바뀌어 같은 변경을 다시 찾을 수 없다.

### 유형별 처리

`static_check.py` 가 `PLAN_REF` 로 위치를 뽑는다. 처리는 유형이 정한다.

| 유형 | 예 | 처리 |
| --- | --- | --- |
| 출처 표기 | 결정 문장 끝에 계획서 번호를 괄호로 붙인 것 | 지운다 |
| 내용 위임 | 내용을 적지 않고 계획서를 읽으라고 한 것 | 내용을 책임 문서로 옮기고 지운다 |
| 시간 축 | 계획서 번호를 시간 순서로 쓰는 판정 기준 | 날짜로 바꾼다 |
| 절차 설명 | 계획서를 만드는 방법을 설명한 것 | 유지한다 |

**계획서 번호를 시간 축으로 쓰지 않는다.**
번호는 계획서와 함께 사라지므로, 사라진 뒤에는 어느 쪽이 최근인지 판정할 수 없다.
날짜처럼 계획서 수명과 무관한 값을 쓴다.

### 예외

아래 둘은 발견으로 올리지 않는다.

- **기존 파일과 식별자의 이름.** 이름은 참조가 아니라 식별자다.
  바꾸면 그 이름을 부르는 쪽도 함께 고쳐야 해서 비용이 참조 하나보다 크다.
  새로 만드는 이름에는 계획서 번호를 넣지 않는다.
- **측정 기록에 남은 실행 경로.** 그 시점의 실행 환경을 적은 것이라, 고치면 기록이 틀린 값이 된다.

## A. 부패

코드가 docs 와 맞는가. 제거된 엔티티가 docs 에 남아있지 않은가.

- 제거된 함수·컴포넌트·엔드포인트명이 docs 에 남아있다.
- DB 스키마와 스키마 문서의 테이블·필드가 불일치한다.
- 디렉터리·파일 경로가 실제와 다르다.
- "제거 완료" ADR 의 제거 대상이 여전히 코드에 존재한다.
- 미갱신 환경변수 표, 실재하지 않는 경로.

> 레포 특화 부패 검사(스키마 파일 경로·라우트·config 키 대조)는 오버레이의 grep 명령을 따른다.

## B. 과대화

ADR·docs 가 구현 세부로 비대해졌는가.

**ADR 은 "기술적 의사결정" 만 담는다.** 구현 결과(컴포넌트 트리·파일 배치·함수 호출)는 코드에 있다.
ADR 이 답해야 할 질문은 *"무엇을 / 왜 / 다른 선택지는 왜 아닌가"* 뿐이다.

**한 ADR 안에서 최종 상태만 기록하고 중간 단계는 제거한다.**
ADR 은 "현재 이렇게 되어 있다" 와 "왜 이 결론에 도달했는가" 만 남긴다.
여러 번 이터레이션한 중간 작업·변경 항목 목록은 삭제한다. 진화 과정이 의미 있으면 한 문장으로 응축한다.

검출 대상:

- ADR 본문 내 긴 코드 블록 (구현 예시)
- 현재 구현의 파일과 디렉터리를 목록으로 복제
- 변수·함수·프롭 이름을 줄 단위로 나열하는 표
- "사용 예시" 섹션에 호출 코드 복붙
- 그 저장소 지침의 스택 규칙을 반복하는 문장
- "새 디렉터리 구조", "변경 항목 목록", "레거시 삭제 목록" 같은 작업 내역

> 정당한 예외: 단일 결정을 구분하는 데 필요한 최소한의 식별자는 허용한다.

### ADR 에 들어간 도메인 기준

**도메인 판단 기준을 담은 ADR 은 발견이다.** 업무 규칙, 기준값, 분류·이름 규칙, 업무 정책이 여기 해당한다.
경계와 옮길 자리는 [spec 의 문서 소유권 「ADR 은 기술 결정만 담는다」](../../spec/references/document-ownership.md#adr-은-기술-결정만-담는다)가 소유한다.

- 판정 질문: 이 결정을 바꾸면 코드 구조, 저장, 계약, 배포, 도구가 바뀌는가, 아니면 업무 판단의 결과만 바뀌는가? 뒤쪽이면 도메인 기준이다.
- 기술 결정이 기준값을 링크로만 가리키면 발견이 아니다. 기준값과 그 이유를 ADR 본문에 적은 것이 발견이다.
- 심각도는 `Warning` 이다. 같은 기준이 도메인 문서와 다르게 적혀 있으면 부패 축의 `Critical` 로 올린다.
- 수정안은 기준을 살아 있는 도메인 문서로 옮기고 ADR 에는 링크를 남기는 것이다. 그 문서가 없으면 spec 으로 만들지 사용자에게 묻는 것을 수정안으로 적는다.
- `superseded` ADR 은 이력이라 옮기지 않는다. 그 안의 기준이 아직 유효한데 도메인 문서에 없을 때만 발견이다.

## C. 의사결정 추론성

ADR 이 "왜" 를 담고 있는가. "결정 / 맥락 / 대안 기각" 구조가 있는가.

검출 대상:

- "결정" 만 있고 "맥락·이유·대안" 이 없는 ADR
- 맥락이 "요구사항 추가" 같은 순환 설명
- 대안 기각이 없거나 "기각" 만 있고 근거가 없음

## D. 중복

같은 내용이 여러 docs 에 본문으로 반복되는가.

검출 대상:

- 같은 필드 목록이 ADR 과 스키마 문서 양쪽에 있음
- 흐름 요약이 PRD 와 flow 문서 양쪽에 있음
- 그 저장소 지침의 스택 규칙이 아키텍처 문서에 복사됨

원칙: **정의는 1곳, 다른 문서는 링크 또는 짧은 참조.**

## E. ADR 자명성

**코드·설정 파일만 봐도 아는 결정은 ADR 로 남기지 않는다.** ADR 의 가치는 "코드를 봐도 알 수 없는 맥락" 에 있다.

폐기 후보 유형:

| 유형 | 예시 | 근거 |
|---|---|---|
| 라이브러리·패키지 선택 | "X 사용", "Y 사용" | 의존성 파일로 자명 |
| 폴더·디렉터리 구조 결정 | "X 폴더 분리" | 디렉터리 트리로 자명 |
| 단순 마이그레이션 기록 | "X 컬럼 제거", "Y 를 Z 로 rename" | 스키마와 git log 로 자명 |
| 일반 프로그래밍 원칙 | "중복 코드는 공통 함수로 추출" | 상식 |
| 환경 설정 | "개발 포트 분리", "Compose 구성" | 설정 파일로 자명 |

유지 기준:

1. **라이브러리 고유 함정** — 문서에 없거나 직관에 반하는 API 특성
2. **실험 결과** — A/B 비교로 도출된 근거 (수치 포함)
3. **대안 기각 근거** — "왜 이 선택이 아닌가" 가 미래 논의에서 재발할 여지가 있을 때
4. **기술 정책 결정** — 코드만으로 드러나지 않는 보안·비용·호환성 trade-off
5. **비용·성능 트레이드오프 근거** — 수치가 있는 결정

자명성 판정 질문:

- 이 ADR이 없어도 코드, 설정과 git 이력에서 같은 정보와 이유를 얻을 수 있는가?
- 맥락이 선택 이유가 아니라 현재 구조를 다시 말하는 데 그치는가?
- 저장소 고유의 제약이나 기각한 대안 없이 일반 원칙만 담는가?

위 질문이 모두 맞으면 폐기 후보로 보고, 연결 문서와 외부 참조를 확인한 뒤 판정한다.

## F. 문서 구조 무결성

문체가 아니라 문서가 실제로 열리고 구조가 깨지지 않는지 점검한다.
한국어 표현과 서식은 이 축이 보지 않는다.

검출 대상:

- 깨진 로컬 링크
- 표의 열 수 불일치
- 닫히지 않은 코드 펜스
- 헤딩 레벨 건너뛰기
- ADR 본문과 INDEX의 파일·번호 불일치
