# 기능 단위 개발 루프

orch 가 전체 루프를 조율한다. 단계별 판단과 산출물은 각 스킬이 소유한다.
입력은 기능 요청 또는 스펙 경로다. 기존 spec 필드 없는 plan 은 기존 worker 절차로 이어 간다.

## 루프를 쓸지 정한다

지시서를 쓰기 전에 정하고 「할 일」 첫 줄에 어느 쪽인지 적는다. 루프의 단계 비용이 PR 하나보다 커지는 것을 막으려는 것이다.

| 루프를 쓴다 | 루프 없이 바로 구현한다 |
| --- | --- |
| 새 사용자 동작, 도메인 판단 의미 변경, 새 외부 계약(API, 저장 구조), 여러 PR 로 나뉘는 기능 | 의미·계약을 유지하는 버그 수정, 정리·삭제, 허용 범위 안의 설정 값 조정, 측정, 오타 수정 |

**지시서에는 `## 할 일` 제목을 두고, 그 아래 첫 줄을 아래 세 꼴 가운데 하나로 시작한다.** 빈 줄은 건너뛰고, 목록 기호와 굵게는 있어도 된다.

| 첫 줄 | 언제 | `launch-worker` 가 막는 경우 |
| --- | --- | --- |
| `루프를 쓴다(스펙: <경로>)` | 사용자가 확인한 스펙이 있다 | 스펙이 없거나 그 제목 아래 `확인: YYYY-MM-DD` 줄이 없다 |
| `루프를 쓴다(스펙: 새로 쓴다)` | worker 가 spec 인터뷰부터 한다. 아래 「spec 인터뷰 중계」 를 따른다 | 막지 않는다 |
| `루프 없이: <이유>` | 위 표의 오른쪽 열 | 이유가 비었다 |

```markdown
## 할 일

루프를 쓴다(스펙: docs/features/run-cancel/spec.md). spec 은 확인이 끝났으니 technical-design 부터 시작한다. 기존 설계가 있으면 검토 결과를 확인하고 plan 으로 잇는다.
```

```markdown
## 할 일

루프 없이: 머지 큐 로그의 오타만 고치는 버그 수정이다.
```

스펙 경로는 대상 저장소 루트 기준 상대경로나 절대경로다.
**상대경로 스펙은 worker 가 시작할 곳에 있어야 통과한다.** 새 워크트리는 기준 브랜치(`origin/<base>`) 위에 만들어지므로 거기에 커밋돼 있어야 한다. 커밋하지 않은 스펙을 상대경로로 적으면 worker 가 읽지 못한다. 커밋하지 않은 스펙(인터뷰를 마친 임시 스펙)은 절대경로로 적는다.
`--resume-remote` 는 지시서 브랜치의 원격 ref 에서, `--worktree` 로 이어 띄우면 그 워크트리에서 읽는다.
첫 줄 검사는 `spec-lint` 의 `루프` 발견이고 `launch-worker` 가 워크트리를 만들기 전에 종료 코드 5 로 멈춘다. 넘기는 길은 `--lint-ack "<이유>"` 뿐이다. 판정 규칙은 `spec-lint.ts` 머리 주석의 「루프」 가 소유한다.
`리뷰 PR:` 줄이나 `중간 과정:` 줄이 있는 지시서는 기능 구현이 아니라 보지 않는다. 이미 떠 있는 worker 의 지시서(`--active`)도 보지 않는다.
`--terminal` 로 같은 worker 에게 이어 띄우는 후속 지시서는 새 일이라 본다. 기존 PR 을 마무리하는 후속 지시서면 `중간 과정:` 줄을 둔다([`spec-writing.md`](spec-writing.md)).

루프를 건너뛸지는 코디네이터가 위 표로 정하고 이유가 타당한지는 검사하지 않는다. 대신 `루프 없이` 로 띄우면 사용자에게 보내는 띄우기 보고에 그 이유를 한 줄로 적는다([`launch.md`](launch.md) 의 「띄운 직후 확인」).

루프 없이 가는 일도 구현과 수정 확인, 필요한 독립 검토를 수행하고 PR 본문에 근거를 적는다. 단계 문서의 생략이 검증의 생략은 아니다.
그 일에서도 사용자 동작·권한·데이터 보존을 바꾸는 선택이 생기면 그 결정만 결정 질문 형식으로 묻는다. spec 인터뷰 전체를 돌리지 않는다.
저장소마다 판단이 갈린 실제 예(PR 번호, 업무)는 `.orch/overlay.md` 에 둔다. 기준을 오버레이에 다시 적지 않는다.

| 순서 | 실행할 스킬 | 넘길 것 | 다음 단계 조건 |
| --- | --- | --- | --- |
| 1 | spec | 사용자 요청·관련 코드·계약 | 제품 결정이 닫혔고 사용자가 스펙을 확인함 |
| 2 | technical-design | 확인한 스펙·관련 코드·원칙 | 책임·소유권·상호작용·검증 전략과 독립 검토 완료 |
| 3 | plan | 스펙·설계 | 이번 PR 의 요구사항과 실행 계획이 critic 검토를 통과함 |
| 4 | implementation | 스펙·설계·계획 전체 경로·작업 공간 | 구현과 개발 검증 완료 |
| 5 | verify | 같은 커밋·스펙·설계·계획·개발 검증 | PR 전 인수 조건·문서 검토 통과. PR 자동 코드 리뷰는 대기로 인계 가능 |
| 6 | docs-consolidate | 기능 문서·diff·검증 결과 | 문서 대조와 후보 추출 완료. 후보 없음도 완료 |
| 7 | orch 의 기존 PR·머지·배포·정리 | 아래 인계 기록 | PR 반영과 필요한 원격 검증 완료 |

작은 변경은 기존 구조를 유지하는 짧은 기술 설계로 충분하다. 같은 기능의 후속 PR 은 spec/design 을 재사용한다.
문서 충돌은 [문서 소유권](../../spec/references/document-ownership.md)으로 조율한다. 같은 공유 문서를 바꾸는 worker 는 순차 실행하거나 소유자를 하나로 정한다.
계획·검증 계획의 보존과 삭제는 [계획 수명 규칙](../../plan/references/plan-lifecycle.md)이 소유한다.
계획 경로는 `docs/features/<기능>/tasks/<계획>` 이 기본이다. 기존 계획은 이동하지 않는다.
PLAN 은 마지막 디렉터리명, TASKS_DIR 은 그 부모다. 경로 인계를 유지해 다른 기능의 동명 계획과 섞이지 않게 한다.

## 전이

- 발견을 나눠 돌려보낸다. 사용자 의도·결정 누락은 spec(그 결정만 인터뷰하고 확인을 다시 받는다), 구조·경계 결함은 technical-design, 계획 결함은 plan, 구현 결함은 implementation, 범위 밖 개선은 후속으로 남긴다. 해결되지 않은 단계에서 다음으로 가지 않는다.
- 환경·권한 때문에 실행하지 못하면 필요한 것을 보고한다. 통과로 취급하지 않는다.
- spec·설계 또는 코드가 바뀌면 영향받는 계획과 검증을 갱신한다. 이전 커밋의 결과를 새 변경에 그대로 쓰지 않는다.
- 공통 후보가 없거나 공통화가 보류돼도 기능 완료를 막지 않는다. 동작을 바꾸는 모순은 verify 에서 해결한다.
- 문서만 수정하면 verify 의 문서 검토만 다시 받는다. 원격 검증의 선행 조건이 채워지면 그 검증을 수행한다.

## spec 인터뷰 중계

worker 는 사용자에게 직접 묻지 못한다. worker 쪽 절차는 spec 의 [인터뷰 절차](../../spec/references/interview.md) 「직접 묻지 못할 때」 가, 코디네이터 쪽 중계는 [`replying.md`](replying.md) 의 「spec 인터뷰를 중계한다」 가 정한다.
worker 지시서에는 공통 지시서 틀의 `spec-interview` 표지 줄이 있으면 된다. 저장소 오버레이에 같은 규칙을 다시 적지 않는다.

## worker 와 PR

새 기능 worker 지시서에 `spec → technical-design → plan → implementation → verify → docs-consolidate 후보 추출` 을 적고, 「할 일」 첫 줄은 위 「루프를 쓸지 정한다」 의 꼴로 쓴다.
스펙·설계·계획이 이미 있으면 필요한 단계부터 시작한다. 단계를 나눠도 worker 의 완료 기준 PR 하나의 MERGED 는 유지한다.
implementation 의 구현 완료는 중간 상태다. worker_done 으로 dispatch 를 끝내지 않는다.
PR 전 실행 검증·문서 대조·후보 추출 뒤 PR 생성이 허락됐으면 worker 가 PR 을 열고, 아니라면 코디네이터가 허락 범위에 따라 처리한다.
머지와 작업 공간 정리는 기존 orch 절차가 맡는다. 여러 plan 이면 PR 하나가 머지된 뒤 다음 plan 을 구체화한다.

PR 을 열기 전에 스펙·설계·계획 전체 경로·인수 검증 절차/기대값·요구사항 ID, verify 결과, 검증 커밋, 남은 원격 검증과 공통 후보를 본문에 보존한다.
계획서를 지우기 전에 `index.json` 의 `deferred` 전체(목표·이유·선행 조건)도 PR 본문에 옮긴다.
다음 worker 에게 앞 PR 의 이 목록과 스펙을 넘겨 다음 plan 을 만들게 한다. 중앙 진행표 갱신은 요구하지 않는다.
`remote-verification.md` 는 [기존 원격 검증 규칙](../../plan/references/task-create.md#원격-검증-목록)대로 시점·위치·명령·기대값을 옮긴다.
필수 `PR 전` 검증의 통과 결과가 없으면 PR 을 열지 않는다. 해당 검증이 없는 계획은 이 조건을 적용하지 않는다. `PR 뒤` 검증이 남았으면 머지/배포 뒤 실행하고 결과를 보존한다.
계획의 보존·삭제는 저장소 정책을 따른다. 삭제 시 검증과 기록 보존을 마친 해당 계획 폴더만 PR 안에서 제거한다. 스펙·설계·공유 계약과 다른 계획은 남긴다.
계획서 삭제 같은 비제품 변경은 제품 검증을 반복하지 않지만 문서/링크 검사는 확인한다.
기준 브랜치 병합·충돌 해결·리뷰 수정으로 코드가 바뀌면 verify 를 다시 거친 뒤 머지한다.

마지막 PR 에서 스펙 전체의 요구사항 증거와 통합 동작을 확인한다.
부분 PR 의 PASS, MERGED 또는 보드 done 만으로 기능 전체 완료를 선언하지 않는다.
필요한 배포 후 검증이 남으면 기능 완료 보고에 미완료로 남긴다.

## 공통화 후속

후보는 PR 별 기록에서 읽는다. 공유 후보 목록에 worker 들이 동시에 쓰게 하지 않는다.
관련 기능 묶음을 마쳤거나 사용자가 정리를 요청하면 docs-consolidate 의 공통화 모드로 묶어 맡긴다.
제품 계약 변경이 필요하면 별도 spec 으로 돌린다. 공통화 PR 도 검토·문서 검증을 거쳐 기존 머지 절차를 따른다.

새 상태 머신이나 타이머를 추가하지 않는다. 스킬 인계로 한 기능을 끝내고 실제 사용에서 드러난 문제를 고친다.

## PR 과 완료 근거

[PR 근거 양식](../templates/feature-evidence.md)은 기능 PR 마다 PR 본문에 한 번만 둔다. 코드 블록 안의 예시는 근거로 읽지 않는다.
인수 검증·문서 대조는 통과 뒤 PR 을 연다. 코드 검토를 PR 자동 리뷰에 맡기면 독립 리뷰만 대기로 열 수 있다.
자동 리뷰가 생략되거나 실패하면 별도 독립 검토를 받고 실제 결과를 기록한다. 필수 리뷰를 없애지 않는다.
머지 전에 독립 리뷰까지 통과하고 현재 HEAD 의 근거로 갱신한다. 기존 리뷰 정책과 CI·스레드 검사도 그대로 적용한다.
머지 큐는 양식과 현재 HEAD 를 검사하고, 코디네이터는 연결된 실행 증거와 검토 내용을 읽는다. 문구만으로 실제 실행을 증명하지 않는다.

자동 머지는 지시서의 기능 루프 선택을 읽어 블록 누락을 막는다. 기능 자동 머지는 `queue.auto_review` 설정과 현재 HEAD 의 실제 리뷰 판정도 요구한다. 설정이 없으면 코디네이터의 수동 검토로 넘긴다. 직접 머지 큐도 기본·설정 지시서와 PR 의 블록을 확인한다.
Orca 밖에서 스킬을 직접 쓰는 기능 PR 도 이 블록을 넣는다. 지시서도 블록도 없는 기존 PR 은 호환 경로라 기능 여부를 자동 판별하지 않는다.
커스텀 지시서 경로는 `finish.specs_dir` 에 지정한다. 기능 지시서는 마무리 검증 전에 지우지 않는다.

후속 검증이 있으면 담당, 선행 조건, 실행 위치·명령·기대값을 본문에 보존하고 `후속 검증: 대기` 로 둔다.
배포 후 코디네이터가 해당 검증을 실행하거나 검증 담당에게 맡기고 실제 결과로 본문을 갱신한다. `after-deploy` 업무 완료 핸들러는 이 확인 뒤 실행한다.
finish-pr 은 갱신된 본문을 읽고 대기·실패면 지시서와 보드를 남긴 채 FINISH-FAIL 로 끝난다.
근거를 갱신하고 같은 finish-pr 명령으로 재개한다. 외부 업무 완료 핸들러도 후속 검증 통과 뒤에만 업무를 닫아야 한다.
**워크트리·브랜치·빈 터미널은 MERGED 직후 지운다.** 지시서, 보드 done, 업무 완료만 후속 검증 뒤로 남긴다(사용자 결정 2026-11-04). 후속 검증은 배포된 환경에서 돌므로 워크트리가 필요 없고, 남겨 두면 머지된 워크트리가 한 시간 넘게 쌓였다. 배포 성공만으로 기능 완료를 선언하지 않는다.

상주 정리와 보드 동기화도 PR 의 후속 검증 근거를 확인한다. 마무리 프로세스가 끝나도 대기 중인 기능의 지시서를 지우거나 done 으로 바꾸지 않는다.
