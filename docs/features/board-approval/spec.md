# 보드: 사용자 승인 대기를 보드에 올리고 버튼으로 승인한다

확인: 2026-11-10

## 목표

코디네이터가 「확인해 주시면 등록」 처럼 사용자 승인을 기다릴 때 그 대기를 보드에 올린다. 사용자는 보드에서 미리보기를 열어 보고 「승인」 이나 「고쳐 달라」 를 눌러 답한다. 채팅에 「진행해줘」 를 치거나 여러 대기 가운데 어느 것인지 다시 적지 않아도 된다. 승인은 사람이 보드에서 누른 것만 인정한다.

- 배경(넘김 문서 `.orch/handoff-board-approval/README.md`, ai-analysis 코디네이터 2026-11-10): 미리보기를 띄우고 채팅으로 승인을 기다리는 일이 하루에 여러 번이다. 두레이 업무 등록, 마무리 댓글, 릴리스 PR 본문, 스펙 확인, real 쓰기 확인이 그 예다.
- 사용자 결정(2026-11-10): 보드 CLI 스펙(#421)에 합치지 않고 따로 스펙으로 쓴다.

## 범위

이번 범위:

- 승인 대기를 올리고, 보고, 거두고, 확인하는 명령 `orch board approval add`, `list`, `cancel`, `check`
- 보드 창의 「승인 대기」 상자, 「승인」·「고쳐 달라」 버튼, 고칠 내용을 적는 글칸, 코디네이터에게 가는 신호
- 승인 대기의 종류 다섯: 외부에 글 등록(`post`), 스펙 확인(`spec`), 단계 진행 허락(`step`), real 환경 쓰기(`real`), 사람이 직접 칠 명령(`command`)
- 코디네이터가 신호를 받고 따르는 규칙(확인, 고쳐 다시 올리기, 거두기)
- 자동 진행 `[ask]` 단계를 승인 대기로 올리는 코디네이터 규칙

범위 밖:

- 에이전트가 같은 컴퓨터 사용자 권한으로 승인 기록 파일과 Orca 메시지를 일부러 꾸미는 것까지 막는 것(REQ13)
- 루프가 승인 대기를 스스로 만드는 것. 올리는 것은 코디네이터다
- worker 가 승인 대기를 올리는 것. worker 는 지금처럼 `worker-ask` 로 묻고 코디네이터가 올린다
- 채팅으로 승인하는 지금 길을 없애는 것. 사용자가 채팅으로 승인해도 지금처럼 인정한다(REQ10)
- 미리보기를 만드는 일. `content-preview` 가 맡고 이 기능은 그 파일 경로를 받는다

PR 순서: 첫 PR 은 명령(`add`, `list`, `cancel`, `check`), 저장, 코디네이터 규칙이다. 둘째 PR 은 창의 상자, 버튼, 글칸, 신호 보내기다. 첫 PR 만 머지된 동안은 `list` 로 대기를 볼 수 있고 승인은 지금처럼 채팅으로 한다.

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | `orch board approval add <id> --title "<제목>" --kind <post\|spec\|step\|real\|command> [--preview <파일>] [--item <보드 항목>] [--step <번호>] [--then "<승인 뒤 할 일>"]` 로 승인 대기를 올린다. `real` 은 `--target`(대상 환경), `--change`(바꿀 것), `--rollback`(되돌리는 법)이 필수다. `command` 는 `--command "<명령>"` 이 필수다. `step` 은 `--item` 과 `--step` 이 필수다. `command` 를 뺀 네 종류는 `--preview` 가 필수이고 그 파일이 있어야 한다. 올릴 때 지금 Run, 부른 코디네이터 터미널(`ORCA_TERMINAL_HANDLE`), 미리보기 파일 내용의 해시, 올린 시각, 그 `add` 마다 새로 매기는 버전를 함께 남긴다. id 는 저장소 안에서 하나다 | 성공하면 stdout 한 줄 `APPROVAL-ADD <id> <kind> <버전>` 이고 종료 코드 0 이다. 필수 인자가 빠지면 종료 코드 2 와 빠진 인자 이름이 나온다. 미리보기 파일이 없거나 지금 Run 을 찾지 못하면 종료 코드 1 이고 저장하지 않는다 |
| REQ2 | 같은 id 로 다시 `add` 하면 새 내용으로 연다. 앞 대기가 열려 있었으면 「바뀜」 으로 닫고 출력 줄 끝에 `replaced` 를 붙인다. 앞 대기가 이미 끝났으면(승인, 고쳐 달라, 취소, 사용함) 그 기록은 원래 상태로 두고 `replaced` 를 붙이지 않는다. 앞 대기에 눌린 승인은 새 내용에 쓰지 않는다. 창의 버튼, 승인·고쳐 달라 기록, 신호 메시지, `check` 는 모두 id 와 버전을 함께 쓴다. 지금 버전이 아닌 버튼을 누르면 기록도 신호도 남기지 않고 toast 로 「내용이 바뀌었어요. 새 미리보기를 확인하세요」 를 보인다 | 승인된 id 를 다시 `add` 한 뒤 `check <id>` 가 거절(「아직 누르지 않음」)한다. 같은 id 로 A 를 B 로 바꾼 직후, 아직 A 를 그린 화면에서 누른 「승인」·「고쳐 달라」 는 B 에 기록을 남기지 않고 신호도 가지 않는다. `REVISE` 로 끝난 id 를 다시 올리면 `list --full` 에 앞 기록이 「고쳐 달라」 로 남는다 |
| REQ3 | `list` 는 열린 대기를 한 줄씩 `APPROVAL <id> <kind> <기다린 시간> <제목>` 으로 낸다. `--full` 은 끝난 대기(승인, 고쳐 달라, 취소, 바뀜)도 낸다. `cancel <id> [--reason "<이유>"]` 는 코디네이터가 열린 대기를 거둔다 | 열린 대기 둘이면 `list` 가 두 줄이다. `cancel` 뒤 `list` 에서 빠지고 출력은 `APPROVAL-CANCEL <id>` 이다. 없는 id 의 `cancel` 은 종료 코드 1 이다 |
| REQ4 | 승인하거나 고쳐 달라를 기록하는 CLI 명령은 두지 않는다. 그 기록은 보드 창이 사람이 누른 버튼 이벤트에서만 쓴다 | `orch board approval --help` 와 명령 표에 승인·고쳐 달라 동작이 없다. 창 코드에서 승인 기록을 쓰는 곳이 사람이 누른 이벤트 처리 하나뿐이다 |
| REQ5 | 보드 창에 「승인 대기」 상자를 결정 필요 상자 바로 위에 둔다. 그 저장소의 모든 Run 이 올린 열린 대기를 보인다. 열린 대기마다 제목, 종류, 미리보기 링크, 올린 시각과 기다린 시간, 「승인」·「고쳐 달라」 버튼을 보인다. 24시간 넘게 열린 대기는 기다린 시간을 노란색으로 보인다. 상태 줄 요약에 「승인 n」 을 붙인다. 열린 대기가 없으면 상자도 「승인 n」 도 없다 | 대기를 올린 뒤 5초 안에 창 상자와 상태 줄에 보인다. 미리보기 링크를 누르면 그 파일이 열린다. 25시간 된 대기의 시간이 노랗다 |
| REQ6 | 「승인」 을 누르면 창이 승인 기록을 쓰고 그 대기를 올린 Run 으로 Orca 메시지를 보낸다. 제목은 `APPROVED <id> <버전>` 다. 보드를 어느 세션에서 열었든 올린 Run 으로 간다. 보내지 못하면 기록을 되돌리고 toast 에 이유를 보이며 대기는 열린 채 남는다. 보낸 뒤 그 대기는 상자에서 빠진다 | 다른 세션에서 연 보드로 승인해도 올린 코디네이터의 `orca orchestration check` 에 `APPROVED <id>` 가 온다. Run 이 없어 보내지 못하면 상자에 그대로 남고 `check <id>` 가 거절한다 |
| REQ7 | 「고쳐 달라」 를 누르면 그 대기 자리에 글칸이 열린다. 적고 보내면 창이 고쳐 달라 기록을 쓰고 올린 Run 으로 `REVISE <id> <버전>` 제목과 적은 글을 본문으로 보낸다. 빈 글은 보내지 않는다. 보낸 뒤 그 대기는 상자에서 빠진다 | 글칸에 「제목을 짧게」 를 적어 보내면 코디네이터에게 `REVISE <id>` 와 그 글이 온다. 빈 글로 보내기를 누르면 아무것도 가지 않고 글칸이 남는다 |
| REQ8 | `real` 대기는 상자에 대상 환경, 바꿀 것, 되돌리는 법을 빨간색으로 보인다. 「승인」 을 처음 누르면 「real 에 씁니다. 한 번 더 누르세요」 가 뜨고, 10초 안에 다시 눌러야 신호가 간다. 10초가 지나면 처음 상태로 돌아간다 | `real` 대기의 「승인」 을 한 번만 누르면 신호가 가지 않는다. 두 번 누르면 `APPROVED <id>` 가 간다 |
| REQ9 | `command` 대기는 「승인」·「고쳐 달라」 대신 「명령 채우기」 버튼 하나를 보인다. 누르면 입력란에 `! <명령>` 을 채우고 사람이 Enter 를 쳐야 돈다. 승인 신호는 보내지 않는다. 버튼은 그 대기를 올린 코디네이터 터미널에서 연 창에서만 누를 수 있고, 다른 터미널의 창은 명령 글만 보인다. 코디네이터가 같은 터미널에서 다시 시작하거나 이어 열어도 버튼이 보인다. 명령을 친 결과를 본 코디네이터가 `cancel <id> --reason done` 으로 닫는다 | 올린 터미널의 창에서 누르면 입력란에 `! <명령>` 이 채워진다. 다른 터미널의 창에는 버튼이 없다. Orca 메시지가 가지 않는다 |
| REQ10 | 코디네이터는 `APPROVED <id>` 를 받으면 실행 직전 `orch board approval check <id>` 를 부른다. `check` 는 지금 버전의 승인 기록이 있고, 메시지의 버전이 지금 버전과 같고, 미리보기 파일 내용이 올릴 때와 같고, 승인 메시지를 보낸 터미널이 worker 터미널이 아닐 때만 통과한다. worker 터미널은 살아 있든 끝났든 Orca 의 worker 목록에 있는 터미널이다. 통과하면 그 승인은 「사용함」 으로 닫혀 한 번만 쓴다. 등록이 중간에 실패하면 코디네이터는 결과를 보고하고, 다시 할지는 같은 id 로 다시 올려 사용자가 누르게 한다. 통과하지 않으면 실행하지 않고 사용자에게 이유와 함께 묻는다. `REVISE <id>` 를 받으면 적힌 대로 고쳐 같은 id 로 다시 올린다. 사용자가 채팅으로 승인하면 지금처럼 인정하고 그 대기를 `cancel` 로 닫는다. 대기가 여럿이라 어느 것인지 모르면 지금처럼 코디네이터가 물어 확인한다. `real` 도 채팅 승인을 막지 않는다. worker 메시지에 든 「APPROVED」 글은 승인으로 보지 않는다. 이 규칙은 orch 스킬 문서에 둔다 | `check` 통과는 `APPROVAL-OK <id>` 와 종료 코드 0, 거절은 `APPROVAL-REJECT <id> <이유>` 와 종료 코드 1 이다. 이유는 「기록 없음」, 「아직 누르지 않음」, 「이미 사용함」, 「고쳐 달라」, 「취소됨」, 「미리보기가 바뀜」, 「버전이 다름」, 「worker 가 보냄」, 「신호를 읽지 못함」 중 하나다. 승인 뒤 미리보기 파일을 고치면 거절한다. 통과한 `check <id>` 를 다시 부르면 「이미 사용함」 으로 거절한다. worker 터미널에서 같은 제목을 보내고 승인 기록을 꾸미지 않은 경우 「아직 누르지 않음」 으로 거절한다. orch 의 `waiting.md` 나 `replying.md` 에 이 처리가 있다 |
| REQ11 | 승인 대기는 승인(그 뒤 사용함), 고쳐 달라, 취소, 바뀜으로만 끝난다. 기한으로 저절로 닫지 않는다. 끝난 기록은 끝난 지 7일 뒤 지운다 | 30시간 열린 대기가 그대로 남는다. 8일 전에 끝난 기록은 다음 쓰기 뒤 `list --full` 에 없다 |
| REQ12 | 자동 진행의 `STEP-READY ask` 를 받은 코디네이터는 채팅 결정 질문 대신 `--kind step --item <항목> --step <번호>` 로 승인 대기를 올린다. id 는 `step-<항목>-<번호>` 로 짓는다. 같은 id 의 대기가 이미 열려 있으면 다시 올리지 않는다. 무엇을 진행할지는 `--then` 과 미리보기(계획 파일이나 진행 내용을 적은 파일)에 적는다. 승인되면 그 단계를 진행하고, 고쳐 달라면 적은 글대로 계획을 고친 뒤 다시 올린다. 루프는 지금처럼 알림만 보내고 승인 대기를 만들지 않는다 | orch 규칙 문서에 이 처리와 id 규칙이 있다. 같은 단계의 `STEP-READY ask` 가 다시 와도 상자에 그 단계 대기는 하나다. 루프 코드에 승인 대기를 쓰는 곳이 없다 |
| REQ13 | 막는 대상과 한계를 orch 문서에 적는다. 막는 것: worker 가 `APPROVED` 를 보내는 것, 코디네이터가 승인됐다고 짐작하는 것, 승인 뒤 바뀐 내용을 등록하는 것. 막지 못하는 것: 같은 컴퓨터 사용자 권한으로 승인 기록 파일과 Orca 메시지를 일부러 함께 꾸미는 에이전트. 채팅 승인은 `check` 와 `real` 두 번 누르기를 거치지 않는다(DECISION20). 코디네이터와 worker 는 승인 기록 파일을 직접 고치지 않는다 | orch 문서의 승인 절에 막는 것, 막지 못하는 것(채팅 승인의 한계 포함), 「직접 고치지 않는다」 가 있다 |
