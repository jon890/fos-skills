# orch: 공개 저장소에 비공개 문자열이 들어가지 않게 커밋과 머지 관문에서 막는다

확인: 2026-11-21

## 목표

공개 저장소에서 일하는 worker 가 운영 정보(사용자 이름이 든 경로, 서버 데이터 경로, 컨테이너 이름, 다른 비공개 저장소의 내부 이름)를 커밋하거나 PR 본문에 적으면, 공개 이력에 남기 전에 막는다.

- 배경(2026-11-21): 코디네이터가 인터뷰 중 홈서버에서 읽은 운영 정보를 스펙 배경에 적었고, worker 가 그 스펙을 공개 저장소 PR 에 커밋해 push 했다. 독립 리뷰가 지적한 뒤에야 알았고, PR 을 닫고 새 브랜치로 다시 올려야 했다. 옛 커밋은 SHA 로 한동안 남는다.
- 후보: fos-skills `.orch/feedback/public-repo-private-leak-guard.md`.
- 지금 있는 것: `orch worker launch` 가 worker 워크트리마다 커밋 검사 훅을 건다(`skills/orch/scripts/lib/commit-check.ts`, 워크트리 전용 `core.hooksPath`). 지금은 한국어 커밋 검사만 한다.

## 범위

- 대상은 GitHub 에서 공개인 저장소다. 비공개 저장소에서는 검사하지 않는다.
- 막는 곳은 둘이다. worker 워크트리의 커밋과, `orch queue gate`(머지 큐와 자동 머지가 같은 판정을 쓴다)가 보는 PR 본문과 그 PR 의 댓글·리뷰 본문이다.
- 범위 밖
  - 이미 공개 이력에 남은 커밋을 정리하는 일
  - worker 워크트리 밖에서 사람이 하는 커밋(주 checkout 등)
  - 비공개 문자열 목록을 자동으로 채우는 일. 목록은 사용자가 관리한다

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 비공개 문자열 목록은 개인 설정 파일 하나(`~/.config/orch/private-words.txt`)에 둔다. 한 줄에 낱말 하나, 빈 줄과 `#` 로 시작하는 줄은 건너뛴다. 어느 저장소에도 커밋하지 않는다 | 가짜 홈에 목록을 둔 테스트에서 검사가 그 낱말을 읽는다. 저장소 파일 어디에도 목록 경로 밖의 실제 낱말이 없다 |
| REQ2 | 목록 파일이 없거나 비었으면 검사를 건너뛴다. 건너뛴 사실은 `orch doctor` 가 공개 저장소에서 한 줄로 알린다 | 목록 없는 가짜 홈에서 커밋과 관문이 통과하고, doctor 출력에 안내 줄이 있다 |
| REQ3 | 공개 저장소의 worker 워크트리에서 커밋할 때, 커밋에 더해지는 줄과 커밋 메시지에 목록 낱말이 있으면 커밋을 막는다 | 목록 낱말이 든 파일을 stage 한 커밋과, 낱말이 든 커밋 메시지가 거절된다. 낱말이 없으면 통과한다. 지우는 줄에만 있으면 통과한다 |
| REQ4 | `orch queue gate` 는 공개 저장소 PR 의 본문과 그 PR 의 댓글·리뷰 본문에 목록 낱말이 있으면 `GATE-FAIL` 로 막는다 | 낱말이 든 본문 또는 댓글의 PR 이 GATE-FAIL 이고, 이유 줄이 어느 곳(본문, 댓글 id)인지 알린다 |
| REQ5 | 걸리면 걸린 위치(파일과 줄, 또는 PR 본문·댓글)를 알리되, 걸린 값 자체는 출력과 로그에 쓰지 않는다 | 거절 출력과 루프 로그에 목록 낱말이 나오지 않는다 |
| REQ6 | 저장소가 공개인지는 GitHub 에서 읽고, 같은 저장소는 한동안 기억해 커밋마다 조회하지 않는다. 읽지 못하면 공개로 보고 검사한다 | 공개 여부 조회가 실패하는 가짜 gh 로 커밋하면 검사가 돈다. 같은 저장소의 연속 커밋에서 gh 조회가 매번 일어나지 않는다 |
