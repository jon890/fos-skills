# work-board 동작 세부

창이 무엇을 어떤 규칙으로 그리는지, 보드 명령이 파일을 어떻게 고치는지 적는다.
독자는 창이나 보드 명령을 고치는 사람이다. 처음 쓰는 방법과 활용법은 [README](../README.md) 가 소유한다.
창의 동작과 보드 명령의 규칙은 이 문서가 소유한다([ADR-006](../../docs/adr/006-work-board-in-plugin.md)).

## 창과 단축키

- 창: `/board`. 결정 필요, 진행 중, 대기, 완료 순으로 묶는다
- 접힌 보기: 항목마다 「표시 · 제목」 한 줄, 그 아래 막대 한 줄, 「▶ 지금 단계」 한 줄, worker 가 있으면 worker 한 줄만 보인다. 끝낸 단계는 「✓ n개」, 지금 단계 뒤에 남은 단계는 「남은 단계 n개」 로 접힌다. 수는 막대와 같은 값에서 낸다(진행률을 세는 쪽의 단계 줄, `progress` 가 있으면 그 값)
- 펼친 보기: `d` 를 누르면 담당·PR, details 와 next 의 모든 줄을 적힌 순서대로 보이고 완료 칸도 펼친다. 끝낸 줄은 취소선과 흐림, 지금 단계는 굵게, 남은 단계는 보통 글씨, 번호 없는 참고 줄은 흐리게 보인다. 다시 누르면 접힌다
- 단계 줄 모양: details 와 next 의 모든 줄이 같은 들여쓰기와 두 칸짜리 표시 칸(끝냄 「✓」, 지금 「▶」, 남음과 참고 줄은 빈칸)을 갖는다. `done` 값으로 표시를 정해 번호와 본문이 같은 열에서 시작하고, 줄바꿈된 뒷줄도 본문 열에서 시작한다
- 지금 단계: 진행률을 세는 쪽(아래 「진행률」)의 끝나지 않은 첫 단계 줄이다. 거기 없으면 다른 쪽의 끝나지 않은 첫 단계, 단계 줄이 하나도 없으면 첫 참고 줄을 쓴다. 단계가 모두 끝났으면 지금 단계는 없다
- 머리 줄: `live.at`(실제 상태를 읽은 시각)과 보드 파일의 `updatedAt` 중 늦은 쪽을 「HH:MM 업데이트」 한 줄로 보인다. 둘 다 없으면 「읽는 중」이다. Run ID 와 수동·자동 구분은 보이지 않는다
- 플러그인 버전: 머리 줄의 시각 뒤에 지금 세션이 읽은 설치본을 「fos-skills 1.4.0 (b1e2c09)」 처럼 version 과 커밋 앞 7자리로 보인다. `--plugin-dir` 로 읽은 작업 트리는 「작업 트리」 와 HEAD 커밋이다. main 과 같으면 「최신」 을 흐리게, 다르면 「→ 최신 1.5.0 (…) · p 로 갱신」 을 노란색으로, 읽지 못하면 「최신 확인 불가」 를 흐리게 붙인다
  - 설치본은 `$.plugin.root`(마켓플레이스 캐시 폴더)와 같은 설정 폴더의 `plugins/installed_plugins.json` 에서 scope 와 커밋을 읽는다
  - main 은 `git ls-remote <plugin.json 의 repository> refs/heads/main` 과 그 커밋의 `plugin.json` 원문(`curl`)으로 읽는다. 세션 시작, `/board` 열 때, 30분마다, 갱신 직후에 읽고 명령마다 10초를 기다린다
  - 둘 다 version 이 있으면 version 으로 비교한다. version 을 올리지 않은 커밋은 `update` 가 받지 않기 때문이다. 어느 한쪽에 없으면 커밋으로 비교한다
- 플러그인 갱신: `p` 는 그 설치본의 scope 로 `claude plugin update fos-skills@fos-skills --scope <scope>` 를 돌린다(project·local scope 는 그 프로젝트 폴더에서). 성공하면 입력란에 `/reload-plugins` 를 채우고 Enter 로 새 설치본을 읽는다. 실패하면 toast 에 이유를 보이고 입력란은 그대로다. directory 소스 마켓플레이스의 폴더를 그대로 읽은 설치본(`known_marketplaces.json` 의 directory path 가 `$.plugin.root` 와 같고 어떻게 읽었든(`--plugin-dir` 포함) 같은 설치본이다. 등록되지 않은 다른 폴더만 작업 트리다)은 `claude plugin update` 가 받을 것이 없으므로, `p` 가 그 폴더에서 현재 브랜치가 main 인지, 추적 파일 변경이 없는지, `git fetch origin main` 뒤 fast-forward 할 수 있는지 보고 `git pull --ff-only origin main` 을 돌린다. 하나라도 어긋나면 받지 않고 toast 에 「main 이 아니라서」, 「고치는 중인 파일이 있어서」, 「fast-forward 할 수 없어서」 중 이유를 보인다. 받은 뒤 설치본을 다시 읽어 머리 줄이 새 version 을 보인다. 최신으로 확인됐거나 작업 트리면 `p` 가 없다
- 단축키 상자: 「단축키」 제목의 테두리 상자 하나에 `s` 오늘 시작, `q` 정할 것 묻기, `i` 알림 답변(알림함이 켜졌을 때), `x` 알림 넘기기(보이는 알림이 있을 때), `z` 넘김 되돌리기(이 세션에서 넘긴 알림이 있을 때), `c` 항목 상태 확인(진행 중이나 대기 항목이 있을 때), `a` PR 작성자 필터, `d` 펼치기, `p` 플러그인 갱신(뒤처졌거나 확인하지 못했을 때) 버튼을 모은다. 버튼 폭의 합이 상자보다 넓으면 다음 줄로 넘어간다
- 열린 PR: 줄마다 작성자를 「@login」 으로 흐리게 붙인다. `a` 는 전체에서 작성자 가나다순으로 돌아 다시 전체로 오며, 필터를 적용한 동안에는 상자 머리에 「작성자 @login」 과 필터 적용 뒤의 수를 보인다. 선택한 작성자의 PR 이 모두 닫히면 전체로 돌아간다. 필터 값은 세션 동안만 남는다
- 머지 줄: 큐를 쓰는 저장소에서만 열린 PR 상자의 PR 마다 CI 줄 아래에 한 줄을 붙인다. 머지 큐를 위한 상자를 따로 두지 않고, 보드 항목 제목 옆에도 큐 순서를 붙이지 않는다
  - 큐를 쓰는 저장소: orch 설정의 `queue.auto_merge` 가 true 이거나, 코디네이터가 건 큐의 차례 기록(`state/queue-turn/<pid>.json`)이 살아 있다. 아니면 큐에 관한 말을 하나도 보이지 않아 열린 PR 상자가 머지 큐를 더하기 전 모양이다
  - 상태는 열린 PR 을 읽을 때마다 `bin/merge-queue.ts --repo <주 checkout>` 으로 읽는다. 이 명령은 orch 설정, 상태 폴더의 파일과 로그만 읽고 gh 를 부르지 않는다. 읽는 곳과 판정 순서는 그 파일의 머리 주석이 소유한다
  - 줄의 글: 큐의 차례면 「머지 중」(차례 단계가 머지가 아니면 「머지 중 · 체크 대기」 처럼 단계를 잇는다), 큐 안에서 기다리면 「머지 큐 n 번째」, 루프가 자동 머지 판정을 통과시켰으면(`AUTO-MERGE-BASIS`) 「머지 가능」, 막혔으면 「대기: <이유>」 다. 이유는 루프의 `AUTO-MERGE-WAIT` 이유를 「체크 대기」, 「미해결 대화 1」, 「리뷰 보류」, 「기능 완료 근거 없음」 같은 말로 옮긴 것이고 옮기는 표는 `hooks/register.js` 의 `WAIT_TEXTS` 가 소유한다. 표에 없는 이유는 그대로 보인다
  - 시각: 그 상태가 된 시각을 「HH:MM 부터」 로 잇는다. 시각을 읽지 못하면 잇지 않는다
  - 큐를 쓰는 저장소라도 그 PR 의 기록이 없거나 출력을 읽지 못하면 줄을 붙이지 않는다. 줄마다 「모름」 을 쓰지 않는다. 루프 로그만 읽지 못했으면 열린 PR 상자 맨 위에 한 번 흐리게 알린다
  - 새 정보는 새 상자를 더하기보다 이미 있는 상자의 줄에 붙인다. 상자가 늘면 창이 길어지고 같은 PR 이 여러 곳에 나뉘어 보이기 때문이다
- 창 포커스: Orca 터미널에서는 창을 클릭해도 포커스가 가지 않는다. `ctrl+x` 다음 `tab` 으로 옮긴다. 단축키는 포커스가 있을 때만 동작한다
- 오늘 시작: 창의 `오늘 시작`(`s`) 은 입력란에 하루를 시작하는 요청문(보드 갱신, 정리, 감시 확인, 보고, 확인 단계 확인)을 채운다. Enter 를 누르면 코디네이터에게 간다
- 정할 것 묻기: 창의 `정할 것 묻기`(`q`) 는 지금 정할 것을 모아 묻는 요청문을 채운다. 요청문은 막힘과 Orca 자동 알림을 다루는 방법도 담는다. worker 가 직접 올린 막힘은 코디네이터가 먼저 처리하고 사람이 정할 것만 묻는다. 자동 알림은 묻지 않고 처리 결과만 알린다. 일이 끝난 worker 는 답장 대신 해제로 닫는다. 두 요청문은 `hooks/register.js` 의 `START_PROMPT`, `DECIDE_PROMPT` 가 소유한다
- 항목 상태 확인: `c` 를 누르면 진행 중과 대기 항목의 표시(▶, ◇) 자리에 화면 순서대로 `1`~`9` 번호가 붙고 단축키 상자에 안내 줄이 붙는다. 9개를 넘으면 앞 9개만 받는다. 번호를 누르면 그 항목의 요청문을 입력란에 채우고 모드가 꺼진다. 진행 중 항목은 상태 확인 요청문(`checkPrompt`), 대기 항목은 재개 요청문(`resumePrompt`)이다. 다시 `c` 나 `Esc` 를 누르면 창은 남기고 번호만 지운다. 확인 모드에서는 닫기 표시처럼 사람이 닫는 다른 동작도 한 번은 번호만 지운다(`ui.close` 는 Esc 와 닫기 표시를 같은 origin `person` 으로 준다). 확인 모드 동안 알림 버튼은 숫자 키에도, 클릭이나 Enter 에도 반응하지 않는다. 고를 항목이 없어지면 보드를 읽을 때 모드를 끈다
  - 진행 중과 대기 항목의 제목 줄(표시와 제목)은 `c` 없이도 버튼이다. 클릭하거나 포커스를 두고 Enter 를 누르면 같은 요청문을 채운다. 9개 제한이 없고, 숫자 단축키는 확인 모드에서만 붙는다. 확인 모드에서 누르면 번호를 누른 것처럼 모드가 꺼진다. 넘기기(`x`) 모드에서는 아무것도 하지 않는다. 완료와 결정 항목, 펼친 보기의 상세 줄은 버튼이 아니다. 제목에 업무 링크가 있으면 링크는 따로 눌리고 그 앞 글까지가 버튼이다
  - 재개 요청문은 항목 id 와 제목, 대기 사유, 업무 주소(`task`), worker, PR 을 적고, 기다리던 답이나 결정, 배포, 외부 회신이 왔는지 확인하게 한다. 왔으면 다음 단계를 진행해 진행 중으로 올리고, 아직이면 무엇을 누구에게 기다리는지와 재촉하거나 우회할 방법을 제안하게 한다. 대기 사유(`waitReasons`)는 끝나지 않은 단계(지금 단계 포함)와, 끝나지 않은 참고 줄 가운데 「대기」, 「기다」, 「회신」 이 든 줄이다. 없으면 「적혀 있지 않음」 이다
  - 요청문은 항목 id, 제목, 끝나지 않은 단계, worker, PR 번호를 적고 PR·CI·배포·worker 보고·업무 상태와 대조해 지금 상태를 확인하게 한다. 멈춰 있으면 다음 단계를 진행하거나 정할 것을 묻게 한다. 지시 부분은 `register.js` 의 `CHECK_PROMPT` 가 소유한다
  - 숫자 단축키를 알림과 함께 쓰므로 `c` 와 `x` 는 함께 켜지지 않는다. 하나를 켜면 다른 하나가 꺼진다. 확인 모드 동안 알림 상자의 번호는 같은 자리에 흐리게 남지만 눌리지 않는다
- 훅이 직접 보내지 않는 이유: 훅의 `prompt.submit` 과 `command.run` 의 `text` 는 코디네이터 모델에 닿지 않는다. 그래서 입력란을 채우고 사람이 Enter 로 보낸다. `/board` 외의 명령은 등록하지 않는다
- 상태 줄: 프롬프트 아래에 개수 요약이 5초마다 갱신된다. 글이 바뀔 때만 보낸다. SDK(`stream-json`)로 실린 세션은 상태 줄마다 `ui_status` 메시지를 host 에 보내기 때문이다. 보드 파일, 실제 상태, 새 업무 알림이 모두 없으면 나오지 않는다. 새 업무 알림이 있으면 맨 앞에 「알림 n」 이 붙는다
- 업무 알림: 결정 필요 아래의 「알림」 상자. 1분마다 같은 플러그인의 `inbox/scripts/inbox.ts board --repo <주 checkout> --json` 을 불러 그린다. 받기, 저장소 필터, 답함 판정은 [`inbox`](../../inbox/README.md) 스킬이 하고 창은 그리기만 한다. 알림함 설정이 없거나 그 저장소의 필터가 `"enabled": false` 면 상자도 상태 줄의 「알림 n」 도 `i` 도 없다
  - 머리 「알림 n · HH:MM 확인」 의 n 은 새 항목 수다. 받지 못한 출처는 「두레이 메신저 확인 불가: …」 처럼 빨간 줄로, 이 세션에서 알림함이 켜진 것을 본 뒤 명령 자체가 실패하면 「알림함 확인 불가: …」 로 보이고 직전 항목은 남는다. 켜진 적이 없으면 상자를 그리지 않는다
  - 항목 줄: 새 항목 「●」, 제목, 머리말 링크(「[두레이]」, 「[메신저]」), 보낸 사람 · 종류(멘션·담당·참조) · 시각. 멘션은 본문 앞부분을 흐리게 한 줄 붙인다
  - 답한 항목(`state: answered`)은 목록에서 빼고 상자 끝에 「답함 n」 수만 흐리게 보인다
  - 앞 9개 항목에 `1`~`9` 단축키가 붙어 그 항목의 답변 요청문을 채운다. `i` 는 새 항목 전체를 훑는 요청문을 채운다. 두 요청문은 `register.js` 의 `replyPrompt`, `INBOX_PROMPT` 가 소유한다
  - 넘기기: `x` 를 누른 뒤 번호를 누르면 에이전트를 거치지 않고 그 알림을 답하지 않음으로 넘긴다. `x` 를 누르면 상자에 안내 줄이 붙고 번호가 빨갛게 바뀐다. 다시 `x` 를 누르면 그만둔다. 한 번에 한 항목만 넘기고, 넘기면 모드가 꺼진다. 저장은 `inbox.ts dismiss <id>` 를 불러 같은 넘김 기록(`dismissed.json`)에 적으므로 모든 저장소의 보드에서 사라진다. 상자에서는 다음 읽기를 기다리지 않고 바로 빠진다

  - 「멈춤 · 터미널 종료」: Orca 가 프로세스가 끝났다고 본 worker 다. `pipeline.idle_exited` 가 false 면 보지 않는다
  - 「오류: <요약>」: 그 worker 의 가장 늦은 `msg_chaterr_` 오류 알림 하나다. 요약은 「계정 한도」, 「모델 용량 부족」 같은 분류어이고, 분류하지 못하면 오류 첫 줄이다. 그 뒤 워크트리 파일이나 커밋이 바뀌었거나 worker 가 해제·중지되면 사라진다. 화면 변화는 보지 않는다. 오류 알림 자체가 화면을 바꾸기 때문이다
  - 「입력 대기」, 「오류로 멈춤」, 「종료 보고」: 그 worker 의 가장 늦은 `msg_stop_` 멈춤 보고 하나다. 이유(`stopReason`)가 needs-input, errored, exited 인 것이고, 턴만 끝낸 것(finished)은 글이 없다. 사라지는 조건은 오류와 같다. 이미 「멈춤 · 터미널 종료」 인 worker 에는 「종료 보고」 를 붙이지 않는다
  - 「⚙ worker 없음 · N시간」: doing 항목에 끝나지 않은 단계가 있는데 맡은 worker 가 없고, 그 항목의 `stepAt` 부터 `pipeline.idle_min` 이 지났으면 경과 시간을 붙이고 노란색으로 그린다. `stepAt` 이 없는 옛 항목은 다음 단계 갱신부터 보인다. orch 루프가 없는 저장소에서도 같다. worker 목록을 읽지 못했으면 정말 worker 가 없는지 몰라 경과 시간을 붙이지 않는다
  - 판정 명령이 실패하면 멈춤 글은 붙이지 않는다. 오류 글은 그대로 붙이고, 「worker 없음」 의 경과 시간은 기본 30분으로 잰다
- 결정 필요: worker 의 `question` 과 worker 가 직접 보낸 `escalation` 만 보인다. Orca 자동 알림(id 가 `msg_stop_`, `msg_chaterr_` 로 시작한다)은 상자에도 수에도 넣지 않고 worker 줄 표시로 옮긴다. 같은 제목이라도 worker 가 보낸 메시지(id 가 `msg_<hex>`)는 넣는다. worker 가 직접 올린 막힘은 답장이나 그 worker 의 해제·중지로 사라지고, worker 가 다시 움직여도 남는다. 현재 Run 의 `check --all` 과 `--peek` 에 `--types question,escalation` 을 붙여 질문 후보를 모으고, 질문마다 발신자, `dispatch:<payload.dispatchId>`, 그 질문이 붙은 살아 있는 worker 의 `dispatch:<id>` 를 `inbox --terminal` 로 읽는다(같은 handle 은 한 번, 네 개씩). 코디네이터 터미널에서 `orca orchestration reply` 로 보낸 회신은 `dispatch:<그 worker 터미널의 지금 dispatch>` 로 가서 발신 터미널 `term_*` 의 inbox 에는 나오지 않기 때문이다. 질문의 thread 에 받는 쪽(`to_handle`)이 있고 그것이 Run(`run:<Run>`)이 아닌 메시지가 있으면 답한 질문이다. 보낸 사람이 Run 인지 `term_*` 인지는 보지 않고, worker 가 Run 으로 보낸 후속 status 는 답이 아니다. 질문의 dispatch 는 `payload.dispatchId`, 없으면 발신자 handle 의 `dispatch:` 접두사로 정하고, 둘 다 없으면 발신 터미널 handle 을 `worker-list` 의 `agentTerminalHandle` 과 대조한다. `pending`, `dispatched`, `running` 인 worker 에 속하지 않는 질문은 후보에서 뺀다. 그 질문은 다른 경로로 처리됐고, 닫힌 dispatch 의 inbox 에는 답변이 남지 않아 답해도 줄지 않기 때문이다. `worker-list` 를 읽지 못하면 질문도 「확인 불가」 로 보인다. 답하면 다음 조회에서 줄고, ack 만 하면 남는다. 같은 worker(살아 있는 worker 의 id, 없으면 질문의 dispatch, 그것도 없으면 발신자)의 질문은 묶는다. 답한 질문보다 늦지 않은 미답변은 빼고(답한 자동 알림도 이 기준에 든다), 남은 미답변 가운데 가장 늦은 것(`created_at`, 같으면 뒤에 온 것) 하나만 「다시 보냄 n」 과 함께 보인다. `ask` 는 답을 받을 때까지 막혀 worker 하나에 열린 질문은 하나이고, 다시 보낸 질문은 본문이 달라 본문으로는 묶지 않는다. 수동 `decide` 항목도 더한다. 전체 inbox 는 읽지 않는다. decide 항목은 끝나지 않은 줄을 세고, 줄이 없으면 항목 하나로 센다. 빈 줄(공백뿐 포함)은 줄로 세지 않고, 줄이 모두 끝난 decide 항목만 남으면 결정 필요 상자를 보이지 않는다. 답한 줄은 `board.ts mark` 로 끝내고, 줄이 모두 끝난 decide 항목은 `mark` 나 `step` 이 done 으로 바꾼다(`--undo` 는 status 를 바꾸지 않는다)
- 질문 조회 범위: Orca 의 `--all` 과 `--peek` 는 각각 100건까지 반환한다. 상한에 닿으면 「최근 질문 기준」 을 표시하며, 그 밖의 미답변은 빠질 수 있다. 질문의 handle 마다 수신 기록은 200건까지 조회한다. 상한에 닿은 handle 의 질문이 모든 handle 의 회신을 합쳐도 미답변이면 답변 여부를 판단할 수 없어 조회 오류를 표시한다. 다른 handle 의 회신으로 답한 것이 확인되면 오류가 아니다
- 명령 출력 한도: Claude Code 2.1.309 의 `$.process.run` 은 stdout 과 stderr 를 각각 4MiB(4,194,304바이트)에서 자른다. 설치 실행 파일의 `Hat=4194304`, `Bat` 수집기와 `VQr` 반환값으로 확인했다. 보드는 `isStdoutTruncated` 를 검사해 잘린 JSON 대신 출력 한도 오류를 표시한다
- 단계 줄: 번호로 시작하는 줄이다(「1 …」, 「1. …」, 「1) …」). `done: true` 는 끝낸 단계, `done: false` 는 끝나지 않은 단계다. 번호로 시작하지 않는 참고 줄은 세지 않는다
- 진행률: 하위 항목(details)의 단계 줄을 세고, details 에 단계가 없으면 다음 할 일(next)의 줄을 센다. `progress` 필드(「7/10」)가 있으면 그 값이 우선한다. 단계로 나타낼 수 없을 때만 쓴다
- 진행률 표시: 창 맨 위에 진행 중 항목들의 끝낸 단계 합 / 전체 단계 합을 전체 막대로 그린다. 완료가 아닌 항목마다 제목 바로 아래 줄에 막대를 그리고(제목 길이와 상관없이 같은 자리), 진행률이 없는 옛 항목은 「진행률 없음」 으로 보인다. `board.ts list` 도 항목마다 「n/m (p%)」 를 붙인다
- 진행률 필수: `board.ts set` 은 doing 항목에 단계 줄이나 `--progress N/M` 이 없으면 거절하고 보드를 고치지 않는다. `--next` 를 여러 번 주면 줄로 이어 단계 줄을 적을 수 있다
- 마일스톤 단계: orch 가 띄울 때 만드는 항목은 지시서의 할 일이 아니라 사용자 마일스톤 단계(기본 「PR」, 「머지」)를 갖는다. `stages` 필드(「pr=1,merge=2」)가 어느 단계를 어느 사건이 끝내는지 기억하고, `board.ts set --stages` 로 쓴다. 사건은 `pr`, `merge`, `deploy`, `release` 다. 단계를 끝내는 시점은 [갱신 담당 표](../../orch/references/board.md#갱신-담당)가 소유한다
- 직접 작성한 사건 단계: `3. develop 머지 (#665 merge)`, `4. dev 배포 (#665 deploy)`, `5. real 반영 (#665 release)` 처럼 줄 끝에 `(#PR번호 사건)` 을 붙인다. 사건은 `pr`, `merge`, `deploy`, `release` 다. 꼬리표가 있는 항목은 goal 도 사건별 단계만 끝내며, 꼬리표 없는 줄과 항목 상태는 자동으로 바꾸지 않는다. 진행률을 세는 쪽의 단계가 대상이다. 창에서는 꼬리표를 숨기고 파일과 `board.ts steps` 출력에는 보존한다
- 단계 끝내기: `board.ts step <id> <n>` 이 진행률을 세는 줄에서 n 번 단계를 끝낸다. `done` 값만 `true` 로 바꾼다(`--undo` 는 `false`). `set --progress auto` 는 `progress` 값을 지워 단계 수로 세게 한다. `board.ts steps <id>` 는 진행률을 세는 단계 줄을 JSON 으로 낸다. orch 의 `board-sync.ts` 가 이것으로 단계를 판정한다. 단계 밖의 줄(참고 줄, 세지 않는 쪽의 줄)은 JSON 에 넣지 않고 stderr 에 「단계 밖의 줄(mark 번호):」 머리와 함께 낸다
- 줄 끝내기: `board.ts mark <id> <n>` 은 번호 없는 줄도 끝낸다. n 은 details 다음 next 순서로 1부터 센 줄 번호이고, 빈 줄(공백뿐 포함)은 건너뛴다. `done` 값만 바꾼다(`--undo` 는 되돌린다). `board.ts list` 는 항목 줄 아래에 모든 줄을 `    <n> ✓ <text>`(끝냄)나 `    <n>   <text>`(안 끝냄)로 보이고, n 은 `mark` 의 번호와 같다. `step` 의 단계 번호와 `mark` 의 줄 번호는 다르다
- 갱신: orch 의 띄우기와 루프가 자동 반영한다. 시점과 담당은 [갱신 담당 표](../../orch/references/board.md#갱신-담당)를 따른다. 수동 보정은 `node --disable-warning=ExperimentalWarning "$BOARD_BIN" set <id> doing --title "..." --next "..."`. `$BOARD_BIN` 은 `work-board/bin/board.ts` 다

## 저장 형식

`next` 와 `details` 는 줄마다 `text` 와 불리언 `done` 을 가진 객체의 목록이다. 번호 없는 참고 줄도 같은 형식으로 저장하지만 진행률에는 세지 않는다.

`stepAt` 은 `board.ts` 가 그 항목의 `status`, `details`, `next` 를 마지막으로 바꾼 시각이다. 꼴은 `updatedAt` 과 같다. 새 항목도 남기고, 제목만 바꾸거나 같은 줄을 다시 쓰면 그대로다. 창이 worker 없이 남은 단계의 경과 시간을 이 값으로 잰다.

```json
{
  "id": "example",
  "status": "doing",
  "next": [{"text": "2. 리뷰", "done": false}],
  "details": [
    {"text": "1. 구현", "done": true},
    {"text": "2. 리뷰", "done": false},
    {"text": "참고: 배포는 별도", "done": false}
  ]
}
```

`set --next/--detail` 은 계속 글을 받는다. 입력 줄 앞의 `✓`, `[x]`, `[X]` 는 `done: true` 로 읽고, `[ ]`, `▶`, `◇` 는 `done: false` 로 읽는다. 표시는 `text` 에서 떼며 창이 체크 표시와 취소선을 그린다.

옛 `next` 문자열과 `details` 문자열 목록은 읽을 때 객체로 변환한다. 객체와 문자열을 섞은 파일도 읽는다. `list` 와 `steps` 는 파일을 고치지 않고, 다음 쓰기 명령에서 모든 항목을 새 형식으로 저장한다. `steps` 출력은 `[{"number": 1, "done": true, "text": "1. 구현"}]` 이며 `text` 에 완료 표시는 없다.

## 플러그인에 싣기

`.claude-plugin/plugin.json` 의 `hooks` 배열이 `work-board/hooks/hooks.json` 을 가리킨다. 훅 모듈은 `hooks/register.js` 하나다.
