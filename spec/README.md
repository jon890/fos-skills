# spec

기능을 정할 때 사용자를 인터뷰해 결정을 모두 닫고, 사용자가 확인한 스펙을 남긴다. 구현 도중 「이건 어떻게 하지」 로 멈추거나 에이전트가 혼자 정해 버리는 일을 줄인다.

## 이럴 때 쓴다

- 「이 기능 설계해 보자」, 「어떻게 만들지 정하자」 처럼 새 기능의 동작과 범위를 정할 때
- 「취소 기능을 추가하자」, 「목록을 날짜순으로 바꾸자」 처럼 새 동작을 요청할 때. 스킬 이름을 말하지 않아도 구현 전에 먼저 불린다. 버그 수정, 정리, 조회에는 불리지 않는다
- API·데이터·권한·실패 동작을 기능 단위로 합의할 때
- 이미 있는 스펙에 빠진 결정을 다시 인터뷰할 때

## 사용 예시

> “작업 취소 기능 설계해 보자.”
> 관련 코드를 읽고 요청을 되짚은 뒤 범위를 열린 질문으로 묻는다.
> 이어서 취소 권한, 반복 요청 응답 같은 결정을 4개씩 선택지와 권장안으로 묻는다.
> 결정 표가 닫히면 대화를 모르는 검토자가 스펙만 읽고 짐작해야 하는 곳을 찾는다.
> 스펙 요약을 보여 확인을 받고 `확인:` 날짜를 적는다.

## 받는 것

- `docs/features/<기능>/spec.md`: 요구사항과 인수 조건, 설계, 결정 표, 확인 날짜
- 결정마다 누가 정했는지(사용자와 날짜, 또는 작성자와 근거)
- 다음 planning 에 넘길 스펙 경로

## 함께 쓰는 스킬

- `planning`: 확인한 스펙을 PR 하나의 작업으로 나눈다. 사용자에게 다시 묻지 않는다
- `orch`: worker 가 spec 을 돌릴 때 질문과 확인을 사용자에게 중계한다
- `verify`: 구현이 스펙을 만족하는지 확인한다
