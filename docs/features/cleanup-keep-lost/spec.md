# orch: 재부팅으로 끊긴 worker 와 후속 검증을 기다리는 일의 워크트리를 정리하지 않는다

확인: 2026-11-20

## 목표

Mac 재부팅이나 Orca 재시작으로 끊긴 worker 의 워크트리와 지시서를 정리 도구가 지우지 않는다.
코디네이터가 재시작 뒤 `orch worker resume` 으로 그 worker 를 이어 갈 수 있다.

2026-11-20 16:06 에 ai-analysis 에서 재부팅으로 worker 11개가 끊겼다(Orca `stopReason=lost`, dispatch failed).
그 가운데 정해진 시각까지 일부러 쉬던 worker 넷의 워크트리와 지시서 둘을, 16:5x 머지 뒤 자동 정리가 지웠다(요청 R6).
지금 정리 도구는 failed 로 닫힌 dispatch 를 끝난 것으로 본다(사용자 결정 2026-10-30). 재부팅으로 끊긴 것도 failed 로 닫혀 같이 지워진다.

## 범위

이번 범위:

- `orch cleanup sweep` 과 머지 뒤 자동 정리가 끊긴(lost) worker 의 워크트리, 터미널, 지시서를 지우지 않는다.
- 지시서의 후속 검증이 대기인 워크트리도 지우지 않는다.
- 남긴 워크트리를 `orch doctor` 가 알려 쌓이지 않게 한다.

범위 밖:

- 오류로 끝난 failed dispatch. 지금처럼 끝난 것으로 본다.
- 끊긴 worker 를 자동으로 다시 띄우는 것.

## 요구사항과 인수 조건

| ID | 요구사항 | 관측할 인수 조건 |
| --- | --- | --- |
| REQ1 | 끊긴 worker 는 남긴다 | 어떤 워크트리의 가장 최근 dispatch 가 재부팅·재시작으로 끊겨(Orca 의 lost) 닫혔으면, PR 이 MERGED 여도 정리 도구가 그 워크트리, 터미널, 지시서를 지우지 않고 `남김 <경로>: 끊긴 worker <dispatch>, 다시 띄우거나 직접 정리한다` 를 낸다. 미리 보기에서도 지울 대상으로 나오지 않는다 |
| REQ2 | 다시 띄우면 보통 규칙으로 돌아간다 | 그 워크트리에서 `orch worker resume` 이나 새 dispatch 가 뜨면, 그 뒤로는 새 dispatch 의 상태로 지금 규칙대로 판단한다 |
| REQ3 | 후속 검증 대기는 남긴다 | 그 워크트리 브랜치의 PR 본문에서 후속 검증이 아직 대기이면, 워크트리와 지시서를 함께 남긴다. 지금처럼 지시서만 남기고 워크트리를 지우지 않는다. 마무리는 그 대기를 배포 뒤 할 일 목록에 올리고 실패로 끝내지 않는다. `orch followup done <PR>` 로 끝내면 다시 띄운 마무리가 남긴 워크트리를 지운다(DECISION6) |
| REQ4 | 오류로 끝난 failed 는 그대로다 | 끊김이 아닌 이유로 failed 가 된 dispatch 의 워크트리는 지금처럼 정리한다 |
| REQ5 | 직접 정리할 수 있다 | 코디네이터가 남긴 워크트리를 지우는 명령이 있고, 그 명령이 REQ1·REQ3 의 남김을 넘어선다. 커밋 안 된 변경, 원격에 없는 커밋 검사는 그대로 막는다 |
| REQ6 | 남은 것을 알린다 | REQ1 로 남긴 워크트리가 끊긴 지 하루가 넘으면 `orch doctor` 가 경로, dispatch, 끊긴 시각과 REQ5 의 명령 한 줄을 낸다 |
| REQ7 | 끊김을 모르면 남긴다 | dispatch 기록으로 끊김인지 오류인지 알 수 없으면 남기는 쪽으로 본다 |
