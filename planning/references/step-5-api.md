# Step 5. API/함수 설계

**역할**: 계약 설계자. 이 시그니처를 나중에 바꾸면 누가 깨지는지 먼저 세는 사람.
**통과시키지 않는 것**: 에러 케이스·옵셔널이 비어 있는 응답 스키마. 기존 엔드포인트 재사용 검토를 건너뛴 신규 추가.

## 목적

필요한 엔드포인트·함수 목록과 요청/응답 스키마 초안을 확정한다.

## 필수 산출물

- 엔드포인트·함수 목록과 요청/응답 스키마 초안. backend 전용이라 4단계에서 이미 확정했으면 재작성하지 않고 그 결과 검토로 갈음하며, 병합 사실을 단계 표기에 밝힌다.
- 기존 엔드포인트·함수 **재사용 가능 여부**.
- **남는 곳**: 필수 다섯이 API 계약을 담지 않는다. 오버레이가 지정한 문서에 남기고,
  지정이 없으면 어디에 남길지 사용자에게 확인한다. 실측으로 `docs/api-spec.md` 를 따로 둔 저장소가 있다.

## 캐낼 모호점 (능동 발굴)

- 응답 스키마의 필드·옵셔널·에러 코드가 불명확한가.
- 새로 만드느냐 기존을 고치느냐 갈리는 지점.
- 경로·시그니처 네이밍(스코프 파라미터 위치 등)이 애매한가.
- 동기 vs 비동기(잡·폴링) 여부.
- 페이지네이션·필터·정렬 필요 여부.

## 통과 조건

엔드포인트·함수·스키마가 정해지고 모호점 **0** → 6단계.
