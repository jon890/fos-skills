# 팀원 위임 계약

**팀원을 띄우기 전에 읽는다.**

## 이 스킬이 하네스에 요구하는 것

하네스마다 부르는 이름이 다르다. 재투입은 없을 수도 있다.

| 요구 | 없으면 |
| --- | --- |
| 하위 에이전트에게 지시와 함께 일을 맡긴다 | 이 스킬이 돌지 않는다 |
| 그 결과가 team-lead 로 돌아온다 | 결과를 파일에 쓰게 하고 team-lead 가 읽는다 |
| 맥락을 유지한 채 재투입한다 | 재투입할 때 직전 맥락을 프롬프트에 다시 담아 새로 띄운다 |

셋째가 갈리는 곳은 `REVISE` 재평가와 `FIX_NEEDED` 재투입이다.
맥락이 이어지면 바뀐 파일만 알려주면 되고, 이어지지 않으면 첫 판정과 바뀐 내용을 함께 다시 준다.

## 하네스별 대응

| | Claude Code | 그 밖 (Codex 등) |
| --- | --- | --- |
| 띄우는 단위 | 이름을 가진 팀원 | subagent |
| 지시 | 스폰 프롬프트, 이후 `SendMessage` | 스폰 프롬프트 하나 |
| 결과 회신 | `SendMessage` 로 team-lead 에게 | 그 하네스가 부모에게 돌려주는 경로 |
| 재투입 | 이름으로 `SendMessage` 하면 컨텍스트를 유지한 채 재개된다 | 새로 띄우고 직전 맥락을 프롬프트에 담는다 |
| 종료 | `TaskStop` | 한 번 쓰고 끝난다. 종료 지시가 필요 없다 |
| 전제 | `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 이 `settings.json` 의 `env` 나 셸 환경에 있어야 팀이 구성된다 | 없음 |

**팀원을 이름으로 재개할 수 있는 하네스에서는 재스폰이 최후 수단이다.** 컨텍스트를 버리기 때문이다.
재개할 수 없는 하네스에서는 재스폰이 정상 경로이고, SKILL.md 5단계의 종료 절차가 발동하지 않는다.

## 이름

`critic`, `executor-p{N}`, `code-reviewer`, `docs-verifier` 를 쓴다.
**작업 공간이 둘 이상 동시에 돌면 나머지 팀원 이름에도 plan 번호를 붙인다** (`critic-p{N}` 형태).
같은 이름을 쓰면 응답이 다른 작업 공간의 team-lead 에 도착해, 본 plan 과 무관한 분석을 받는다.

이름을 붙이는 이유는 능력이 아니라 **주소가 사람이 읽을 수 있는 것이 되는 것**이다.
Claude Code 에서는 이름 없이 띄워도 스폰 결과가 주는 id 로 메시지를 보낼 수 있고 결과도 돌아온다 (실측).
이름 없이 띄웠으면 그 id 를 실행 보고에 남긴다. 나중에 부를 주소가 그것뿐이다.

**띄운 직후 반환된 id 와 이름을 확인한다.** 이름을 빠뜨려도 호출은 오류 없이 성공한다.

## 절대경로

하위 에이전트는 main 워킹 디렉터리에서 실행될 수 있다.
상대경로로 지시하면 작업 공간 브랜치의 최신 파일이 아니라 main 의 옛 파일을 읽는다.

- 파일 참조는 작업 공간 절대경로로 준다. 역할 계약 파일도 마찬가지다.
- 팀원이 구버전을 본다고 의심되면 `grep` 한 실제 내용을 메시지에 붙이고 절대경로를 재확인시킨다.

## 스폰 프롬프트에 넣는 문구

아래를 그대로 포함한다.

**모든 팀원, 회신 강제.** 자기 화면에만 출력하고 끝내면 team-lead 에 전달되지 않는다.

```
회신은 반드시 team-lead 에게 메시지로 전송할 것.
자기 화면에 텍스트만 출력하고 종료하면 team-lead 까지 전달되지 않음.
판정/결론 + 핵심 사유 1-2 문단을 메시지 본문으로 보낼 것.
```

**executor, cwd 격리.** main 워킹 디렉터리에서 실행돼 main 브랜치를 직접 고치는 사고가 관측된다.

```
모든 파일 경로 / cd / git 명령은 지정된 작업 공간 절대경로 기준으로만 수행.
main repo 루트 직접 cd / 직접 편집 금지. 의심되면 `pwd` 로 확인 후 진행.
```

**executor, scope 확장 보고.** 범위 밖 수정을 스스로 넣으면 critic 과 code-reviewer 검토를 우회한다.

```
task 범위 외 코드 수정(pre-existing 에러, 발견한 bug, 규칙 위반 자체 변경)은 자체 판단 금지.
필요 시 보고: "task 범위 외 X 발견, Y 필요. 본 phase 포함 / 별도 plan 분리 결정 부탁".
team-lead 의 명시적 승인 후에만 추가.
lint/타입 검사 무시 주석(disable/ignore 류) 자체 추가 금지 — 규칙 위반은 정책 변경이라 사용자 결정 영역.
verification 보고는 검증 명령 전체 결과를 보고할 것. "프로덕션 코드만" 같은 한정 표현 금지.
```

team-lead 가 scope 확장 보고를 받으면 critic 사후 평가로 ACCEPT 와 REJECT 를 가른다.
ACCEPT 면 commit 메시지에 범위 확장을 명시한다.

## 무응답

**회신이 오지 않으면 한 번 재요청하고, 그래도 무응답이면 사용자에게 올린다.**
얼마나 기다려야 죽은 것인지 판정할 기준은 없다. 임의 시간으로 단정하지 않는다.

Claude Code 는 대기와 실패를 `idleReason` 으로 가른다.
`available` 은 턴이 끝나 대기 중이므로 이름으로 부르면 재개된다.
`failed` 는 `failureReason` 을 읽고 판단한다. 세션 한도면 재스폰해도 같은 이유로 막힌다.

## 실패 사례

Claude Code 에서 관측된 것이다.

- **`Could not determine current tmux pane/window`**
  `teammateMode` 를 `tmux`, `auto`, `iterm2` 로 켠 환경에서 난다.
  재시작이나 셸 설정으로는 고쳐지지 않는다. `in-process` 로 되돌리거나 이름 없이 띄운다.
- **`no progress 600s` 로 executor 가 멈춤**
  무거운 외부 상호작용(DB 를 여는 테스트, 긴 통합 실행)에서 난다.
  같은 형태로 재시도하면 같은 자리에서 멈춘다. 그 상호작용을 없애는 쪽으로 작업을 다시 짠다.
  DB 하네스가 없는 레포라면 파이프라인이 쓰는 순수 함수만 테스트 안에서 조립해 검증한다.
