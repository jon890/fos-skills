# 상주 루프 자동 재시작 검증 기록

- 상태: PR 전 인수 조건 REQ1-REQ8 통과. 실제 플러그인 업데이트로 다시 뜨는 것은 두 번 확인했다. 60분 상한을 실제 시간으로 기다리는 확인은 남아 있다.
- 원본: [스펙](spec.md), [설계](design.md), [ADR-032](../../adr/032-loop-bundle-handover.md).
- 이 기록은 끝난 계획 폴더(`tasks/self-update/`)의 검증 계획과 결과를 옮긴 것이다. 계획 폴더는 이 PR 에서 지웠다.

## 요구사항별 인수 검증

실행 환경은 로컬 node, 임시 저장소·임시 설정 폴더·가짜 Orca CLI 다. 명령은 저장소 루트에서 실행한다.
검증 커밋은 PR #488 의 head `2dbbfccda15a838dcfea5bc7c1280104b6c1fd2b` 다. 구현자 테스트(`node scripts/run-tests.ts` 로 바뀐 orch 테스트 10개 파일)는 통과 10, 실패 0 이었고 CI `Tests` 도 통과했다.
독립 검증은 임시 저장소와 임시 `ORCH_DIR`·`CLAUDE_CONFIG_DIR`, 설치 캐시에 둔 PR head 사본 두 벌(1.0.0, 2.0.0)로 `bin/orch loop start --run r1` 경로를 지나게 했다. 이 저장소의 상주 루프는 건드리지 않았다.

## 실제 플러그인 업데이트 확인

검증 계획의 「PR 뒤」 REQ2 행(이 기능이 든 버전을 수동으로 한 번 다시 띄운 뒤, 다음 플러그인 갱신에서 사람 손 없이 다시 뜨는지 본다)은 2026-11-13 에 두 번 확인했다.
근거는 이 저장소 루프의 `.orch/state/loop.log` 와 코디네이터 Run 알림이다.

| 갱신 | 시각(UTC) | loop.log | Run 알림 |
| --- | --- | --- | --- |
| 18.14.0 → 18.15.0 | 14:08:21 틱 11 뒤 14:08:46 새 루프의 틱 1 | `LOOP-STALE 18.14.0 18.15.0 <18.15.0 진입점>`, `LOOP-HANDOVER 22943 18.14.0 18.15.0` | 「fos-skills 루프: 18.14.0 → 18.15.0 으로 다시 떴다」 |
| 18.15.0 → 18.16.0 | 15:29:17 틱 15 뒤 15:29:48 새 루프의 틱 1 | `LOOP-STALE 18.15.0 18.16.0 <18.16.0 진입점>`, `LOOP-HANDOVER 1963 18.15.0 18.16.0` | 「fos-skills 루프: 18.15.0 → 18.16.0 으로 다시 떴다」 |

두 번 모두 틱 번호가 이어지다 새 pid 의 틱 1 로 바뀌었고, 사람이 `orch loop stop`·`start` 를 부르지 않았다.

## 확인하지 못한 것

- 60분 상한을 실제 시간으로 기다리는 확인. 함수 판정 사례(`decide` 의 59분 기다림, 60분 넘김)로만 확인했다. 실제 환경에서 마무리나 머지 큐가 60분 넘게 도는 일이 생기기 전에는 확인할 수 없다.
- 위 두 번의 확인에서는 마무리나 머지 큐를 기다리는 `LOOP-STALE-WAIT` 경로를 지나지 않았다(두 번 모두 loop.log 에 `LOOP-STALE-WAIT` 없이 곧바로 넘겼다). 기다림 경로는 임시 설치본 시나리오로만 확인했다.

## 참고

새 설치본의 진입점이 망가진 채로 `LOOP-UPDATE-FAIL` 이 오면, 설치본의 실행기가 설치 기록을 따라 망가진 새 번들로 가므로 `orch loop stop` 이 듣지 않는다. 옛 번들의 루프 진입점 스크립트에 멈춤 옵션을 직접 줘서 멈췄다. 이 기능이 만든 문제가 아니라 범위 밖으로 남겼다.
