## 검증 방법

기존 테스트를 그대로 돌린 것과 이번에 따로 짠 시나리오를 구분한다. 따로 짠 시나리오는 임시 테스트 파일로 돌리고 지웠다. 저장소에 남기지 않았다.

1. 기존 테스트 10개 파일: `board-find`, `feature-stages`, `lib-wait-events`, `lib-proc`, `spec-lint`, `board-sync`, `finish-pr`, `board-attach`, `core-step-ready`, `orch-loop-step-ready`. 결과는 통과 10, 실패 0이다(`node scripts/run-tests.ts <파일들>`, 74초).
2. 보드 맞추기(`board-sync.ts`) 경로 시나리오 3개. 실제 `board.ts` 명령과 가짜 `gh` 로 돌렸다. 통과 3, 실패 0.
3. 마무리(`finish-pr.ts`) 경로 시나리오 4개. 통과 4, 실패 0.
4. 사건 대기 시나리오 4개. 실제 보드 파일과 실제 `runGroup` 으로 돌렸다. 통과 4, 실패 0.
5. 띄우기 전 검사(`spec-lint.ts`) 직접 실행. 임시 저장소에 보드 파일과 지시서 여섯 개를 두고 CLI 로 돌렸다.
6. 띄우기 전체(`launch-worker.spec.ts` 의 「보드 항목 id 도 붙일 항목도 없으면 5 로 멈추고…」)를 다시 돌렸다. 통과.

## 관찰

실패는 아니다. 스펙이나 문서가 더 분명하면 좋은 곳이다.

1. 사건 대기 줄이 풀려도 항목 상태는 `wait` 그대로다. 시각 대기(`[wait: 시각]`)와 같은 동작이고 `board.md` 에도 적혀 있다. 스펙 REQ4 의 「대기를 푼다」 를 상태 변경으로 읽으면 어긋나므로, 코디네이터가 `WAIT-EVENT` 를 받은 뒤 `orch board set` 으로 상태를 바꾼다는 점이 알려져야 한다.
2. 알림은 `board.auto_advance: false` 이면 오지 않는다. `STEP-READY` 가 그 설정을 따르기 때문이다. 스펙 REQ2 의 「코디네이터에게 알린다」 는 설정을 켠 경우의 동작이다. 설계에는 적혀 있다.
3. 설계 PR 머지 뒤 `[ask]` 줄은 항상 `implementation 1/1` 로 만든다(몇 번에 나눌지 이 시점에는 모른다). 지시서의 `implementation 1/n` 이 올 때 띄우기가 그 줄을 `1/n` 으로 바꾼다. 이 동작은 `board-attach.spec.ts` 와 `spec-lint.spec.ts` 가 보지만 설명 문서에는 없다(아래 문서 어긋남 2).
4. `TERM` 을 무시하는 프로세스를 끊을 때 확인 한 번이 약 11초 걸렸다(상한 1초 뒤 유예 시간과 다시 확인). 느린 틱 안에서 끝나는 값이라 문제는 아니지만, 사건 명령이 `TERM` 을 무시하면 한 틱이 그만큼 길어진다.

## 남은 검증과 기능 전체

PR 전 필수 미검증은 없다. 실제 Orca 에서 코디네이터가 `STEP-READY` 와 `WAIT-EVENT` 를 받는 흐름은 가짜 알림 함수로만 봤다. 실제 Dooray 업무가 붙은 기능 항목(`task-ref` 와 `feature` 가 함께 있는 경우)의 마무리는 단위 테스트로만 봤다. 이 둘은 다음 기능을 이 방식으로 돌려 보며 확인할 일이다.
