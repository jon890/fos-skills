# Task 생성 가이드

레포별 검증 명령과 레이어 구조는 레포 설정이 채운다. 찾는 순서는 [`monorepo.md`](monorepo.md) 가 정한다.
이 문서의 `docs/` 와 `tasks/` 는 레포 설정의 경로로 바꿔 읽는다.

**phase 는 이 대화를 전혀 보지 못한 구현자가 읽는다.** 읽는 사람이 되물어야 실행할 수 있는 phase, 「여기서 정한 대로」 같은 대화 의존 표현을 남기지 않는다.
task 를 쓰기 전에 스펙의 인수 조건(스펙 없는 계획이면 사용자의 원래 요청과 성공 기준)과 반복 함정 목록을 읽고, 인수 조건은 phase 를 실행한 뒤 관측할 결과로, 함정은 작업 항목으로 옮긴다.

반복 함정 목록은 레포 설정이 지정하면 그것을 따르고, **지정이 없으면 `docs/pitfalls/` 를 읽는다.**
그 디렉터리도 없으면 사전 확인 항목을 건너뛴다.
이 스킬은 그 목록에 새로 쓰지 않는다. 목록의 항목은 저장소 규칙으로 옮길 후보이고, 옮기는 일은 `docs-consolidate` 의 별도 공통화가 맡는다. 넣을 곳은 [`rule-placement.md`](rule-placement.md) 가 정한다.

기능 계획은 `spec`, `design`, `requirements` 와 phase 별 `requirements` 를 더한다. 요구사항 ID 는 REQ1 형식이다. 값과 검사는 [plan](../SKILL.md)의 「4. task 작성」 을 따른다.
기능의 인수 조건은 스펙, 구조와 검증 전략은 기술 설계가 소유한다. 아래 기존 ADR·전역 문서 규칙은 해당 문서를 실제로 바꿀 때만 적용한다.

## 기능 계획 경로

새 기능은 `<스펙의 부모>/tasks/<목적이 드러나는 이름>/` 아래 index 와 phase 를 만든다.
예: `docs/features/job-cancel/tasks/cancel-api/`. 전역 번호는 쓰지 않는다. 같은 기능 안에서 이름 충돌을 확인하고 자기 계획 폴더만 만든다.
`name` 은 `cancel-api`, 브랜치는 `feat/job-cancel-cancel-api` 처럼 기능과 계획을 함께 넣는다.
명령에는 `PLAN=cancel-api`, `TASKS_DIR=docs/features/job-cancel/tasks` 를 전달한다. 다른 기능의 같은 이름을 자동 선택하지 않는다.
명시한 기존 계획 경로나 오버레이 경로는 그대로 사용하고 일괄 이동하지 않는다. 기존 계획의 ID 도 일괄 변환하지 않는다.
각 worker 는 자기 계획 폴더만 갱신한다. spec/design 은 의미가 실제로 바뀔 때만 고치고, 기능 전체 진행용 index 는 만들지 않는다.
인계에는 저장소 상대경로인 계획 전체 경로를 남긴다.

## 기존 계획과 기능 없는 작업의 번호

다음 번호 절차는 기존 배치 또는 기능에 속하지 않는 작업(이전·정리 작업과 기존 계획)에만 적용한다. 새 기능 계획에는 실행하지 않는다.

`tasks/{접두사}plan{N}-<kebab-slug>/` 아래 `index.json` 과 `phase-*.md` 를 만든다.
접두사와 tasks 경로는 레포 설정이 지정한다. 지정이 없으면 접두사 없이 `tasks/` 다.

**스크립트로 훑는다.** `$SKILL_DIR` 은 plan 번들 경로다.
`$TASKS_DIR` 과 `$PLAN_PREFIX` 는 레포 설정의 tasks 경로와 plan 접두사다. 지정이 없으면 비워 둔다.

```bash
# cwd: 타깃 레포 root
bash "$SKILL_DIR/scripts/plan_number.sh" --tasks-dir "${TASKS_DIR:-tasks}" ${PLAN_PREFIX:+--prefix} ${PLAN_PREFIX:+"$PLAN_PREFIX"}
```

`--prefix` 와 값을 따로 펼친다. `${PLAN_PREFIX:+--prefix "$PLAN_PREFIX"}` 로 묶으면 zsh 가 낱말을 나누지 않아 `--prefix plan` 한 낱말로 넘어간다.

**오버레이가 `tasks/<영역>-<3자리 번호>-<slug>/` 처럼 `plan{N}` 이 아닌 이름을 정했으면 `--prefix` 대신 `--name-regex` 를 준다.**
정규식은 디렉터리 이름 앞에서부터 맞추고, 번호를 잡는 캡처 그룹이 하나다. 접두사도 정규식에 넣는다.

```bash
# cwd: 타깃 레포 root
bash "$SKILL_DIR/scripts/plan_number.sh" --tasks-dir tasks --name-regex 'area-(\d{3})-'
```

`tasks/` 이력에 계획 디렉터리가 있는데 이름 형식으로 읽은 번호가 0개면 스크립트는 종료 코드 2 로 끝난다.
`다음 번호: 1` 로 끝내지 않는다. 형식이 저장소와 다르다는 뜻이므로 `--name-regex` 를 저장소의 이름에 맞춘다.
다른 하위 프로젝트의 계획만 있어 번호가 정말 없는 상태면 `--allow-empty` 를 준다.

마지막 줄이 다음 번호다. 접두사가 있으면 그 접두사의 번호만 센다.
`origin/main 밖에만 있다` 로 나온 번호는 머지되지 않은 브랜치가 쥔 것이고 그 번호도 쓰지 않는다.
로컬 `tasks/` 만 보면 그 번호가 보이지 않는다.
`지워졌고 git 이력에만 있다` 로 나온 번호는 구현이 끝나 지운 계획서다. 그 번호도 다시 쓰지 않는다.
`PR 브랜치 이름에만 있다` 는 계획서를 지운 뒤 squash 머지하고 브랜치까지 지운 번호다.

**plan 브랜치 이름은 `{접두사}plan{N}-{slug}` 나 `plan/{접두사}{N}-{slug}` 로 짓는다.**
squash 머지 뒤에는 git 이력에 계획서가 남지 않아, 스크립트가 `gh pr list` 의 브랜치 이름에서 번호를 읽는다.
다른 형식이면 그 번호를 읽지 못한다. 마지막 줄 앞에 `PR 이력을 보지 못했다` 가 나오면 `gh` 인증을 고치고 다시 돌린다.

- 저장소가 번호 확보 관례를 따로 두면 그것을 따른다. 없으면 이 스크립트의 결과를 쓴다.

## index.json 스키마

새 기능은 [index 양식](../templates/index.json)을 읽고 스펙·설계·요구사항·검증 계획 경로를 채운다. 기능 없는 기존 작업은 spec/design/requirements/verification_plan 을 생략할 수 있다.

`pr_scope` 와 `deferred` 는 [`plan-size.md`](plan-size.md) 가 소유한다. 2026-10-25 이후에 만든 plan 은 둘이 없으면 `verify_task.py` 가 위반으로 센다.

## 문서 영향과 ADR

**기능의 구조 결정은 technical-design 이 소유한다.** 이 절은 이번 PR 이 전역 문서(흐름, 코드 구조, 데이터 스키마)나 ADR 을 실제로 바꿀 때만 적용한다.
공유 경계나 ADR 결정이 필요하면 technical-design 으로 돌아가 먼저 해결한다. 문서 결정을 phase 로 미루지 않는다.

- 바뀌는 책임 문서만 고치고, 같은 정보를 두 문서에 쓰지 않는다. 필요하면 링크한다.
- `git diff -- docs/` 로 용어, 상태, API, 저장 모델이 서로 맞는지 확인한다.
- 없는 문서는 이번 변경이 그 내용을 실제로 소유할 때만 만든다. 장기 기술 결정이 없으면 빈 ADR 을 만들지 않는다.

**ADR 을 남길 조건, 양식, 대체와 이동 규약은 technical-design 이 소유한다.** [ADR 규칙](../../technical-design/references/adr-rules.md)을 읽고 따른다.
이 PR 이 ADR 을 만들거나 대체하면 그 문서의 검사 명령을 실행한다.

### 계획서를 가리키지 않는다

`docs/` 는 계획서보다 오래 남는다. 계획의 수명은 [계획 수명 규칙](plan-lifecycle.md)을 따른다.
`docs/` 가 계획서를 번호로 가리키면 그때 깨진 참조가 된다.

- **기본은 아무것도 적지 않는다.** 무엇이 언제 왜 바뀌었는지는 git 이력이 이미 추적한다.
- 결정의 근거가 필요하면 ADR 번호를 적는다.
- 변경의 이력이 필요하면 PR 번호를 적는다.
- 커밋 SHA 는 적지 않는다. rebase 와 squash 로 값이 바뀌어 같은 변경을 다시 찾을 수 없다.
- 계획서 번호를 시간 축으로 쓰지 않는다. 번호가 계획서와 함께 사라져 어느 쪽이 최근인지 판정할 수 없다.
  날짜처럼 계획서 수명과 무관한 값을 쓴다.

**내용을 계획서에 맡기지 않는다.** 계획서를 읽으라고 적는 것은 그 내용을 아직 옮기지 않았다는 뜻이다.
책임 문서가 그 내용을 소유해야 계획서를 지울 수 있다.

## 인수 검증 계획

[검증 계획 양식](../templates/verification-plan.md)을 읽고 구현 전에 작성한다.
index 의 verification_plan 은 계획 폴더 기준 상대경로다. 기본은 verification-plan.md, 작은 계획은 한 phase 의 인수 검증 계획 절이다.
이번 PR 의 요구사항마다 준비 조건·실행 절차·기대 결과·환경·선행 조건·시점을 연결한다. 같은 요구사항에 정상·실패 등 여러 사례를 둬도 된다.
실행 절차는 실제 테스트 경로·명령 또는 수행 가능한 경계 절차다. 이미 있는 테스트 내용은 복제하지 않고 참조한다.
phase 의 검증은 개발 테스트, 인수 검증 계획은 verify 가 확인할 동작이다. 후자는 PR 뒤 검증도 포함할 수 있다.
remote-verification.md 가 있으면 해당 행을 참조하고 조건·접속 절차의 원본을 두 벌 만들지 않는다.
검증 계획에는 결과를 쓰지 않는다. 실제 결과·커밋·환경은 verify 의 결과 양식으로 PR 에 남긴다.
형식과 요구사항 연결은 검사기, 사례의 충분성·범위·실행 가능성은 critic 과 verify 가 확인한다.

## phase 파일 작성 규칙

**phase 하나는 테스트까지 통과한 커밋 하나로 끝낸다.**
코드를 바꾸는 phase 안에서 그 동작의 테스트를 만들거나 고치고 「검증」 절에서 실행한다.
테스트를 다음 phase 로 미루지 않는다. 작업 항목의 순서는 구현과 검증 의존에 맞게 정한다.
**한 phase 는 한 사람이 한 번에 붙잡고 끝낼 수 있는 크기로 둔다.**

**「검증」 절에는 작업 공간에서 커밋 전에 끝나는 검증만 둔다.**
push, 배포, 원격 호스트 접속이 있어야 끝나는 검증은 phase 에 두지 않는다.
그 검증을 끝내려면 먼저 커밋하고 push 해야 해서, 실패를 고친 커밋이 phase 밖에 생긴다.
원격 검증만 담은 phase 도 만들지 않는다. 그 phase 에는 커밋할 대상이 없다.
원격 검증은 아래 「원격 검증 목록」 에 모은다.

**느린 e2e 테스트는 phase 「검증」 절에 넣지 않는다.** 마지막 phase 의 검증 절이나 `implementation` 4단계 누적 개발 검증에서 한 번 돈다.
무엇이 느린 e2e 인지는 저장소 오버레이가 정한다. 오버레이가 없으면 브라우저나 외부 서비스가 필요한 테스트로 본다.
그 phase 의 검증 절에는 e2e 가 아닌 같은 phase 의 테스트 실행 명령을 그대로 둔다.

### phase 파일 구조

작성 전에 [phase 양식](../templates/phase.md)을 읽는다. 명령은 작업 공간에서 실행할 수 있어야 하며 실제 코드·테스트 경로를 쓴다.

### 변경 파일 작성

작업 항목의 변경 경로를 이 목록에 모은다. `implementation` 는 커밋 전에 staged 파일과 대조한다.
목록에 없는 변경이 생기면 계획에 빠진 파일인지 무관한 변경인지 먼저 판정한다.
근거 문서 갱신은 목록에 포함한다. 단 4단계에서 이미 쓴 docs(ADR 과 `docs/` 갱신)는 계획 커밋에 함께 들어가므로 표에 넣지 않는다.
표에 「신규」 로 적으면 파일이 이미 있어 검사가 위반으로 센다. 커밋 전 `docs/` 신규 파일을 표에 적은 경우에는 경고로 낮추지만, 표에서 빼는 것이 맞다.
phase 문서의 링크는 그 phase 파일 위치 기준 상대 경로로 푼다. 저장소 루트 기준으로 적으면 없는 파일로 보여 위반이다. 링크가 번거로우면 백틱 경로로 쓴다.
계획 자신의 `index.json`, `verification-plan.md` 와 같은 폴더 바로 아래 `phase-*.md` 는 진행 상태·계획 보완용 메타데이터다.
변경 파일 표에 넣지 않아도 `--staged` 가 허용한다. 최상위 `tasks/<계획>/` 과 기능별 `docs/features/<기능>/tasks/<계획>/` 에 같은 규칙을 적용한다.
다른 계획의 파일과 자기 계획의 다른 파일·하위 폴더는 이 예외에 들어가지 않는다.
메타데이터만 바꾼 커밋에는 이미 커밋한 신규 구현 파일을 다시 요구하지 않는다. 구현 파일이 함께 staged 되어 있으면 범위·변경 종류·신규 파일 누락을 그대로 검사한다.
`--staged` 는 현재 index 를 대조하며 앞 커밋의 변경을 누적하지 않는다. phase 구현은 한 커밋으로 끝내고, 메타데이터 보완을 구현 완료의 증거로 쓰지 않는다.
보존·삭제는 [계획 수명 규칙](plan-lifecycle.md)을 따른다.

- 파일 경로를 `.../` 로 생략하지 않는다. 커밋 전 대조가 생략 경로를 실제 파일과 맞추지 못한다.
- `수정`과 `삭제`의 glob 은 일치하는 파일이 하나 이상 있어야 한다.
  `*`는 한 경로 조각, `**`는 하위 디렉터리까지 뜻한다.
- 신규 파일은 개별 경로를 적는다. 신규 glob 은 구체 파일의 부재를 확인하지 못하므로 경고한다.
- 에셋 내보내기처럼 도구가 만드는 파일을 미리 다 알 수 없으면 glob 행의 종류를 `신규·수정` 으로 적는다.
  glob 아래 파일 가운데 새 파일과 고친 파일이 섞여도 두 종류 모두 받는다. 삭제는 받지 않는다. 일치하는 파일이 없어도 위반이 아니다.
  `신규·수정` 은 glob 행에만 쓴다. 구체 경로에 쓰면 위반이다. 그 경로가 새 파일인지 고칠 파일인지 정해서 `신규` 나 `수정` 으로 적는다.
  생략 경로(`...`)는 위반이다. 여러 파일은 glob 으로 적는다.
- 신규로 적은 개별 파일이 커밋 전 staged 파일에 없으면 위반이다. 수정·삭제로 적은 파일이 없으면 경고한다.
- 앞 phase 가 만든 파일은 뒤 phase 에서 수정하거나 삭제할 수 있다. 앞 phase 의 신규 glob 에 맞는 경로도 같다.
  앞 phase 가 삭제한 파일을 뒤 phase 에서 수정할 수는 없다.
- 아직 머지되지 않은 다른 계획이 만들 파일을 고쳐야 하면 생성 검사가 위반으로 센다.
  그 계획이 머지된 뒤 기준 브랜치로 rebase 해 다시 돌리면 위반이 사라진다.

### 원격 검증 목록

push, 배포, 원격 호스트 접속이 있어야 끝나는 검증은 plan 디렉터리의 `remote-verification.md` 에 모은다.
`index.json` 의 `phases` 에 넣지 않는다. 원격 검증이 없으면 이 파일을 만들지 않는다.
implementation 은 이 목록을 verify 에 인계한다. orch 가 기록을 보존하고 [계획 수명 규칙](plan-lifecycle.md)에 따라 마감한다.

```markdown
# 원격 검증

| 선행 조건 | 시점 | 실행 위치 | 명령 | 기대값 |
|---|---|---|---|---|
| 없음 | PR 전 | app | 읽기 전용 배치 비용 측정 절차 | 전체 배치 비용이 기준 이하 |
| push | PR 뒤 | app | `scripts/verify.sh live` | 종료 코드 0 |
```

- **선행 조건**은 그 명령이 돌기 전에 끝나야 하는 것이다. `없음`, `push`, `머지`, `배포` 가운데 하나로 시작한다.
  원격 데이터를 읽기만 하는 추출과 측정은 이번 코드가 원격에 있을 필요가 없어 `없음` 이다.
- **시점**은 `PR 전` 또는 `PR 뒤` 다. `PR 전` 은 PR 을 열기 전에 결과가 있어야 하는 검증이다.
  verify 가 통합 검증과 함께 PR 을 만들기 전에 확인한다. 기존 호환 절차의 실행 주체는 유지한다.
- `PR 전` 에는 원격 상태를 바꾸지 않는 읽기 전용 명령만 둔다. 상태를 바꾸는 검증은 사람이 시점을 고르게 `PR 뒤` 로 둔다.
  선행 조건이 `머지` 나 `배포` 면 `PR 전` 일 수 없다. 검사기가 위반으로 센다.
- 시점 열이 없는 옛 표는 모두 `PR 뒤` 로 읽고 경고만 한다.
- **명령**에는 절차 이름이나 저장소 스크립트만 적고, **실행 위치**에는 저장소 이름만 적는다. 접속 대상, 서버 경로와 운영 값은 공개 계획서에 옮기지 않는다. 검사기는 명령 칸의 원격 접속 형태를 경고한다.

### 검사기와 작성자가 확인할 범위

검사기가 잡는 것과 경고 문구는 `verify_task.py` 가 소유한다. 걸리면 출력이 고칠 방법을 알려준다.
아래는 작성할 때 먼저 지키면 재작성이 줄어드는 규칙이다.

- 검증 절에는 같은 phase 의 테스트를 실행하는 명령을 적는다. lint 나 grep 만으로는 통과하지 않는다.
- 테스트 파일을 직접 지정하는 명령은 작업 항목에 선언한 테스트를 포함한다.
- 테스트 출력을 `tee` 로 넘기면 `set -o pipefail` 을 함께 적는다.
- 보조 파일(fixture, helper, `conftest.py`)만 바꾸는 phase 도 그 파일을 쓰는 테스트를 실행하는 명령을 적는다.
- 저장소의 `scripts/check-*`, `scripts/verify.*`, `scripts/test-*` 를 검증에 쓰면
  그 파일을 직접 열어 테스트 범위와 실패 종료 코드를 확인한다.
- 설정이나 배포 구성만 바꾸는 phase 도 실행 가능한 검증 스크립트나 저장소 테스트 명령을 적는다.

검사기는 명령을 실행하거나 테스트가 목표 동작을 확인하는지 판단하지 않는다.
작성자는 다음을 직접 확인하고 필요한 내용을 작업 항목과 검증 절에 적는다.

| 확인할 것 | 남길 근거 |
| --- | --- |
| 테스트가 바꾼 동작을 확인한다 | 정상 입력과 이 phase 가 다루는 실패 입력, 기대 결과 |
| 저장소 전체 명령이 위 테스트를 실행한다 | 테스트 검색 경로, 모듈 범위, 제외 설정 |
| 스크립트가 실패를 숨기지 않는다 | 단언 방법과 실패 종료 코드 |
| 기존 식별자, 경로와 스키마가 docs와 코드에 맞는다 | 실제 정의를 읽고 일치시킨 이름과 타입 |
| 스키마, table, 설정의 개수를 상수로 단언하는 기존 테스트가 이 phase 의 변경에 깨지지 않는다 | 그 테스트를 변경 파일 표에 넣고 고칠 값을 작업 항목에 적는다. 레포의 테스트 프레임워크에서 개수를 단언하는 형태를 찾는다 |
| 테스트 명령에 필요한 환경값을 모두 적었다 | phase 마다 환경값 전체를 적는다. 앞 phase 를 가리키지 않는다. 구현자는 그 phase 만 읽는다 |
| 새로 만드는 키, 경로, 식별자가 기존 값과 겹치지 않는다 | 같은 종류의 기존 값을 `git grep` 으로 찾은 결과. 멱등 키나 설정 키가 다른 명령의 키와 같아지면 서로 덮어쓴다 |
| 시그니처를 바꾸는 phase 가 하위 클래스와 호출부를 모두 변경 파일에 넣었다 | `git grep -n "extends <클래스>\|new <클래스>("` 로 찾은 파일. 생성자 인자를 더하면 상속한 하위 클래스도 컴파일이 깨진다. 작업 항목에 바꾸는 함수를 `save()` 처럼 호출 형태로 적으면 검사기가 변경 파일에 없는 호출 파일을 경고로 낸다 |
| 여러 phase 에 걸친 이전이 각 phase 커밋에서 모든 호출부의 동작을 이전과 같게 둔다 | 기존 메서드를 새 메서드에 위임한다고 적기 전에 호출부를 `git grep` 으로 세고 반환 형식 차이를 확인한다. 중간 커밋에서 호출부 동작이 바뀌면 구현자가 멈춘다 |

`Critical Files`라는 기존 절 이름은 읽기 호환으로 받는다. 새 계획은 「변경 파일」을 쓴다.
검사기의 구현 후 문서 검사와 커밋 전 대조 인자는 `verify_task.py --help`가 설명한다.

## task 를 만든 직후 검사한다

task 파일을 만든 직후, 구현 전 상태에서 스크립트를 돌린다. 종료 코드 0 이어야 한다.
경고는 작성자가 확인하고 대조하지 못한 경로와 검증 범위를 보고에 남긴다.

`$PLAN` 은 `plan9-db-backup` 같은 디렉터리 이름이다.
`$TASKS_DIR` 은 레포 설정의 tasks 경로이고 지정이 없으면 `tasks` 다.

```bash
# cwd: 타깃 레포 root
python3 "$SKILL_DIR/scripts/verify_task.py" "$PLAN" --tasks-dir "${TASKS_DIR:-tasks}"
```

구현이 끝난 뒤, 그리고 구현 PR 에서 계획서를 검증할 때는 같은 명령에 `--audit` 를 붙인다.
붙이지 않으면 phase 「변경 파일」에 신규로 적은 파일이 이미 있어 위반으로 센다.

```bash
python3 "$SKILL_DIR/scripts/verify_task.py" "$PLAN" --tasks-dir "${TASKS_DIR:-tasks}" --audit
```

형식 위반은 고치고 다시 돌린다. 합의한 범위나 결정을 바꿔야 하는 위반은 spec 으로 돌려보낸다. 스펙 없는 계획이면 선택지를 붙여 사용자에게 묻는다.
