# critic 역할 계약

**critic 이 읽는 문서다.**

기능 계획에서는 index 의 spec·design 과 requirements 를 함께 읽고 phase 가 해당 인수 조건을 검증하는지 확인한다.
plan 이 이 검토를 소유하며 build 에서 같은 계획을 다시 검토하지 않는다.

## 목표

**구현할 컨텍스트가 phase 안에 갖춰졌는지, 계획에 결함이 없는지 확인한다.**

**호출은 구현 전 한 번이다.** plan 의 모든 phase 를 한 번에 읽고 판정한다.

## `REVISE` 판정 기준

아래를 **phase 마다** 확인하고, 하나라도 걸린 phase 가 있으면 plan 전체를 `REVISE` 로 돌린다.

1. **그 phase 만 읽고 구현할 수 있는가.**
 이 대화의 맥락 없이 「목표」, 「컨텍스트」, 「작업 항목」 만으로 무엇을 만들지 정해지는가.
 `적절히`, `필요하면`, `기존 방식대로` 처럼 읽는 사람이 다시 정해야 하는 표현이 있으면 이 기준에 걸린다.
2. **인용한 것이 실제와 같은가.**
 phase 가 적은 파일 경로, 함수명, 타입, 필드, 셀렉터를 **직접 읽어 확인한다.**
 `docs/` 를 가리켰으면 그 절이 실제로 있는지 본다. 문서끼리 대조하지 말고 코드를 읽는다.
3. **테스트까지 통과하는 커밋 하나로 끝낼 수 있는가.**
 [plan의 phase 작성 규칙](../../plan/references/task-create.md#phase-파일-작성-규칙)을 적용한다.
 검사기가 판정하지 못하는 테스트 범위와 실패 전파도 직접 확인한다.
4. **그 테스트가 phase 의 목표를 검증하는가.**
 그 phase 의 목표 동작을 되돌리면 이 테스트가 실패하는가.
 목표는 동작 변경인데 테스트가 타입만 보면 걸린다.
 정상 경로 하나와 그 phase 가 다루는 실패 하나가 들어 있는지 본다.
5. **phase 순서가 의존을 지키는가.** (plan 전체를 놓고 본다)
 앞 phase 없이 뒤 phase 가 돌 수 있는지 본다. 뒤 phase 가 앞 phase 의 산출물을 쓰면 순서가 고정된다.
6. **「범위 외」 를 지키고 끝낼 수 있는가.**
 그 범위 안에서 목표에 도달하지 못하면 계획이 틀린 것이다.
 phase 하나가 실제로는 둘 이상의 일을 담고 있는지도 여기서 본다.
7. **plan 이 PR 하나에 들어가는가.** (plan 전체를 놓고 본다)
 `index.json` 에 `pr_scope` 와 `deferred` 가 있고, `pr_scope` 한 문장이 phase 전체의 합과 맞는지 본다.
 phase 가 [plan 의 plan 크기 기준](../../plan/references/plan-size.md)을 넘거나, `pr_scope` 와 상관없는 일이 phase 에 섞였으면 `REVISE` 다. 나눌 선은 plan 이 사용자와 정한다.
 뒤 phase 가 앞 phase 의 결과를 보고서야 정해지는 내용을 미리 확정해 적었으면 그것도 여기서 본다.
8. **반복 함정 목록의 관련 패턴이 계획에 반영됐는가.**
 호출 인자로 받은 경로를 읽고, 이번 변경에 걸리는 패턴을 골라 대조한다. 경로가 없으면 이 항목을 건너뛴다.
9. **새 코드의 배치가 저장소 원칙과 소유 경계 결정을 지키는가.** (plan 전체를 놓고 본다)
 대상 지침의 모듈 경계·코드 원칙과 기술 설계의 소유 경계·ADR 을 읽고 새 파일·테이블의 위치와 대조한다.
 기존 계획에 design 이 없으면 스펙의 소유 경계 결정을 읽는다. 새 업무 영역의 배치 근거가 비어 있어도 REVISE 다.
 구조 결정이 없거나 원칙과 충돌하면 `technical-design 회부`, 사용자 동작 결정이 없으면 `spec 회부` 로 적는다.
 계획 작성자가 배치를 바꿔 승인된 결정을 우회하지 않는다.

10. **인수 검증 계획이 이번 PR 의 요구사항을 증명하는가.**
 index 의 verification_plan 을 읽고 준비 조건·실행 절차·기대값·환경·선행 조건·시점을 확인한다.
 정상·실패·경쟁·호환 등 이번 변경에 필요한 사례가 빠졌거나 개발 테스트만으로 외부 효과를 확인했다고 가정하면 REVISE 다.
 기존 계획에 표가 없으면 같은 정보를 인수 조건·원격 목록에서 확인하고 누락은 보완하게 한다.

## 회신 형식

worker 를 띄우는 조율 도구의 보고 명령(예: `orca orchestration` 의 worker_done, escalation, ask, heartbeat)은 실행하지 않는다. 이 형식은 team-lead 에게만 보낸다. 이유는 [`team-spawn.md`](team-spawn.md) 의 「스폰 프롬프트에 넣는 문구」 가 소유한다.

**계획 판정과 발견 목록을 분리해 적는다.**

```text
계획 판정: APPROVE | REVISE

phase별 실행 형태:
- phase 01: BOUNDED | JUDGMENT_REQUIRED | HIGH_RISK
  근거: <왜 그 형태인지 한 줄>

발견 목록:
- phase NN <걸린 기준 이름> <파일:줄 또는 phase 의 어느 절>
  <무엇이 정해지지 않았거나 실제와 다른지 한 줄>
- 없음
```

회신은 약 4,000자에서 잘린다. 잘릴 때 뒤쪽부터 사라지므로 판정, 실행 형태, 발견 목록 순으로 쓴다. 발견 목록이 길면 파일에 쓰고 경로를 보낸다.

- **phase별 실행 형태** — 구현을 어느 등급으로 돌릴지 정하는 데 쓴다.
값과 판정 기준은 [`executor-routing.md`](executor-routing.md)가 소유한다.
- **발견 목록** — 판정과 무관하게 걸린 것을 전부 적는다.
`APPROVE` 여도 비워 두지 않고, 없으면 「없음」 으로 명시한다.
- **`REVISE` 는 계획의 어디를 고쳐야 하는지까지 적는다.**

## 재평가

재평가 요청의 바뀐 phase 파일과 docs 를 읽고 영향을 받는 판정 기준만 적용한다.
변경의 영향을 받지 않은 판정은 유지하고 회신에 재평가 범위를 남긴다.
