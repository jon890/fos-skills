# ADR-009: orch 는 단계마다 이벤트를 내고, 저장소 고유 일은 저장소의 이벤트 핸들러가 맡는다

- **status**: `accepted`
- **결정**: orch 의 공용 코어는 worker 띄우기부터 정리까지 단계마다 정해진 이벤트를 낸다.
  저장소는 `<주 checkout>/.orch/hooks/<이벤트>.ts` 에 핸들러를 두어 그 시점에 필요한 일을 끼워 넣는다.
  `before-` 로 시작하는 이벤트와 `verify-merged` 의 핸들러는 다음 동작을 거부할 수 있다.
  `.orch/config.json` 의 셸 명령 칸(`queue.before`, `queue.verify_merged`, `queue.after_merged`, `finish.complete_cmd`)은 핸들러로 옮긴다.
  사용자 결정 2026-10-24.
- **맥락**: 저장소마다 다른 일(DB 백업, 로컬 배포, 업무 완료, 문서 PR 바로 머지, 쌓인 PR 의 base 옮기기)을 끼울 자리가 셸 명령 칸 몇 개뿐이었다.
  칸이 없는 일은 저장소가 로컬 스크립트로 orch 를 통째로 대신했다. 그 스크립트는 상주 루프, 슬롯, 충돌 판정을 다시 구현했고,
  터미널 직접 입력 금지 hook 과 다른 사람 PR 제외 같은 코어의 보호 장치를 거치지 않았다.
  한편 공용 스킬에는 한 저장소의 명령 이름, CI job 이름, 배포 스크립트가 분류 정규식과 예시 문서로 들어와 있었다.
- **대안 기각**:
  - 셸 명령 칸을 늘린다. 칸마다 환경 변수 이름과 종료 코드 뜻을 따로 정하게 되고, 여러 줄 로직은 결국 저장소 스크립트를 부르는 한 줄이 된다. 입력이 문자열 환경 변수라 목록과 구조를 넘기지 못한다.
  - 저장소가 코어 모듈을 import 해 자기 루프를 짠다. 플러그인 설치 경로가 커밋 SHA 마다 바뀌어 import 경로가 갱신마다 깨지고, 루프와 보호 장치가 저장소마다 다시 갈라진다.
  - 이벤트 하나에 여러 핸들러 파일(`<이벤트>/<번호>-<이름>.ts`)을 둔다. 순서 규칙과 부분 실패 처리를 코어가 더 가져야 한다. 한 파일 안에서 import 로 나누면 순서는 그 코드가 정한다.
  - 아무 실행 파일을 핸들러로 받는다. 실행기, 시간 제한, 가드 환경이 언어마다 갈린다. 다른 언어가 필요하면 ts 핸들러가 자식 프로세스로 부른다.
- **결과**:
  - 얻는 것: 저장소 로컬 루프를 코어의 상주 루프와 핸들러로 바꿀 수 있다. 저장소 고유 값이 공용 스킬에서 빠진다.
  - 얻는 것: 핸들러는 가드 shim 을 거친 `orca` 와 `gh` 만 받아, 코어의 보호 장치를 우회하지 못한다.
  - 감당할 것: 이벤트 이름과 입력 JSON 이 저장소와의 계약이 된다. 필드를 빼거나 뜻을 바꾸면 major 로 올린다. 더하는 것은 minor 다.
  - 감당할 것: 쓰던 저장소는 셸 명령 칸을 핸들러로 옮겨야 한다. 옮기는 명령과 경고 기간을 둔다.
