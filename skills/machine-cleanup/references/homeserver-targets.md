# 홈서버 정리 대상과 등급

홈서버 2단계(후보 분류)와 4단계(실행)에서 읽는다. `hs_classify.ts` 가 이 규칙대로 등급을 붙이고, 이 문서는 그 규칙과 정리 명령을 소유한다.
경로, 이미지 이름, 보관 규칙 같은 홈서버 고유 값은 이 문서에 두지 않는다. fos-home-infra 오버레이(`hs_overlay.ts` 머리 주석의 키)와 그 저장소의 백업 보관 규칙 표가 소유한다.

후보마다 **누가 소유하는지**를 먼저 정하고, 그 소유자가 등급을 정한다.

| 등급 | 뜻 | 스킬이 하는 일 |
| --- | --- | --- |
| 유지 | 자동 정리나 다른 스크립트가 소유한다 | 지우지 않고 승인 질문에 넣지 않는다. 규칙보다 많이 남았으면 원인을 찾는다 |
| 안전 | 다시 받으면 되는 사본이거나, 소유자가 정한 정리 명령이 보관 개수를 지킨다 | 묶음으로 승인받아 지운다 |
| 확인 필요 | 되돌릴 수 없거나 사람이 판단하기로 한 것이다 | 내용과 날짜를 보이고 항목별로 승인받는다 |

## 백업 루트

`hs_classify.ts` 표의 「「백업」 표의 보관」 열이 그 용도의 보관 규칙이다.

| 보관 칸 | 등급 | 정리 |
| --- | --- | --- |
| 「명시적 정리」 와 「최신 N개」 가 든 것 | 안전 | `hs_delete.ts backup --keep N`. 폴더 안에서 최신 N개를 남기고 오래된 항목만 지운다. N 은 보관 칸의 개수다 |
| 「명시적 정리」 인데 개수가 없거나 「서비스별」 처럼 대상별 개수인 것 | 확인 필요 | 남길 것을 사용자에게 묻는다. 폴더째 지우지 않는다 |
| 「사람이」 가 든 것 | 확인 필요 | 표의 조건(업그레이드 뒤 운영 확인, 되살리지 않기로 결정)을 사용자에게 묻고 `hs_delete.ts backup` |
| 매일 정리, 「최신 N개」, 타이머, 보존 기간 | 유지 | 없다. 규칙보다 많이 남았으면 아래 「자동 정리가 놓친 것」 |
| 표에 없음 | 확인 필요 | 지울지와 함께 표에 올릴지 묻는다 |

**`hs_delete.ts backup` 은 지우기 직전에 보관 규칙 표를 다시 읽는다.** 자동 정리가 소유한 용도는 거부하고, 「명시적 정리」 용도는 `--keep` 이 없거나 규칙의 개수보다 적으면 거부한다.
표를 읽지 못하면 `--keep` 없이 폴더째 지우지 않는다. 승인 묶음은 「최신 N개만 남김」 인데 폴더째 지워 복구 판단에 쓸 최신 백업까지 사라지는 일을 막는다.

**표에 없는 용도는 3단계 승인에서 용도마다 두 가지를 함께 묻는다.** 지울지, 그리고 남긴다면 보관 규칙 표에 올릴지다.
`<이름>-<UTC 시각>` 처럼 시각이 붙은 일회성 용도가 대부분이다. 남길 것을 표에 올리지 않으면 다음 조사에서 다시 후보로 나온다.
표에 올리기로 한 용도는 5단계 보고의 「표에 올릴 용도」 에 남긴다. 표를 고치는 일은 fos-home-infra 변경이라 스킬이 하지 않는다.

## Docker

| 대상 | 등급 | 정리 |
| --- | --- | --- |
| 오버레이 `owned_images` 에 맞는 이미지, build cache | 유지 | 자동 정리가 소유한다 |
| 「설정이 가리킴」 이 붙은 이미지 | 유지 | Compose, Dockerfile 의 FROM, settings, 내용 해시 태그가 지금 쓰도록 정한 것이다. 컨테이너가 없어도 작업이 생기면 바로 쓴다 |
| 「실행 중인 다른 버전」 이 있는 이미지 | 확인 필요 | 레지스트리에서 다시 받을 수 있다. `hs_delete.ts images` |
| 그 밖의 쓰지 않는 이미지 | 확인 필요 | fos-home-infra 에서 이름을 `git grep` 해 쓰는 곳이 없을 때만 `hs_delete.ts images`. 직접 빌드한 이미지는 다시 만들 수 없다 |
| dangling volume | 확인 필요 | 내용을 연 뒤 이름을 지정해 `docker volume rm` |

**`docker image prune -a` 와 `docker system prune -a` 는 쓰지 않는다.**
멈춘 컨테이너가 없는 순간에 돌면 보관 중인 복구 이미지와, 작업이 생기면 쓰는 이미지까지 모두 지운다. 태그나 ID 를 하나씩 지정한다.

## 경로

| 경로 | 등급 | 정리 |
| --- | --- | --- |
| 오버레이 `owned_paths` | 유지 | 소유한 스크립트가 지운다 |
| `~/.npm` | 안전 | `npm cache clean --force` |
| `~/.local/share/pnpm` | 안전 | `pnpm store prune`. pnpm 이 없으면 건너뛴다 |
| `~/.local/share/Trash` | 확인 필요 | 옮긴 시각을 보이고 고른 항목만 `hs_delete.ts trash`. 오늘 옮긴 것은 권하지 않는다 |
| `~/.cache` | 확인 필요 | 하위 폴더별 크기를 보이고 고른 것만 지운다 |
| 홈 아래 큰 폴더 | 확인 필요 | 크기 상위와, 순위 밖이어도 사본 이름(`<이름>.failed-*`, `*.bak`, `*-backup`)을 보인다. 실패한 작업이 남긴 사본에는 비밀 파일 사본이 들었을 수 있어 내용을 본 뒤 사용자가 지운다. 지우는 스크립트는 없다 |
| `/var/cache/apt` | 안전, sudo | `sudo apt-get clean` |
| journal | 확인 필요, sudo | 지금 줄이기는 `sudo journalctl --vacuum-size=1G`. 상한은 `/etc/systemd/journald.conf` 의 `SystemMaxUse` 가 소유한다 |
| snap 이전 리비전 | 안전, sudo | `sudo snap remove "$NAME" --revision="$REV"` |
| `/tmp`, `/var/tmp`, `/var/log` | 유지 | 시스템과 로그 회전이 소유한다. 참고로만 보인다 |

sudo 명령은 `hs_classify.ts` 가 `ssh -t` 꼴로 낸다. 실행은 `homeserver.md` 의 「sudo 넘기기」 를 따른다.

## git 저장소

맥과 같은 기준이다(`git-and-sessions.md` 의 「워크트리」, 「브랜치」). 홈서버에서 다른 점만 적는다.

- 오버레이 `repos` 에 적힌 저장소만 본다. 현재 받은 브랜치는 후보가 아니다.
- 워크트리 사용 확인은 Orca 대신 그 워크트리 안에서 도는 프로세스로 한다. 있거나 확인하지 못하면 지우지 않는다.
- `survey_only` 저장소는 조사만 한다. 브랜치를 옮기기만 해도 운영이 깨질 수 있어 승인 질문에 넣지 않는다. `build_worktrees` 에 맞는 워크트리는 원인 수정 제안으로 보고한다.
- 운영 checkout 의 브랜치와 워크트리는 운영 작업 잠금 아래에서 지운다.

## 대화 기록과 Hermes 세션

| 대상 | 등급 | 정리 |
| --- | --- | --- |
| Claude·Codex 대화 기록 | 확인 필요 | 맥과 같은 세 기준(30일 지난 기록, 워크트리가 사라진 기록, 오래 떠 있는 에이전트 프로세스). 기록이 없으면 「없음」 이다 |
| Hermes 세션 트리 | 확인 필요 | 30일 지났고 assistant 대화에 연결되지 않은 트리의 루트만. 출처별 묶음으로 묻고 고른 묶음만 `hs_delete.ts hermes`. 채팅 출처(discord)는 다시 이어 쓰는 대화일 수 있어 권장하지 않는다 |
| Hermes 세션 DB 공간 회수 | 사용자 몫 | 스킬이 하지 않는다. Hermes 가 DB 를 쥐고 있으면 돌지 않아 Hermes 를 멈춰야 한다. 세션을 지운 DB 의 크기와 함께 「Hermes 를 멈춘 점검 시간에 optimize」 를 보고에 남긴다. `--force` 는 쓰지 않는다 |

Hermes 는 부모를 지우면 자식도 지울 수 있어 트리 단위로 본다. 트리 안에 연결된 세션이나 30일 안에 활동한 세션이 하나라도 있으면 트리 전체를 뺀다.
연결 조회가 실패하면 후보를 하나도 내지 않는다. 연결을 확인하지 못한 세션을 지우면 assistant 화면의 대화가 깨진다.

## 자동 정리가 놓친 것

유지 등급인데 규칙보다 많이 남았으면 **지우지 말고 원인을 찾는다.** 스킬로 지워도 다음 배포부터 다시 쌓인다.

- `hs_classify.ts` 가 `정상(마지막 매일 정리 뒤에 생김)` 이라고 했으면 끝이다.
- `원인 확인 필요: <용도>` 면 그 용도를 만드는 스크립트와 매일 정리 스크립트를 fos-home-infra 에서 읽어, 정리하는 쪽이 그 용도를 부르는지 본다.
- 부르지 않으면 원인 수정을 제안한다. 판정은 `원인: <정리하지 않는 스크립트와 이유>` 로 적는다. 보관 규칙을 바꾸는 수정이면 fos-home-infra 에 ADR 을 남기라고 제안한다.
