# 인터뷰 절차

spec 의 2~4단계에서 읽는다. 결정을 빠뜨리지 않고 모으고, 사용자에게 묻고, 다 닫혔는지 판정하는 방법을 정한다.

## 점검 축

결정 목록을 만들 때 축마다 이번 기능에 걸리는 결정을 찾는다. 걸리는 것이 없으면 「해당 없음」 과 이유 한 줄을 적는다.
축을 빠뜨리지 않으려는 목록이다. 축마다 질문을 만들어 내라는 뜻이 아니다.

| 축 | 찾을 결정 |
| --- | --- |
| 범위 | 이번에 하지 않는 것. 여러 PR 로 나뉘면 첫 PR 이 어디까지인가 |
| 사용자 흐름 | 누가 시작하나(사람, 자동, 다른 시스템). 화면이면 어디에 무엇이 뜨고 어떻게 이동하나. CLI 면 인자와 플래그 |
| 실패와 빈 상태 | 실패, 타임아웃, 권한 없음, 데이터 없음일 때 무엇을 보이고 무엇을 남기나 |
| 동시성 | 중복 요청, 반복 요청, 잠금 충돌을 어떻게 하나 |
| 권한 | 누가 할 수 있고 누가 못 하나 |
| 외부 계약 | API 필드, 옵셔널, 에러 코드. 기존 필드를 바꾸면 소비자는 어디고 무엇을 먼저 배포하나. 동기인가 비동기인가 |
| 데이터 | 무엇을 저장하고 얼마나 두나. 지울 때 함께 지워지는 것. 기존 데이터를 옮기나 |
| 운영과 비용 | 설정 값, 알림, 비용이 드는 호출, 문제가 나면 끄는 방법 |
| 인수 조건 | 무엇을 관측하면 끝인가. 어느 환경에서 확인하나 |

## 누가 정하나

| `사용자` 가 정한다 | `작성자` 가 근거를 남기고 정한다 |
| --- | --- |
| 사용자 동작, 권한, 데이터 보존·삭제, 외부 계약과 호환, 운영·비용에 닿는 결정 | 내부 이름, 파일 배치, 기존 관례를 따르는 선택 |
| 범위를 넓히거나 줄이는 결정 | 코드와 문서를 읽어 답이 하나로 정해지는 것 |
| 근거 없이 정한 임시 값(기한, 상한, 기본값) | 되돌리기 쉬운 기술 선택 |

**작성자가 답을 이미 정했어도 왼쪽 열에 들면 `사용자` 로 둔다.** 권장안으로 그 답을 내고 확인받는다.
작성자가 스스로 「정했다」 고 본 결정은 자기 점검으로 다시 보이지 않는다. 그래서 묻는 쪽으로 기운다.

## 질문 라운드

**첫 라운드**: 요청을 되짚는다. 사용자가 말한 것과 작성자가 짐작한 것을 나눠 적는다.
목표와 범위의 빈칸은 열린 질문으로 묻는다. 선택지를 먼저 주면 답이 선택지 쪽으로 끌려간다.

**다음 라운드부터**: 결정을 한 번에 최대 4개씩 묻는다. 큰 갈래(범위, 사용자 흐름)를 먼저, 세부(이름, 기본값)는 뒤에 묻는다.
결정 하나는 아래 형식으로 쓴다. orch 의 사용자 결정 질문 형식과 같다.

```text
결정: 반복 취소 요청의 응답
배경: 취소된 실행에 다시 취소를 보내면 지금은 409 다. 화면은 재시도한다(web/src/run/cancel.ts:42).
선택지:
- 200 과 현재 상태: 재시도가 안전하다. 409 를 기대하는 소비자가 있으면 깨진다
- 409 유지: 소비자 변경이 없다. 화면이 오류를 숨겨야 한다
권장: 200 과 현재 상태. 화면 재시도가 이미 있고 409 소비자는 없다
```

- 선택지는 2~4개다. 선택지마다 고르면 생기는 결과를 적는다.
- 배경에는 근거 경로를 붙인다. 사용자가 코드를 열지 않고 판단할 수 있게 한다.
- 구조화 질문 도구(AskUserQuestion 같은 것)가 있으면 그것으로 묻는다. 한 번에 4개가 도구의 상한이다.
- 답이 연 후속 질문은 결정 표에 더해 다음 라운드에 묻는다.

**라운드 상한과 출구**

- 사용자가 「그만 묻고 진행」 이라 하면 남은 `사용자` 결정을 권장안으로 닫고 「누가」 를 `작성자(위임)` 로 적는다. 확인 단계에서 이 행들을 따로 보인다.
- 결정 라운드가 5회를 넘으면 기능이 크다는 신호다. 기능을 나누자고 제안한다.

## 결정 표

스펙의 `## 결정` 절에 둔다. 진행 로그가 아니라 지금 유효한 결정만 둔다.

```markdown
| ID | 결정 | 답 | 누가 | 근거 |
| --- | --- | --- | --- | --- |
| D1 | 취소 권한 | 소유자와 관리자 | 사용자 2026-11-02 | 관리자 대리 취소 요청이 있었다 |
| D2 | 반복 취소 응답 | 200, 상태 그대로 | 작성자 | 기존 멱등 API 관례(docs/contracts/idempotency.md) |
| D3 | 예약 실행 취소 | 범위 밖 | 사용자 2026-11-02 | 다음 기능으로 미룬다 |
```

- 「누가」 는 `사용자 YYYY-MM-DD`, `작성자`, `작성자(위임)` 중 하나다.
- 「답」 이 비었거나 `미정`, `TBD`, `?` 면 닫히지 않은 것이다.
- 결정이 하나도 없는 기능이면 표 대신 `없음: <이유>` 한 줄을 둔다. 이유가 없으면 검사기가 막는다.

형식은 `planning/scripts/check_feature.py` 가 검사한다. 의미가 맞는지는 다음 절의 검토자와 사용자가 본다.

## 독립 검토자 검사

결정 표가 닫히면, 이 대화를 모르는 하위 에이전트 하나에게 스펙과 코드만 주고 아래를 맡긴다.
구현자의 설명이나 예상 답은 주지 않는다. 위임 방식은 [팀원 위임 계약](../../build-with-teams/references/team-spawn.md)을 따른다.

```text
이 스펙만 읽고 PR 단위 구현 계획을 쓴다고 가정한다.
계획을 쓰려면 짐작해야 하고, 짐작이 틀리면 사용자에게 보이는 결과가 달라지는 곳만 찾아라.
찾은 곳마다 스펙의 위치, 짐작해야 하는 것, 갈릴 수 있는 답 두 개를 적어라.
내부 이름과 파일 배치처럼 계획 작성자가 정해도 되는 것은 적지 마라. 없으면 「없음」 이라고 적어라.
```

발견마다 「누가 정하나」 표로 나눈다. `사용자` 몫은 한 라운드 더 묻고, `작성자` 몫은 근거와 함께 결정 표에 적는다.
하위 에이전트를 띄울 수 없는 환경이면 검사를 건너뛴 사실을 확인 단계에서 사용자에게 알린다.

## 직접 묻지 못할 때

orch worker 처럼 사용자와 대화하지 못하는 세션은 코디네이터를 거쳐 묻는다. 절차는 같고 전달 방법만 다르다.

1. 첫 라운드와 결정 라운드를 `worker-ask` 질문 하나씩으로 보낸다. 질문 첫 줄에 스펙 초안 경로를 적고, 결정은 위 형식의 블록을 이어 붙인 뒤 `--decision` 을 붙인다. 한 질문에 4개를 넘겨도 된다. 코디네이터가 4개씩 나눠 묻고 답을 모아 돌려준다.
2. 답을 받으면 스펙을 고친다. 후속 질문이 생기면 1을 다시 한다.
3. 결정 표가 닫히고 독립 검토자 검사를 마치면, 스펙 전문과 「확인 요청」 을 `worker-ask` 로 보낸다.
4. 코디네이터가 사용자의 확인을 돌려주면 확인 줄을 적고 planning 으로 간다. **확인 답을 받기 전에는 planning 과 구현을 시작하지 않는다.**

`worker-ask` 를 부르는 명령과 종료 코드는 공통 지시서가 정한다. 코디네이터 쪽 중계는 orch 의 `references/replying.md` 가 정한다.
