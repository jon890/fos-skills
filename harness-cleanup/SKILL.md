# harness-cleanup

하네스 지시를 인상이 아니라 현재 설정과 실행 가능한 증거로 교정한다.
발견과 판정표 작성까지 먼저 수행하고, 사용자가 승인한 변경만 적용한다.

지시가 틀리면 에이전트가 그대로 따라 실패한다.
그래서 **사실 오류와 동작하지 않는 지시를 먼저 잡고, 분량은 그다음에 줄인다.**
순서를 바꾸면 틀린 내용을 그대로 남긴 채 짧아진다.

## 스크립트 실행 위치

검사 스크립트는 이 스킬 번들 안에 있다. 대상 저장소는 인자로 넘긴다.

```bash
S=~/.claude/skills/harness-cleanup/scripts
bash $S/collect_targets.sh <대상 저장소>
```

**스크립트를 대상 저장소로 복사하지 않는다.**
복사본은 원본과 갈라진다 — 이 스킬이 잡으려는 바로 그 문제다.

## 기준점 확정

감사 시작 전에 현재 환경이 실제로 사용하는 기준점을 찾는다.

- 실행 중인 하네스 설정과 생성된 모델 설정에서 최상위 역량 역할의 실제 값을 읽는다.
- 해당 모델 계열의 공식 지침이 필요하면 최신 원문을 확인한다.
- **모델 역량과 하네스 런타임 동작은 별개 기준점이다.** 둘 다 확인한다.
  지침이 특정 도구·팀·에이전트 동작을 전제하면 그 동작을 재현하거나 공식 문서로 확인한다.
  도구 설명 원문은 1차 자료이므로 산문 기억보다 우선한다.
- 설정값을 찾지 못하면 모델을 추측하지 말고 기준점 미확정으로 기록한다.
- 모델 식별자와 버전을 하네스 산문에 복사하지 않는다.
  문서에는 값을 소유한 설정 경로와 읽는 방법만 남긴다.

최근 모델이 잘할 것이라는 기대와 예전 모델이 실패했다는 기억만으로 판정하지 않는다.
현재 설정, 실행 결과, git 이력처럼 다시 확인할 수 있는 근거를 우선한다.

## 대상 선택

사용자가 지정한 범위와 현재 하네스의 참조 관계를 따라 감사 대상을 정한다.
아래 위치는 시작점이며, 설정이나 문서가 직접 가리키는 다른 하네스 파일도 포함한다.

| 유형 | 경로 예 |
|---|---|
| 전역 지침 | `$HOME/.claude/CLAUDE.md`, `$HOME/.claude/rules/*.md` |
| 프로젝트 지침 | `CLAUDE.md`, `.claude/rules/` |
| 하네스별 역할 정의 | `.claude/agents/*.md`, `.codex/agents/*.toml` |
| 공유 역할 계약 | `.agents/roles/*.md` |
| 공용 스킬 원본 | 각 `SKILL.md`, `references/`, `scripts/` |
| 프로젝트 스킬과 오버레이 | `.claude/skills/*/`, `.claude/*-overlay.md` |
| 공개 스킬 | `skills/*/SKILL.md`, `skills/*/references/*.md` |
| 회피 패턴 문서 | `docs/pitfalls/` 처럼 실행 중 소비되는 것 |

제외 대상이 둘이다.

- **`docs/`** — 설명이 있어야 하는 곳이다.
  프로젝트 일반 문서와 planning 관리 문서의 코드 정합성 감사는 `docs-check`로 보낸다.
- **저장소 밖을 가리키는 symlink** — 공용 자산이라 고치면 다른 저장소에 영향이 간다.
  `collect_targets.sh`가 따로 표시하고 합계에서 뺀다.

한 번에 검토 가능한 범위를 넘으면 소유권 단위로 나눈다.

여러 하네스가 같은 역할을 각자의 형식으로 정의하고 있으면 두 정의가 어긋났는지 먼저 대조한다.
형식이 달라 파일 하나로 합칠 수 없으면 **내용만 공유 역할 계약으로 모으고 양쪽을 얇은 래퍼로 줄인다.**
래퍼에는 실제로 다른 것만 남긴다 (보고 경로, 쓰기 도구 제한 유무).

## 측정

판정 전에 원본 상태를 보존하고 숫자와 실행 결과를 수집한다.

### 구조 측정

```bash
bash    $S/collect_targets.sh    <대상 저장소>   # 줄 수 합계, 파일 개수, 저장소 밖 symlink 구분
python3 $S/check_references.py   <대상 저장소>   # 참조가 실재하는지
python3 $S/check_facts.py        <대상 저장소>   # 개수 표기, 여러 문서에 흩어진 목록
python3 $S/check_duplication.py  <대상 저장소>   # 같은 내용을 소유한 파일이 둘 이상인지
bash    $S/check_rename_drift.sh <대상 저장소>   # 본문만 고치고 참조 문서를 안 고쳤는지
```

`check_rename_drift.sh`는 교정 **직후에도** 실행한다.
본문에서 절 이름이나 개념을 바꾸고 그것을 위임받은 참조 문서를 그대로 두면
요약본과 소유자 문서가 서로 다른 것을 지시하게 된다.
이 저장소에서 네 번 반복된 실패라 사람 눈으로는 잡히지 않는다.

- 다른 스크립트와 달리 **종료 코드로 판정한다** — 0 통과, 1 드리프트 검출, 2 사용법 오류.
- **stderr 의 "검사한 SKILL.md" 줄을 반드시 읽는다.** 0개면 통과가 아니라 볼 것이 없었다는 뜻이다.
  기준 커밋을 잘못 줘 빈 입력을 훑고 0건을 낸 것을 통과로 읽으면 회귀가 그대로 지나간다.
- 라벨을 담은 참조 문서가 **하나도** 안 바뀌었을 때만 걸린다.
  소유자를 옮기는 리팩토링(새 참조 파일로 이동)은 오탐으로 잡히지 않지만,
  옮긴 곳이 없는 순수 삭제도 걸리지 않으므로 그 축은 사람이 본다.

스크립트가 판정하지는 않는다. 재현 가능한 검토 지점을 뽑아 줄 뿐이다.

- `check_references.py`는 네 형태를 본다 — 마크다운 링크, 백틱으로 감싼 경로,
  `"섹션명" 섹션` 같은 다른 문서 섹션 참조, `` `이름` skill `` 같은 스킬 참조.
  뒤 두 형태는 직관되지 않으니 감사 대상 문서가 그 형태로 참조를 적었는지 함께 본다.
- **깨진 참조는 대개 한쪽만 고친 흔적이다.** 섹션을 지우고 그것을 가리키는 문서를 갱신하지 않으면 남는다.
  반대 방향도 본다 — 대상 표에 적은 예시 경로는 검사 저장소에 없는 것이 정상이라 거짓 검출로 나온다.
- **중복 검출 0건은 중복이 없다는 뜻이 아니다.** 줄 단위 문자열 일치만 보므로,
  같은 규칙을 문서마다 다르게 표현해 두면 걸리지 않는다.
  "A가 단일 소스다"라고 적어 두고 내용을 복사해 둔 경우가 가장 흔하다 — 그 복사본은 반드시 원본과 어긋난다.
  그래서 규칙 이름으로 직접 훑어 같은 개념을 언급하는 파일을 센다.

  ```bash
  grep -rniE "<규칙 이름>|<다른 규칙 이름>" CLAUDE.md .claude/ | cut -d: -f1 | sort | uniq -c | sort -rn
  ```

  한 개념이 세 파일 이상에서 언급되면 어느 쪽이 단일 소스인지 정한다.
- `check_facts.py`가 뽑은 옵션이 실재하는지는 `--help`로, 목록이 맞는지는 실제 파일과 대조해 확인한다.

스크립트가 다루지 않는 축이 둘 남는다.

- 조건부 절차가 상시 본문에 차지하는 줄 수를 센다.
- 스킬을 감사하면 변경 전에 저장소의 `evaluation/score.sh <skill-name>`을 실행한다.

숫자는 품질 판정 자체가 아니라 비대화, 끊긴 참조, 계층 혼재를 재현하는 출발점이다.

### 검출 명령 검증

**이 단계를 건너뛰지 않는다.**
문서에 적힌 검출 명령이 아무것도 검사하지 않는 상태는 사람이 읽어서 발견할 수 없다.

```bash
bash $S/run_doc_snippets.sh <파일> "<블록 앞에 오는 머리말>"
```

이 스크립트만은 **대상 저장소 안에서** 실행한다. 추출한 명령이 상대 경로를 쓰므로 cwd가 결과를 바꾼다.
문서의 코드 블록을 그대로 꺼내 bash와 zsh 양쪽에서 돌린다 — 배열 확장처럼 셸마다 갈리는 동작이 여기서 드러난다.

1. 명령이 기대하는 작업 디렉터리와 입력 경로를 확인한다.
2. 입력 경로가 현재 진입점과 검사 대상을 실제로 포함하는지 확인한다.
3. 명령을 그대로 실행하고 종료 상태와 출력을 기록한다.
4. 0건이면 깨끗한 결과인지, 아무 입력도 보지 않은 결과인지 구분한다.
5. 의도적으로 심은 안전한 표본으로 검출력을 확인한다. 확인에 성공한 명령만 통과로 판정한다.

음성 대조 표본은 두 경우를 모두 심는다.

- 항목 하나를 추가한 경우
- 항목 하나를 추가하면서 다른 하나를 지워 **개수가 그대로인 경우**

이 단계에서 드러나는 대표 결함이 셋이다.

- **플레이스홀더를 그대로 정규식에 넣은 grep** — 항상 0건이 나와 통과로 오독된다
- **자기참조 검사** — 위반을 찾는 검사가 걸어내는 것이 전부 그 규칙 자신이라 실제 검사 대상이 0이다
- **셸에 따라 다른 변수 확장** — 한 셸에서는 전체를, 다른 셸에서는 첫 원소만 검사한다

### 사용 이력 확인

- `frontmatter`의 출처와 도입 근거 필드가 있으면 원문을 따라간다.
- `git log`, `git blame`, 실행 회고에서 규칙이 추가된 이유와 실제 사용 흔적을 찾는다.
- 모델 기본 역량 후보는 해당 지시를 뺀 격리 실행으로 같은 행동이 재현되는지 확인한다.
  지시가 없던 과거 실행도 근거로 사용할 수 있다.
- 선택 단계가 계속 생략됐다면 생략 조건과 호출 패턴이 겹치는지 확인한다.
- 이력이 없다는 사실만으로 바로 제거하지 않는다.
  환경 고유 사실처럼 실행 빈도가 낮아도 필요한 지시인지 별도로 판정한다.

## 판정

무엇을 찾을지는 [`references/audit-axes.md`](references/audit-axes.md)의 감사 축을 모두 적용한다.
찾은 항목을 유지할지 지울지는 [`references/judgment.md`](references/judgment.md)의 기준으로 문장 단위 판정한다.
축 이름만 맞추지 말고 각 사례가 보여 주는 실패 원리를 현재 대상에 대입한다.

판정과 근거 등급은 분리한다.

| 등급 | 의미 | 판정에 쓰는 방법 |
|---|---|---|
| 실측 | 실행과 이력으로 직접 확인 | 유지나 제거를 뒷받침한다 |
| 도구 대체 | 기계가 실행 경로에서 규칙을 강제 | 산문을 도구 경로로 대신한다 |
| 추정 | 모델 역량이나 필요성을 관찰 없이 예상 | 판정을 보류한다 |

"이제는 안 틀릴 것 같다"와 "혹시 모르니 남기자"는 모두 추정이다.
어느 쪽도 판정 근거로 승격하지 않는다.

**도구 대체 등급은 주장만으로 승격하지 않는다.** 그 도구가 실제로 막는지 확인한다.

```bash
bash $S/check_enforcement.sh <대상 저장소> gitignore <경로>
bash $S/check_enforcement.sh <대상 저장소> lint <probe 경로> '<probe 내용>' '<검사 명령>'
bash $S/check_enforcement.sh <대상 저장소> grep <probe 경로> '<probe 내용>' '<검사 명령>'
bash $S/check_enforcement.sh <대상 저장소> tools <agent 정의 파일>
```

모드별 통과 조건과 `lint`·`grep`의 방향 차이는 judgment.md가 소유한다.

## 판정표와 승인

수정 전에 발견 항목을 다음 네 열로 보고한다.

| 대상 | 판정 | 근거 | 등급 |
|---|---|---|---|
| `<파일>`의 `<절 이름>` | 제거 | 실행 결과와 소유 문서 | 실측 |

대상은 줄 번호가 아니라 절 이름으로 가리킨다.
줄 번호는 그 파일이 한 번 바뀌면 낡고, 판정표를 다시 읽을 때 무엇을 가리켰는지 알 수 없다.

판정표에는 유지 항목과 보류 항목도 넣는다.
제거 후보만 보여 주면 감사자가 무엇을 보존했는지 사용자가 검증할 수 없다.

판정표를 제시한 뒤 사용자의 승인을 받는다.
삭제뿐 아니라 이동, 검출 명령 교체, 정책 문구 변경도 승인 범위 안에서만 수행한다.

## 승인 후 교정

승인된 항목을 소유권과 관심사 단위로 고친다.

- 중복은 한 소유 문서에만 남기고 소비 위치에는 짧은 참조를 둔다.
- 죽은 검출은 현재 진입점과 실제 검사 대상을 향하도록 고친다.
- 목록을 지키는 드리프트 검사는 집합 비교로 만든다 (형태와 이유는 judgment.md).
- 모델이나 버전 값은 산문에서 제거하고 실제 설정 경로를 읽게 한다.
- 조건부 절차는 상시 본문에서 빼고 `references/`에 둔 뒤 발동 조건을 본문에 적는다.
- 새 정책과 충돌하는 옛 문구는 실행 절차 가까운 곳까지 검색해 함께 정리한다.
- 사용 이력 0인 절차는 생략 조건과 대체 경로를 확인한다.
  그 결과에 따라 제거하거나 발동 조건을 고친다.

반복 실행하는 코드가 5줄을 넘으면 `scripts/`로 분리하고 실제로 실행해 검증한다.
새 설명 문서는 실행 중 소비될 때만 만든다.
소비되지 않는 폐기 근거는 커밋 메시지와 git 이력이 소유한다.

변경은 관심사별 원자 커밋으로 나눈다.
이 감사에서는 보통 네 유형이 나오며, 독립적으로 되돌릴 수 있으므로 섞지 않는다.

- 사실 오류 수정
- 참조 갱신
- 중복 제거
- 설명 제거

커밋 메시지에는 **무엇이 어떻게 틀렸는지**를 남긴다. 같은 오류가 다시 들어오는 것을 막는다.

## 재측정과 완료

변경 뒤 처음과 같은 측정을 다시 실행한다.

- 줄 수, 참조 수, 중복 검출 결과를 전후 비교한다.
- 고친 검출 명령을 실제로 실행하고 검출력이 살아 있는지 확인한다.
- 이동한 참조와 스크립트가 실제 경로에서 열리고 실행되는지 확인한다.
- 스킬을 감사했다면 `evaluation/score.sh <skill-name>`을 다시 실행한다.
- 승인받지 않은 파일이 diff에 포함되지 않았는지 확인한다.

정리를 마치면 별도 에이전트에게 리뷰를 맡긴다.
**리뷰 지적도 실측으로 걸러야 한다** — 서브에이전트도 틀린다.

완료 보고에는 판정표의 처리 결과, 전후 측정값, 실행한 검증, 커밋 목록, 남은 보류 항목을 담는다.
추정만 남은 항목은 완료로 꾸미지 말고 다음에 필요한 관측 방법을 적는다.

## 하지 않을 것

- **사용자가 이미 편집한 파일을 되돌리지 않는다.**
  손상으로 보여도 먼저 확인한다. 포매터 손상과 사용자 편집이 섞여 있으면 손상만 골라 고친다.
- **문서를 통째로 덮어쓰지 않는다.**
  경계를 잘못 잡으면 의도하지 않은 구간이 사라진다.
  섹션 삭제는 다음 헤더까지로 범위를 잡고, 삭제 전후 헤더 목록을 비교한다.
- **새로 쓸 때는 원본에만 있던 요소를 대조한다.**
  뱃지, 링크, 라이선스 표기처럼 본문과 성격이 다른 요소는 제거 대상이 아니다.
  재작성 전후로 원본에만 있는 줄을 `diff`로 확인한다.
