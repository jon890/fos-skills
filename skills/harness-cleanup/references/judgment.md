# 판정 기준

감사 축이 찾아낸 항목을 유지할지 지울지 문장 단위로 판정한다.
축은 무엇을 찾을지를, 이 문서는 찾은 것을 어떻게 처리할지를 소유한다.

## 유지

모델이 현재 입력과 도구만으로 추론할 수 없는 지시를 유지한다.

- 도구가 지금 어떻게 동작하는지에 대한 사실과 그 회피법
- 팀 컨벤션과 운영값
- 계정, 경로, 권한, 상태 전이, 외부 부수 효과처럼 환경에 고유한 사실
- 다른 세션의 동시 실행 여부처럼 현재 세션이 관측할 수 없는 사실
- 안전, 개인정보, 공개 범위, 승인 경계
- 자동 검사가 보장하지 못하는 산출물의 형식과 담을 내용

**도구 동작은 지금의 사실로 한 줄 적는다.** 예: 「`npm cache clean` 은 `_npx` 를 비우지 않는다」.
그 사실을 알게 된 사건의 경위, 수치, 날짜는 남기지 않는다. 기준은 아래 「지난 일의 기록은 남기지 않는다」 가 소유한다.
무엇이 어떻게 달라지는지 없이 경고만 남은 문구는 도구 동작 사실로 취급하지 않는다.

**실측이라도 무엇을 관측한 것인지로 판정한다.** 아래 「10. 실측의 관측 대상: 도구 동작과 모델 행동」 축이 그것을 다룬다.

## 제거

다음 조건을 근거로 제거 후보를 만든다.

- 다른 문서가 이미 소유한 중복
- 지시 없이 수행되는 현재 모델의 기본 역량
- 린터, CI, 훅처럼 도구가 이미 강제하는 규칙
- 지난 일의 기록. 지난 조사와 경과, 실측 수치, 사고 기록, 결정 날짜, 폐기된 규칙의 역사 서술
- 행동을 지시하지 않는 자기 소개
- 아무 행동이나 판단도 바꾸지 않는 절

### 지난 일의 기록은 남기지 않는다

**스킬 문서에는 지금 동작만 남긴다.** 규칙을 따르는 데 그 규칙이 언제 어떻게 생겼는지는 필요하지 않다.

| 지운다 | 남긴다 |
| --- | --- |
| 지난 조사와 경과(「처음에는 … 였다가 … 로 바꿨다」) | 지금의 규칙 |
| 실측 수치(표본 수, 측정값, 전후 비교) | 규칙의 값(상한, 기준값, 종료 코드) |
| 사고 기록(「… 한 일이 있었다」) | 도구가 지금 어떻게 동작하는지 한 줄 |
| 결정 날짜와 「(사용자 결정 YYYY-MM-DD)」 꼬리, 「(실측)」 꼬리표 | 규칙의 이유 한 줄 |
| 앞으로의 계획(「다음 major 에 지운다」) | 지금 에이전트가 할 행동 |

- 사고 기록에서 도구 동작을 뽑아낼 수 있으면 그 사실만 남긴다. 「끊긴 worker 의 컨테이너가 계속 돌았다」 는 「trap 은 셸이 신호로 죽으면 돌지 않는다」 로 쓴다.
- 근거를 받을 `docs/` 문서(ADR, 기능 문서)가 있으면 이유 뒤에 링크한다. 없으면 근거를 지우고 커밋 기록에 맡긴다. 근거를 담으려고 문서를 새로 만들지 않는다.
- 예는 찾을 모양이나 쓸 모양을 보이는 한 줄로 쓴다. 그때 몇 건이 나왔고 어떻게 끝났는지는 적지 않는다.
- **예외:** 오버레이의 함정 항목에 붙인 확인 날짜는 남긴다. 화면과 외부 서비스는 예고 없이 바뀌므로, 언제 확인한 사실인지가 다시 확인할 때를 정한다.

### 스크립트가 있으면 그 docstring 도 소유자다

「다른 문서가 이미 소유한 중복」의 소유자는 문서만이 아니다.
스크립트가 함께 있는 스킬에서는 그 파일의 docstring 이 사용법과 내부 동작을 소유한다.
찾는 방법은 [`audit-axes.md`](audit-axes.md) 의 「소유권 중복」 이 소유한다.

남기는 기준은 그대로다. 스크립트가 알려주지 않는 판단, 함정, 도구 동작 사실은 남긴다.
`counts` 의 ERR 과 PARTIAL 을 보고에 적어야 하는 이유가 그 예다.

### 도구가 강제한다는 근거는 실제로 확인한다

"이미 린터가 잡으니 문장 지침은 지운다"는 판단은 자주 틀린다.
막는다고 믿은 수단에 구멍이 있으면 유일한 지시를 지운 셈이 된다.
`scripts/check_enforcement.ts`로 무엇이 실제로 막는지 판정한다.
그 검사가 실패를 막을 때만 산문을 제거한다.

| 모드 | 판정 대상 | 통과 조건 |
|---|---|---|
| `gitignore` | 그 경로가 정말 걸리는지 | `git check-ignore -v` 히트 |
| `lint` | 규칙이 그 패턴을 잡는지 | probe를 심고 실행해 non-zero |
| `grep` | 문서의 검증 grep이 그 패턴을 잡는지 | probe를 심고 실행해 히트 |
| `tools` | frontmatter가 막은 도구 밖에 우회 경로가 남았는지 | 파일을 고칠 도구가 남지 않음 |

도구 제한은 특히 믿기 쉽다.
`disallowedTools: Write, Edit` 로 막아도 `Bash` 가 있으면 리다이렉트로 파일을 덮어쓸 수 있다.

도구가 존재하기만 하고 호출되지 않거나, 검사 범위가 대상을 비켜 가면 대체 근거가 아니다.

## 1. 판정할 수 있는 지시

읽는 쪽이 스스로 「지켰는지」 답할 수 없는 지시는 지켜지지 않는다.
내면 상태를 묻는 것이 그렇다. 목록이나 파일처럼 밖에 있는 것으로 바꾼다.

| 쓰지 않음 | 씀 | 왜 |
|---|---|---|
| 조금이라도 모호하면 사용자와 논의한다 | 남은 질문이 없다 | 모호함을 인식하지 못하면 늘 0 이다 |
| 「알아서 됐겠지」 로 지나가지 않는다 | 각 문서의 완료 조건이 채워졌다 | 지나갔는지 확인할 방법이 없다 |
| 명확히 하나의 작업 단위 | 한 사람이 한 번에 붙잡고 끝낼 크기 | 명확함의 기준이 없다 |
| 냉정하게 본다, 끝까지 본다 | (지운다) | 냉정함과 끝의 기준이 없다 |

**스스로 짚는 체크리스트는 자기 승인이다.** 수행 여부가 산출물에 남지 않는다.
자동으로 판정할 수 있는 항목은 스크립트로 옮기고, 남은 것만 목록으로 둔다.

## 2. 할 일을 말하는 제목

제목은 그 절에서 무엇을 하라는 것인지 말한다. 분위기나 목적을 적지 않는다.

| 쓰지 않음 | 씀 |
|---|---|
| 단계 강제: 뭉개기·건너뛰기 방지 | 단계는 하나씩 순차로 진행한다 |
| 캐낼 모호점 (능동 발굴) | 물어서 확정할 것 |
| 누락 체크리스트 | 빠뜨리기 쉬운 것 |
| 번호·동시성 | 번호를 정하는 방법 |
| 자동 검출 6 패턴 | 스크립트가 잡는 것 |

괄호로 시점이나 필수 여부를 덧붙이지 않는다. 본문이 말한다.

**규칙에 이름을 새로 지어내지 않는다.** 지어낸 이름은 그 문서 밖에서 뜻이 통하지 않는다.

## 3. 설명과 지시의 구분

지침 파일에는 "무엇을 하라 / 하지 마라"만 둔다.
"무엇이 어떻게 동작한다"는 `docs/`로 보낸다.

| 판정 | 예 |
|---|---|
| 설명 — 옮기거나 지운다 | "스킬은 패키지 경로를 직접 가리키지 않고 관리 저장소를 거쳐 연결된다" |
| 지시 — 남긴다 | "새 버전으로 설치했으면 스킬 갱신 명령을 직접 실행한다" |

한 단락에 섞여 있으면 지시만 남기고 나머지를 지운다.

**예외**: 판단 근거가 되는 짧은 이유는 남긴다. 이유를 알면 변형 상황에서도 옳게 행동한다.
셸 배열을 quote로 감싸는 이유(한 셸은 단어 분할을 하지 않고 다른 셸은 첫 원소로 축약한다)가 그 예다.
그 주석이 없으면 다음 사람이 문자열 변수로 되돌린다.

**예외를 문단 단위로 늘리지 않는다.** 이유가 지시보다 길어지면 설명으로 넘어간 것이다.

## 4. 애초에 하지 않을 일의 금지

최신 모델이 하지 않을 행동을 막는 지시는 자리만 차지한다.
지운 예를 보면 성격이 드러난다.

- "공식 문서 사본을 저장소에 두지 않는다" — 사본을 만들 이유가 없다
- "인증 문제가 아니므로 토큰을 붙여도 달라지지 않는다" — 원인을 정확히 적었으면 토큰을 시도하지 않는다
- "검출 명령을 여기에 복사하지 않는다" — 참조가 명확하면 복사할 이유가 없다
- "특정 HTTP 라이브러리 사용 금지" — 쓸 것을 적었으면 충분하다

**남기는 기준**: 실제로 그 실수가 일어난 기록이 있는가.
`git log`로 확인한다. 커밋 제목의 이모지 접두사를 금지하는 지시라면 그런 커밋이 히스토리에 있는지 본다.

판단이 자명하지 않은 금지도 남긴다.
릴리스 노트 자동 생성 옵션을 쓰지 말라는 지시가 그 예다. 그것을 쓰면 이슈 연결 목록이 빠진다.

## 5. 부정형으로 쓴 행동 지시

행동을 시키는 자리는 긍정형으로 쓴다.
금지한 행동을 문장에 담으면 그 행동이 컨텍스트에 올라와 오히려 더 나온다.

| 쓰지 않음 | 씀 |
|---|---|
| 건너뛰지 말고 근거를 남긴다 | 근거를 남긴다 |
| 자의로 진행하지 말고 질문한다 | 옵션과 트레이드오프를 붙여 질문한다 |
| 추측하지 말고 사용자에게 확인받는다 | 사용자에게 확인받는다 |

`A 하지 말고 B 한다` 는 `B 한다` 로 줄인다. 긍정문 뒤에 같은 뜻의 부정문을 덧붙인 것도 지운다.

**경계와 차단 조건은 부정형을 그대로 둔다.**
무엇이 금지인지가 곧 규칙이라, 긍정으로 바꾸면 경계값이 흐려진다.
`판정보다 낮은 role 로 스폰하지 않는다` 를 `같거나 높은 role 로 스폰한다` 로 바꾸면
어디가 경계인지 읽는 쪽이 다시 계산해야 한다.

범위 선언도 그대로 둔다. `git 조작은 이 스킬이 정하지 않는다` 는 안 한다는 것이 정보다.

## 6. 하네스 전용 도구 이름

스킬은 Claude Code 밖에서도 돈다. 도구 이름을 박으면 그 하네스에서만 동작한다.

| 쓰지 않음 | 씀 |
|---|---|
| `AskUserQuestion` 으로 확정받는다 | 선택지와 트레이드오프를 붙여 묻고 확정받는다 |
| `TaskCreate` 로 단계를 만든다 | 밟을 단계를 각각 할 일로 만든다 |

도구가 있으면 쓰라고만 적는다. 「구조화 질문 도구가 있으면 그것을 쓴다」 형태다.

**그 하네스 위에 서 있는 스킬은 예외다.** 에이전트 팀을 오케스트레이션하는 스킬이
`SendMessage` 를 부르는 것이 그렇다. 이름을 빼면 무엇을 부르라는 것인지 사라진다.

## 7. description 에 섞인 지침

`description` 은 언제 이 스킬을 쓸지 정하는 자리다. 무엇을 어떻게 하는지는 본문이 소유한다.

| 남길 것 | 뺄 것 |
|---|---|
| 목표 한 문장 | 절차와 단계 나열 |
| 트리거 문구 | 산출물 형식 |
| 경계 문장 (`X 는 다른 스킬이 맡는다`) | 오버레이가 무엇을 채우는지 |

본문에서 지운 규칙이 description 에만 남으면 사실과 어긋난다. 본문을 고칠 때 description 도 함께 본다.

## 8. 모델이 판단해도 되는 것의 규정

관례를 세세히 규정하면 문서만 늘고 어긋난다.

- 브랜치 명명 표와 PR 제목 형식 — 히스토리를 보면 판단할 수 있다
- 커밋 메시지 형식 — 같다

**남기는 기준**: 히스토리로 유추할 수 없는 프로젝트 고유 정책인가.
"커밋 메시지는 한국어로 작성한다"는 남긴다. 영문 커밋이 섞인 히스토리에서는 유추되지 않는다.

## 9. 문서에 박은 개수와 목록

**개수는 적지 않는다.** "N개"는 지시의 힘을 더하지 않는다.

목록은 다르다. **복제된 목록만 지운다.**
이 기준은 같은 목록이 여러 곳에 있는 상황을 전제한다.
그 목록이 유일한 출처면 지우는 순간 정보가 사라진다.

### 목록을 지우기 전 절차

"이 목록을 지우면 같은 정보를 어디서 얻는가"에 **구체적인 명령으로** 답한다.
답이 없으면 그 목록이 단일 소스다. 남기고 대신 드리프트 검사를 붙인다.

이름이 경로에서 유추되지 않는 대응 표가 대표적인 단일 소스다.
라우트 파일과 문서를 잇는 표가 그렇다. 양쪽 다 서로를 밝히지 않아, 표를 지우면 역추적할 길이 없다.

남길 때는 드리프트 검사를 함께 붙인다.

```bash
diff <(<실제 목록을 뽑는 명령> | sort) <(<문서에서 뽑는 명령> | sort)
```

**개수 비교가 아니라 집합 비교를 쓴다.**
개수 비교는 항목 하나가 늘고 다른 하나가 지워지면 상쇄되어 통과한다.

## 10. 실측의 관측 대상: 도구 동작과 모델 행동

규칙에 붙은 근거를 둘로 나눈다. **무엇을 관측했는가**가 기준이다.

| | 관측 대상 | 처리 |
| --- | --- | --- |
| 도구 동작 | 도구, 런타임, git, CLI 가 실제로 어떻게 동작하는가 | 지금의 사실 한 줄로 유지 |
| 모델 행동 | 모델이 그때 그렇게 했다 | 제거 |

**도구 동작은 모델이 추론할 수 없다.** 실행해 보거나 도구 계약을 읽어야 알 수 있고,
문서에 적혀 있지 않으면 알아낼 방법이 없다.

**모델 행동은 성능이 오르면 사실이 아니게 된다.**
그 관측이 옛 모델의 것인지 지금 모델의 것인지 문서로는 가릴 수 없고,
낡았다는 것을 알아차릴 계기도 없다. 규칙 자체는 남기고 관측만 지운다.

| 쓰지 않음 | 씀 | 왜 |
| --- | --- | --- |
| 바뀐 파일을 다시 읽지 않아 첫 평가를 그대로 보낸 사고가 있었다 | (지운다. 「다시 읽고 판정한다」 규칙만 남긴다) | 모델 행동 |
| main 을 직접 고치는 사고가 관측된다 | 하위 에이전트의 cwd 는 지정하지 않으면 main 워킹 디렉터리다 | 관측을 환경 사실로 |
| 무관한 차이 50여 건이 섞여 판정이 오염됐다 | 2-dot 은 분기 후 들어온 외부 커밋까지 끌어온다 | 사건 수치를 git 동작으로 |
| 모델 인자 없이 스폰해 등급이 다르게 떴다 | (지운다. 「스폰 시점에 명시 지정한다」 규칙만 남긴다) | 모델 행동 |
| (10-31 실측) 그 설정 파일에 넣은 허용 규칙이 먹지 않아 worker 가 멈췄다 | 그 설정 파일의 허용 규칙은 적용되지 않는다 | 날짜와 경위를 지금의 사실로 |

**규칙을 지우는 것이 아니다.** 규칙이 왜 있는지를 도구 동작으로 댈 수 있으면 그것을 쓰고,
모델 행동으로만 댈 수 있으면 근거 없이 규칙만 남긴다.

## 11. 없어도 행동이 같은 실측

축 10 을 통과한 실측에 한 번 더 묻는다.
**그 문장이 없을 때 다르게 행동하는가.** 없어도 같게 행동하면 지운다.

「제거」 절의 「아무 행동이나 판단도 바꾸지 않는 절」이 같은 조건이다.
**실측이나 날짜가 붙었다고 그 조건을 면제받지 않는다.**
축 10 은 관측 대상만 보므로 도구 동작이면 통과시킨다. 이 축이 그 뒤에 서는 이유다.

다른 문장에서 바로 나오는 결론이 그렇다. 놀랍지 않은 사실에 「실측」 을 붙여도 신뢰가 늘지 않는다.

| 판정 | 사례 | 왜 |
| --- | --- | --- |
| 지운다 | 다른 API 를 부르므로 한쪽이 막혀도 다른 쪽은 돈다 | 다른 API 를 부른다는 데서 나오는 결론이다 |
| 지운다 | 로더를 고친 뒤에도 여러 건이 skip 상태로 남아 있었다 | 지난 사건의 경과다. 지금 할 행동이 없다 |
| 남긴다 | 클라이언트가 끊어도 서버는 차감한다 | 끊어도 비용이 나간다는 것을 모르면 끊고 다시 부른다 |
| 남긴다 | 조회 한 번이 한도의 큰 몫을 쓴다 | 모르면 연결 테스트로 같은 조회를 부른다 |

## 12. 목표문의 입력과 결과

**스킬을 위에서부터 읽는 에이전트가 첫 다섯 줄에서 무엇을 하는 스킬인지 알아야 한다.**
목표문에 셋이 있는지 본다.

| 있어야 할 것 | 빠졌을 때 생기는 일 |
| --- | --- |
| 무엇을 입력으로 받아 판단하는가 | 판단 근거를 스스로 고르고, 쉽게 구할 수 있는 신호가 그 자리를 대신한다 |
| 무엇을 산출하는가 | 계약을 검증기 코드에서 뒤늦게 발견한다 |
| 사용자가 그다음에 무엇을 하는가 | 산출물을 만들고 끝낸다 |

예: 목표가 「지원할 가치가 있는 것을 순위로 만든다」 뿐이면 무엇으로 순위를 매기는지가 없다.
「해온 일과 선호에 얼마나 맞는지」 처럼 입력을, 「바로 지원을 이어갈 수 있게」 처럼 그다음 행동을 목표에 넣는다.

목표를 고친 뒤 단계 하나하나가 목표의 어느 조각을 맡는지 대조한다.
어느 단계도 맡지 않는 조각과, 목표에 없는데 존재하는 단계를 함께 찾는다.

## 13. 판정 대상 용어의 정의

**스킬 안에서 이름 붙인 것은 처음 나오는 자리에서 정의한다.**
문서 밖에서 뜻이 정해지지 않는 이름이 대상이다.

| 신호 | 확인 방법 |
| --- | --- |
| 이름이 무엇의 무엇인지 말하지 않는다 | `제외 규칙` 은 무엇을 제외하는 규칙인지 이름만으로 알 수 없다 |
| 세는 말이 앞에 붙어 뜻을 가린다 | `네 축 기준값` 은 어느 넷인지, 무엇의 기준인지 없다 |
| 스키마 필드 이름을 그대로 썼는데 정의가 없다 | `businessRisk` 를 「위험」으로 옮겨 적기만 하면 채우는 사람마다 다른 것을 넣는다 |

예: 산출물에 「위험」 을 적게 하고 무엇이 위험인지 정하지 않으면 어느 항목에나 붙는 일반론이 채워진다.
「이 자리가 없어질 가능성」 처럼 항목마다 값이 달라지는 정의를 쓴다.

정의를 쓸 때 확인하지 못했을 때 무엇을 적을지도 함께 정한다.
그 자리가 비면 모델이 일반론으로 채운다.

## 14. 근거가 절반만 맞는 회피 결정

결론이 맞아도 이유가 틀리면 다음 사람이 잘못된 조건에서 되돌린다.

적힌 이유가 해소 가능한 것이면 진짜 이유를 찾아 다시 적는다.
예: 「공용 검사기를 실행하지 않는다」 의 이유가 「선택 인자가 필요해서」 로 적혀 있으면 인자를 생략할 수 있게 되는 순간 금지가 풀린다.
실제 이유가 「출력이 노이즈로 임계를 넘는다」 라면 그것을 적는다.

## 15. 공개 스킬의 독자와 필요한 정보

스킬은 에이전트가 실행하지만, 사용자가 검토하고 유지보수 방향을 정하는 문서이기도 하다.
사용자는 자연어로 지시하고, 에이전트는 파일과 명령을 직접 실행한다.

| 필요 | 불필요 |
|---|---|
| 명령 시그니처와 옵션 | 설치·시작 안내 (사용자가 이미 했다) |
| 판단 기준 — 언제 이 명령을 쓰는가 | 두 명령을 순서대로 실행하는 것뿐인 예시 |
| 함정 — 무엇이 직관과 다른가 | 내부 구현 방식 |
| 출력 스키마 — 무엇을 파싱하는가 | 기능 소개 |
| 되돌릴 수 없는 동작 | |

되돌릴 수 없는 동작은 특히 중요하다.
"명령마다 다르니 확인하라"는 안내로는 에이전트가 어느 삭제 명령이 확인 없이 실행되는지 알 수 없다.
표로 준다.
